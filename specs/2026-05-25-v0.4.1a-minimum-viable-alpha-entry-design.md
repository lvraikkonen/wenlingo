# WenLingo V0.4.1a Minimum Viable Alpha Entry Design

Date: 2026-05-25
Status: Review updates applied; pending written spec approval

## Goal

V0.4.1a lets a real invited parent-like user enter WenLingo through a controlled Alpha path, create a real child profile, hand the device to the child, let the child complete the existing V0.4 assessment, and then view a minimal parent growth summary based on real learning data.

This release is for 3-5 trusted invited families under manual developer monitoring. It is not a public launch, full MVP, full auth release, analytics release, or curriculum expansion.

## Scope

Implement in V0.4.1a:

- Manual Alpha entry at `/alpha/start`
- Real `ParentUser` creation or reuse for Alpha parents
- Browser-held Alpha parent context using `localStorage`
- Child creation API and UI
- Parent children list
- Device handoff moment after child creation
- Minimal parent summary from real data
- Conservative parent/child navigation distinction
- Hosted Alpha deployment runbook
- Manual QA checklist
- Regression tests for demo flow and V0.4 assessment continuity

Defer to V0.4.1b:

- Invite code table and invite validation
- Product events table
- Child task feedback
- Parent feedback
- Admin Alpha dashboard
- Formal analytics dashboard
- Full data deletion/export tooling
- Full authentication
- Reading Canyon
- Full weekly report
- Full gamification expansion

## Alpha Identity Model

V0.4.1a uses a real server-side `ParentUser` row plus a browser-held Alpha parent id.

Flow:

```text
Parent opens /alpha/start
-> accepts Alpha notice
-> frontend calls POST /api/alpha/parents
-> backend creates ParentUser
-> frontend stores parent_id in localStorage
-> parent pages use parent_id to list/create children and read summaries
```

The backend database remains the source of truth:

```text
ParentUser
-> StudentProfile(parent_id)
-> AbilityProfile(student_id)
-> Assessment / SentenceTraining / Essay / EssayVersion / AbilityHistory / GameEvent
```

The frontend stores only a temporary pointer:

```text
wenlingo_alpha_parent_id = <ParentUser.id>
```

Known limitation: this is not full authentication. The same browser can continue using the Alpha parent context, but changing browser/device or clearing browser storage requires manual developer recovery or creating a new Alpha parent. This is acceptable for V0.4.1a because the release is limited to 3-5 trusted families.

Security boundary: frontend `localStorage` is only a convenience pointer. All parent-scoped backend APIs must enforce ownership or parent existence server-side where applicable. In V0.4.1a this means child list and child creation must verify the `ParentUser` exists, and parent summary must verify `StudentProfile.parent_id == parent_id`. If implementation adds any other parent-scoped child API, it must follow the same backend ownership rule instead of relying on hidden frontend links.

## Alpha Entry

Add a frontend page:

```text
/alpha/start
```

The page shows the Alpha notice before collecting child data. The notice must include:

- WenLingo is in a small Alpha test.
- The system stores child nickname, grade, writing content, AI feedback, ability changes, and usage records.
- Parents should not enter real full name, school, address, phone, photo, or other sensitive information.
- Child writing may be sent to AI services to generate learning feedback.
- Continuing means the parent agrees to participate in this Alpha.

If `wenlingo_alpha_parent_id` already exists in `localStorage`, `/alpha/start` should not immediately create another parent. It should offer a primary action such as:

```text
继续使用当前 Alpha 家庭
```

That action routes to `/parent/children`. A secondary restart action may clear the stored Alpha parent id and create a new Alpha parent, but the default path should avoid accidental duplicate `ParentUser` rows.

API:

```text
POST /api/alpha/parents
{
  "display_name": "小星家长"
}
```

The backend creates a `ParentUser` with:

- `display_name` from the request or a safe default
- generated internal email such as `alpha-{uuid}@wenlingo.local`
- normal `ParentUser.id`

Response:

```text
{
  "parent": {
    "id": "...",
    "display_name": "小星家长"
  },
  "children_url": "/parent/children"
}
```

## Parent Children Flow

Add:

```text
/parent/children
/parent/children/new
```

`/parent/children` reads `wenlingo_alpha_parent_id` from `localStorage`. If it is missing, the page sends the parent back to `/alpha/start`.

API:

```text
GET /api/alpha/parents/{parent_id}/children
```

Each child card shows:

- nickname
- grade label
- assessment status
- optional last activity if cheap to compute
- `进入孩子空间`
- `查看成长摘要`

Child creation API:

```text
POST /api/alpha/parents/{parent_id}/children
{
  "nickname": "小星",
  "grade": 4
}
```

Validation:

- `nickname` is required after trimming
- nickname rejects values longer than 24 characters after trimming
- grade is required
- grade supports at least 3-6
- normal Chinese nicknames and spaces are allowed safely

The backend creates:

```text
StudentProfile(
  parent_id=parent.id,
  name=nickname,
  grade_label="<n>年级",
  persona=StudentPersona.real_child,
  is_real_child=True
)

AbilityProfile(student_id=student.id)
```

The new ability profile uses existing default ability values. This intentionally preserves the current V0.4 dashboard behavior where an all-default ability profile receives the `入门小试炼` recommendation.

## Device Handoff

After child creation, the parent should not be sent straight into the dashboard. Show a handoff confirmation:

```text
小星已加入小文星球！
现在可以把设备交给小星，开始第一次语文冒险。
```

Primary button:

```text
进入小文星球
```

The button links to:

```text
/children/{studentId}
```

Use the existing child dashboard route. In the current Next.js app, `apps/web/src/app/children/[studentId]/page.tsx` maps to `/children/{studentId}`. If the implementation later changes the actual dashboard route to `/children/{studentId}/dashboard`, the handoff button should use that existing route rather than creating a parallel dashboard route.

This makes the parent-to-child transition explicit and keeps the first child moment focused on the learning space.

## Assessment Continuity

V0.4.1a must reuse the existing V0.4 assessment flow.

Expected flow:

```text
new child dashboard
-> recommends 入门小试炼
-> child opens /children/{studentId}/assessment
-> child completes sentence upgrade and short writing
-> backend creates Assessment, SentenceTraining, Essay, EssayVersion, AbilityHistory, GameEvent
-> ability sketch appears
-> child returns to dashboard
-> dashboard no longer recommends assessment as the main task
```

Do not rewrite the assessment service or assessment UI unless a small integration bug requires it.

## Minimal Parent Summary

Add:

```text
/parent/children/{studentId}/summary
```

API:

```text
GET /api/alpha/parents/{parent_id}/children/{student_id}/summary
```

The backend must verify that `StudentProfile.parent_id == parent_id`. If the child does not belong to that parent, return 404.

The summary is read-only and should not create a `Report` row. It uses existing real data:

- `Assessment`
- `SentenceTraining`
- `Essay`
- `EssayVersion`
- `AbilityHistory`
- `AbilityProfile`
- `GameEvent` if useful

Minimum response shape:

```text
{
  "student": { ... },
  "assessment_completed": true,
  "practice_counts": {
    "assessments": 1,
    "sentence_trainings": 1,
    "essays": 1
  },
  "ability_changes": [
    { "ability_name": "expression", "delta": 9, "label": "表达力" }
  ],
  "recent_highlight": "孩子完成了第一次能力草图。",
  "next_suggestion": "继续练习把句子写具体。",
  "empty_state": null
}
```

For a new child with no training data:

```text
empty_state = "还没有训练记录。完成入门小试炼后，这里会出现第一份成长摘要。"
```

The frontend page shows:

- 最近练习
- 能力变化
- 最近亮点
- 下一步建议
- `进入孩子空间`

## Navigation Distinction

Keep the navigation split conservative to avoid demo regressions.

Demo path:

- Keep `/`, `demoLogin()`, seeded demo family behavior, `FamilyTopbar`, and `/parent/[studentId]/report` intact unless a tiny compatibility change is required.

Alpha parent pages:

- Add an Alpha parent navigation component or page-local parent header.
- Use parent management language: `我的孩子`, `创建孩子档案`, `查看成长摘要`, `进入孩子空间`.

Child learning pages:

- Reuse existing child dashboard and assessment pages for V0.4.1a.
- If copy is touched, use child-facing language such as `我的小文星球`, `开始今日挑战`, `看看我的能力草图`, `继续句子工坊`.
- Reading Canyon may remain under construction, but any visible state must be friendly and clear.

Do not do a broad rewrite of `FamilyTopbar` in V0.4.1a.

## Backend Components

Add an Alpha route module, for example:

```text
apps/api/app/api/routes/alpha.py
```

Register it in `apps/api/app/main.py`.

Recommended endpoints:

```text
POST /api/alpha/parents
GET /api/alpha/parents/{parent_id}/children
POST /api/alpha/parents/{parent_id}/children
GET /api/alpha/parents/{parent_id}/children/{student_id}/summary
```

Keep request/response models local to the route module unless they become shared across modules.

No database migration is required if V0.4.1a only creates `ParentUser`, `StudentProfile`, and `AbilityProfile` rows using existing tables.

## Frontend Components

Add pages:

```text
apps/web/src/app/alpha/start/page.tsx
apps/web/src/app/parent/children/page.tsx
apps/web/src/app/parent/children/new/page.tsx
apps/web/src/app/parent/children/[studentId]/summary/page.tsx
```

```text
apps/web/src/lib/api.ts

```

Suggested helper names:

```text
createAlphaParent
getAlphaChildren
createAlphaChild
getAlphaChildSummary
```

Add small client-side localStorage helpers if useful, but keep them scoped to the Alpha parent pages.

## Testing

Backend tests should cover:

- Alpha parent creation creates a real `ParentUser`
- Child creation creates `StudentProfile`
- Child creation creates default `AbilityProfile`
- Child links to the requested `ParentUser`
- Invalid nickname and grade are rejected
- Parent children list returns created children
- Parent summary returns friendly empty state for a new child
- Parent summary reflects assessment and `AbilityHistory` after V0.4 assessment
- Parent summary rejects a child from another parent
- Demo login still returns four seeded demo children

Frontend tests should cover:

- Alpha notice renders before child creation
- Alpha parent id is saved or reused from `localStorage`
- Child creation form validates required fields
- Successful child creation shows the handoff message
- Children list shows created child cards
- Parent summary renders empty state
- Parent summary renders populated state
- Existing `FamilyTopbar` demo behavior remains stable

E2E coverage is desirable if it fits the implementation window:

```text
/alpha/start
-> accept notice
-> create child
-> handoff
-> enter dashboard
-> complete assessment
-> return dashboard
-> view parent summary
```

## Documentation

Implementation must add:

```text
qa/2026-05-25-v0.4.1a-alpha-entry-manual-qa.md
docs/alpha-deploy.md
```

The manual QA checklist must include:

- Fresh Alpha user opens `/alpha/start`
- Alpha notice appears before child data collection
- Parent accepts Alpha notice
- Parent creates child with valid nickname and grade
- Parent cannot create child with empty nickname
- Parent cannot create child with invalid grade
- Parent can create a second child
- Both children appear in parent children list
- Parent sees device handoff confirmation
- Parent enters child dashboard
- New child dashboard recommends assessment
- Child completes V0.4 assessment
- Ability sketch appears
- Child returns to dashboard
- Dashboard no longer recommends assessment
- Parent opens summary
- Summary shows real assessment and `AbilityHistory` data
- New child summary with no training shows friendly empty state
- Demo family flow still works
- Existing V0.4 assessment tests still pass
- Reading Canyon, if visible, is clearly marked as under construction
- No real-name, school, phone, address, birthdate, or photo field is collected
- Browser storage and URLs do not contain sensitive child information beyond the Alpha parent id and child ids

The deployment runbook must cover:

- recommended hosted architecture
- frontend deployment
- backend deployment
- persistent PostgreSQL requirement
- environment variables
- LLM key handling
- migration command
- smoke test steps
- rollback note
- manual Alpha link distribution
- manual backup/deletion note

The Alpha environment must use persistent PostgreSQL. It must not use local SQLite, a disposable demo database, or a database file tied to a developer machine.

## Acceptance Criteria

V0.4.1a is ready for implementation review when:

- A parent can enter through `/alpha/start`
- A real `ParentUser` row is created
- The browser stores the Alpha parent id
- A real child can be created without `seed_demo_data`
- The child gets a default `AbilityProfile`
- The child appears in the Alpha parent children list
- The handoff moment is shown after child creation
- The child can reach and complete the V0.4 assessment
- Returning dashboard no longer recommends assessment as the main task
- Parent summary shows empty state before training
- Parent summary shows real assessment and ability-change data after assessment
- Existing demo flow remains intact
- Hosted Alpha deployment runbook exists
- Alpha deployment runbook explicitly forbids SQLite/disposable demo DB for Alpha and requires persistent PostgreSQL
- Manual QA checklist exists
- Relevant backend and frontend regression tests pass

## Known Limitations

- No full authentication
- Manual Alpha link only
- Browser-held Alpha parent context only
- Changing device/browser or clearing storage needs manual recovery
- No invite codes
- No formal product event analytics
- No child reaction collection
- No parent feedback collection
- No admin Alpha dashboard
- No automated data deletion/export tooling
- Reading Canyon remains under construction
- Trusted 3-5 family Alpha only
- Developer manually monitors usage
