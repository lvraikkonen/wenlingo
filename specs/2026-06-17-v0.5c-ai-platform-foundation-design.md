# WenLingo V0.5c AI Platform Foundation Design

Date: 2026-06-17
Status: Approved by Claus
Source roadmap: `reviews/2026-06-12-v0.5b-to-v1.0-roadmap.md`
Source review: `reviews/2026-06-16-v0.5b.1-multi-perspective-review.md`

## Goal

V0.5c establishes the AI execution foundation needed before V0.6 Writing Castle adds new LLM tasks.

The release goal is:

```text
All production AI calls go through one configurable, observable, fallback-capable, testable execution layer.
```

This version does not add new learning features. It makes the existing AI paths safer to scale:

- sentence upgrade feedback
- sentence challenge generation
- sentence challenge feedback
- essay draft feedback
- essay revision comparison

V0.5c must preserve the positive learning loop from the MVP:

```text
Draft or sentence attempt -> AI feedback -> Revision or completion -> Comparison/settlement -> Encouragement -> Parent-visible progress
```

## Non-Goals

V0.5c must not include:

- Streaming or SSE.
- New AI learning task types.
- V0.6 Writing Castle prompt content.
- Dynamic model selection.
- A/B testing.
- Automatic routing by quality/cost score.
- Plugin systems or policy engines.
- Provider-specific SDK integrations.
- Admin charts, export, reports, or daily digests.
- Frontend framework upgrades.

## Release Boundary

V0.5c has three scope bands.

### P0: V0.5c Core

P0 is the release gate. V0.5c is not complete until all P0 items are done.

- Add a task-level AI execution boundary, named `AITaskRunner` or `run_ai_task()` in implementation.
- Add code-level routing config with clear `task -> logical model -> provider profile -> pricing` layers.
- Add OpenAI-compatible HTTP provider profiles for primary and fallback providers.
- Add provider fallback for timeout, API/rate-limit error, malformed JSON, and schema validation failure.
- Add per-task primary/fallback timeout and total latency budget config.
- Move daily limits to task-level product semantics.
- Add a code-level Cost Registry.
- Extend `LLMCallLog` for task-level routing, fallback, status, pricing, and latency observability.
- Extend Admin AI usage endpoint or page with minimal task/model/provider/fallback visibility.
- Add fallback integration tests.
- Add Playwright E2E coverage for Magic Code login and the sentence challenge flow.
- Ensure Alpha operations can observe login, child creation, sentence challenge completion, fallback/daily-limit events, and summary views.

### P1: Can Slip To V0.5c.1

P1 items are valuable but do not block the V0.5c release.

- Admin model usage dashboard polish beyond the minimal P0 table.
- Prompt Registry naming cleanup.
- `AIInteractionState` in the sentence workshop only.
- Behavior-preserving split of `admin_alpha.py`.
- Parent summary one-line copy improvement if it stays within a half-day implementation budget.

- `qa/smoke-checklist-template.md`.

## Architecture

V0.5c introduces one task-level AI execution boundary. Existing task wrappers remain the product-facing API, but they delegate execution to the new runner.

Wrappers continue to own:

- task payload construction
- prompt key selection
- output schema selection
- deterministic fallback object construction
- task-specific validation hooks
- privacy-safe input summary construction
- ghostwriting checks where already present

The runner owns:

1. Resolving task config.
2. Enforcing task-level daily limits.
3. Executing primary and fallback provider attempts.
4. Recording task-level logs and costs.

The spec does not require exact internal function names. The implementation should keep the four responsibilities clear and independently testable.

### Runner Interface Contract

The runner needs enough information from wrappers to execute validation and fallback centrally. The implementation can choose exact Python names and types, but the interface should have this shape:

```python
run_ai_task(
    *,
    task_name: str,
    student_id: str | None,
    payload: dict,
    output_schema: type[BaseModel],
    prompt_key: str,
    input_summary: str,
    validate_output: Callable[[BaseModel], None] | None = None,
    deterministic_fallback_factory: Callable[[FailureContext], BaseModel] | None = None,
) -> AITaskResult
```

Wrapper responsibilities stay outside the runner: constructing payload, choosing prompt key, choosing schema, providing task-specific validation, and providing a deterministic fallback factory when the product has a safe fallback. Runner responsibilities stay centralized: resolving routing config, calling providers, parsing schema, running validation hooks, triggering fallback, applying daily-limit semantics, calculating cost, and writing one task-level log.

This prevents two failure modes:

- wrappers handling deterministic fallback outside centralized logging
- runner attempting schema or task validation without the wrapper-provided contract

### Configuration Layers

Routing config has four layers:

```text
task config -> logical model -> provider profile -> pricing
```

Provider profiles contain connection information only:

- profile name
- provider type
- base URL environment variable name
- API key environment variable name

Logical models carry product and model semantics:

- logical model key, such as `cheap_fast` or `strong_default`
- provider profile
- concrete model name
- pricing key
- cost tier label

Task configs reference logical models, not provider credentials:

- `primary_model`
- `fallback_model`
- timeouts and latency budgets
- daily limit
- prompt key allowlist/default
- enabled flag

Cost Registry is keyed by `pricing_key`. Staging and production startup must validate that every enabled task resolves to models with configured pricing.

Environment variables may provide credentials, base URLs, and narrowly scoped model overrides for deployment. If a model override changes the concrete model used by a logical model, the resolved model must still map to a Cost Registry entry in staging and production. There must be no global `LLM_MODEL` bypass around ModelRouter for production AI calls.

### Task Config Registry

ModelRouter is a code-level, versioned registry. It follows the same reviewable style as the Prompt Registry.

Each existing production task must have a config:

- `sentence_upgrade_feedback`
- `sentence_challenge_generation`
- `sentence_challenge_feedback`
- `essay_feedback`
- `essay_revision_comparison`

Each task config includes:

- `task_name`
- `primary_model`
- `fallback_model`
- `primary_timeout_seconds`
- `fallback_timeout_seconds`
- `max_total_latency_seconds`
- `daily_limit`
- `cost_tier`
- `allowed_prompt_keys`
- `default_prompt_key`
- `enabled`

Unknown task names fail closed. They must not silently use a default strong model.

Wrappers remain responsible for selecting the prompt key for the concrete task call. The runner validates the prompt key against `allowed_prompt_keys`; if a wrapper does not pass a prompt key, the runner may use `default_prompt_key`. This keeps Prompt Registry as the source of prompt content while preventing task/prompt mismatches.

V0.6 Writing Castle task names may be reserved as disabled placeholders. Placeholder tasks must not register prompt content and must not be callable in V0.5c.

Reserved names:

- `writing_topic_analysis`
- `material_questions`
- `material_card_generation`
- `outline_generation`

### Provider Profiles

V0.5c supports named OpenAI-compatible HTTP profiles only.

Examples:

- `primary_http`
- `fallback_http`

Environment variables provide credentials, base URLs, and model overrides. The routing relationship stays in code.

Provider profiles include:

- profile name
- provider type, limited to OpenAI-compatible HTTP in V0.5c
- base URL environment variable name
- API key environment variable name
- optional request timeout override

V0.5c does not use provider-specific SDKs. This keeps fallback behavior uniform and avoids vendor-specific code paths before the platform needs them.

### Timeout And Latency Budget

Task timeout config distinguishes per-attempt timeout from total task latency.

Examples:

```text
sentence_challenge_generation:
  primary_timeout_seconds: 8
  fallback_timeout_seconds: 7
  max_total_latency_seconds: 15

essay_feedback:
  primary_timeout_seconds: 25
  fallback_timeout_seconds: 20
  max_total_latency_seconds: 45
```

If the primary attempt consumes the total latency budget, the runner should skip provider fallback and move to deterministic fallback or controlled failure. Provider profile timeout overrides must not exceed the task attempt timeout. Timeout values must be chosen with child UX in mind.

### Task Wrapper Migration

Current wrappers should migrate from this shape:

```text
wrapper(provider, session, settings-derived cost args, settings-derived limit args, ...)
```

to this shape:

```text
wrapper(runner, session, student_id, product payload args, ...)
```

Routes should stop passing global provider, cost, and daily-limit parameters into every wrapper. Those concerns move behind the runner.

Compatibility with existing route behavior must be preserved.

## Daily Limit Semantics

Daily limits are counted by product task, not provider attempt.

The counting key is:

```text
student_id + task_name + product day
```

The product day uses the configured product timezone.

Primary-to-fallback execution counts as one user-visible AI task. It must not count twice because two provider attempts happened. It also must not bypass the limit by switching provider or model.

Daily limit handling:

- If the task is over limit, the runner does not call any provider.
- It records a log with `final_status=daily_limit_reached`.
- Existing child-friendly rest copy remains the user-facing behavior for sentence challenges.
- Admin can count daily-limit hits.

Mock and deterministic local fallback calls do not count as real provider usage or cost.

Product daily limit counts only user-visible learning outputs:

- `primary_success`: count 1
- `fallback_success`: count 1
- `deterministic_fallback_used`: count 1
- `failed`: count 0
- `daily_limit_reached`: count 0, but record the hit

System failure should not consume a child's practice allowance. Provider abuse and cost protection for repeated failed calls are out of V0.5c scope and should rely on existing API/session rate limiting or future infra rate limits.

The daily-limit check and usage recording must be transactionally safe enough that two simultaneous requests for the same `student_id + task_name + product day` cannot both pass a one-call limit. The implementation may use a lightweight reservation/status in existing logging, a database lock, or another simple database-backed mechanism, but it should not rely on an unprotected read-then-call sequence.

## Fallback Behavior

Each AI task gets at most two provider attempts:

```text
primary profile once -> fallback profile once
```

There is no primary retry loop in V0.5c. This avoids hidden latency and cost growth.

Fallback-triggering failures:

- primary timeout
- primary API error
- primary rate limit
- malformed JSON
- schema validation failure
- task-specific validation hook failure

V0.5c does not repair JSON and does not ask another LLM to fix a failed response. The fallback provider gets the original task payload.

Final behavior:

- `primary_success`: primary provider returns a valid response.
- `fallback_success`: fallback provider returns a valid response after primary failure.
- `deterministic_fallback_used`: both providers fail, and the task has a safe local fallback.
- `daily_limit_reached`: the task is blocked before provider execution.
- `failed`: both providers fail and there is no safe local fallback.

`fallback_reason` must use a fixed enum:

- `timeout`
- `api_error`
- `rate_limit`
- `malformed_json`
- `schema_validation_failed`
- `task_validation_failed`
- `provider_config_error`
- `pricing_unconfigured`
- `unknown_error`

In staging and production, provider config and pricing problems should fail at startup before real calls. The enum values still exist for development, tests, and defensive logging.

For existing tasks, deterministic local fallback should preserve the learning loop whenever it is safe:

- sentence challenge generation returns a safe local challenge.
- sentence challenge feedback returns safe short feedback.
- essay draft feedback returns safe revision guidance.
- essay revision comparison returns safe encouragement and next step.

For future tasks without deterministic fallback, the API must return a child-friendly retry or rest message. It must not expose provider errors, stack traces, model names, or raw technical details to children.

## Cost Registry

Cost Registry is code-level and reviewable.

Each real routed model must have:

- pricing key
- provider/profile key
- model name
- input price per 1K tokens
- output price per 1K tokens
- pricing version or effective date

`cost_tier` in task config is an operator-facing label only. Estimated cost must come from provider/model pricing, not from `cost_tier`.

Pricing behavior by environment:

- `development`: missing pricing allows the call but records `pricing_unconfigured`.
- `staging` and `production`: missing pricing for a real routed model fails fast before provider execution.

If token usage is missing from the provider response, the call can succeed, but estimated cost must be marked unconfigured or unavailable rather than recorded as a misleading `$0`.

Fallback cost semantics:

- `prompt_tokens`, `completion_tokens`, and `total_tokens` on `LLMCallLog` record the sum of all billable provider attempts for the task.
- `estimated_cost` records the sum of all billable provider attempts for the task.
- `resolved_provider` and `resolved_model` record the provider/model that produced the user-visible result.
- `attempt_summaries` records per-attempt token, cost, latency, status, and pricing details for debugging and QA.

This matters because a primary attempt that returns malformed JSON or fails schema validation may still have consumed tokens and incurred provider cost.

## LLMCallLog Design

V0.5c keeps one `LLMCallLog` row per user-visible AI task. It does not add attempt-level tables.

Existing `provider` and `model` fields remain as compatibility fields for the final resolved provider and model.

New or repurposed fields should let Admin and QA answer:

- Which task ran?
- Which provider/model was primary?
- Which provider/model was fallback?
- Did fallback happen?
- Why did fallback happen?
- How many provider attempts happened?
- What final status did the task reach?
- Were pricing and token usage configured?
- What was the final latency and estimated cost?

Required observability fields:

- `resolved_provider`
- `resolved_model`
- `primary_provider`
- `primary_model`
- `fallback_provider`
- `fallback_model`
- `fallback_reason`
- `attempt_count`
- `final_status`
- `pricing_status`
- `attempt_summaries`

Existing usage fields remain:

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `estimated_cost`
- `latency_ms`

Top-level `latency_ms` records total runner wall-clock latency for the task. Per-attempt latency is stored in `attempt_summaries`.

`attempt_summaries` is a privacy-safe JSON list. It must not contain raw prompts, child writing, or raw provider responses. Example:

```json
[
  {
    "attempt_index": 1,
    "role": "primary",
    "provider": "openrouter",
    "model": "cheap-model",
    "status": "schema_validation_failed",
    "error_class": "schema_validation_failed",
    "latency_ms": 8200,
    "prompt_tokens": 300,
    "completion_tokens": 120,
    "estimated_cost": 0.00012,
    "pricing_status": "configured"
  },
  {
    "attempt_index": 2,
    "role": "fallback",
    "provider": "openai",
    "model": "strong-model",
    "status": "success",
    "error_class": "",
    "latency_ms": 5300,
    "prompt_tokens": 300,
    "completion_tokens": 110,
    "estimated_cost": 0.0012,
    "pricing_status": "configured"
  }
]
```

`raw_response`, `output_json`, and `input_summary` must continue to avoid leaking child text through Admin endpoints.

## Admin Observability

P0 Admin observability is intentionally minimal. The backend aggregation endpoint is required. The existing Admin AI usage page should surface those fields as a plain table if it is already part of the touched surface. Dashboard polish beyond that minimal table belongs to P1.

The existing `/api/admin/alpha/ai-usage` endpoint should aggregate by:

- product date
- task name
- provider
- model
- final status

It should return:

- call count
- success count
- fallback success count
- deterministic fallback count
- failure count
- daily limit hit count
- prompt tokens
- completion tokens
- total tokens
- estimated cost
- pricing status
- average latency

If the Admin UI is updated in P0, it should show these fields in a plain table. P0 does not require filters, charts, trend lines, exports, or scheduled reports.

Admin responses must not include:

- raw provider response
- raw child writing
- raw prompts
- API keys or provider credentials

## Alpha Operations Observation

During V0.5c, WenLingo can invite 5-10 new Alpha families based on V0.5b.1 readiness.

V0.5c code must make the following observable through existing Admin views, `ProductEvent`, `LLMCallLog`, or a simple manual tracking sheet:

- family successfully logged in
- child created
- at least one sentence challenge completed
- fallback event happened or did not happen
- daily limit hit happened or did not happen
- parent summary viewed

Code release gates:

- The fields and events needed for this tracking exist.
- Admin or manual inspection can retrieve them.
- 5-10 new family invitations are sent or ready to send.

Operational success metrics do not block code release:

- 80% of invited families complete at least one sentence challenge.
- At least one fallback event is observed in Dev or controlled QA.
- At least three parents view summary and provide feedback.

## Error Handling

Provider errors are internal. Child-facing surfaces must remain encouraging and non-technical.

Routes should map runner statuses as follows:

- `primary_success`: normal response.
- `fallback_success`: normal response.
- `deterministic_fallback_used`: normal response with safe fallback content.
- `daily_limit_reached`: existing rest message and status behavior.
- `failed`: child-friendly retry/rest message.

Admin can see operational status and fallback reason. Children and parents should not see model names, provider names, stack traces, or schema validation details.

Session/database errors remain normal API errors. V0.5c does not change auth boundaries or family access rules.

## Testing Strategy

V0.5c must use TDD whenever practical. Tests should be written or updated before behavior changes.

### Unit Tests

Add tests for:

- task config registry loads all existing AI tasks.
- unknown task fails closed.
- V0.6 placeholder task names are disabled and not callable.
- task config resolves through `task -> logical model -> provider profile -> pricing`.
- prompt keys must be in the task's allowed prompt key list.
- provider profile config rejects missing required credentials for real profiles.
- Cost Registry returns configured prices.
- development missing pricing records `pricing_unconfigured`.
- staging/production missing pricing fails fast.
- daily limit key ignores provider/model and uses `student_id + task_name + product day`.
- task timeout config distinguishes primary timeout, fallback timeout, and max total latency.

### Integration Tests

Add tests for:

- primary timeout triggers fallback.
- primary API/rate-limit error triggers fallback.
- primary malformed JSON or schema validation failure triggers fallback.
- fallback schema failure uses deterministic local fallback when available.
- both providers failing without deterministic fallback returns controlled failure.
- fallback attempts produce one `LLMCallLog`, not multiple task logs.
- `attempt_count`, `fallback_reason`, `final_status`, provider/model fields, latency, pricing status, total billable cost, and attempt summaries are recorded correctly.
- daily limit hit creates no provider call.
- failed tasks do not consume product daily limit.
- concurrent requests cannot both pass a one-call daily limit for the same student/task/day.

### API And Admin Tests

Add tests for:

- sentence challenge generation succeeds through primary.
- sentence challenge generation succeeds through fallback.
- sentence challenge generation uses deterministic fallback after double provider failure.
- sentence challenge feedback follows the same paths.
- essay feedback and revision comparison still preserve existing behavior.
- Admin AI usage aggregates by task/provider/model/final status.
- Admin responses do not include raw child text or raw provider responses.

### E2E Tests

Add Playwright tests for:

- Magic Code login flow.
- Sentence challenge complete flow.

Before running Playwright E2E, remove the ignored local SQLite database:

```text
apps/api/playwright-e2e.db
```

This avoids stale schema from previous runs.

## Migration Notes

Database migration is required for new `LLMCallLog` fields.

Migration verification must include:

- Alembic migration file test or equivalent migration check.
- Model test proving new fields can be persisted.
- `attempt_summaries` persistence with privacy-safe attempt metadata.
- Existing `LLMCallLog` rows remain readable.
- Existing Admin AI usage tests updated for the new aggregation shape.

The migration should use compatibility defaults so existing historical logs do not break Admin pages.

## Rollout And Rollback

Startup validation must verify:

- all enabled tasks have valid primary and fallback logical model config.
- all enabled logical models resolve to valid provider profiles.
- all enabled provider profiles have required credentials in non-test real-provider mode.
- all staging/production routed models have configured pricing.
- all task prompt keys are registered and allowed by task config.
- disabled V0.6 placeholders are not callable.

Railway Dev validation should include:

- primary success smoke.
- fallback success smoke.
- deterministic fallback smoke.
- daily-limit no-provider-call smoke.
- Admin AI usage smoke showing final status, fallback counts, pricing status, and no raw child text.

Rollback strategy:

- Roll back the deployment or pin the previous known-good commit.
- Do not silently bypass ModelRouter by falling back to global `LLM_MODEL`.
- Keep migration defaults compatible so old logs remain readable during rollback.
- If a routed real model lacks pricing in staging/production, fail startup rather than routing through an unpriced model.

## Acceptance Criteria

### ModelRouter And Runner

- All existing production AI tasks resolve through the task config registry.
- Task config resolves through logical models, provider profiles, and pricing keys.
- Unknown task names fail closed.
- V0.6 placeholder task names are disabled and not callable.
- Prompt keys are selected by wrappers and validated against task config allowlists.
- Routes no longer pass global provider/cost/limit parameters through every task wrapper.
- Existing wrapper behavior is preserved.

### Fallback And Reliability

- Each task uses at most primary once plus fallback once.
- Per-task primary timeout, fallback timeout, and max total latency are enforced.
- Timeout, API error, rate limit, malformed JSON, and schema validation failure trigger fallback.
- `fallback_reason` uses the fixed enum defined in this spec.
- Existing deterministic fallbacks preserve the child learning loop after double provider failure.
- Children see normal feedback or child-friendly retry/rest copy, not technical errors.

### Daily Limits

- Limit key is `student_id + task_name + product day`.
- Only user-visible learning outputs consume product daily limit.
- Failed tasks do not consume product daily limit.
- Provider fallback does not double count.
- Switching provider/model cannot bypass the task daily limit.
- Daily limit hit makes zero provider calls.
- Daily-limit check/record behavior is transactionally safe enough for simultaneous requests.

### Cost And Observability

- Every routed real model in staging/production has configured pricing.
- Development can run with missing pricing but records `pricing_unconfigured`.
- `LLMCallLog` records final status, fallback reason, attempt count, primary/fallback provider/model, total latency, pricing status, summed billable tokens, summed estimated cost, and privacy-safe attempt summaries.
- Admin AI usage exposes task/model/provider/fallback visibility without sensitive raw content.

### Tests

- ModelRouter and Cost Registry unit tests pass.
- Fallback integration tests cover timeout, API/rate-limit error, and schema validation failure.
- Daily limit integration tests pass.
- Admin AI usage tests pass.
- Magic Code login Playwright E2E passes.
- Sentence challenge Playwright E2E passes.
- Existing backend and relevant frontend tests continue to pass.

### Scope Control

- No V0.6 prompt content is added.
- No dynamic model routing is added.
- No A/B testing is added.
- No provider-specific SDK is added.
- No new learning feature is added.
- No global `LLM_MODEL` bypass is used for production AI calls.
