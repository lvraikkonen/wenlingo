# WenLingo V0.6d Essay Archive + Multi-Round Revision Design

Date: 2026-06-30

Status: Approved

Historical filename:
`2026-06-30-v0.6c.1-essay-archive-multi-round-revision-design.md`

Official roadmap version:
V0.6d

Note:
This design originated as V0.6c.1 brainstorming but is now promoted to V0.6d
scope in the 2026-06-30 roadmap v6.

## 1. Summary

V0.6d adds a small essay archive and linear multi-round revision management to
Writing Castle. The goal is to make a child's writing progress visible without
turning the product into an essay file manager.

The release solves two user-facing problems:

1. Children and parents cannot easily review submitted essays, AI feedback,
   revisions, and comparison feedback after leaving the page.
2. Once a child submits a first draft or revision, the current Writing Castle
   state can keep occupying the page and make it hard to start a new essay.

The new behavior keeps the writing surface primary. A hidden right-side archive
drawer lets the child restore a recent essay into the main revision area, while
the child can still start a new essay after submitting a first draft.

## 3. Product Decisions From Brainstorming

- Implement the full V0.6d scope: archive list, read-only detail, continue
  revision, and child hide / parent restore rules.
- Hide and restore ship together or both stay disabled. V0.6d must not ship a
  child hide action without a parent-visible restore path.
- Multi-round revision is linear. A new draft compares only against the
  previous draft, not against all earlier drafts.
- Submitting a first draft does not block starting a new essay.
- After first-draft feedback, the primary recommendation remains "continue
  this revision", but the child can also start a new essay or restore an older
  essay.
- The archive drawer only includes essays with a submitted first draft.
- The child-facing drawer shows at most the 3 most recently submitted or
  revised non-hidden archived essays.
- The archive drawer is hidden by default and opens from the right edge on
  desktop, iPad, and phone widths.
- Clicking an archive item loads that essay's latest content and previous AI
  revision guidance into the main Writing Castle revision area.
- If the main area has unsubmitted input, switching to another archived essay
  requires confirmation.
- Children can hide essays from their own archive. Parents can still see and
  restore them.
- Parent views default to summary, with full text and detailed feedback
  expandable.
- First revision keeps the existing full settlement. Later revisions record
  encouragement and limited revision ability growth, not full XP settlement.

## 4. Goals

Children should be able to:

- Find the last few essays they have already submitted.
- Continue revising a previous essay without losing the main writing flow.
- Start a new essay even if an older essay still has unfinished revision work.
- Hide an essay from their own archive without deleting learning history.

Parents should be able to:

- See whether an essay has only a first draft, one completed revision, or
  multiple revisions.
- See a concise summary of the child's progress before choosing to expand full
  text.
- Recover essays hidden by the child from a parent-visible archive or summary
  surface, without already knowing the hidden essay ID.

The product should:

- Reward revision effort without encouraging XP farming.
- Preserve structured AI feedback and traceable learning data.
- Avoid exposing AI-generated essay body text because WenLingo does not
  ghostwrite essays for children.

## 5. Non-Goals

V0.6d does not include:

- Arbitrary branching version history.
- Rich text editing or inline diff editing.
- Permanent hard deletion of essays, versions, LLM logs, ability history, or
  product events.
- A full "view all essays" archive management page.
- Parent weekly report redesign.
- Token Streaming, Progress SSE, or streaming LLM log changes.
- New prompt keys or hardcoded prompts for essay revision. Existing registered
  `essay_revision_comparison` remains the source of AI comparison behavior.

## 6. User Experience

### 6.1 Writing Castle Main Area

The main Writing Castle area always represents the current action:

- start a school-assigned essay,
- start an AI-topic essay,
- write a direct first draft,
- continue revising a selected essay.

After the child submits a first draft, the main area shows:

- the AI feedback,
- the latest revision task or guidance,
- a revision text area,
- a "submit next draft" action,
- a secondary "new essay" action.

Starting a new essay does not treat the earlier essay as failed. The earlier
essay remains available in the archive as "needs revision" or equivalent copy.

### 6.2 Right-Side Archive Drawer

The essay archive is hidden by default. The page exposes a right-edge "archive"
button aligned to the far right of the viewport.

Responsive behavior:

- Desktop web: fixed right-side drawer, overlaying the page edge without
  resizing the main writing area.
- iPad / narrow desktop: right-side overlay around 56-64 percent viewport
  width.
- Phone: right-side near-full-screen overlay. It still opens from the right,
  not from the bottom.

The drawer lists at most 3 non-hidden essays with submitted first drafts,
ordered by `Essay.last_version_submitted_at desc`. "Recent" means recent child
writing submission or revision. Hide and restore actions must not move an old
essay to the top of the child drawer.

Each item shows:

- title,
- status label,
- latest round label,
- latest submitted or revised date,
- primary action such as "continue revising" or "review".

The child drawer does not show hidden essays in V0.6d. Parent-facing views
provide the restore surface for essays hidden by the child.

### 6.3 Loading An Archived Essay Into The Main Area

When the child clicks an archive item:

1. If the main area has no unsubmitted input, load the selected essay.
2. If the main area has unsubmitted input, show a confirmation dialog saying
   that switching will discard the current unsubmitted input.
3. After confirmation, the main area shows the selected essay's latest content
   in an editable revision box.
4. The previous version's AI feedback or the latest comparison's `next_step`
   becomes the visible revision guidance.

Loading an archived essay into the editor never mutates the latest
`EssayVersion`. The editor is prefilled from latest child-authored content, but
submit always appends a new `EssayVersion`.

This makes "restore old essay" a continue-writing action, not a detour through
a management page.

### 6.4 Essay Detail

The archive detail view is read-only. It is used for complete review and parent
expansion, not as the primary continue-editing path.

The detail view shows a timeline:

- first draft,
- first-draft AI feedback and revision task,
- second draft and comparison,
- later drafts and pairwise comparison feedback.

It must not show AI-written essay body content. It may show child-authored
draft content, AI feedback, evidence, and next-step guidance.

### 6.5 Parent View

The parent view defaults to summary:

- topic,
- current status,
- number of drafts / revision rounds,
- recent improvement,
- next suggestion.

Full draft text and per-round feedback are expandable. This keeps the parent
experience focused on "how is my child doing?" rather than making parents read
every essay by default.

Parents can view essays hidden by the child and restore them to the child's
archive from a parent archive or parent summary surface.

## 7. Data Model

### 7.1 Essay

Add archive and recency fields to `Essay`:

- `updated_at: datetime`
- `last_version_submitted_at: datetime | None`
- `visibility_changed_at: datetime | None`
- `hidden_at: datetime | None`
- `hidden_by: str`

`hidden_by` values:

- `""` when visible,
- `"child"` when hidden by the child,
- `"parent"` reserved for future parent hide behavior.

V0.6d only implements child hide and parent restore. Restore clears
`hidden_at` and `hidden_by`, and sets `visibility_changed_at`.

Timestamp semantics:

- `updated_at` is the technical row update time.
- `last_version_submitted_at` changes only when the child submits a first draft
  or any revision draft.
- `visibility_changed_at` changes only when an essay is hidden or restored.

The child drawer sorts by `last_version_submitted_at desc`. Parent hidden
management surfaces may sort by `visibility_changed_at desc`.

### 7.2 EssayVersion

Preserve the existing table and add a linear round field:

- `round_index: int | None`

`round_index` should use the database's ordinary integer ID-compatible type.

Version label mapping is fixed:

- round 1: `version_label = "first_draft"`,
- round 2: `version_label = "revision"` for legacy compatibility,
- round 3 and later: `version_label = "revision_round_{round_index}"`.

`round_index` is the ordering source of truth for multi-round behavior.

Add helpers and use them in runtime code:

```python
get_round_index(version) -> int
get_version_label_for_round(round_index: int) -> str
```

Migration behavior:

1. Add nullable `EssayVersion.round_index`.
2. Backfill `version_label = "first_draft"` to `round_index = 1`.
3. Backfill `version_label = "revision"` to `round_index = 2`.
4. Audit rows with unknown or missing `version_label`.
5. Audit duplicate `essay_id + round_index` before adding a constraint.
6. Add a partial unique index: unique `(essay_id, round_index)` where
   `round_index is not null`.
7. Backfill `Essay.last_version_submitted_at` from
   `max(EssayVersion.created_at)`.
8. Add helper functions and migrate runtime code to `round_index` ordering.

The existing `(essay_id, version_label)` uniqueness rule remains compatible
because each round receives a distinct label.

After migration, all new `EssayVersion` writes must set a non-null
`round_index`. Runtime code must reject creating first-draft or revision
versions without `round_index`.

### 7.3 EssayRevisionAttempt

V0.6d must preserve child-authored submitted content if AI comparison fails.

Add a recoverable attempt record:

- `id`
- `essay_id`
- `base_version_id`
- `target_round_index`
- `submitted_content: str | None`
- `submitted_content_hash`
- `idempotency_key`
- `status`: `pending_comparison | comparison_failed | completed`
- `new_version_id: str | None`
- `error_code: str | None`
- `created_at`
- `updated_at`

Uniqueness rules:

- idempotency key: unique `(essay_id, base_version_id, idempotency_key)`,
- target round reservation: partial unique
  `(essay_id, base_version_id, target_round_index)` where `status in
  ('pending_comparison', 'completed')`.

The idempotency key handles retries of the same submit action. The target round
reservation handles different submit actions racing from the same base version
before either has finished its LLM comparison.

Content retention:

- `pending_comparison` and `comparison_failed` attempts retain
  `submitted_content` so the child-authored text can be retried or recovered.
- `completed` attempts may clear `submitted_content` after `new_version_id` is
  committed, because the child-authored content is then preserved in
  `EssayVersion`. Keep `submitted_content_hash`, idempotency metadata, and
  `new_version_id` for audit and stable retry responses.

If AI comparison fails:

- do not create a completed `EssayVersion`,
- do not award XP or ability growth,
- preserve the child-authored submitted content in `EssayRevisionAttempt`,
- show a child-friendly retry message,
- allow retry comparison from the preserved attempt.

### 7.4 Topic Metadata

Archive payloads should preserve V0.6c topic-origin metadata where it already
exists. V0.6d uses the existing runtime vocabulary and must not introduce a
second archive-only topic-origin enum:

- `topic_origin`: `teacher_provided | ai_topic_idea | direct_draft`
- `topic_type`
- `topic_variant`
- `scaffold_template_version`
- `selected_topic_idea`
- `generated_topic_metadata`

The child UI does not need to show every field, but archive detail and parent
summary must not lose this metadata.

### 7.5 Settlement And Ability History

First revision keeps current behavior:

- full essay settlement,
- existing XP behavior,
- existing revision ability delta rule.

P0 settlement safety for later revisions:

- round 3 and later never grant full XP settlement,
- round 3 and later never create duplicate full essay settlement,
- growth for `essay_id + round_index` is awarded at most once.

P1 reward policy for later revisions:

- round 3: `revision +2`,
- round 4: `revision +1`,
- round 5 and later: no ability growth.

If there is not enough time to implement the polished cap, the safe fallback is
to store round 3 and later feedback with no ability growth. The unsafe fallback
of repeated full XP is not allowed.

Later revision growth is awarded only if:

- normalized content differs from the previous version,
- normalized edit distance is at least 3 percent or normalized length delta is
  at least 20 characters,
- growth for `essay_id + round_index` has not already been awarded.

After the cap, the system still stores feedback and product events but does
not apply more ability growth for that essay.

## 8. Derived Archive Status

Archive status is derived by the backend. Frontend renders it and must not
reimplement status business logic.

| Condition | Status |
|---|---|
| No first draft | `not_archived` |
| Round 1 exists, feedback complete, no round 2 | `needs_revision` |
| Round 2 exists, no later rounds | `revised_once` |
| Round 3 or later exists | `multi_round_revision` |
| Child-hidden essay in a parent-visible surface | `hidden_by_child` |
| Recoverable AI feedback/comparison failure exists | `needs_retry` |

For child archive lists, hidden essays are excluded instead of returned with
`hidden_by_child`.

Status priority:

1. Child archive list visibility filtering runs first, so hidden essays are not
   returned to the child.
2. Parent hidden-management surfaces use `hidden_by_child` for child-hidden
   essays.
3. Active continue-revision surfaces use `needs_retry` when a recoverable
   failed attempt exists.
4. Otherwise the progress status is derived from the latest round.

Action booleans are also backend-derived:

- `needs_revision` means the product educationally recommends another revision.
  It is usually true when round 1 feedback is complete and no round 2 exists;
  it may also be true for `needs_retry`.
- `can_continue_revision` means the essay is technically and product-wise
  allowed to append a next draft. It is generally true for visible,
  non-assessment essays with round 1 or later, including `revised_once` and
  `multi_round_revision`.
- `can_retry_revision_attempt` means a `comparison_failed` attempt exists and
  its `base_version_id` is still the latest version.

Hidden essays are not returned in child-facing archive surfaces. Parent-facing
detail may show that a hidden essay can be restored before the child continues.
`summary_label` is backend-generated display copy for the current status;
frontend pages may render it but should not derive it locally.

## 9. API Design

### 9.1 Child Archive List

`GET /api/students/{student_id}/essay-archive?limit=3`

Returns child-visible archive items:

- only essays owned by the student,
- only essays with at least one `EssayVersion` round 1 / `first_draft`,
- excludes hidden essays by default,
- sorted by `Essay.last_version_submitted_at desc`,
- capped at `min(requested_limit, 3)` for the V0.6d child drawer.

Each item includes:

- `essay_id`,
- `title`,
- `status`,
- `hidden`,
- `hidden_by`,
- `hidden_at`,
- `latest_round_index`,
- `latest_version_id`,
- `last_version_submitted_at`,
- `revision_round_count`,
- `needs_revision`,
- `can_continue_revision`,
- `can_retry_revision_attempt`,
- `summary_label`,
- topic metadata from Section 7.4 when present.

### 9.2 Parent Archive List

`GET /api/parents/students/{student_id}/essay-archive?include_hidden=true&limit=20`

Returns parent-visible archive items for a child:

- only students belonging to the authenticated parent family,
- includes child-hidden essays when `include_hidden=true`,
- defaults to visible essays only when `include_hidden` is omitted or false,
- sorted by `visibility_changed_at desc` for hidden-management views, or by
  `last_version_submitted_at desc` for ordinary parent summaries.

Each item includes:

```json
{
  "essay_id": "...",
  "title": "...",
  "hidden": true,
  "hidden_by": "child",
  "hidden_at": "...",
  "latest_round_index": 3,
  "status": "hidden_by_child",
  "needs_revision": false,
  "can_continue_revision": false,
  "can_retry_revision_attempt": false
}
```

The parent restore surface uses this endpoint so parents can restore hidden
essays without already knowing an essay ID.

### 9.3 Archive Detail

`GET /api/essays/{essay_id}/archive-detail`

This is the child-facing archive detail / continue surface. It does not return
child-hidden essays. If a child accesses a hidden essay through stale frontend
state or an old URL, return 404 and let the frontend show friendly hidden-state
copy.

`GET /api/parents/essays/{essay_id}/archive-detail`

This is the parent-facing archive detail surface. It can return child-hidden
essays and offer restore. Do not use frontend-supplied display metadata such as
`actor_type` to decide whether a request is parent-facing; the parent path and
authenticated parent session define that behavior.

Returns:

- essay metadata,
- child / parent visibility state,
- topic metadata from Section 7.4 when present,
- ordered versions,
- recoverable revision attempt state, if any,
- current continue-revision payload,
- parent summary payload.

The continue-revision payload includes:

- latest version ID,
- latest content,
- previous AI guidance to show beside the editor,
- next round index.

### 9.4 Multi-Round Revision Submit

`POST /api/essays/{essay_id}/revision`

V0.6d changes the route from "single revision only" to "append next linear
revision".

Request:

```json
{
  "base_version_id": "latest-version-id-seen-by-client",
  "content": "child-authored next draft",
  "idempotency_key": "client-generated-uuid"
}
```

Rules:

1. Require a first draft.
2. Look up an existing `EssayRevisionAttempt` by
   `essay_id + base_version_id + idempotency_key` before any stale latest check.
3. If the existing attempt is `completed`, return the existing `new_version`
   result even if `base_version_id` is no longer the server latest version.
   This is required for true network-retry idempotency.
4. If the existing attempt is `comparison_failed`, return retry metadata and
   preserved submitted content state instead of creating a duplicate attempt.
5. If the existing attempt is `pending_comparison` and not expired, return 202
   with stable in-progress metadata and do not call the LLM again:

   ```json
   {
     "status": "pending_comparison",
     "attempt_id": "...",
     "message": "这次修改正在保存，请不要重复提交。"
   }
   ```

6. If the existing attempt is `pending_comparison` and older than
   `REVISION_ATTEMPT_TIMEOUT_SECONDS`, mark it `comparison_failed` with
   `error_code = "attempt_timeout"`, keep `submitted_content`, and return retry
   metadata.
7. If no same-key attempt exists, find the latest version by `round_index`.
8. If `base_version_id` is not the server latest version ID, return 409 before
   calling the LLM.
9. Calculate `target_round_index = latest.round_index + 1`.
10. Atomically create a pending `EssayRevisionAttempt` reservation for
   `essay_id + base_version_id + target_round_index`.
11. Commit the pending attempt / target-round reservation before LLM work.
    Do not keep a database transaction open while calling the LLM.
12. If another pending or completed attempt already owns that target round:
    - same `idempotency_key`: return the existing attempt state from steps 3-5,
    - different `idempotency_key`: return 202/in-progress for pending owner, or
      409 with latest continue-revision payload for completed owner,
    - never call the LLM for the losing request.
13. Compare latest version content to request content with the registered
   `essay_revision_comparison` prompt.
14. In a second short transaction, create a new `EssayVersion` with
   `round_index = target_round_index`.
15. Mark the attempt as `completed` with `new_version_id`.
16. Apply settlement rules:
    - if new round is 2, run current full settlement,
    - if new round is greater than 2, apply limited revision-only growth if
      within the safety rules and cap.
17. Update `Essay.last_version_submitted_at`.
18. Return the new version, comparison, and settlement/growth metadata.

The `(essay_id, round_index)` uniqueness rule remains the final concurrency
backstop. The same-key idempotency lookup and target-round reservation must
prevent avoidable duplicate LLM calls before that backstop is needed.

The route still rejects:

- missing essay,
- cross-family access,
- missing first draft,
- assessment-only essays,
- stale `base_version_id`,
- different-key concurrent ownership of the same target round,
- concurrent duplicate round insertion.

### 9.5 Retry Preserved Revision Attempt

`POST /api/essays/{essay_id}/revision-attempts/{attempt_id}/retry-comparison`

Rules:

- only retries attempts owned by the current child / family context,
- only retries `comparison_failed` attempts,
- reuses the preserved `submitted_content`,
- checks that `base_version_id` is still the server latest version before
  calling the LLM,
- switches the attempt back to `pending_comparison` and reacquires the
  target-round reservation before calling the LLM,
- if another pending or completed attempt already owns that target round,
  returns in-progress or stale-state metadata before LLM work,
- on success, creates the next `EssayVersion` and marks the attempt completed,
- on stale base version, returns 409 with the latest continue-revision payload.

### 9.6 Visibility

`PATCH /api/essays/{essay_id}/visibility`

Child-facing visibility endpoint. V0.6d uses this path for child hide only.

Request:

```json
{ "hidden": true }
```

`PATCH /api/parents/essays/{essay_id}/visibility`

Parent-facing visibility endpoint. V0.6d uses this path for parent restore
only.

Request:

```json
{ "hidden": false }
```

Rules:

- child context may hide only through `/api/essays/{essay_id}/visibility`,
- parent context may restore only through
  `/api/parents/essays/{essay_id}/visibility`,
- restore must be reachable from the parent archive / summary surface,
- hidden essays remain available to parent detail and reporting,
- hiding does not delete any essay versions, LLM logs, ability history, or
  product events,
- hide and restore are released together.

### 9.7 Active Writing Castle Essay

The current active-essay lookup must stop treating essays with submitted first
drafts or completed revisions as blocking active work.

It should only auto-resume open prewriting essays that have no submitted first
draft yet. Submitted essays move to archive / continue-revision flows.

## 10. Prompt And Copy Requirements

Use the existing registered prompt key `essay_revision_comparison`, but ensure
the prompt version and UI copy are pairwise and round-neutral.

Required wording model:

- previous draft,
- this draft,
- this revision,
- next suggestion.

Avoid hardcoded "first draft vs second draft" or "second draft" copy in prompt
text, route code, or UI surfaces that can be reached by round 3 and later.
Do not introduce a new prompt key for V0.6d.

## 11. Product Events

Add or reuse event types for:

- archive drawer opened,
- archived essay selected,
- essay hidden by child,
- essay restored by parent,
- multi-round revision submitted,
- revision comparison failed,
- preserved revision attempt retried.

Payloads should include safe metadata:

- `essay_id`,
- `round_index`,
- `previous_version_id`,
- `new_version_id`,
- `attempt_id`,
- `hidden`,
- `revision_growth_awarded`,
- `actor_type`: `child_surface | parent`,
- `student_id`,
- `parent_account_id`, if available.

Payloads must not include full essay content.

## 12. Error Handling

- If switching archived essays would discard unsubmitted input, the frontend
  asks for confirmation.
- If an archive item was hidden or restored elsewhere, refetch and show a
  friendly stale-state message.
- If a child directly accesses a hidden essay through an old URL or stale
  frontend state, child-facing archive/detail/continue APIs return 404 and the
  frontend shows friendly hidden-state copy.
- If the same idempotency key is retried after a completed attempt, return the
  completed result even when the original `base_version_id` is no longer
  latest.
- If the same idempotency key sees `pending_comparison`, return 202 with
  in-progress metadata and never call the LLM again.
- If a different idempotency key races for the same
  `essay_id + base_version_id + target_round_index`, return in-progress or
  stale-state metadata before LLM work.
- If `base_version_id` is stale, the API returns 409 before LLM work and the
  frontend refreshes the essay state, but only after same-key idempotency
  lookup has had a chance to return an existing completed result.
- If duplicate revision submission races occur after stale/idempotency checks,
  the API returns 409 and the frontend prompts the child to refresh the essay
  state.
- If AI comparison fails for a revision, no completed version is created,
  no XP or ability growth is awarded, and the submitted child content remains
  recoverable through `EssayRevisionAttempt`.
- Cross-family access returns 404, preserving existing auth boundaries.
- Hidden child essays do not appear in the default child drawer but remain in
  parent-visible detail/report contexts.

## 13. Testing And Verification

Backend tests:

- Child archive list returns only essays with submitted first drafts.
- Child archive list excludes hidden essays and caps child drawer results at 3.
- Child archive list orders by `last_version_submitted_at desc`, not
  hide/restore time.
- Parent archive list can include child-hidden essays when
  `include_hidden=true`.
- Parent can restore a hidden essay discovered from the parent archive list.
- Child-facing detail/continue APIs return 404 for child-hidden essays reached
  through old URLs or stale frontend state.
- Archive detail returns ordered version timeline.
- Archive detail preserves V0.6c topic origin and generated-topic metadata.
- Existing `first_draft` / `revision` data maps to rounds 1 and 2.
- Third draft submission compares round 2 to round 3 and succeeds.
- New `EssayVersion` runtime writes reject missing `round_index`.
- Revision submit with the same completed idempotency key returns the existing
  result without another LLM call, even after latest has advanced.
- Revision submit with the same pending idempotency key returns 202
  `pending_comparison` without another LLM call.
- Revision submit rejects stale `base_version_id` before calling the LLM only
  after same-key idempotency lookup has been checked.
- Concurrent revision submits with different idempotency keys but the same
  `base_version_id + target_round_index` do not both call the LLM.
- AI comparison failure stores a recoverable `EssayRevisionAttempt` and awards
  no XP or ability growth.
- Retry from a preserved revision attempt can complete the comparison and
  append the next version.
- Completed `EssayRevisionAttempt` content retention follows the spec: content
  can be loaded from `new_version_id`, while attempt metadata/hash remains.
- Existing second revision 409 tests are replaced or updated to assert duplicate
  same-round conflicts, not a blanket "essay already settled" rule.
- First revision still creates full settlement.
- Later revisions never create full settlement and only create capped revision
  ability growth when anti-farming checks pass.
- Hiding an essay preserves versions, LLM logs, ability history, and product
  events.
- Cross-family archive list/detail/visibility access returns 404.
- Migration tests cover new columns, indexes, backfills, audits, and uniqueness
  constraints.

Frontend tests:

- Archive drawer is hidden by default and opens from the right.
- The drawer renders at most 3 archive items.
- Responsive behavior keeps the right-side drawer model on desktop, iPad, and
  phone widths.
- Clicking an archive item loads latest content and AI guidance into the main
  revision area.
- Loading an archived essay into the editor does not mutate the latest
  `EssayVersion`.
- Switching away with unsubmitted input shows confirmation.
- Starting a new essay is possible after submitting a first draft or completing
  a revision.
- Parent summary defaults to concise status and can expand full text.
- Parent archive / summary surface lists child-hidden essays and offers restore.
- Child drawer refetches after restore and shows the essay only after restore
  completes.
- Frontend uses backend-derived `can_continue_revision` rather than
  `needs_revision` as the continue-action gate.
- Round 3 and later comparison copy uses round-neutral wording.

E2E / manual QA:

- Direct draft: submit first draft, start a new essay, then restore the first

- Writing Castle prewriting path: submit first draft, leave page, return,

- AI-topic path: interest + grade -> 3 topic ideas -> select one -> prewriting
  -> first draft -> archive item appears.

  rather than stale 409.
- Two-tab concurrent submit path: two different idempotency keys based on the
  same base version do not both reach the LLM.
- Stale submit path: open the same essay in two tabs, submit one, then verify
  the other returns 409 before LLM work after idempotency lookup.
- AI failure path: force comparison failure, verify submitted child content can
  be retried.
- Hide/restore path: child hides essay, child drawer no longer shows it, parent
  can discover it and restore it.
- Mobile browser: right-side drawer opens from the right and does not make the
  page unusable.

## 14. Acceptance Criteria

- Child can find up to 3 recent submitted essays from the hidden right-side
  archive drawer.
- "Recent" in the child drawer means recent child draft submission, not
  hide/restore activity.
- Child can click an archived essay and continue revising it in the main
  Writing Castle area.
- Continuing an archived essay is append-only and never overwrites an existing
  `EssayVersion`.
- Child can start a new essay after submitting a first draft or revision of a
  previous essay.
- Details can show first draft, AI feedback, later drafts, and comparison
  feedback in a linear timeline.
- Third and later drafts are supported without arbitrary branching.
- Revision submit checks same-key idempotency before stale latest checks, so a
  lost-response retry returns the original completed result rather than a stale
  409.
- Revision submit uses `base_version_id`, `idempotency_key`, and target-round
  reservation to prevent stale writes and avoidable duplicate LLM work.
- Same-key `pending_comparison` retries return stable in-progress metadata and
  never call the LLM again.
- Different-key concurrent submits for the same
  `essay_id + base_version_id + target_round_index` are stopped before LLM
  work.
- If AI comparison fails, child-authored submitted content remains recoverable
  and retryable.
- First revision keeps existing settlement behavior.
- Later revisions do not grant full XP repeatedly and only apply capped
  revision growth when safety checks pass.
- Child hide is soft hide; parent can list child-hidden essays and restore them
  without already knowing an essay ID.
- Child-facing archive/detail/continue surfaces do not return child-hidden
  essays, including old URL or stale state access.
- Child drawer hides a restored essay until restore completes, then refetches.
- Hide and restore either ship together or both stay disabled.
- No permanent deletion of learning or AI logs occurs in V0.6d.
- Existing V0.6c topic breadth and AI-topic paths remain usable.
- Existing `essay_revision_comparison` prompt behavior is round-neutral for
  round 3 and later without introducing a new prompt key.

## 15. Implementation Constraints

- The frontend may implement archive detail as a route, modal, or parent-only
  expansion, but continuing a draft from the child drawer must load into the
  main Writing Castle area.
- The old `version_label == "revision"` code paths should be kept compatible
  during migration, then gradually replaced with `round_index` based helpers.
- Runtime code should use `get_round_index(version)` and
  `get_version_label_for_round(round_index)` instead of open-coded label rules.
- Frontend pages render backend-derived archive status. They should not
  duplicate archive status business logic.
- Frontend continue/retry actions should use backend-derived
  `can_continue_revision` and `can_retry_revision_attempt`. `needs_revision`
  is an educational recommendation signal, not the sole action gate.
- Revision submit implementation must check an existing
  `EssayRevisionAttempt` by idempotency key before checking whether
  `base_version_id` is latest.
- Revision submit implementation must create the pending attempt / target-round
  reservation before LLM work and must not rely only on final
  `(essay_id, round_index)` uniqueness to stop avoidable duplicate LLM calls.
- Later-revision settlement code must fail safe: no full XP for round 3 and
  later, even if polished reward caps are deferred.
- Prompt text must come from Prompt Registry through the existing task wrapper;
  V0.6d must not hardcode new LLM prompt text in services or routes.
