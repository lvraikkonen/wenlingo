# WenLingo V0.4.1b Alpha Feedback & Observation Design

Date: 2026-05-27
Status: Brainstorming design approved; pending written spec review

## Goal

V0.4.1b establishes a minimal but complete Alpha feedback and observation loop.
An invited parent enters through a warm product onboarding page, uses a one-time
invite code, creates or continues a real Alpha family, lets the child complete
core learning tasks, and gives WenLingo enough privacy-safe operational signal to
understand where each family is in the Alpha funnel and whether AI feedback feels
useful.

This release is still for a small trusted Alpha group. It is not public signup,
full authentication, a broad analytics product, or a curriculum expansion.

## Product Scope

V0.4.1b uses a vertical closed-loop approach:

```text
invite code
-> Alpha onboarding
-> Alpha parent and child flow
-> child learning task
-> child reaction
-> parent summary feedback
-> admin overview and family timeline
```

Implement in V0.4.1b:

- One-time invite codes, one code per family.
- Product events for the Alpha funnel and key learning actions.
- Browser-held anonymous Alpha session id using `wenlingo_alpha_session_id`.
- Child reaction collection for Assessment, Sentence, Essay draft, and Essay
  revision AI feedback.
- Parent usefulness feedback on the Alpha child summary page.
- Token-protected, read-only `/admin/alpha` experience with overview and
  family timeline drill-down.
- Scripts to generate invite codes and bind existing V0.4.1a Alpha parents to
  invite codes before production rollout.
- Deployment and QA documentation updates.

Defer beyond V0.4.1b:

- Full authentication or public account management.
- Public registration.
- Admin write operations.
- Full analytics dashboard.
- Data export or deletion UI.
- Reading Canyon expansion.
- Full weekly report.
- Gamification expansion.
- Showing child writing text or AI feedback body in admin.

## Alpha Onboarding

`/alpha/start` becomes an Alpha invitation onboarding page rather than a
marketing landing page. The page should feel like a first product touchpoint:
warm, clear, and trustworthy, without long-form sales content.

The first screen includes:

- WenLingo / 小文星球 identity.
- Clear Alpha participation note.
- Privacy and AI usage notice.
- One-time invite code input.
- Primary continue action.

The page creates or reads:

```text
wenlingo_alpha_session_id = <random browser session id>
```

This id is not an authentication credential. It exists only to connect
pre-parent events such as page view and invite validation attempts.

If `wenlingo_alpha_parent_id` already exists, the page keeps the V0.4.1a
continuation behavior and offers:

```text
继续使用当前 Alpha 家庭
```

Existing families should not be asked to re-enter an invite code. Before
V0.4.1b production rollout, existing V0.4.1a parents are bound to invite codes
with an operational script so admin data stays complete.

## Data Model

V0.4.1b adds four data concepts. They should be simple, explicit, and easy to
query during a small Alpha. SQLModel table names may follow the existing project
style.

### AlphaInviteCode

Purpose: gate Alpha entry and associate each family with one invite.

Suggested fields:

```text
id
code_hash or code
label
status
issued_to_note
consumed_by_parent_id
consumed_at
created_at
```

Status values:

```text
issued
consumed
disabled
```

Prefer storing a hash if implementation cost stays reasonable. If V0.4.1b stores
the code directly for Alpha speed, the code must still be treated as sensitive:
avoid returning it from general APIs and avoid logging full codes in product
events.

### ProductEvent

Purpose: preserve a privacy-safe timeline for funnel and learning actions.

Suggested fields:

```text
id
event_type
parent_id
student_id
invite_code_id
alpha_session_id
payload JSON
created_at
```

`payload` must not include:

- child writing text
- AI feedback body
- full invite code
- school
- address
- phone
- photo
- real full name
- other sensitive personal details

Allowed payload examples:

- route path
- task type
- target type
- target id
- status
- error category
- duration bucket if later added
- counts and booleans

### FeedbackReaction

Purpose: let the child mark how an AI feedback moment felt.

Suggested fields:

```text
id
parent_id
student_id
target_type
target_id
reaction
alpha_session_id
created_at
updated_at
```

`target_type` values:

```text
assessment
sentence_training
essay_draft
essay_revision
```

`reaction` values:

```text
positive
neutral
negative
```

UI labels may use:

```text
😊
😐
😞
```

Uniqueness:

```text
student_id + target_type + target_id
```

Repeated clicks update the existing row.

### ParentFeedback

Purpose: let the parent mark whether the Alpha summary was useful.

Suggested fields:

```text
id
parent_id
student_id
target_type
target_id
usefulness
alpha_session_id
created_at
updated_at
```

`target_type` for V0.4.1b:

```text
alpha_summary
```

`usefulness` values:

```text
helpful
not_helpful
```

V0.4.1b continues using the real-time Alpha summary endpoint. It should not
create a formal `Report` row just to collect this feedback.

## Event Taxonomy

Events should use stable string names. The first set should be intentionally
small enough for the admin timeline to stay readable.

Frontend-originated events:

```text
alpha_start_viewed
invite_code_submitted
parent_children_viewed
child_handoff_clicked
child_dashboard_viewed
summary_viewed
```

Server-originated events:

```text
invite_code_validated
invite_code_rejected
alpha_parent_created
alpha_child_created
assessment_submitted
assessment_completed
sentence_training_submitted
sentence_training_completed
essay_draft_submitted
essay_draft_feedback_completed
essay_revision_submitted
essay_revision_feedback_completed
child_feedback_reaction_submitted
parent_summary_feedback_submitted
ai_feedback_failed
```

If an existing API cannot easily distinguish submitted and completed states, it
may record only the completed event in V0.4.1b. The event name must still be
specific to the task so admin can show the funnel clearly.

## Backend/API Design

Keep Alpha additions close to the existing Alpha route surface. Extending
`apps/api/app/api/routes/alpha.py` is acceptable. If the admin endpoints become
too large, add a separate `admin_alpha.py` route module.

### Invite Validation

```text
POST /api/alpha/invites/validate
```

Request:

```json
{
  "code": "ABC123",
  "alpha_session_id": "..."
}
```

Response:

```json
{
  "valid": true,
  "invite_id": "...",
  "invite_token": "..."
}
```

The invite token can be a short-lived signed value or another simple server-side
validation mechanism suitable for this Alpha. It exists so parent creation does
not trust a raw frontend-only boolean.

Behavior:

- Accept only `issued` invite codes.
- Reject `consumed`, `disabled`, missing, and malformed codes.
- Record success and failure events.
- Do not store the full submitted code in event payload.

### Alpha Parent Creation

```text
POST /api/alpha/parents
```

V0.4.1b extends the V0.4.1a API so new parents must provide valid invite proof.

Request:

```json
{
  "display_name": "小星家长",
  "invite_token": "...",
  "alpha_session_id": "..."
}
```

Behavior:

- Validate invite proof server-side.
- Create `ParentUser`.
- Mark invite as `consumed`.
- Set `consumed_by_parent_id`.
- Write `alpha_parent_created`.
- Preserve the existing response shape enough that current frontend helpers can
  evolve without a broad rewrite.

Existing V0.4.1a parents are not forced through this endpoint again.

### Product Event Intake

```text
POST /api/alpha/events
```

Purpose: record frontend-only events such as page view and navigation clicks.

Rules:

- Whitelist allowed `event_type` values.
- Sanitize payload keys.
- Accept optional `parent_id`, `student_id`, `invite_id`, and
  `alpha_session_id`.
- Never treat this endpoint as authorization evidence.
- Keep failures non-fatal for the user experience.

### Child Feedback Reaction

Route can be either:

```text
POST /api/students/{student_id}/feedback-reactions
```

or an Alpha-scoped route if that fits the implementation better.

Request:

```json
{
  "target_type": "assessment",
  "target_id": "...",
  "reaction": "positive",
  "alpha_session_id": "..."
}
```

Behavior:

- Verify the target exists and belongs to `student_id`.
- Derive `parent_id` from `StudentProfile`, not from a trusted frontend claim.
- Upsert by `student_id + target_type + target_id`.
- Record `child_feedback_reaction_submitted`.
- Return the saved reaction state.

### Parent Summary Feedback

```text
POST /api/alpha/parents/{parent_id}/children/{student_id}/summary-feedback
```

Request:

```json
{
  "usefulness": "helpful",
  "alpha_session_id": "..."
}
```

Behavior:

- Reuse the existing Alpha parent-child ownership check.
- Upsert feedback for the current Alpha summary context.
- Record `parent_summary_feedback_submitted`.
- Return the saved feedback state.

### Admin APIs

Admin APIs use `ALPHA_ADMIN_TOKEN`. V0.4.1b does not introduce full auth.

Token requirements:

- Missing or wrong token returns 401 or 403.
- Token may be sent by the frontend in a header.
- Frontend stores the token only in `sessionStorage`.

Overview:

```text
GET /api/admin/alpha/overview
```

Response includes invite/family rows with:

- invite label
- invite status
- parent id
- parent display name
- child count
- funnel stage flags
- assessment completed count
- summary viewed flag
- child reaction counts
- latest parent feedback
- last event time

Family detail:

```text
GET /api/admin/alpha/families/{parent_id}
```

Response includes:

- parent metadata
- children metadata
- privacy-safe family event timeline
- reaction and parent feedback summaries

Admin responses must not include child writing text or AI feedback body.

## Operational Scripts

Add small operational commands or scripts under the API app or another existing
project convention.

### Create Alpha Invites

Purpose: generate one-time invite codes for 3-5 families or another explicit
small batch.

Inputs:

- count
- optional label prefix
- optional issued-to note

Output:

- codes printed once for manual distribution
- created invite ids and labels

### Bind Existing Alpha Parent

Purpose: bind a V0.4.1a production parent to an invite code before V0.4.1b
rollout.

Inputs:

- parent id
- invite code or invite id
- optional note

Behavior:

- Verify the parent exists.
- Verify the invite is not already consumed by a different parent.
- Mark invite consumed by that parent.
- Optionally write an operational product event such as
  `legacy_parent_invite_bound`.

## Frontend UX Design

### Alpha Start

`/alpha/start` should become the first-use Alpha onboarding surface:

- product identity is visible in the first viewport
- Alpha nature is clear
- privacy and AI usage note is concise
- invite code input is prominent
- existing Alpha parent context can continue without re-entering a code

The page records `alpha_start_viewed` and `invite_code_submitted` as frontend
events. Invite validation errors should be plain and non-technical.

### Child Reaction UI

Reaction appears near the AI feedback result, after feedback is available.

Prompt tone:

```text
这次 AI 教练的提示对你有帮助吗？
```

Controls:

```text
😊  😐  😞
```

Behavior:

- Click saves immediately.
- Selected state is visible.
- Clicking another reaction updates the previous choice.
- Save failure does not block the child from continuing.

Coverage:

- Assessment result.
- Sentence feedback.
- Essay draft feedback.
- Essay revision comparison.

### Parent Summary Feedback

Location:

```text
/parent/children/{studentId}/summary
```

Prompt:

```text
这份成长摘要对你有帮助吗？
```

Controls:

```text
有帮助
没帮助
```

Behavior:

- Click saves immediately.
- Selected state is visible.
- Clicking the other option updates the previous choice.
- Failure shows a light retry message.

### Admin Alpha UI

Route:

```text
/admin/alpha
```

Access:

- first view asks for admin token
- token stored in `sessionStorage`
- wrong token shows a clear error

Overview:

- invite/family table or dense list
- family display name
- invite label/status
- child count
- current funnel stage
- assessment completion
- summary viewed
- reaction counts
- parent feedback
- last activity

Family drill-down:

- click a row to show a single family detail view
- show children metadata
- show event timeline in time order
- show reaction and parent feedback summaries

Admin UI is read-only in V0.4.1b.

## Privacy Rules

V0.4.1b admin and product events are for Alpha observation, not content review.

Do not show or store in product event payloads:

- child writing text
- upgraded sentence text
- essay draft text
- essay revision text
- AI feedback body
- full invite code
- real full name
- school
- address
- phone
- photo

Admin may show:

- child nickname
- grade label
- parent display name
- task type
- target type
- timestamps
- status
- counts
- reaction result
- parent usefulness result
- sanitized error category

## Testing Strategy

Backend tests should cover:

- invite code validation accepts issued codes
- consumed and disabled invite codes are rejected
- parent creation requires valid invite proof
- parent creation consumes invite and binds parent
- existing Alpha child/list/summary behavior still passes
- product event endpoint rejects unknown event types
- product event payload is sanitized
- child reaction validates target ownership
- child reaction upserts repeated clicks
- parent summary feedback enforces parent-child ownership
- parent summary feedback upserts repeated clicks
- admin overview requires valid token
- admin family detail requires valid token
- admin responses exclude child writing text and AI feedback body
- demo login still returns seeded demo family

Frontend tests should cover:

- `/alpha/start` renders onboarding and invite input
- existing `wenlingo_alpha_parent_id` can continue to children list
- Alpha session id is generated and reused
- invite validation success leads into parent creation or continuation
- invite validation failure shows a useful error
- child reaction UI renders and saves for the four feedback surfaces
- summary feedback renders and saves
- admin token gate
- admin overview rendering
- admin family timeline rendering
- existing FamilyTopbar Alpha and demo behavior does not regress

Manual QA should cover:

- fresh invited family enters with a valid invite code
- consumed invite code is rejected
- parent creates child and enters child space
- child completes assessment and records reaction
- child records reaction on sentence and essay feedback when available
- parent views summary and records usefulness feedback
- admin overview shows the family moving through the funnel
- admin family timeline shows the expected events
- admin does not display writing text or AI feedback body
- V0.4.1a Alpha path for existing bound parent still works
- demo family path still works

## Migration And Deployment

V0.4.1b requires a database migration for the new tables. Production Alpha must
continue using persistent PostgreSQL.

Deployment steps:

1. Deploy migration to the Alpha PostgreSQL database.
2. Set `ALPHA_ADMIN_TOKEN` for the API service.
3. Generate one-time invite codes with the operational script.
4. Bind existing V0.4.1a production parents to invite codes before inviting new
   families.
5. Deploy API and web updates.
6. Run smoke tests for new invite flow, existing Alpha continuation, reaction,
   parent feedback, and admin overview.

Update `docs/alpha-deploy.md` with:

- `ALPHA_ADMIN_TOKEN`
- invite generation script usage
- legacy parent binding script usage
- migration notes
- smoke test steps
- privacy boundary for admin and product events

## Acceptance Criteria

V0.4.1b is ready for implementation review when:

- A new invited parent can enter `/alpha/start` with a valid one-time invite
  code.
- Invalid, consumed, or disabled invite codes are rejected.
- Creating a new Alpha parent consumes and binds the invite code.
- Existing V0.4.1a Alpha parents can be bound to invite codes before rollout and
  continue without re-entering a code.
- `wenlingo_alpha_session_id` is created and included in frontend-originated
  product events.
- Product events record the Alpha funnel and key learning actions.
- Child reactions can be saved and updated for Assessment, Sentence, Essay
  draft, and Essay revision feedback.
- Parent summary usefulness feedback can be saved and updated.
- `/admin/alpha` requires `ALPHA_ADMIN_TOKEN`.
- Admin overview shows invite/family funnel progress.
- Admin family drill-down shows a privacy-safe event timeline.
- Admin does not show child writing text or AI feedback body.
- Demo flow remains intact.
- V0.4.1a Alpha child creation, children list, dashboard handoff, and summary
  path remain intact.
- Relevant backend and frontend tests pass.
- Manual QA checklist and deployment docs are updated.

## Known Limitations

- No full authentication.
- Admin token is a lightweight Alpha-only control.
- Browser-held parent context remains the Alpha identity bridge.
- Browser/device changes still require manual recovery.
- Product events are not a full analytics warehouse.
- Admin is read-only.
- No content moderation review UI.
- No automatic data export or deletion UI.
- The Alpha is still intended for a small trusted user group.
