# WenLingo V0.5a Alpha User Foundation Design

Date: 2026-06-01
Status: Draft approved in brainstorming, pending written spec review

## Goal

V0.5a moves WenLingo Alpha identity from browser-held `localStorage` to a
server-side parent account and session model. The release must preserve the
current 3-5 Alpha families and all existing learning data, while keeping login
simple enough for a small trusted Alpha cohort.

The chosen authentication method is email Magic Code: a parent enters an email
address, receives a 6 digit code, verifies it, and receives an httpOnly session
cookie. V0.5a also lets a parent bind a phone number as account information, but
phone numbers are not used for SMS login or verification in this release.

V0.5a is an identity foundation release. It does not introduce V0.6 writing
castle functionality, public signup growth mechanics, OAuth, passwords, SMS OTP,
or complex account settings.

## Non-Negotiables

- Preserve existing 3-5 Alpha families and their child, assessment, sentence,
  essay, feedback, parent summary, and admin event data.
- Replace `localStorage` parent identity with server-side account/session
  identity for authenticated APIs.
- Do not introduce passwords, Google login, WeChat login, Apple login, SMS OTP,
  payment identity, or public registration.
- Do not make phone binding a login factor in V0.5a.
- Do not implement V0.6 writing castle pre-writing or mode selection features.
- Do not break existing invite, assessment, sentence, essay, parent summary, or
  Admin Alpha Lite flows.
- Do not trust `parent_id` or `student_id` from the frontend as proof of
  authorization once auth-required mode is enabled.
- Do not store raw Magic Codes, raw session tokens, invite codes, child writing
  text, or AI feedback bodies in product event payloads.
- Keep rollback possible through a feature flag and additive database changes.

## Current Identity Model Problems

V0.4.1c uses two browser-held values:

```text
wenlingo_alpha_parent_id
wenlingo_alpha_session_id
```

`wenlingo_alpha_parent_id` is the practical identity credential. Parent pages
read it from `localStorage`, send it in API paths, and the backend returns or
mutates data for that parent. This has several problems:

- Clearing browser data loses the family from the user's point of view.
- Changing devices loses the family because the identity never existed on the
  server as a login credential.
- Anyone who obtains a `parent_id` can currently act as that parent because API
  paths carry the identifier and there is no authenticated session boundary.
- Child-facing routes such as dashboard, assessment, sentence, essay, reading,
  report, and feedback reaction accept `student_id` directly and only verify
  that the student exists.
- `wenlingo_alpha_session_id` is useful for anonymous product observation, but
  it is not an authentication credential and should remain non-authoritative.
- Admin Alpha Lite is token-gated, but family-facing APIs are not.

V0.5a fixes the foundation without changing the learning product loop. The
browser may still keep the legacy parent id temporarily as a migration hint, but
it is no longer accepted as the long-term authority for family access.

## Recommended Approach

Use a separate account table instead of turning `ParentUser` into the login
record.

```text
ParentAccount 1 -- 1 ParentUser -- many StudentProfile
```

`ParentAccount` owns login identifiers and sessions. `ParentUser` remains the
family-facing parent profile already referenced by students, invites, feedback,
and product events. This keeps existing data stable and avoids rewriting the
learning model around auth.

Rejected alternatives:

- Extend `ParentUser` directly into the auth table. This is smaller now but
  mixes family profile fields with login credentials and makes future multiple
  guardian, billing, or account recovery work harder.
- Use only invite/recovery codes. This solves browser loss only partially and
  does not feel like a real user foundation.
- Enable both email and SMS login immediately. This doubles auth states,
  provider dependencies, cost controls, and failure modes before Alpha needs
  them.
- Adopt a hosted auth product. It may be useful later, but V0.5a needs a
  transparent minimal model that can be reviewed and rolled back.

## Minimum Account Model

### ParentAccount

Purpose: login identity for a parent account.

Suggested fields:

```text
id
email_normalized
email_verified_at
phone_e164
phone_bound_at
phone_verified_at
status
created_at
updated_at
last_login_at
```

Rules:

- `email_normalized` is required, lowercased, trimmed, and unique.
- `email_verified_at` is set after a valid Magic Code verification.
- `phone_e164` is optional. V0.5a may accept a normalized China mainland mobile
  number or an explicit E.164 value.
- `phone_bound_at` is set when the user saves a phone number.
- `phone_verified_at` remains null in V0.5a because SMS verification is not
  implemented.
- `status` values are `active`, `disabled`.

### ParentUser Changes

Existing `ParentUser` keeps its current role as the family profile.

Add:

```text
account_id
account_linked_at
```

Rules:

- `account_id` is nullable during rollout.
- `account_id` is unique when present, keeping V0.5a at one account per family.
- Existing Alpha rows remain in place. No student or learning artifact changes
  parent ids during migration.
- `ParentUser.email` is treated as a legacy/display-compatible field. New auth
  logic must use `ParentAccount.email_normalized`, not `ParentUser.email`.

### AuthMagicCode

Purpose: short-lived email login code.

Suggested fields:

```text
id
email_normalized
code_hash
purpose
expires_at
consumed_at
attempt_count
created_at
last_attempt_at
alpha_session_id
request_ip_hash
```

Rules:

- Store only a hash of the 6 digit code.
- Code length is exactly 6 digits.
- Code TTL is 10 minutes.
- A code is single use.
- A code allows at most 5 failed verification attempts.
- Requesting a new code invalidates prior unconsumed codes for the same email
  and purpose.
- Code request responses must not reveal whether the email already has an
  account. Return the same friendly message for new and existing emails:
  `如果邮箱可用，我们已经发送验证码。`
- Do not return account-existence messages such as `这个邮箱已经注册` or
  `这个邮箱不存在`.
- Verification failure responses should also stay generic, for example:
  `验证码无效或已过期。`
- `purpose` is `parent_login` for V0.5a.
- Product events may record that a code was requested or verified, but never the
  raw code or full email.

### Magic Code Rate Limits

V0.5a must include request rate limits to prevent email bombing and reduce brute
force pressure on 6 digit codes.

Required limits:

```text
same email: max 3 requests / 10 minutes
same IP: max 20 requests / hour
same alpha_session_id: max 5 requests / hour
verification failure: max 5 attempts per code, then consumed/locked
```

Implementation notes:

- Use `AuthMagicCode` request rows for Alpha-scale counting.
- Store `request_ip_hash`, not raw IP, if IP-based limiting is implemented in
  the database.
- Trust forwarded IP headers only when the deployment explicitly configures a
  trusted proxy chain.
- Rate-limit failures should return a friendly generic message and must not say
  whether the email exists.
- Product events may record `magic_code_rate_limited` with safe payload fields
  such as `status` and `error_category`, but not email, phone, IP, or code.

### ParentSession

Purpose: server-side session record backed by an httpOnly cookie.

Suggested fields:

```text
id
account_id
token_hash
created_at
expires_at
last_seen_at
revoked_at
```

Rules:

- The browser receives only an opaque random token in an httpOnly cookie.
- The database stores only `token_hash`.
- Cookie name: `wenlingo_parent_session`.
- Cookie attributes: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` in
  production.
- Session TTL: 30 days for Alpha.
- Logout sets `revoked_at` and clears the cookie.
- Expired or revoked sessions return 401.

## Migration Strategy

Migration is additive and preserves all existing family data in place.

### Existing Alpha Family Migration

When `/alpha/start` loads:

1. Frontend calls `/api/auth/session`.
2. If a valid session with a linked parent exists, continue to `/parent/children`.
3. If no valid session exists but `wenlingo_alpha_parent_id` exists, show a
   "绑定邮箱继续使用当前 Alpha 家庭" flow.
4. Parent enters email.
5. Backend sends a 6 digit Magic Code.
6. Parent enters the code.
7. Backend creates or finds `ParentAccount`, verifies the email, sets a session
   cookie.
8. Frontend calls a legacy bind endpoint with the local legacy parent id.
9. Backend links `ParentUser.account_id` if that parent exists and is not
   already linked to another account.
10. Backend records a `legacy_parent_account_bound` product event.
11. Frontend removes reliance on `wenlingo_alpha_parent_id` for auth and routes
   to `/parent/children`.

The legacy bind endpoint is acceptable because V0.4.1c already treats
`parent_id` as the browser-held credential. V0.5a should reduce future exposure
by allowing the endpoint only while the auth migration feature flag is enabled,
only for unlinked parents, and only after a verified email session exists.

Required legacy bind restrictions:

```text
AUTH_REQUIRED_FOR_ALPHA migration window enabled
parent_user.account_id is null
current session email_verified_at is not null
legacy_parent_id belongs to an Alpha-created parent
bind attempt emits ProductEvent
bind attempt emits a server log/audit line
optional: allow only within N days after V0.5a rollout
```

The "Alpha-created parent" check should use existing Alpha evidence, such as a
consumed invite, Alpha product event history, or real-child profiles created
through the Alpha flow. It should not allow arbitrary demo parents to bind
through this endpoint.

If a parent row is already linked to another account, return 409 and show a
support/admin message:

```text
这个家庭已经绑定过账号，请联系邀请人处理。
```

Do not display the other account's email address in the conflict response or UI.
Ops can manually resolve the family.

### New Alpha Family Flow

New families still enter through invite-gated Alpha onboarding:

```text
/alpha/start
-> enter display name, invite code, email
-> validate invite
-> request Magic Code
-> verify Magic Code and set session cookie
-> create ParentUser linked to account
-> consume invite
-> create child profile
-> continue existing learning flow
```

The existing invite consumption guarantees remain: an invite can be consumed
only once, and the parent creation plus invite consumption should remain one
transaction.

### Already Migrated Family Recovery

If cookies expire or are cleared:

1. Parent returns to `/alpha/start`.
2. Parent enters the same email.
3. Backend sends a new Magic Code.
4. Parent verifies the code.
5. `/api/auth/session` returns the linked `ParentUser`.
6. Parent continues to `/parent/children`.

No learning data depends on the cookie. The cookie is only a renewable proof that
the user has recently verified control of the email address.

### Ops-Assisted Migration

For the small existing Alpha cohort, ops may also pre-bind accounts if a family
contacts support or cannot complete self-serve migration.

Provide scripts or admin-only operations for:

- list unlinked Alpha parents
- bind an email account to a parent id
- show account-linked status for each invite/family
- revoke sessions for an account

## API Authentication Boundary

### Public or Pre-Auth Endpoints

These remain callable without a parent session:

```text
GET  /health
POST /api/auth/demo-login
GET  /api/auth/session
POST /api/auth/magic-codes/request
POST /api/auth/magic-codes/verify
POST /api/alpha/invites/validate
POST /api/alpha/events
```

Notes:

- `/api/auth/demo-login` remains for the seeded demo flow and should not be
  converted into Alpha auth.
- `/api/auth/session` is a session introspection endpoint. Without a valid
  session it returns an unauthenticated state, not protected family data.
- `/api/alpha/events` should accept anonymous pre-auth events such as
  `alpha_start_viewed` and invite validation/rejection signals.
- If `/api/alpha/events` receives a valid parent session, backend may enrich the
  event with the authenticated parent id.
- If no session exists, the endpoint must not accept arbitrary `parent_id` as
  authoritative for protected parent/child events.

### Auth-Required Parent Endpoints

These require a valid `ParentSession`:

```text
POST /api/auth/logout
PATCH /api/auth/account/phone
POST /api/alpha/legacy-parent-bind
POST /api/alpha/parents
GET  /api/alpha/parents/me/children
POST /api/alpha/parents/me/children
GET  /api/alpha/parents/me/children/{student_id}/summary
POST /api/alpha/parents/me/children/{student_id}/summary-feedback
```

V0.5a may keep legacy path-shaped endpoints temporarily for compatibility, but
when auth-required mode is enabled they must verify that path `parent_id`
matches the authenticated account's linked parent.

### Auth-Required Student Endpoints

These require a valid parent session and must verify that the requested student
belongs to the authenticated parent:

```text
GET  /api/students/{student_id}/dashboard
POST /api/students/{student_id}/assessment
POST /api/students/{student_id}/sentences
POST /api/students/{student_id}/essays
POST /api/essays/{essay_id}/revision
POST /api/students/{student_id}/readings
POST /api/students/{student_id}/reports
POST /api/students/{student_id}/feedback-reactions
```

For essay revision, authorization is derived through:

```text
essay_id -> Essay.student_id -> StudentProfile.parent_id -> authenticated parent
```

### Endpoint Compatibility Matrix

V0.5a keeps stable user-facing URLs where possible, but changes backend
authorization rules. This matrix is the implementation guide for compatibility:

| Endpoint type | V0.5a behavior |
| --- | --- |
| `/api/alpha/parents/{parent_id}/children` | Deprecated, but may remain during rollout. In auth-required mode, backend must verify `parent_id == session parent`. |
| `/api/alpha/parents/me/children` | New preferred endpoint. Parent id comes from the session. |
| `/api/alpha/parents/{parent_id}/children/{student_id}/summary` | Deprecated path shape. In auth-required mode, verify both `parent_id == session parent` and child ownership. |
| `/api/alpha/parents/me/children/{student_id}/summary` | New preferred endpoint. Parent id comes from the session; `student_id` must belong to that parent. |
| `/api/students/{student_id}/...` | Keep URL shape, but backend verifies student ownership from session. |
| `/api/essays/{essay_id}/revision` | Keep URL shape, but backend authorizes through essay -> student -> parent. |
| `/api/auth/demo-login` | Demo-only. Does not create or require `ParentAccount` and does not enter Alpha account auth. |
| `/api/admin/alpha/...` | Admin-only. Continues to use `X-Alpha-Admin-Token`, not parent session cookies. |

### CSRF Strategy

V0.5a uses cookie sessions, so browsers will automatically attach the session
cookie to matching requests. `HttpOnly` prevents JavaScript from reading the
cookie, but it does not stop the browser from sending it. `SameSite=Lax` reduces
CSRF risk but is not the full policy.

Use a lightweight CSRF strategy for V0.5a:

```text
SameSite=Lax session cookie
all state-changing APIs require Content-Type: application/json
reject non-JSON form POST bodies for authenticated state changes
check Origin or Referer against configured production web origins
future: add explicit CSRF token if product surface or embedding risk grows
```

Scope:

- Apply to authenticated POST/PATCH/PUT/DELETE endpoints.
- Keep public read-only or pre-auth endpoints simple, but still reject malformed
  bodies.
- Reuse the existing CORS allowed origins configuration where possible, while
  keeping Origin/Referer checks explicit for authenticated state changes.

### Admin Endpoints

Admin Alpha Lite remains separate:

```text
GET /api/admin/alpha/overview
GET /api/admin/alpha/families/{parent_id}
```

Rules:

- Continue using `X-Alpha-Admin-Token`.
- Do not accept parent sessions for admin access.
- Do not expose child writing text or AI feedback body.
- Add account migration status fields, but keep the admin surface read-only in
  V0.5a unless an ops script is used outside the web UI.

## Frontend Session Handling

### Core Client Rules

- All authenticated API calls use `credentials: "include"`.
- The browser never stores raw session tokens.
- The session cookie is httpOnly and invisible to JavaScript.
- `wenlingo_alpha_session_id` remains in localStorage for anonymous product
  observation.
- `wenlingo_alpha_parent_id` becomes legacy migration data only. It should not
  be used as the primary source of identity after migration succeeds.

### `/alpha/start`

The Alpha start page becomes a state machine:

```text
checking session
-> already signed in
-> legacy family migration
-> new invite + email Magic Code
-> error/support state
```

Existing family path:

- If a legacy parent id exists and no session exists, show email Magic Code
  migration.
- After successful bind, clear or ignore the legacy parent id for auth.

New family path:

- Parent provides display name, invite code, and email.
- Invite is validated.
- Magic Code is requested and verified.
- Parent is created under the verified account.
- Continue to child creation.

### Parent Pages

Parent pages call `/api/auth/session` or an authenticated children endpoint.

401 behavior:

- Redirect to `/alpha/start`.
- Preserve enough route intent to return after login if implementation cost is
  low.
- Do not show a scary auth error to the child or parent.

### Child Pages

Child pages still use URLs like `/children/{studentId}` for continuity, but the
API must verify the session. This supports the existing handoff pattern where the
parent signs in on the browser and passes the same device to the child.

If the session is missing or expired:

- Show a gentle message asking the parent to sign in again.
- Route to `/alpha/start`.

### Phone Binding UI

V0.5a includes a small account section reachable from parent space, or a compact
phone binding field on the parent children page if a separate settings page is
too much.

Rules:

- Label phone as optional.
- Make clear that phone is saved for future account recovery/contact, not used
  for SMS login yet.
- Store the normalized value on the account after authenticated save.

## Admin And Ops Impact

### Admin Alpha Lite

Add only the minimum account foundation fields to the Admin Alpha web UI:

```text
account_linked
account_email_masked
phone_bound
last_login_at
```

Masking examples:

```text
li***@example.com
138****1234
```

Keep richer operational signals out of the V0.5a Admin UI unless implementation
later proves they are needed for the 3-5 family rollout. Backend responses or
ops scripts may expose them for internal use:

- unlinked consumed invites
- linked parents without active sessions
- latest auth-related event
- migration conflict count if any
- session_count_active

Do not add admin write actions in the web UI for V0.5a unless implementation
later discovers that ops scripts are insufficient.

### Product Events

Add auth/migration events:

```text
magic_code_requested
magic_code_verified
magic_code_failed
magic_code_rate_limited
parent_session_created
parent_session_revoked
legacy_parent_account_bound
phone_bound
```

Payloads must be privacy-safe:

- allowed: status, error_category, target_type, target_id, path
- not allowed: raw code, full email, full phone, invite code, child writing text,
  AI feedback body

### Ops Scripts

Add scripts under `apps/api/app/ops`:

```text
list_unlinked_alpha_parents.py
bind_parent_account.py
revoke_parent_sessions.py
```

Expected use cases:

- Identify which Alpha families have not migrated.
- Manually bind a parent to an email after support contact.
- Revoke sessions if a family reports a shared device issue.

## Database Migration Design

Create one additive Alembic migration after
`20260527_alpha_feedback_obs`.

Suggested revision name:

```text
20260601_v05a_alpha_user_foundation
```

Upgrade:

1. Create `parentaccount`.
2. Create unique index on `parentaccount.email_normalized`.
3. Create optional index on `parentaccount.phone_e164`.
4. Add nullable `account_id` and `account_linked_at` to `parentuser`.
5. Create a unique index on `parentuser.account_id`.
6. Add foreign key from `parentuser.account_id` to `parentaccount.id`.
7. Create `authmagiccode`.
8. Index `authmagiccode.email_normalized`, `request_ip_hash`,
   `alpha_session_id`, `expires_at`, and `consumed_at`.
9. Create `parentsession`.
10. Create unique index on `parentsession.token_hash`.
11. Index `parentsession.account_id`, `expires_at`, and `revoked_at`.

Downgrade:

1. Drop `parentsession` indexes and table.
2. Drop `authmagiccode` indexes and table.
3. Drop `parentuser.account_id` indexes and foreign key.
4. Drop `parentuser.account_id` and `account_linked_at`.
5. Drop `parentaccount` indexes and table.

Production rollback note:

- Prefer code rollback plus feature flag disablement over dropping auth tables
  after real users have migrated.
- Do not delete migrated account/session data unless explicitly performing a
  controlled database restore.

## Configuration

Add settings:

```text
AUTH_REQUIRED_FOR_ALPHA=false by default until rollout
AUTH_SESSION_COOKIE_NAME=wenlingo_parent_session
AUTH_SESSION_DAYS=30
MAGIC_CODE_TTL_MINUTES=10
MAGIC_CODE_MAX_ATTEMPTS=5
MAGIC_CODE_EMAIL_RATE_LIMIT=3 per 10 minutes
MAGIC_CODE_IP_RATE_LIMIT=20 per hour
MAGIC_CODE_ALPHA_SESSION_RATE_LIMIT=5 per hour
MAGIC_CODE_FROM_EMAIL
MAGIC_CODE_EMAIL_PROVIDER
MAGIC_CODE_DEV_ECHO=false
LEGACY_BIND_WINDOW_DAYS=14
AUTH_ALLOWED_ORIGINS=<production web origins>
```

Email provider design:

- Use a small interface such as `EmailSender`.
- Production sender uses configured provider.
- Test/dev sender captures or logs codes without sending real email.
- Tests should not require network access.

Production safety rules:

- Production startup must fail fast if `MAGIC_CODE_DEV_ECHO=true`.
- In production, if `MAGIC_CODE_EMAIL_PROVIDER` or required provider settings are
  missing, Magic Code request must return service unavailable rather than logging
  or echoing a code.
- Test/dev may use a captured sender so tests can read the code without network
  access.

Rollout:

1. Deploy database migration and code with `AUTH_REQUIRED_FOR_ALPHA=false`.
2. Verify old Alpha flow still works.
3. Enable auth-required mode in staging/local manual QA.
4. Enable for production Alpha after QA passes and backup is confirmed.

  emails.

## Rollback Plan

V0.5a rollback must protect learning data first.

### Before Rollout

- Take a production database backup.
- Deploy the additive migration before enabling auth-required mode.
- Keep `AUTH_REQUIRED_FOR_ALPHA=false` until staging and manual QA pass.
- Keep legacy `wenlingo_alpha_parent_id` handling available for one release.

### If Email Sending Fails

- Keep the new schema.
- Set `AUTH_REQUIRED_FOR_ALPHA=false`.
- Continue with the V0.4.1c legacy flow while email provider configuration is
  fixed.
- Existing migrated account data remains harmless and can be reused later.

### If Session Auth Breaks Parent Or Child Flow

- Set `AUTH_REQUIRED_FOR_ALPHA=false`.
- Roll back application code if needed.
- Do not drop auth tables.
- Use Admin Alpha Lite and existing tests to confirm invite, assessment,
  sentence, essay, feedback, summary, and admin flows still work.

### If A Family Is Linked To The Wrong Account

- Revoke sessions for the incorrect account.
- Use an ops script to unlink or rebind the parent account after manual
  verification.
- Preserve all child and learning artifacts.
- Record an ops note outside ProductEvent if sensitive details are involved.

### If Database Migration Must Be Reverted

- Only run the downgrade if no real parent has completed migration, or after a
  controlled restore plan is approved.
- Prefer restoring from backup over hand-editing auth rows in production.
- Because V0.5a does not move learning data, rollback should never require
  deleting child, assessment, sentence, essay, feedback, or product event rows.

## Acceptance Criteria

- Existing Alpha families can bind an email account and keep all history.
- New Alpha families can join with invite + email Magic Code.
- Clearing browser storage no longer loses access to a family after email login.
- Auth-required APIs reject unauthenticated requests.
- Auth-required APIs reject cross-family access.
- Magic Code requests are rate limited by email, IP, and alpha session.
- Magic Code request and verification responses do not reveal account existence.
- Cookie session auth includes the V0.5a CSRF protections.
- Production does not echo or log Magic Codes through dev/test sender paths.
- `localStorage` parent id is not treated as long-term authority.
- Phone number can be saved as optional account info, but SMS login is not
  available.
- Invite, assessment, sentence, essay, parent summary, feedback reactions, and
  Admin Alpha Lite continue to work.
- Product events remain privacy-safe.
- Rollback can return production to the V0.4.1c legacy flow without data loss.

## Explicitly Out Of Scope

- Password login.
- SMS login or phone verification.
- OAuth login.
- WeChat login.
- Multiple guardians per family.
- Public signup without Alpha invite.
- Payment or subscription identity.
- Full account settings page beyond minimal email/session/phone display.
- V0.6 writing castle pre-writing flow.
- Reading Canyon expansion.
- Admin write UI.
- Admin v2 UI work such as session counts, migration conflict dashboards,
  auth-event drilldowns, unlinked-invite views, filters, or export.
- Export, deletion, or privacy self-service workflows.
