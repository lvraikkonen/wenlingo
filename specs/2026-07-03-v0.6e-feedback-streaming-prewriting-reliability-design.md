# WenLingo V0.6e Feedback Streaming + Prewriting Reliability Design

Date: 2026-07-03

Status: Approved

Official roadmap version:
V0.6e

## 1. Summary

V0.6e makes AI waiting time feel alive without weakening WenLingo's learning
data contracts.

The release ships five P0 items together:

1. `essay_feedback` structured content streaming for both direct draft and
   Writing Castle prewriting first-draft submissions.
2. `LLMCallLog` streaming and reliability fields before user-facing streaming
   becomes the default path.
3. Daily-limit rules for streaming and client-disconnect cases.
4. Progress SSE for prewriting JSON tasks, especially material cards and
   outline generation.
5. Material-card provider reliability improvements with Admin-visible metrics.

The product rule is simple: children may see feedback appear step by step, but
WenLingo only saves complete, schema-validated learning results. Prewriting JSON
tasks do not stream partial JSON to the browser.

## 3. Product Decisions From Brainstorming

- V0.6e keeps all five roadmap P0 items as must-ship release criteria.
- `essay_feedback` streaming must cover both direct draft submission and
  Writing Castle prewriting first-draft submission.
- The child-facing streaming experience is structured card streaming:
  strengths, improvements, sentence notes, and revision tasks appear in order.
  It is not raw token-by-token chat output.
- Use the existing `essay_feedback` prompt key with a new versioned,
  stream-friendly response contract. Do not create a separate
  `essay_feedback_streaming` prompt key.
- If the client disconnects after first visible content, the backend should
  continue provider consumption where possible, validate the complete feedback,
  and save the result so the child can return to it.
- Prewriting Progress SSE uses a lightweight job model for
  `material_card_generation` and `outline_generation`.
- Material-card reliability success is judged by online observable improvement
  in live LLM success, timeout rate, and deterministic fallback rate. Offline
  benchmarks can support QA but are not the release gate.
- Extend the existing Admin AI usage table for reliability metrics. Do not add a
  separate reliability dashboard in V0.6e.
- Feature flags and frontend capability checks are required. Old JSON paths
  remain available for automatic fallback.
- The underlying streaming primitive should be reusable for future
  `sentence_feedback`, but sentence streaming is not in V0.6e scope.

## 4. Goals

Children should:

- See essay feedback arrive progressively after submitting a first draft.
- Never see incomplete or malformed AI feedback saved as learning content.
- Be able to return to completed feedback if the browser disconnects after AI
  has started producing useful feedback.
- See real progress during material-card and outline generation instead of only
  a local spinner.

Parents and operators should:

- Preserve full essay archive, revision, and learning-progress visibility.
- See whether material-card generation is improving compared with the V0.6b
  pattern of frequent deterministic fallback.
- Inspect streaming usage, missing usage, fallback, timeout, and latency metrics
  in Admin AI usage.

The system should:

- Preserve Prompt Registry as the only legal prompt source.
- Preserve existing `EssayFeedback`, `EssayVersion`, ability-update, and
  archive contracts.
- Keep token/cost accounting on the backend.
- Keep provider chunks behind a WenLingo-owned event protocol.

## 5. Non-Goals

V0.6e does not include:

- Token Streaming for `sentence_feedback`, `sentence_challenge_feedback`, or
  `essay_revision_comparison`.
- Token Streaming for prewriting JSON tasks such as material cards or outlines.
- A universal AI job platform for every LLM task.
- LangChain, LangGraph, Vercel AI SDK as the primary execution layer, or a new
  frontend framework.
- A separate Admin reliability page, charting system, export flow, or daily
  report.
- A large provider benchmark gate before release.
- Parent weekly report redesign.
- Any AI-generated copy-ready essay body.

## 6. Architecture

V0.6e uses a thin streaming layer rather than an AI platform rewrite.

```text
Browser
  -> essay feedback streaming endpoints
     -> WenLingo SSE events
     -> structured feedback cards

Browser
  -> prewriting job create endpoints
  -> prewriting job EventSource
     -> progress events only
     -> completed essay state after schema-validated save

FastAPI
  -> streaming essay-feedback runner
  -> existing JSON AI runner for prewriting jobs
  -> Prompt Registry
  -> ModelRouter / provider profiles
  -> DailyTaskLimitCounter reservation
  -> LLMCallLog
  -> Essay / EssayVersion / ProductEvent
```

The existing JSON endpoints remain valid:

- `POST /api/students/{student_id}/essays`
- `POST /api/essays/{essay_id}/first-draft`
- `POST /api/essays/{essay_id}/material-cards`
- `POST /api/essays/{essay_id}/outline`

V0.6e adds streaming and job endpoints alongside them. The old endpoints become
the fallback path when streaming is disabled or unsupported.

## 7. Data Model

### 7.1 LLMCallLog

Add streaming and reliability fields to `LLMCallLog`. Existing fields remain the
source of product-result and cost summaries.

New fields:

- `streaming_enabled: bool`
- `stream_protocol: str` with values `none` or `sse`
- `stream_started_at: datetime | None`
- `first_provider_delta_at: datetime | None`
- `first_visible_content_at: datetime | None`
- `last_content_at: datetime | None`
- `usage_received_at: datetime | None`
- `client_disconnected_at: datetime | None`
- `provider_stream_completed_at: datetime | None`
- `usage_available: bool`
- `usage_source: str`
- `usage_is_estimated: bool`
- `usage_details_json: dict`
- `stream_final_status: str`
- `cost_source: str`
- `pricing_snapshot_id: str | None`
- `pricing_snapshot_version: str`
- `provider_reported_cost_usd: float | None`
- `cost_calculation_version: str`
- `provider_request_id: str | None`
- `provider_generation_id: str | None`

Token fields that already exist remain in place:

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `estimated_cost`

The existing `estimated_cost` database field represents USD and should be
treated as `estimated_cost_usd` in API/Admin naming when V0.6e touches those
surfaces.

If existing token/cost columns are nullable, set `prompt_tokens`,
`completion_tokens`, `total_tokens`, and `estimated_cost` to `null` when
authoritative provider/gateway usage is unavailable. If the current schema keeps
these columns non-nullable, Admin/API aggregation must not rely on their zero
values for real token or cost totals; it must use `usage_available`,
`usage_source`, and `usage_details_json` to exclude unknown usage from
authoritative totals.

`usage_source` values:

- `provider_final_chunk`
- `gateway_final_chunk`
- `provider_generation_stats`
- `tokenizer_estimate`
- `unavailable`

`usage_available=true` means authoritative provider or gateway usage was
received. When `usage_source=tokenizer_estimate`, set `usage_available=false`
and `usage_is_estimated=true`. Provider-owned token fields remain `null`.
Estimated token fields, if stored, must live under
`usage_details_json.estimated_*`. Admin must distinguish authoritative usage
from tokenizer estimates.

`cost_source` values:

- `provider_usage_x_pricing_snapshot`
- `provider_reported_cost`
- `tokenizer_estimate_x_pricing_snapshot`
- `unavailable`

`usage_details_json` is required and must be owned by the backend. It may
include:

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `cached_input_tokens`
- `reasoning_tokens`
- `thoughts_tokens`
- `audio_tokens`
- `image_tokens`
- `provider_raw_usage`
- `usage_unavailable_reason`

`usage_details_json` must distinguish zero from unknown:

- When provider usage is available, token fields are integers. A value of `0`
  means the provider explicitly reported zero.
- When provider usage is unavailable, provider-owned token fields are `null`,
  not `0`.
- When provider usage is unavailable, `usage_available=false`,
  `usage_source=unavailable`, and `usage_unavailable_reason` is required.
- When provider usage is unavailable, `estimated_cost` must be `null` or
  `cost_source=unavailable`; it must not be recorded as `0`.

Cost invariants:

1. Browser code never calculates token usage or estimated cost.
2. Provider usage is the token-count truth when available.
3. WenLingo Cost Registry pricing snapshot is the product
   `estimated_cost` truth.
4. Missing provider usage must not be silently recorded as `$0`.

`estimated_cost_usd` is always calculated by WenLingo using provider token usage
and the Cost Registry pricing snapshot when provider token usage is available.
`provider_reported_cost_usd` is audit data only. It must not overwrite
`estimated_cost_usd` unless a Cost Registry entry explicitly delegates cost
calculation for that model/provider to provider-reported cost.

Provider streaming behavior differs by provider. OpenAI-style streaming usage is
expected from a final usage chunk when enabled; Anthropic-style usage deltas are
cumulative; Gemini-style `usageMetadata` may appear only on the final chunk and
may separate thinking tokens. The WenLingo normalizer must convert these into a
single backend-owned usage record.

`final_status` continues to mean product result:

- `primary_success`
- `fallback_success`
- `deterministic_fallback_used`
- `daily_limit_reached`
- `failed`

`stream_final_status` describes transport and lifecycle:

- `not_streaming`
- `completed`
- `client_disconnected_before_visible_content`
- `client_disconnected_after_visible_content_completed`
- `client_disconnected_after_visible_content_aborted`
- `provider_failed_before_visible_content`
- `provider_failed_after_visible_content`

Missing usage is not a separate stream lifecycle status. Use
`stream_final_status=completed`, `usage_available=false`, and
`usage_source=unavailable` for a completed stream whose final provider usage was
not received.

This separation avoids mixing user-visible learning outcomes with transport
mechanics.

Attempt-level usage and cost are required. V0.6e may use the existing
`attempt_summaries` JSON if it can record every primary/fallback attempt with
usage, cost, status, and error fields. If that becomes too hard to query or
validate, implementation should add a narrow `LLMCallAttempt` table. A provider
attempt that fails before visible content but produces billable tokens must
still be represented in attempt-level accounting.

### 7.2 PrewritingAIJob

Add a lightweight job table for prewriting AI progress. It is scoped to
`material_card_generation` and `outline_generation`.

Required fields:

- `id`
- `essay_id`
- `student_id`
- `task_name`
- `status`
- `stage`
- `attempt_count`
- `locked_by`
- `lease_expires_at`
- `last_heartbeat_at`
- `progress_event_seq`
- `schema_version`
- `result_ref_type`
- `result_ref_id`
- `result_payload_json`
- `error_code`
- `llm_call_log_id`
- `idempotency_key`
- `created_at`
- `started_at`
- `completed_at`
- `updated_at`
- `expires_at`

Allowed `status` values:

- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`

Allowed `stage` values include:

- `queued`
- `primary_started`
- `primary_slow`
- `fallback_started`
- `deterministic_fallback_used`
- `saving_result`
- `completed`
- `failed`

`result_ref_type` and `result_ref_id` point to canonical essay state. The job
table must not duplicate child-authored writing, generated material cards, or
outline content by default. `result_payload_json` is only for tiny non-PII UI
metadata.

Job recovery rules:

- Enforce `unique(student_id, essay_id, task_name, idempotency_key)`.
- Creating a job with the same idempotency key returns the existing active or
  completed matching job.
- A job runner may start execution only after atomically acquiring the job
  lease.
- Repeated create calls must not double-start the same job.
- The event endpoint emits the current job snapshot on reconnect before new
  events.
- Every progress event has a sequence number.
- A running job whose lease expires can be retried or marked failed.
- Terminal results are recovered from canonical essay state, not from partial
  job payload.

### 7.3 EssayFeedbackSubmission

Add a lightweight submission ledger for direct-draft and prewriting first-draft
feedback submissions. This protects both streaming and JSON fallback paths from
duplicate essays, duplicate first drafts, duplicate feedback, and duplicate
daily-limit reservations.

Required fields:

- `id`
- `student_id`
- `essay_id: str | None`
- `task_name`
- `client_submission_id`
- `payload_hash`
- `status`
- `llm_call_log_id`
- `essay_version_id`
- `daily_limit_counter_id`
- `daily_limit_reservation_token`
- `created_at`
- `updated_at`
- `completed_at`

Allowed `status` values:

```text
created
reserved
streaming_started
first_visible_content_sent
backend_continuing_after_disconnect
saving_result
completed
failed_released
expired_released
idempotency_conflict
```

Database uniqueness must handle nullable `essay_id` explicitly. Use one of
these patterns:

1. Partial unique indexes:
   - direct draft:
     `unique(student_id, task_name, client_submission_id) where essay_id is null`
   - existing/prewriting essay:
     `unique(student_id, essay_id, task_name, client_submission_id) where essay_id is not null`
2. A normalized `idempotency_scope` column:
   - `idempotency_scope = essay_id` when present;
   - `idempotency_scope = "direct:" + student_id` for direct drafts;
   - `unique(idempotency_scope, task_name, client_submission_id)`.

Behavior:

- Same key and same payload returns the existing active or completed result.
- Same key and different payload returns `409 IDEMPOTENCY_PAYLOAD_MISMATCH`.
- JSON fallback before first visible content must reuse the same
  `client_submission_id`.
- After first visible content, the frontend must not submit JSON fallback.
- Daily-limit reservation finalization must happen through the submission
  ledger exactly once.

Submission recovery:

- Stale `reserved` or `streaming_started` submissions without saved results are
  released by cleanup.
- Stale `first_visible_content_sent` or
  `backend_continuing_after_disconnect` submissions may be marked
  `failed_released` unless a saved canonical result exists.
- Completed submissions are immutable except for admin repair metadata.
- The daily-limit reservation transitions to consumed, released, or expired
  exactly once under row lock.

`payload_hash` is calculated server-side from a canonical payload.

Canonicalization rules:

- include only product-significant fields;
- normalize JSON key order;
- trim transport-only fields;
- normalize empty optional fields to `null`;
- include `payload_schema_version`;
- include `task_name` and route scope;
- exclude `client_submission_id`, timestamps, auth/session metadata.

Direct draft and prewriting first-draft submissions must each define their
canonical hash input in implementation tests.

JSON fallback with the same `client_submission_id` follows this table:

| Submission status | JSON fallback behavior |
| --- | --- |
| `created` / `reserved`, provider not started | May take over the same submission and execute the non-streaming path. |
| `streaming_started`, no first visible content yet | Must not start a second provider call. Return `202 IN_PROGRESS` with `submission_id` and status/fetch URL, or wait for current execution up to a configured short timeout. |
| `first_visible_content_sent` / `backend_continuing_after_disconnect` | Must not execute. Return `202 IN_PROGRESS` or the existing result reference if completed. |
| `completed` | Return the existing completed result reference. |
| `failed_released` / `expired_released` | Allow explicit user retry with a new `client_submission_id`. |

## 8. API Design

### 8.1 Essay Feedback Streaming

Add endpoints alongside existing JSON routes:

```text
POST /api/students/{student_id}/essays/stream-feedback
POST /api/essays/{essay_id}/first-draft/stream-feedback
```

Both endpoints require the same auth rules as the existing JSON endpoints. Both
return `text/event-stream` when streaming is enabled and supported.

All essay-feedback submission endpoints, including JSON fallback paths, must
accept `client_submission_id`. The same `client_submission_id` must follow a
submission across streaming, early fallback, reconnect, and result fetch.

The server emits `start` only after the submission ledger row and daily-limit
reservation are created, and before provider execution begins. If the frontend
times out waiting for `start`, JSON fallback must first query or reuse the same
`EssayFeedbackSubmission` by `client_submission_id`; it must not blindly create
a fresh reservation.

The final `done` event returns result references, not the full essay payload.
The frontend then fetches canonical essay state through a normal JSON request.
This keeps SSE responsible for progressive experience and terminal references,
while existing JSON routes and types remain responsible for page state.

Required `done` result fields:

- `essay_id`
- `first_draft_version_id`
- `fetch_url`

The frontend treats `fetch_url` as opaque. It must not construct the result URL
from `essay_id` or `first_draft_version_id`.

After the follow-up fetch, the child page must end in the same state as the
existing JSON route.

### 8.2 Prewriting Progress Jobs

Add job create and event endpoints:

```text
POST /api/essays/{essay_id}/material-cards/jobs
POST /api/essays/{essay_id}/outline/jobs
GET  /api/prewriting/jobs/{job_id}/events
GET  /api/prewriting/jobs/{job_id}
```

The create endpoints:

- enforce the same prewriting editability and auth rules as current routes;
- accept an idempotency key;
- create or return the active matching job;
- start the job execution;
- return `202 Accepted` with `job_id` and initial status.

The event endpoint:

- streams progress events for the job;
- emits terminal `completed` or `failed`;
- never emits partial material-card or outline JSON.

The job status endpoint:

- supports recovery after page refresh or EventSource failure;
- returns terminal result references and enough information to fetch the updated
  essay state;
- does not return partial or duplicated material-card or outline content from
  the job table.

### 8.3 Frontend Streaming Transport

Direct draft and first-draft feedback streaming are POST requests with an SSE
response body. Browser-native `EventSource` is not enough for these requests.
The web app should use either:

- `fetch` + `ReadableStream` + `eventsource-parser`; or
- `@microsoft/fetch-event-source`.

Prewriting job events are GET requests and may use native `EventSource`.

Transport guardrails:

- `Content-Type: text/event-stream`
- `Cache-Control: no-cache, no-transform`
- `Connection: keep-alive`
- `X-Accel-Buffering: no` when supported
- heartbeat or ping every 10 to 15 seconds
- no proxy buffering for streaming responses
- child-safe slow-provider warning when `first_visible_content_at` exceeds the
  configured threshold

## 10. Prompt And Response Contract

The `essay_feedback` prompt key remains the source of truth. V0.6e introduces a
new version for stream-friendly output.

Requirements:

- Register the new prompt version through `register_prompt()`.
- Preserve the final `EssayFeedback` fields used today.
- Keep the anti-ghostwriting posture: feedback and revision tasks only, no
  copy-ready essay body.
- Make the model output easy for the backend to segment into strengths,
  improvements, sentence notes, and revision tasks.
- Keep final validation against the Pydantic `EssayFeedback` contract before
  saving any official result.

Provider output must use a simple parseable section grammar:

```text
<strengths>
- ...
- ...
</strengths>
<improvements>
- ...
- ...
</improvements>
<sentence_notes>
- ...
</sentence_notes>
<revision_tasks>
- ...
</revision_tasks>
```

Provider output must:

- emit sections in the exact order shown above;
- emit no prose outside section tags;
- emit no Markdown code fence;
- not nest section tags;
- close each section before starting the next section.

Backend section rules:

- Buffer provider deltas until a full section closing tag is seen.
- Parse and validate section item count, item length, child-safe tone, and
  anti-ghostwriting constraints before emitting a preview.
- Emit only validated `feedback_section_preview` events.
- Enforce max buffer bytes per section and max section wait time.
- Treat duplicate sections as validation errors.
- Treat missing required sections as final validation errors.
- Build the final `EssayFeedback` at provider completion and run full Pydantic
  validation before saving.
- If final validation fails, do not save the official result, even if previews
  were shown.
- After `done`, the frontend replaces previews with canonical fetched feedback.

Parser and stream validation error codes:

- `STREAM_SECTION_TIMEOUT`
- `STREAM_SECTION_TOO_LARGE`
- `STREAM_SECTION_DUPLICATE`
- `STREAM_SECTION_OUT_OF_ORDER`
- `STREAM_FINAL_SCHEMA_INVALID`
- `STREAM_ANTI_GHOSTWRITING_BLOCKED`

These codes should be recorded in `LLMCallLog` and surfaced in Admin aggregates
where useful.

Routes and services must not hardcode new prompt text. The Prompt Registry
remains the only legal prompt source.

## 10.1 Provider Stream Normalization

Every provider stream must be normalized before the browser sees anything.

Normalized internal events:

- `text_delta`
- `section_candidate`
- `usage_final`
- `provider_done`
- `provider_error`

The browser contract is only the WenLingo SSE protocol. Provider raw chunks,
provider usage chunk shapes, and provider event names must not leak to the web
client.

The normalizer is responsible for:

- tracking `first_provider_delta_at`;
- detecting `first_visible_content_at` only when a validated section preview is
  emitted;
- avoiding double-counting cumulative usage deltas;
- preserving final usage details when available;
- marking usage as unavailable or estimated when the stream ends without final
  provider usage.

## 10.2 Backend Continuation After Disconnect

Once `first_visible_content_at` is set, provider consumption must no longer be
owned solely by the SSE response generator.

Required mechanism:

1. Hand off provider consumption to a shielded backend task.
2. Let the SSE generator mirror normalized events to the connected client.
3. If the client disconnects, continue the backend task until one terminal
   condition occurs:
   - provider done, final usage handled, feedback validated, and result saved;
   - provider error;
   - schema validation failure;
   - configured timeout.
4. Record `client_disconnected_at`.
5. Set `stream_final_status` to
   `client_disconnected_after_visible_content_completed` when the backend saves
   the result, or `client_disconnected_after_visible_content_aborted` when it
   cannot.

Before `first_visible_content_at`, the backend may cancel the provider stream
and release the daily-limit reservation.

V0.6e backend continuation is process-local best effort, not a durable queue. If
the process exits, deploys, or crashes before saving the canonical result,
cleanup releases or expires the product daily-limit reservation and marks the
submission/stream as `expired_released` or `failed_released`.

## 11. Daily-Limit Rules

The product rule is:

> Only a saved, reviewable learning result consumes the child's daily product
> limit. Provider attempts and costs are logged separately.

Required scenarios:

| Scenario | Saved result | Daily limit | Cost / attempt log |
| --- | --- | --- | --- |
| Normal stream completion | Yes | consume | usage and cost recorded |
| Client disconnects before first visible content | No | release | usage may be unavailable |
| Client disconnects after first visible content; backend completes | Yes | consume | usage and cost recorded |
| Client disconnects after first visible content; backend cannot complete | No | release | attempt log retained |
| Provider fails before visible content and server-side fallback fails | No | release | failed attempts retained |
| Provider fails after visible content without complete valid feedback | No | release | partial content not saved |
| Deterministic fallback saved as official result | Yes | consume | final status is deterministic fallback |

The streaming runner should reserve before provider execution and finalize the
reservation exactly once. It must be safe against duplicate client retries.

Reservation states for V0.6e:

- `reserved`
- `consumed`
- `released`
- `expired`

No saved official learning result means the reservation is released and never
counted against the product daily limit. A saved official learning result means
the reservation is consumed. A stuck reservation expires through cleanup and is
not counted. Provider costs are recorded independently in `LLMCallLog` and
attempt-level accounting.

Provider failure before first visible content should use server-side fallback
inside the same reservation and `client_submission_id`. Frontend JSON fallback is
for cases where streaming is disabled, unsupported, or fails before business
execution begins.

## 12. Frontend Experience

### 12.1 Essay Feedback

When streaming is available:

1. Submit disables the form and opens the feedback area.
2. The UI shows phase copy while waiting for the first visible structured
   section.
3. Feedback cards appear in this order:
   - strengths
   - improvements
   - sentence notes
   - revision tasks
4. After `done`, the page enters the same state as the JSON route:
   - first draft id is known;
   - revision tasks are selectable;
   - the child can submit the next draft;
   - the essay appears in the archive.

If the connection drops after visible content has started, the UI shows
child-friendly copy that the AI coach is still saving the feedback. On return,
the child should be able to recover from current essay state or the archive.

### 12.2 Prewriting Progress

Material-card and outline steps show true progress events when jobs are enabled.
The existing staged `AiWaitingStatus` remains the local fallback when no server
events are available.

The UI must not show partial material-card or outline content before the backend
validates and saves the complete result.

### 12.3 Feature Flags And Fallback

Add backend and frontend configuration for:

- essay feedback streaming;
- prewriting progress jobs;
- frontend streaming capability use.

Automatic fallback to JSON is allowed only before first visible content is
received. After first visible content, the frontend must not send a second JSON
request for the same submission.

More precisely, automatic JSON fallback is allowed only before business
execution begins or before `first_visible_content_at` is set and only when the
same `client_submission_id` is reused. After `first_visible_content_at`, the
frontend must wait for recovery through the submission ledger, result fetch, or
archive state.

## 13. Material-Card Reliability

V0.6e treats material-card reliability as a P0 product issue because V0.6b
observed slow provider responses and frequent deterministic fallback.

Required improvements:

- Make `material_card_generation` live LLM success, timeout, and deterministic
  fallback rates visible in Admin.
- Adjust provider/model config, timeout budgets, prompt shape, or output caps as
  needed to improve online reliability.
- Preserve deterministic fallback as a safe child-facing fallback.
- Keep source-reference validation and scaffold slot validation intact.

Release success does not depend on selecting a specific provider. It depends on
showing observable improvement over the V0.6b baseline during Railway Dev smoke
and QA.

Required reliability gate:

Before changes, run a fixed baseline set on the current V0.6d configuration:

- minimum 16 cases;
- 2 cases each across 8 topic families where fixtures are available;
- record live LLM success rate;
- record deterministic fallback rate;
- record timeout rate;
- record p50 and p90 duration;
- record schema validation success rate;
- record source-reference validation success rate;
- record estimated cost;
- record anti-ghostwriting spot-check notes.

Release gate on the same set:

- deterministic fallback rate decreases;
- live LLM success rate increases;
- schema and source-reference validation success do not regress;
- p90 duration stays within the agreed task budget;
- no anti-ghostwriting regression is observed.

Optional additional development support:

- Run a small benchmark matrix across topic families.
- Record p50/p90/p95 latency, schema success, source-reference success, timeout,
  fallback, token, cost, and human quality notes.

The optional benchmark is useful evidence but not a ship gate.

## 15. Error Handling

Early failures that may fall back to JSON:

- feature flag disabled;
- browser capability check fails;
- stream endpoint returns non-streaming HTTP error;
- no `start` event arrives within the client timeout;
- stream endpoint fails before business execution starts.

Failures that must not auto-submit a second request:

- any failure after first visible content has been received;
- any case where the backend may still be completing and saving the result.

Provider and schema failures:

- Do not save partial feedback.
- Record attempts and stream lifecycle in `LLMCallLog`.
- Release the daily-limit reservation when no official result is saved.
- Show child-friendly retry copy.
- Use server-side provider fallback within the same `client_submission_id` before
  asking the frontend to retry.

Prewriting job failures:

- Keep the job terminal state inspectable.
- Allow retry from the existing step.
- Do not mutate essay material cards or outline with partial output.

## 16. Security And Privacy

- Streaming endpoints must enforce the same auth boundaries as existing JSON
  endpoints.
- Job events must not leak cross-family job ids or essay state.
- Provider raw chunks must not become a browser contract.
- The child UI must not display token counts, costs, provider names, request
  ids, or model ids.
- Existing anti-ghostwriting checks remain in force before `essay_feedback`
  provider execution.

## 17. Implementation Invariants

1. Browser code never calculates token usage, estimated cost, provider id, or
   model id.
2. Every provider stream is normalized into backend-owned internal events:
   `text_delta`, `section_candidate`, `usage_final`, `provider_done`, and
   `provider_error`.
3. WenLingo SSE events are the only browser contract. Provider chunks are never
   forwarded raw.
4. Child-visible feedback sections are previews until the final `done` event and
   follow-up result fetch.
5. Official learning state is saved only after full `EssayFeedback` validation.
6. Every essay-feedback submission has `client_submission_id`.
7. JSON fallback before first visible content must reuse the same submission id
   and reservation context.
8. After first visible content, the frontend must not submit a second JSON
   request.
9. Backend continuation after client disconnect is required once
   `first_visible_content_at` is set.
10. Daily product limit is consumed only by a saved, reviewable learning result.
11. Provider attempt cost is logged even when product daily limit is released.
12. Missing provider usage must not be silently recorded as `$0`.
13. Prewriting jobs never store or emit partial material-card or outline JSON.
14. Material-card reliability is judged against a fixed baseline input set.
15. Provider-reported cost is audit data unless the Cost Registry explicitly
   delegates estimated-cost calculation.
16. `start` is emitted only after submission ledger creation and reservation.
17. Process-local backend continuation is best effort and must have cleanup for
   process loss.
18. Job execution starts only after atomic lease acquisition.
19. `usage_available=true` means authoritative provider/gateway usage, not a
   tokenizer estimate.
20. `fetch_url` is opaque to the frontend.
21. `seq` is strictly increasing per stream or job.
22. Submission `payload_hash` uses server-side canonicalization.

## 21. Risks And Mitigations

Risk: Streaming breaks cost or token accounting.

Mitigation: Add `usage_available`, `usage_source`, and stream timestamps before
shipping UI streaming. Backend remains the only cost-accounting owner.

Risk: Provider chunks do not align with structured feedback sections.

Mitigation: The backend may buffer until a section is complete enough to
validate. Child-visible correctness is more important than raw token speed.

Risk: Client disconnect causes duplicate feedback.

Mitigation: After first visible content, do not auto-submit JSON fallback. Use
reservation/idempotency and backend continuation.

Risk: Prewriting jobs become a universal orchestration project.

Mitigation: Scope the job table and endpoints to material cards and outlines in
V0.6e.

Risk: Material-card reliability improvement is hard to prove with small Alpha
volume.

Mitigation: Admin metrics and the fixed baseline input set are required; optional
benchmark evidence can support release judgment.
