# WenLingo V0.6b.1 Hardening Design

Date: 2026-06-27
Status: Approved

## 1. Summary

V0.6b.1 is a narrow hardening release after V0.6b shipped to Railway Dev and
passed manual QA. It closes three low-cost issues found during V0.6b QA without
expanding Writing Castle scope:

1. Tighten the expository topic-analysis fact boundary.
2. Make person-portrait material questions use the child's point of view.
3. Clean temporary Dev QA child profiles created during V0.6b smoke testing.

This release follows the V0.5b.1 pattern: small, traceable, test-backed
hardening before moving into the next feature version.

## 3. Goals

- Keep AI topic analysis for `expository_introduction` from presenting external
  facts as if they were child-confirmed material.
- Keep `person_portrait` material questions child-centered and friendly,
  especially for "我的自画像".
- Remove temporary V0.6b QA child profiles and their learning data from Dev in
  a repeatable, dry-run-first way.
- Preserve all V0.6b scaffold behavior, direct-draft compatibility, parent
  summary behavior, and existing release gates.

## 4. Non-Goals

V0.6b.1 does not include:

- New topic families.
- AI-generated writing topics.
- `topic_type_suggestion`.
- Token streaming, SSE, or prewriting progress streaming.
- Difficulty adaptation.
- Admin UI redesign.
- Parent summary redesign.
- Assessment recommendation-card visual changes.
- F2/F6/F7/F8/F9 review backlog items from the V0.6b autoplan review.
- Provider latency or material-card reliability work; that remains V0.6d scope.

## 5. Design Decisions

### 5.1 Approach

Use a contract-hardening approach:

- Update Prompt Registry specs for `writing_topic_analysis` and
  `material_questions`.
- Add focused contract tests that lock the new prompt requirements.
- Add a child-profile cleanup service and ops CLI with dry-run and explicit
  execute confirmation.

Do not add broad server-side Chinese semantic filters. They would be brittle in
this release and could block legitimate child-provided facts.

### 5.2 Prompt Versions

Prompt Registry remains the only legal prompt source.

- `writing_topic_analysis` bumps to `v0.6b.1-2026-06-27`.
- `material_questions` bumps to `v0.6b.1-2026-06-27`.
- `material_card_generation` keeps its existing `v0.6b.1-2026-06-27` version.
- Other prompt keys do not change.

## 6. Expository Fact Boundary

When `payload.scaffold.topic_type == "expository_introduction"`,
`writing_topic_analysis` must not introduce external facts before the child
has supplied, observed, read, or confirmed them.

Allowed behavior:

- Restate the object already present in the topic.
- Refer to a factual phrase already present in the topic as part of the
  assignment requirement, without expanding it into new facts.
- Explain the writing task shape: introduce the object, choose key aspects,
  confirm sources, and organize facts clearly.
- Ask the child to look for, observe, or confirm source material.

Disallowed behavior:

- Adding facts not present in the topic.
- Adding numbers, habits, labels, background claims, or common fact banks.
- Treating common knowledge as a usable material source.

Example:

- Topic: `国宝大熊猫`
- Allowed: "这篇要介绍大熊猫，先想清楚你想说明哪些方面，并确认资料来源。"
- Disallowed before child/source input: "大熊猫吃竹子", "活化石", "800万年",
  "保护动物".
- Topic: `中国的世界文化遗产——长城`
- Allowed: "这篇要介绍长城这个世界文化遗产。"
- Disallowed before child/source input: "长城修建于……", "长城全长……".

This is a prompt/contract boundary. Runtime source provenance remains enforced
by the V0.6b F1 follow-up logic for material cards.

## 7. Person Portrait Point Of View

When `payload.scaffold.topic_type == "person_portrait"`, `material_questions`
must ask from the child's point of view.

Required behavior:

- Use child-facing prompts such as "你想写谁", "你观察到什么特点", and
  "哪件事能说明这个特点".
- For "我的自画像", guide the child to answer as themselves: what "我" look
  like, like, notice, do, or want to show.
- For teacher, family, and classmate topics, still ask the child what they saw,
  remembered, or chose.

Avoid:

- Generic object-language such as "这个人".
- Detached third-person wording such as "他的/她的" in the question frame.

This does not ban natural object names like "老师", "妈妈", or "同学" when they
come from the topic. The goal is a child-centered interview tone, not a global
third-person tokenizer. For non-self portraits, "他/她" may appear inside a
child-observation question when it does not turn the prompt into detached
object analysis.

## 8. Dev QA Child Profile Cleanup

Cleanup operates at the child-profile level. It does not delete parent accounts.

### 8.1 Match Rules

Default matched child names:

- Prefix pattern: `QA*` after trimming and whitespace normalization.

The prefix covers Dev QA children recorded across release QA notes, including
`QA06b-*`, `QA v0.6c ...`, and `QA v0.6d 2026-07-03`. This is intentionally
aggressive because the operation still runs behind dry-run, Dev/Test execution
guards, confirmation text, and a maximum matched-child limit.

Do not match by parent email, invite code, account status, or created date.

### 8.2 Delete Scope

For matched children, delete child-owned learning and observation records:

- `Assessment`
- `Essay` and `EssayVersion`
- `SentenceTraining`
- `ReadingSession`
- `GameEvent`
- `AbilityProfile`
- `AbilityHistory`
- `Report`
- `FeedbackReaction`
- `ParentFeedback`
- `ProductEvent`
- `LLMCallLog`
- `StudentProfile`

Only delete records that can be deterministically scoped to a matched
`student_id` or to child-owned artifacts such as essay ids or other task ids.
Do not delete parent-level feedback, account-level events, or invite/session
records unless they explicitly reference the matched `student_id` or a
child-owned artifact id.

Keep:

- `ParentAccount`
- `ParentUser`
- `ParentSession`
- `AlphaInviteCode`
- `AuthMagicCode`

### 8.3 Operations

Add a backend service with shared preview and execute matching logic.

Add an ops CLI such as:

```bash
uv run python -m app.ops.cleanup_qa_child_profiles
uv run python -m app.ops.cleanup_qa_child_profiles --execute --confirm "DELETE QA CHILD PROFILES"
```

Behavior:

- Default mode is dry-run.
- Execute requires exact confirmation text: `DELETE QA CHILD PROFILES`.
- Matching zero children is a successful no-op.
- Single run delete limit is 30 children unless explicitly changed in a future
  design.
- Dry-run output lists child id, child name, and parent id.
- Execute output lists deleted child count and per-child record counts.
- Execute mode runs in a single transaction. If any child cleanup fails, roll back
  the entire run.

No Admin UI work is part of V0.6b.1.

### 8.4 Environment Guard

The cleanup command must print the detected environment before listing or
deleting records.

Dry-run may run in any environment so an operator can inspect what would match.
Execute mode must refuse to run unless the environment is clearly Dev/Test:

- `ENVIRONMENT` is `development`, `dev`, or `test`; or
- lowercased `RAILWAY_ENVIRONMENT_NAME` contains `dev`.

Production-like environments must fail execute mode. V0.6b.1 does not include a
high-risk override for production cleanup.

## 9. Error Handling

- Prompt contract changes must not alter API response schemas.
- If live LLM output still drifts, existing validation/fallback behavior remains
  responsible for safe completion.
- Cleanup rejects execute mode without the exact confirmation string.
- Cleanup rejects execute mode outside Dev/Test environments.
- Cleanup fails closed if the matched child count exceeds the limit.
- Cleanup runs execute mode in one transaction and rolls back the entire run on
  unexpected database errors.

## 10. Testing

Backend tests:

- `test_prompt_registry.py`
  - Update expected prompt versions for `writing_topic_analysis` and
    `material_questions`.
  - Assert response contracts include the expository fact boundary and
    person-portrait point-of-view requirements.

- `test_llm_contracts.py`
  - Add focused prompt contract tests for expository no-new-facts language.
  - Add focused prompt contract tests for `person_portrait` child-view wording.
    For `person_portrait.self`, question frames should not use "这个人", "他",
    or "她" as the subject and should include "你", "自己", or "我"-style
    guidance. For teacher/family/classmate portrait topics, tests should check
    that questions ask from the child's observation, such as
    "你观察到老师有什么特点？" and "哪件事让你觉得他/她很有特点？".

- New cleanup tests
  - Dry-run matches any child profile whose normalized name starts with `QA`.
  - Non-matching children remain untouched.
  - Execute deletes matched child data and keeps parent account/user/session.
  - Execute deletes only records deterministically scoped to the matched child
    or child-owned artifacts.
  - Execute with zero matches is a no-op.
  - Execute rejects missing or wrong confirmation.
  - Execute rejects production-like environments.
  - Execute rolls back the full run if any child cleanup fails.
  - Delete limit is enforced.

Railway Dev spot-check gate:

- `国宝大熊猫` with `expository_introduction` topic analysis should guide what to
  look for and confirm, not provide a fact bank before child/source input.
- `我的“自画像”` with `person_portrait.self` material questions should use
  child-centered first-person or second-person wording.

Suggested verification commands for implementation planning:

```bash
cd apps/api
uv run pytest tests/test_prompt_registry.py tests/test_llm_contracts.py -q
uv run pytest tests/test_admin_alpha_delete_test_accounts.py tests/test_qa_child_profile_cleanup.py -q
uv run pytest tests/test_writing_castle_api.py -q
```

If Playwright E2E is run later, follow the repository note to remove stale
`apps/api/playwright-e2e.db` first and clear proxy environment variables for
localhost.

## 12. Acceptance Criteria

- `writing_topic_analysis` prompt contract for `expository_introduction` says
  not to add external facts before child/source confirmation.
- `material_questions` prompt contract for `person_portrait` says to ask from
  the child's point of view and avoid generic third-person framing.
- Prompt Registry tests pass with the new versions.
- LLM contract tests pass for the new boundaries.
- QA child cleanup dry-run and execute behavior is covered by tests.
- Cleanup can delete matched QA children and related data while preserving
  parent accounts.
- Cleanup execute mode refuses to run outside Dev/Test environments.
- Cleanup execute mode runs in one transaction and rolls back on unexpected
  errors.
- Cleanup deletes only records deterministically scoped to matched `student_id`
  or child-owned artifact ids.
- Railway Dev spot-check confirms `国宝大熊猫` topic analysis no longer provides
  a fact bank before child/source input.
- Railway Dev spot-check confirms `我的“自画像”` material questions use
  child-centered first-person or second-person wording.
- Existing Writing Castle API tests remain green.
- V0.6b non-goals remain untouched.
