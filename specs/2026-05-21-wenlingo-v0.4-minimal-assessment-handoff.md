## Goal

A new child enters 小文星球, completes a 3-5 minute entry trial (one sentence upgrade + one short essay), receives their first ability sketch generated from real LLM feedback, and the Dashboard recommends personalized essay or sentence tasks based on this real assessment data — not seed defaults.

This closes the PRD's core journey: **入门诊断 → 初始能力画像 → 推荐今日任务**.

## What Exists Already

### Backend

**`POST /api/students/{student_id}/assessment`** (`apps/api/app/api/routes/assessment.py`):
- Accepts `sentence_before`, `sentence_after`, `short_writing`
- Creates an `Assessment` row with a hardcoded summary
- Creates a `GameEvent` for settlement
- Does NOT run LLM feedback, does NOT create `SentenceTraining` or `Essay` rows, does NOT update `AbilityProfile`, does NOT create `AbilityHistory`

**`Assessment` model** (`apps/api/app/domain/models.py`):
- Fields: `id`, `student_id`, `sentence_before`, `sentence_after`, `short_writing`, `summary`, `created_at`
- No link to `SentenceTraining.id` or `Essay.id`

**`GET /api/students/{student_id}/dashboard`** (`apps/api/app/api/routes/dashboard.py`):
- Checks `has_assessment` to set `ability_note`: "第一张能力草图" vs "等待入门小试点"
- Calls `choose_today_tasks(ability)` — already assessment-gate-free (V0.3)

**`choose_today_tasks`** (`apps/api/app/services/recommendations.py`):
- All-default abilities (40/40/40/40/40/40) → recommends `kind: assessment, title: 入门小试炼`
- Non-default abilities → essay focus based on ability thresholds

**Pre-writing contracts** (`apps/api/app/services/llm_contracts.py`):
- `MaterialCard`, `MaterialQuestion`, `OutlineResult` exist with mock responses
- Do NOT use these in V0.4 — they are for V0.5 pre-writing flow

### Frontend

**`/children/[studentId]/assessment/page.tsx`**:
- Bare form with 3 textareas and a submit button
- Calls `createAssessment()` from `api.ts`
- No child-friendly UX, no step-by-step flow, no ability sketch reveal

**`TaskCards.tsx`**:
- Already routes `task.kind === "assessment"` → `/children/${studentId}/assessment`
- Uses the existing `kind: "assessment"` from `RecommendedTask`

**`api.ts`**:
- `createAssessment()` function exists with correct payload type
- `SentenceFocus` type already defined
- All existing API functions (`createSentenceTraining`, `createEssay`, etc.) are available

## Non-negotiables

1. **The assessment must run real LLM feedback on both the sentence and the essay.** The sentence upgrade must go through `sentence_upgrade_feedback` and the short writing must go through `essay_feedback`. No hardcoded ability deltas for assessment — use the same LLM pipeline as regular training.

2. **The assessment must create `SentenceTraining` and `Essay` + `EssayVersion` rows.** These are the source artifacts. `AbilityHistory` rows link to them. The `Assessment` row references them. Do not create ability deltas without source training artifacts.

3. **The assessment must create `AbilityHistory` rows.** The assessment is the first data point in the child's growth story. Use `apply_ability_delta` with `source_type=TaskType.sentence` (for the sentence part) and `source_type=TaskType.essay` (for the essay part), linked to their respective training artifact IDs.

4. **Post-assessment recommendations must differ from pre-assessment defaults.** When a child completes the assessment, their `AbilityProfile` must have at least one ability value different from 40 (the default). The Dashboard must then recommend essay or sentence tasks based on the real profile, not the "入门小试炼" placeholder.

5. **The entry trial must complete in 3-5 minutes for a fourth-grade child.** Design the flow for this constraint: one sentence upgrade prompt (not free-form topic), one short writing prompt (not open-ended essay), minimal form friction.

6. **Do not break the demo family.** The 4 demo children (小宇/小晴/小川/小禾) must continue to work identically. Their Dashboards, recommendations, and reports must not change. Assessment is an additive path for new children, not a requirement for existing profiles.

7. **Follow the AI quality spine.** All LLM calls must go through `run_validated_llm_task`. User content must be wrapped in `<student_...>` XML tags (per V0.3 AC7).

8. **Existing tests must continue to pass.** `uv run pytest -q`, `pnpm test`, `pnpm exec playwright test`.

## Acceptance Criteria

### AC1: Assessment route rewritten as ability generator

- [ ] `POST /api/students/{student_id}/assessment` rewritten to:
  1. Validate request (sentence_before, sentence_after max 500 chars; short_writing 20-500 chars)
  2. Run `sentence_upgrade_feedback(source_sentence=sentence_before, upgraded_sentence=sentence_after, focus="加细节")` through AI quality spine
  3. Create `SentenceTraining` row (source_sentence, upgraded_sentence, focus="加细节", ai_feedback=feedback.model_dump())
  4. Flush to get `SentenceTraining.id`
  5. Apply sentence ability deltas via `apply_ability_delta(session, ability, deltas, TaskType.sentence, training.id)`
  6. Run `essay_feedback(title="入门小写作", draft=short_writing)` through AI quality spine
  7. Create `Essay` row (title="入门小写作", status="draft_feedback")
  8. Flush, create first draft `EssayVersion` (label="初稿", content=short_writing)
  9. Flush to get `EssayVersion.id`
  10. Apply essay ability deltas via `apply_ability_delta(session, ability, deltas, TaskType.essay, version.id)`
  11. Create `Assessment` row with `sentence_before`, `sentence_after`, `short_writing`, `summary` referencing `SentenceTraining.id` and `Essay.id`
  12. Create settlement `GameEvent` for the assessment
  13. Commit atomically
- [ ] Response includes: `assessment` (id, summary), `ability_sketch` (child_abilities dict with reading_power, specific_writing_power, revision_power), `settlement` (xp_delta, level_after)

## Design Decisions to Follow

### Sentence upgrade in assessment

The assessment uses a fixed sentence prompt: "公园很美。" The child upgrades this to a more specific sentence. This is identical to the sentence workshop flow but with a fixed source sentence and focus (`加细节`). The LLM returns `SentenceFeedback` with `ability_delta`. The route handles non-canonical keys with the same fallback logic that V0.3 post-QA fix (`c345cf6`) introduced.

### Short writing in assessment

The assessment uses a fixed writing prompt: "写一写你最近一次开心的经历" (or similar simple prompt for fourth graders). The child writes 2-5 sentences. This is treated as an essay "existing draft" entry — same flow as `POST /api/students/{student_id}/essays` with `entry=existing_draft`. The LLM returns `EssayFeedback`. Deterministic ability deltas are computed from the feedback structure (2 improvements → +5, 3 improvements → +3), matching V0.3 essay draft logic.

### Assessment completion flag

The `Assessment` row is the completion flag. Dashboard already uses `has_assessment` for `ability_note`. Post-assessment, `has_assessment` is True → "第一张能力草图". Recommendations are driven by the (now non-default) `AbilityProfile`.

### Ability sketch

The ability sketch is the same `child_abilities` dict the Dashboard already returns: `reading_power`, `specific_writing_power`, `revision_power`. After assessment, only `specific_writing_power` and `revision_power` change (from expression, observation, structure, revision deltas). `reading_power` stays at 40 until the child does reading tasks. This is correct — the assessment only covers sentence + essay, not reading.

For the frontend ability sketch reveal (Step 4), use the existing `AbilityBars` component or a simplified version that shows 3 bars with kid-friendly labels:
- `reading_power` → "读懂力" (may show as "等待阅读试炼" if still 40)
- `specific_writing_power` → "写作力"
- `revision_power` → "修改力"
