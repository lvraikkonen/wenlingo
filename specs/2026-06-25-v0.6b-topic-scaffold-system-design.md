# WenLingo V0.6b Topic Scaffold System Design

Date: 2026-06-25

Status: Accepted for V0.6b implementation planning

## 1. Summary

V0.6b upgrades Writing Castle from a fixed narrative prewriting wizard into an
extensible topic-family scaffold system:

```text
TopicType -> ScaffoldTemplate -> Variant -> SourceChain -> QA Matrix
```

V0.6b is not a project to add a few textbook-topic templates. It establishes
the architecture that lets WenLingo support 3-6 grade classroom writing topics
without hardcoding a new flow for every textbook title.

V0.6b P0 implements four broad topic families:

- `generic_narrative`
- `person_portrait`
- `imaginative_story`
- `expository_introduction`

These four families cover the highest-value slice of the 3-6 grade taxonomy
while preserving clear follow-up space for V0.6c and V0.7.

Scaffold selection is P0. Automatic AI topic type suggestion is not a P0
blocker. A child must be able to start V0.6b Writing Castle by manually
choosing one of the supported scaffold families even when AI suggestion fails,
times out, or is unavailable.

## 3. Product Goal

The goal is to make classroom-aligned Writing Castle credible across 3-6 grade
writing assignments.

The child should feel:

- "This scaffold understands my kind of作文."
- "AI is helping me think, not deciding my content."
- "I can still skip, edit, or switch when the scaffold is wrong."

The parent should see:

- The child chose or confirmed a writing type.
- The child supplied or confirmed material.
- AI organized a scaffold from traceable sources.
- The system did not write content for the child.

## 4. Non-Goals

V0.6b does not include:

- AI-generated作文题目.
- All topic families from the 3-6 grade taxonomy.
- Token Streaming.
- Grade-level difficulty adaptation.
- Topic recommendation library.
- Parent weekly report redesign.
- Full `reading_response_recommendation` templates.
- Full `central_idea_reflection` templates.
- `practical_writing` implementation.
- DB/admin template editor.
- Dynamic model selection or A/B testing.
- Broad frontend visual redesign.

Progress SSE may be explored only as a P2 feature-flagged spike. It must not
become Token Streaming for prewriting JSON tasks.

- Backend `ScaffoldTemplate` registry for the four P0 families.
- Manual scaffold selection.
- Required resolved scaffold snapshot before generation.
- Dynamic frontend rendering from the backend scaffold snapshot.
- Template-aware material questions, material cards, and outline sections.
- SourceRef validation and child-confirmed suggestion lifecycle.
- Deterministic unsupported future-type detector for common out-of-scope topics.
- Unsupported future type visible fallback.
- ProductEvent and LLMCallLog topic/scaffold metadata.

P2:

- Progress SSE spike behind a feature flag.

## 4.2 Execution Contracts

Before V0.6b implementation starts, these contracts must remain aligned with
the implementation plan:

1. Direct draft / `submit_first_draft` is not scaffold-gated.
2. V0.6b P0 rejects scaffold change after child answers/cards;
   preserve-answer migration is deferred.
3. V0.6b generated content writes source_refs first; `source_answer_ids` and
   `source_card_ids` are compatibility shorthands only.
4. `unsupported_future_type` is persisted when a supported fallback scaffold is
   selected.
5. Release gates include real API integration tests for all four P0 families.

## 5. Core Principle

V0.6a principle:

> AI must not invent the child's real experience.

V0.6b principle:

> AI must not decide the essay content for the child.

This broader principle supports real experiences, imagined settings, topic
requirements, observation, reading materials, and child-confirmed choices.

Allowed AI behaviors:

- Suggest a likely topic family and variant.
- Explain what a topic asks in child-friendly language.
- Ask material questions appropriate to the selected scaffold.
- Organize child-provided or child-confirmed material into scaffold slots.
- Create empty placeholders when sources are missing.
- Offer optional inspiration that is clearly not content until confirmed.

Disallowed AI behaviors:

- Silently choosing a topic type when confidence is low.
- Inventing factual claims for expository topics.
- Deciding a plot, character trait, event, invention function, or conclusion
  for the child.
- Treating an AI suggestion as a valid source before child confirmation.
- Forcing unsupported topic types into the nearest supported family without
  disclosure.
- Producing copy-ready作文正文.

## 6. Architecture

V0.6b uses a backend code-level `ScaffoldTemplate` registry as the source of
truth. The frontend consumes a resolved scaffold snapshot and does not hardcode
template-specific material slots or outline sections.

Flow:

```text
作文题目输入
-> manual scaffold selection, with optional AI suggestion when available
-> backend resolves ScaffoldTemplate
-> Essay stores topic_type / topic_variant / scaffold_template_version / snapshot
-> topic analysis / material questions / cards / outline receive scaffold context
-> cards and outline validate against SourceRef
-> draft editor and parent summary read the saved scaffold snapshot
```

Responsibilities:

```text
Backend:
- owns TopicType enum
- owns ScaffoldTemplate registry
- owns template versioning
- validates slots, outline sections, and SourceRef
- passes scaffold context into AI task payloads

Frontend:
- renders topic type choices
- renders scaffold-provided material slots and outline sections
- sends child answers, edits, confirmations, and override choices
- does not hardcode V0.6b template logic
```

V0.6b should keep the existing `Essay` table and JSON containers. Do not add a
major prewriting table in this version.

## 7. TopicType And Variant

`TopicType` represents broad writing families, not textbook titles.

V0.6b P0 TopicType:

```ts
type TopicType =
  | "generic_narrative"
  | "person_portrait"
  | "imaginative_story"
  | "expository_introduction";
```

Known future TopicType values:

```ts
type FutureTopicType =
  | "place_scenery"
  | "animal_object_observation"
  | "practical_writing"
  | "story_adaptation"
  | "story_summary"
  | "reading_response_recommendation"
  | "central_idea_reflection"
  | "picture_prompt_story";
```

V0.6b may receive unsupported future-type signals from deterministic rules,
manual "not listed" choice, or P1 AI suggestion. It must not pretend to support
them. If a future type is detected or suggested, V0.6b must:

1. show unsupported-but-safe child copy;
2. prevent silent coercion into a supported scaffold;
3. offer manual supported families;
4. offer direct draft;
5. allow the child/parent to re-enter or replace the practice topic when this is
   not a teacher-required assignment;
6. log `unsupported_suggested_type`.

Suggested copy:

```text
这篇作文更像「书信/读后感/观点表达」，这个脚手架我们还在完善。
你可以：
1. 先选择一个最接近的类型继续；
2. 直接写初稿；
3. 重新输入题目，或换一个练习题。
```

Classification boundary examples:

| Input topic | V0.6b handling |
|---|---|
| `国宝大熊猫` | `expository_introduction.research_introduction` |
| `介绍一种事物` | `expository_introduction.object_introduction` |
| `中国的世界文化遗产` | `expository_introduction.research_introduction` |
| `家乡的风俗` | `expository_introduction.culture_introduction`; emphasize material or experience sources. |
| `我做了一项小实验` | `expository_introduction.experiment_process` |
| `写信` / `我想对您说` | unsupported future type: `practical_writing` |
| `推荐一本书` / `写读后感` | unsupported future type: `reading_response_recommendation` |
| `漫画的启示` / `围绕中心意思写` | unsupported future type: `central_idea_reflection` |

V0.6b P0 includes a small deterministic detector so unsupported fallback UX
works even when P1 AI suggestion is disabled:

```python

```

Minimum deterministic rules:

| Topic text contains | Return |

## 8. ScaffoldTemplate Schema

Suggested registry unit:

```ts
type ScaffoldTemplate = {
  topic_type: TopicType;
  variant: string;
  template_version: string;

  display_name_child: string;
  display_name_parent: string;

  suitable_for: {
    grades: Array<"3" | "4" | "5" | "6">;
    sample_topics: string[];
    writing_modes: string[];
  };

  source_policy: SourcePolicy;

  topic_analysis_cards: TopicAnalysisCardSpec[];
  material_questions: MaterialQuestionSpec[];
  material_slots: MaterialCardSlotSpec[];
  outline_sections: OutlineSectionSpec[];

  fallback_behavior: {
    empty_answer_strategy: "empty_slots";
    unsupported_variant_strategy: "default_variant";
  };
};
```

Resolved scaffold snapshot:

```ts
type WritingCastleScaffoldState = {
  schema_version: "v0.6b.1";
  topic_type: TopicType;
  topic_variant: string;
  scaffold_template_version: string;
  resolved_at: string;
  selection_source: "ai_suggested" | "manual" | "fallback";
  display_name_child: string;
  display_name_parent: string;
  material_slots: MaterialCardSlotSpec[];
  outline_sections: OutlineSectionSpec[];
  source_policy: SourcePolicy;
  unsupported_future_type?: FutureTopicType;
  unsupported_override?: boolean;
};
```

Storage:

```text
Essay.outline.scaffold = full WritingCastleScaffoldState
Essay.material_card.scaffold_ref = {
  topic_type,
  topic_variant,
  scaffold_template_version
}
```

All backend readers must go through one accessor:

```python
resolve_essay_scaffold(essay) -> ResolvedScaffoldSnapshot
```

Accessor rules:

- Read the full snapshot from `Essay.outline.scaffold`.
- Validate that `Essay.material_card.scaffold_ref` matches
  `topic_type`, `topic_variant`, and `scaffold_template_version`.
- Fail closed on mismatch and require explicit scaffold re-resolution.
- Do not guess which scaffold is correct.
- Generation endpoints, draft editor, resume flow, and parent summary must all
  use this accessor.

Snapshot immutability:

- Once saved to an essay, `WritingCastleScaffoldState` is immutable for that
  essay.
- Registry updates or `template_version` bumps must not mutate existing essay
  snapshots.
- Resume flow reads the saved snapshot; it does not silently re-resolve from the
  current registry.
- Re-resolution is allowed only through the explicit scaffold change flow.

New V0.6b sessions must include a resolved scaffold before any generation
endpoint runs.

V0.6a sessions stay on `schema_version: "v0.6a.1"` and are not migrated
destructively. If resumed, they keep the legacy fixed narrative structure.

## 9. Four P0 Templates

### 9.1 generic_narrative

Child label: `写一件事`

Parent/admin label: `叙事类：经历 / 活动 / 成长 / 情绪`

Sample topics:

- `那次经历真难忘`
- `生活万花筒`
- `记一次游戏`
- `那一刻，我长大了`
- `多彩的活动`
- `有你，真好`
- `我学会了____`

Source policy:

- Allowed: `real_experience`, `child_confirmed`
- Required for content: at least one of `real_experience`,
  `child_confirmed`
- AI cannot invent events, people, feelings, dialogue, or lessons.

Material questions:

```text
1. 这件事发生在什么时候、什么地方？
2. 过程中最重要或最难忘的一幕是什么？
3. 当时或后来，你有什么真实感受？
```

Material slots:

```text
event_main         发生了什么
event_background   起因/背景
key_moment         关键经过
concrete_detail    一个具体细节
feeling_change     当时的心情
result_takeaway    结果/收获
```

Outline:

```text
opening_context    开头：点明事情或情境
sequence_process   经过：按顺序写清楚
highlight_moment   重点：展开最难忘/最紧张/最有变化的一幕
ending_reflection  结尾：写结果和感受
```

Variant `learned_skill` shifts questions toward:

```text
学会了什么 / 遇到什么困难 / 怎么克服 / 学会后的心情
```

### 9.2 person_portrait

Child label: `写一个人`

Parent/admin label: `写人类：特点 + 事例`

Sample topics:

- `我的“自画像”`
- `猜猜他是谁`
- `我的家人`
- `“漫画”老师`
- `身边那些有特点的人`
- `他____了`
- `形形色色的人`

Source policy:

- Allowed: `real_experience`, `observation`, `child_confirmed`
- AI can suggest categories such as appearance, action, and language.
- AI cannot invent a trait or example.

Material questions:

```text
1. 你想写谁？他/她给人的第一印象是什么？
2. 这个人最明显的特点是什么？有什么细节能看出来？
3. 哪一件小事最能说明这个特点？
```

Material slots:

```text
person_subject      写谁
first_impression    整体印象
appearance_action   外貌/动作线索
core_trait          核心特点
typical_event       典型事例
speech_expression   语言/动作/神态细节
my_feeling          我对这个人的感受
```

Outline:

```text
opening_impression  开头：给人物一个整体印象
trait_detail        特点：用细节表现
typical_event       事例：用一件事证明特点
ending_feeling      结尾：写感受或评价
```

Variants:

```text
self              自画像
other_person      写别人
teacher_portrait  “漫画”老师
```

### 9.3 imaginative_story

Child label: `编一个想象故事`

Parent/admin label: `想象类：设定 + 冲突 + 行动`

Sample topics:

- `我来编童话`
- `奇妙的想象`
- `这样想象真有趣`
- `我和____过一天`
- `变形记`
- `神奇的探险之旅`
- `笔尖流出的故事`
- `插上科学的翅膀飞`
- `我的奇思妙想`

Source policy:

- Allowed: `imagined_setting`, `topic_requirement`, `child_confirmed`
- AI may offer optional inspiration.
- Story facts become content only after child answer, selection, edit, or
  confirmation.

Material questions:

```text
1. 故事的主角是谁？有什么奇妙设定？
2. 故事发生在哪里？会遇到什么问题或意外？
3. 主角会怎么行动？最后有什么发现或结果？
```

Material slots:

```text
main_character    主角
magic_setting     奇妙设定
story_scene       场景
conflict_problem  问题/冲突
action_solution   解决办法
ending_discovery  结局/发现
```

Outline:

```text
opening_setting  开头：进入奇妙设定
new_world        发展：新世界或新情况出现
conflict         冲突：遇到困难或意外
action           解决：主角怎么行动
ending           结尾：结果和发现
```

Variant `invention_design` material slots:

```text
invention_name        发明名称
appearance_structure  样子结构
main_function         主要功能
use_scene             使用场景
helps_whom            帮助谁
magic_feature         最神奇的地方
```

Variant `invention_design` outline:

```text
invent_what  我想发明什么
appearance   它长什么样
functions    它有什么功能
usefulness   它能帮谁做什么
expectation  我的期待
```

### 9.4 expository_introduction

Child label: `介绍一种事物`

Parent/admin label: `说明介绍类：介绍 / 资料整理 / 实验过程`

Sample topics:

- `国宝大熊猫`
- `介绍一种事物`
- `中国的世界文化遗产`
- `家乡的风俗`
- `我做了一项小实验`

Source policy:

- Allowed: `topic_requirement`, `observation`, `reading_material`,
  `child_confirmed`
- Required for factual claims: `topic_requirement`, `reading_material`,
  `observation`, or `child_confirmed`
- AI must not invent facts.

Material questions:

```text
1. 你要介绍什么？这个题目要求你重点介绍什么？
2. 你已经知道哪些信息？哪些来自观察、资料或题目？
3. 你最想让别人了解哪几个方面？
```

Material slots:

```text
intro_subject      介绍对象
known_information  我已经知道的信息
source_material    资料/题目要求
feature_detail     外形/特点/用途/价值
interesting_fact   一个有趣信息
focus_aspect       我想重点介绍的方面
```

Outline:

```text
opening_subject  开头：介绍对象是什么
aspect_one       方面一：外形/来历/背景
aspect_two       方面二：特点/功能/过程
aspect_three     方面三：价值/用途/有趣信息
ending_summary   结尾：总结为什么介绍它
```

Variant `experiment_process` material slots:

```text
experiment_name  实验名称
materials        准备材料
steps            实验步骤
result           实验结果
discovery        我的发现
```

Variant `experiment_process` outline:

```text
实验目的 -> 准备材料 -> 实验步骤 -> 结果发现 -> 我的感受
```

## 10. Source Chain

Content source types:

```ts
type ContentSourceType =
  | "real_experience"
  | "imagined_setting"
  | "topic_requirement"
  | "observation"
  | "reading_material"
  | "child_confirmed";
```

SourceRef:

```ts
type SourceRef =
  | {
      source_type: "real_experience";
      answer_id?: string;
      card_id?: string;
    }
  | {
      source_type: "imagined_setting";
      answer_id?: string;
      card_id?: string;
    }
  | {
      source_type: "topic_requirement";
      topic_requirement_id: string;
      quote_or_summary: string;
    }
  | {
      source_type: "observation";
      answer_id?: string;
      card_id?: string;
      observation_note_id?: string;
    }
  | {
      source_type: "reading_material";
      reading_material_ref: string;
      quote_or_summary?: string;
    }
  | {
      source_type: "child_confirmed";
      confirmation_id: string;
      confirmed_text: string;
      original_suggestion_id?: string;
    };
```

V0.6b may store reading-material references inline before a dedicated table
exists:

```ts
type ReadingMaterialRef = {
  id: string;
  label: string;
  text_excerpt_or_summary: string;
  provided_by: "topic_text" | "child_input" | "parent_input";
};
```

`topic_requirement` boundary:

- `topic_requirement` SourceRef supports assignment constraints and subject
  selection.
- It supports factual claims only when the requirement text itself explicitly
  contains that fact.
- For expository factual claims, `reading_material`, `observation`, or
  `child_confirmed` are preferred sources.

Example:

```text
题目：国宝大熊猫
```

The topic requirement can support:

```text
我要介绍大熊猫。
这篇作文重点是介绍大熊猫。
```

It cannot support facts such as:

```text
大熊猫主要吃竹子。
大熊猫生活在四川、陕西、甘肃。
```

Those claims require reading material, observation, child input, or
child-confirmed material that explicitly contains the fact.

AI suggestion lifecycle:

```text
1. AI offers optional suggestion.
2. Suggestion is stored as ai_suggestion, not source content.
3. Child clicks, edits, or confirms.
4. System creates child_confirmed SourceRef.
5. Only then can it become material card text or outline note.
```

Source creation UX:

```text
AI inspiration card actions:
- 采用这个想法
- 我改一改
- 不用这个
```

Only `采用这个想法` and `我改一改` create a `child_confirmed` SourceRef.
`不用这个` dismisses the suggestion and must not create source content.

Validation rules:

- Every non-placeholder material card must include at least one SourceRef.
- Every content-bearing outline section must include at least one SourceRef or
  source-card chain that resolves to SourceRefs.
- Pure structural outline sections may have no SourceRef only when
  `content_kind = "structural"`.
- Unknown source IDs fail validation.
- AI suggestion IDs alone are not valid sources.
- Placeholder cards and sections may be empty with no refs, but cannot contain
  content.

Compatibility:

```text
V0.6a source_answer_ids and source_card_ids are SourceRef shorthand:
answer_id -> { source_type: "real_experience", answer_id }
card_id -> card.source_refs
```

V0.6b new content must write `source_refs` first. `source_answer_ids` and
`source_card_ids` may remain as backward-compatible display/reference shorthand,
but V0.6b source semantics must not depend on converting every answer to
`real_experience`.

## 11. Topic Type Selection UX

Topic type selection happens before topic analysis.

Flow:

```text
输入老师作文题目
-> backend creates essay and returns supported scaffold families
-> optional AI suggestion may be shown if available
-> child/parent selects or confirms scaffold
-> backend resolves scaffold snapshot
-> topic analysis begins
```

Manual override always wins over AI suggestion.

AI suggestion is never required to begin. If suggestion fails, times out, or
returns low confidence, the UI still shows the four supported families for
manual selection.

Low-confidence copy:

```text
我不太确定这篇作文属于哪一类，你可以自己选一个最像的。
```

Changing type before child content:

- Safe.
- Re-resolve scaffold.
- Regenerate topic analysis/material questions as needed.

Changing type after topic analysis but before material answers:

- Warn that cards/questions will be regenerated.
- Preserve topic text.
- Clear generated topic analysis and material questions.

Changing type after material answers/cards:

- V0.6b P0 does not support scaffold change after child prewriting content
  exists.
- Do not silently migrate, delete, or re-map child answers.
- Show clear copy and ask the child/parent to start a new Writing Castle essay
  if the scaffold is truly wrong.
- The fuller preserve-answers-and-reset-cards flow is deferred to V0.6b.1/V0.6c.

```text
已经有素材回答了，这次先不自动换脚手架，避免弄丢你的内容。你可以继续写，或重新开始一篇。
```

Changing type after outline confirmation:

- V0.6b P0 does not allow scaffold change after outline confirmation.
- The child can continue writing or start a new Writing Castle essay.

Changing type after first draft submission:

- Do not allow for that essay.
- The child can start a new Writing Castle essay.

## 11.1 P1 Staged Loading Copy

V0.6b should keep the roadmap short-term latency improvement: staged loading
copy while the child waits for AI/backend steps. This is a P1 UX item, not a P0
scaffold blocker.

Scope:

- Apply to Writing Castle waits where the child is waiting on AI or backend
  generation: topic analysis, material questions, material card synthesis,
  outline generation, and first-draft feedback.
- Follow the V0.5b.1 Sentence Workshop pattern: a small sequence of
  child-friendly messages for the same pending action.
- Keep `role="status"` so assistive technology receives the active wait state.
- Do not show fake progress percentages.
- Do not stream partial AI content or bypass JSON/schema validation.
- Do not introduce Progress SSE or Token Streaming for this P1 item.

Suggested staged copy:

| Step | Stage 1 | Stage 2 | Stage 3 |
|---|---|---|---|
| topic analysis | 正在读题目…… | 正在找这类作文的重点…… | 正在整理审题提示…… |
| material questions | 正在根据题型准备问题…… | 正在提醒你从哪里找素材…… | 马上就能开始想素材了…… |
| material cards | 正在整理你的回答…… | 正在把素材放进合适卡片…… | 正在检查有没有替你编内容…… |
| outline generation | 正在搭提纲…… | 正在按题型安排段落…… | 正在检查提纲有没有素材来源…… |
| first-draft feedback | AI 教练正在读你的初稿…… | 正在先找写得好的地方…… | 正在准备一个小修改任务…… |

Copy rules:

- Messages should describe what the product is doing in child-friendly terms,
  not internal implementation details.
- Messages should reinforce WenLingo's learning stance: help the child organize
  their own ideas, not write the essay for them.
- Save-only waits may keep a single concise status message instead of staged
  copy.
- Staged copy should be implemented as a reusable frontend helper so future
  V0.6c templates can reuse the same wait pattern without template-specific
  frontend logic.

## 12. API Changes

Creation response:

```ts
type CreateClassroomEssayResponse = {
  essay: WritingCastleEssay;
  supported_topic_types: TopicTypeChoice[];
  topic_type_suggestion?: TopicTypeSuggestion; // P1; never required for P0.
};
```

Topic type suggestion:

```ts
type TopicTypeSuggestion = {
  suggested_topic_type: TopicType | FutureTopicType | "unknown";
  suggested_variant: string;
  confidence: "high" | "medium" | "low";
  reason_child: string;
  is_supported_in_v0_6b: boolean;
};
```

Scaffold selection request:

```ts
type ScaffoldSelectionRequest = {
  topic_type: TopicType;
  topic_variant?: TopicVariant;
  accepted_suggestion_id?: string;
  override_reason?: "manual_choice" | "suggestion_accepted" | "fallback_selected";
  unsupported_future_type?: FutureTopicType;
};
```

Endpoint:

```text
PATCH /api/essays/{essay_id}/scaffold-selection
```

Rules:

- New V0.6b generation endpoints return `409` when scaffold is missing.
- Unsupported future types cannot be selected as full V0.6b scaffold types.
- User may select a supported fallback manually.
- AI suggestion failure, timeout, or low confidence must not block manual
  scaffold selection.
- Direct draft / `first-draft` submission must not require a resolved scaffold;
  unsupported fallback can bypass prewriting and still submit a child-written
  draft.
- When deterministic unsupported detection finds a future type and the user
  selects a supported fallback, backend must persist `unsupported_future_type`
  and `unsupported_override` in the saved scaffold snapshot.
- For manual P0 scaffold selection, `topic_variant` is optional.
- If `topic_variant` is omitted, backend resolves the default variant for the
  selected `TopicType`.
- An accepted AI suggestion may provide a variant.
- Compatibility aliases may map to a variant.
- Unsupported variants fall back to the default variant only within the same
  supported `TopicType` and must be logged.
- Frontend must not expose or hardcode variant-specific logic unless variant
  choices are returned by the backend.
- Existing V0.6a endpoint behavior remains available for legacy sessions.

## 13. Prompt Registry And AI Tasks

Prompt keys remain task-level, with scaffold context passed in payload.

Do not create prompt keys per topic family.

V0.6b P0 prompt keys:

```text
writing_topic_analysis
material_questions
material_card_generation
outline_generation
```

Existing prompt keys should keep stable names and bump `version`, following the
current registry pattern:

```text
writing_topic_analysis: v0.6b-2026-06-25
material_questions: v0.6b-2026-06-25
material_card_generation: v0.6b-2026-06-25
outline_generation: v0.6b-2026-06-25
```

P1 prompt key:

```text
topic_type_suggestion: v0.6b-2026-06-25
```

AI payloads include:

```json
{
  "topic_text": "...",
  "topic_type": "person_portrait",
  "topic_variant": "teacher_portrait",
  "scaffold_template_version": "person_portrait.teacher_portrait.v0.6b.1",
  "scaffold": {
    "material_slots": [],
    "outline_sections": [],
    "source_policy": {}
  },
  "existing_sources": []
}
```

Output validation:

- AI output must use known scaffold slot IDs.
- AI output must use known outline section IDs.
- Source refs must resolve.
- Factual claims in `expository_introduction` require acceptable sources.
- Unsupported future types cannot accidentally call a P0 template unless the
  user manually selected a supported fallback.

Deterministic fallback:

- Create configured empty slots and sections.
- Populate only from valid sources.
- Never infer facts, traits, plot points, events, or lessons.

## 18. Risks And Mitigations

Risk: `expository_introduction` absorbs application writing, reading response,
and opinion writing.

Mitigation: In V0.6b, `expository_introduction` covers only introduction,
explanation, research-based topics, and experiment process. `practical_writing`,
`reading_response_recommendation`, and `central_idea_reflection` remain future
families.

Risk: `imaginative_story` becomes too broad.

Mitigation: Use variants and per-variant slots. If a variant needs a different
outline, define it explicitly in the registry.

Risk: Source refs become too strict and block children.

Mitigation: Empty placeholders are allowed. Child edits can create
`child_confirmed` SourceRefs on save. The system should not block writing
because a scaffold is incomplete.

Risk: Frontend and backend template logic diverge.

Mitigation: Backend registry and resolved scaffold snapshot are the source of
truth. Frontend renders the snapshot.

Risk: Existing Writing Castle sessions break.

Mitigation: Preserve V0.6a schema and legacy rendering. New V0.6b logic applies
only to new sessions.

## 19. Scope Guard
