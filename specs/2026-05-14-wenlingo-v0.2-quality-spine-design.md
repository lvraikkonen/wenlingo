# WenLingo V0.2 质量脊柱设计

日期：2026-05-14
来源：`specs/2026-05-11-wenlingo-v0.2-product-review.md` + 本轮 brainstorming
状态：Draft for review

## 1. 背景

上一版 MVP 已经跑通了学习闭环骨架，但评审指出两个阻塞真实儿童内测的缺口：

1. 前端仍接近裸 HTML，孩子无法获得清晰、温暖、行动导向的产品体验。
2. AI 陪练质量未被真实 LLM 验证，作文点评和二稿对比仍缺少可观测、可降级、可复盘的质量机制。

已删除的 `plans/2026-05-13-wenlingo-mvp-quality-gap-fix.md` 不再作为实现依据。本设计重新从产品评审出发，收窄 V0.2 的目标与验收链路。

## 2. V0.2 核心目标

V0.2 的目标不是补齐所有 MVP 缺口，而是把 WenLingo 从“可演示骨架”推进到“可让真实孩子完成一次可信的作文修改内测”。

硬验收链路只围绕小宇画像的作文修改闭环：

```text
选择小宇
-> 进入 Dashboard
-> 领取作文任务
-> 写初稿
-> 收到真实 LLM 结构化点评
-> 选择/完成修改任务
-> 提交二稿
-> 看到初稿 vs 二稿对比
-> 获得鼓励式结算
-> 家长看到个性化阶段报告
-> 产出 AI 质量人工评审记录
```

本阶段有两条同等优先级的主线：

1. 儿童内测可用：孩子经过的主路径页面不再是裸 HTML，必须有温暖、清晰、行动导向的基础 UI。
2. AI 质量可验证：作文点评和二稿对比必须能切换真实 LLM，输出必须结构化、可重试、可降级、可记录，并能用于人工评审。

## 3. 非目标

V0.2 暂不做：

- 新增训练模块，例如词语森林、素材湖泊等。
- 移动 App、老师端、支付、班级管理。
- 复杂自适应算法或 ML 学习分析。
- 长期徽章进度、怪物血量、宠物养成、复杂技能树。
- 全站用户行为 analytics 平台。
- 阅读模块扩展为完整阅读训练库。
- 让 AI 生成可直接提交的完整作文或范文。

工程支撑只服务两条主线。必要的 DI、contract tests、LLM 日志、prompt version、迁移和 E2E 验证要做；与主线无关的发布工程和 CI 完整化不纳入本阶段硬范围。

## 4. 主路径范围

V0.2 按“一条作文修改质量脊柱”组织，而不是按所有模块平均铺开。

硬范围：

```text
入口 / Dashboard
-> 作文任务入口
-> 初稿提交
-> AI 点评展示
-> 修改任务选择 / 完成
-> 二稿提交
-> 修改对比
-> 结算反馈
-> 家长阶段报告
```

页面责任：

| 页面 / 组件 | V0.2 责任 | 不做 |
| --- | --- | --- |
| 入口 / Dashboard | 突出“今天要完成的作文修改任务”，弱化地图和其它模块，让孩子清楚下一步 | 不做复杂任务中心 |
| 作文页 | 承担初稿、AI 点评、修改任务、二稿提交、对比结果的完整闭环 | 不拆成大型编辑器 |
| 结算面板 | 强化“你真的变强了”的即时反馈 | 不做复杂战斗系统 |
| 家长报告页 | 展示本次作文修改的具体证据：改了哪里、哪里更具体、下一步练什么 | 不做长期趋势分析 |
| 句子工坊 | 保留为“修改预热”入口 | 不作为硬验收链路 |
| 阅读页 / assessment 页 | 基础视觉清理和友好空状态 | 不扩展阅读内容与题库 |

前端验收不要求“全站精美”，但主路径中孩子会看到的每一屏都不能再是裸 HTML，并且每一屏必须有明确主行动按钮。AI 等待中、失败降级、修改任务未完成等状态都要有儿童友好的文案。

## 5. 前端体验原则

整体风格应符合原 MVP spec 的要求：儿童友好但不过度幼稚，明亮、温暖、积极，卡片式布局，每屏信息不过量，重要动作按钮明显，游戏元素适度。

V0.2 的 UI 改造原则：

- 先建立最小设计系统：色彩 token、字体/字号、间距、圆角、阴影、按钮、卡片、表单、状态提示。
- 优先改造主路径，而不是一次性重写所有页面。
- 作文页是主页面，应围绕“现在该做什么”组织，不让孩子在点评、任务、二稿之间迷路。
- 家长报告比孩子页面更克制专业，但仍要能读出具体证据，而不是泛泛鼓励。
- 使用已安装的 `lucide-react` 做必要图标；避免把 UI 做成复杂手游界面。
- 错误、等待、降级反馈都要有产品文案，不把 HTTP 错误或 provider 异常直接暴露给孩子。

## 6. AI 质量设计

AI 主线只覆盖作文闭环中最关键的两个任务：

```text
essay_feedback
essay_revision_comparison
```

### 6.1 LLM Provider DI

路由层不得直接实例化 `MockLLMProvider()`。作文相关路由通过 FastAPI dependency 获取 provider。

配置支持：

```text
LLM_PROVIDER=mock | http
LLM_MODEL=...
LLM_BASE_URL=...
LLM_API_KEY=...
```

默认行为是 `LLM_PROVIDER=mock`，确保本地新开发者和常规自动化测试不依赖外部网络或付费 key。只有本地显式配置 `LLM_PROVIDER=http` 时，才调用真实 LLM。

### 6.2 真实 LLM 本地测试

真实测试 API key 可以放在本地 `.env`：

```text
LLM_PROVIDER=http
LLM_MODEL=...
LLM_BASE_URL=...
LLM_API_KEY=...
```

安全边界：

- `.env` 只用于本地真实 LLM 测试，不进入 git。
- `.env-sample` 只记录变量名和示例占位，不写真实 key。
- route/API 自动化测试仍以 fake provider 和 mock provider 为主，不依赖真实 key。
- 真实 LLM 测试作为人工验证步骤运行，用来产出 AI 质量评审记录。
- 如果 key 缺失或 provider 配置不完整，系统应返回明确配置错误，不在孩子页面暴露底层异常。

### 6.3 Contract、Retry、Fallback

每个 AI task 的基本流程：

```text
build prompt payload
-> provider.complete_json
-> capture raw response
-> Pydantic schema validation
-> retry on invalid output / provider error
-> return valid parsed output
-> if retries exhausted, return schema-valid fallback
-> write LLMCallLog
```

要求：

- 真实 LLM 输出不合格时最多重试。
- 重试仍失败时，返回儿童友好、安全、schema-valid 的降级反馈。
- 降级不能中断作文流程。
- 降级内容必须清楚说明“先给你一个保守建议”，但不能让孩子看到技术错误。
- 所有失败细节进入 LLM 日志，用于工程复盘。

### 6.4 AI 质量人工评审

V0.2 不追求自动判断 AI 好坏。先固定 4 个孩子画像，重点人工评审小宇画像完整链路。

评审维度：

- 不代写完整作文。
- 先鼓励，再指出具体可改进点。
- 修改任务小而可执行。
- 孩子能理解。
- 家长能信任。
- 输出结构稳定，可被后端解析。
- 二稿对比能引用或概括真实改动证据。

## 7. 数据设计

本阶段的数据采集只服务作文闭环和 AI 质量复盘，不做泛化 analytics 平台。

### 7.1 LLMCallLog 补齐字段

需要能记录：

```text
provider
model
prompt_version
input_summary
raw_response
output_json
validation_ok
error_message
retry_count
```

用途：

- 回看模型原始输出。
- 对比系统最终展示内容。
- 分析 schema validation 失败原因。
- 追踪 prompt 版本变化后的质量差异。

### 7.2 EssayVersion revision 补齐字段

二稿版本需要记录：

```text
completed_tasks
skipped_tasks
duration_seconds
llm_call_log_id
```

用途：

- `duration_seconds` 区分认真修改和快速敷衍提交。
- `completed_tasks/skipped_tasks` 判断 AI 修改任务是否真的被执行。
- `llm_call_log_id` 让二稿对比回溯到对应 AI 调用。

### 7.3 暂不纳入的数据

本阶段不新增：

```text
全站 user_interaction_events
所有页面点击事件
长期徽章进度
怪物血量历史
复杂学习分析报表
```

## 8. 测试与验收

### 8.1 后端测试

必须覆盖：

- route 层通过 `app.dependency_overrides[get_llm_provider]` 注入 fake provider，证明作文路由不再硬编码 mock。
- fake provider `invalid -> valid`，证明 retry 生效。
- fake provider `always invalid`，证明 fallback 仍满足 schema。
- fake provider 抛异常，证明孩子流程不被底层异常炸断。
- LLMCallLog 写入 provider、model、prompt_version、raw_response、validation_ok、error_message、retry_count。
- revision request 能持久化 `duration_seconds`、`completed_tasks`、`skipped_tasks`。
- 迁移验证使用当前实际 SQLModel 表名：`sentencetraining`、`essayversion`、`llmcalllog`，除非实现阶段明确决定增加 `__tablename__`。

### 8.2 前端测试

必须覆盖：

- Dashboard 能突出作文任务入口。
- 作文页能展示初稿表单、AI 点评、修改任务、二稿表单、对比结果。
- AI loading / fallback / error 状态有儿童友好文案。
- 结算面板展示 XP、等级和鼓励信息。
- 家长报告页展示具体修改证据。

### 8.3 E2E 验收

以小宇画像跑完整主路径：

```text
选择小宇
-> Dashboard
-> 作文任务
-> 提交初稿
-> 查看 AI 点评
-> 标记修改任务
-> 提交二稿
-> 查看修改对比
-> 查看结算
-> 生成并查看家长报告
```

### 8.4 真实 LLM 验收

本地配置真实测试 key 后，至少运行一次真实 LLM 作文闭环，并产出简短 AI 质量评审记录。

记录至少包含：

- provider/model。
- prompt_version。
- 初稿摘要。
- AI 点评是否不代写。
- 修改任务是否可执行。
- 二稿对比是否引用或概括真实证据。
- 是否触发 retry/fallback。
- 人工结论：通过 / 需调整 prompt / 需调整 schema。

## 9. 后续实现计划约束

后续 plan 必须吸收已发现的 review findings：

- 不写并行 starter。实现计划必须是顺序任务 + review gate。
- 若使用 subagent-driven development，每个任务要有清晰且尽量不冲突的文件所有权。
- AI route DI 测试必须是真实 route-level integration test，使用 `dependency_overrides[get_llm_provider]`。
- retry/fallback/logging 必须有失败测试，不只测 happy path。
- analytics 只实现本 spec 明确列出的字段，不半截加入全站事件平台。
- UI scope 必须覆盖作文主路径，不能只改 Dashboard 后声称儿童内测可用。
- 迁移表名必须按当前 SQLModel reality 写，或在实现计划中明确先规范 `__tablename__`。

## 10. V0.2 完成定义

V0.2 质量补全完成时，应同时满足：

1. 小宇画像能在浏览器中走完整作文修改闭环，主路径页面具备基础产品视觉，不再是裸 HTML。
2. 作文点评和二稿对比可以通过配置切换 mock/真实 LLM。
3. LLM 输出有 schema validation、retry、fallback 和日志。
4. 至少一次真实 LLM 测试输出被记录并完成 AI 质量人工评审。
5. 后端、前端、E2E 测试覆盖本 spec 的主验收点。
6. 后续新增功能之前，优先根据真实 LLM 评审结果调整 prompt、schema 和作文页体验。
