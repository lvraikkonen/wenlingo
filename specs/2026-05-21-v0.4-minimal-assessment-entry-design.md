# WenLingo V0.4 Minimal Assessment Entry Design

Date: 2026-05-21
Status: Draft for review
Source: `reviews/2026-05-21-v0.3-ability-flywheel-gstack-review.md`, `specs/2026-05-21-wenlingo-v0.4-minimal-assessment-handoff.md`, current codebase inspection

## Goal

V0.4 turns the existing all-default new-child state into a real first experience. A new child completes a 3-5 minute entry trial: one fixed sentence upgrade and one short writing task. The system reuses the existing `sentence_upgrade_feedback` and `essay_feedback` LLM paths, creates real training artifacts, records ability history, returns the first ability sketch, and lets Dashboard recommendations move from "入门小试炼" to personalized essay/sentence tasks.

This release also completes the V0.3 release note and stale SQLite database cleanup documentation before code implementation begins.

## Non-Goals

- No reading diagnostic or reading comprehension task.
- No material-question or outline-generation flow.
- No new LLM task type, prompt version, provider behavior, or dependency.
- No assessment retake/history UI.
- No parent-specific assessment report.
- No changes to the four demo children's seeded ability profiles, dashboard recommendations, or report behavior.

## Chosen Approach

Use a backend service orchestrator for assessment creation.

The route stays thin: validate dependencies, call the assessment service, map known errors to HTTP responses, rollback on failure, and commit only after the service has created all required rows. The service owns the ordered workflow and reuses existing task runner wrappers instead of calling HTTP endpoints.

This is more maintainable than route-inline orchestration and lower risk than refactoring all sentence and essay route logic into shared services during V0.4.

## Data Model

Add explicit nullable artifact references to `Assessment`:

- `sentence_training_id: str | None`, indexed, FK to `sentencetraining.id`
- `essay_id: str | None`, indexed, FK to `essay.id`

The fields are nullable so existing assessment rows remain valid. `summary` remains a human-readable sentence such as "完成入门小试炼，生成第一张能力草图。"; it must not be the only place artifact references live.

`AbilityHistory` does not gain an assessment source. Assessment is a container, not an ability delta source:

- Sentence deltas use `source_type=TaskType.sentence`, `source_id=SentenceTraining.id`.
- Essay draft deltas use `source_type=TaskType.essay`, `source_id=EssayVersion.id`.

## Backend Flow

`POST /api/students/{student_id}/assessment` accepts:

- `sentence_before`: 1-500 chars
- `sentence_after`: 1-500 chars
- `short_writing`: 20-500 chars

The frontend will send the fixed sentence prompt, but the backend keeps accepting both sentence fields for compatibility.

Current enum verification: as of 2026-05-21, `apps/api/app/domain/enums.py` defines the add-detail focus as `SentenceFocus.detail = "加细节"`. Implementation must confirm the real member name before coding and use that enum member's `.value`. If the codebase is renamed to `SentenceFocus.add_detail`, use `SentenceFocus.add_detail.value`; do not hard-code the raw string or use a stale enum member name.

The assessment service performs these steps in one transaction:

1. Load `StudentProfile` and `AbilityProfile`; route returns 404 if either is missing.
2. Call `sentence_upgrade_feedback` with `focus=SentenceFocus.detail.value`, passing `session`, `student_id`, and current `settings.llm_prompt_version`.
3. Create `SentenceTraining` with the original sentence, upgraded sentence, focus string, and AI feedback JSON.
4. Flush to get `SentenceTraining.id`.
5. Choose sentence ability deltas using the existing V0.3 canonical-key gate. If no positive canonical key exists, use `{"expression": 2, "observation": 2}` fallback.
6. Apply sentence deltas through `apply_ability_delta(session, ability, deltas, TaskType.sentence, training.id)`.
7. Call `essay_feedback` with `title="入门小写作"` and `draft=short_writing`.
8. Create `Essay` as an assessment artifact, not an unfinished Essay Castle task. Use a non-normal status such as `assessment_completed`, keep the title as "入门小写作", and rely on the `Assessment.essay_id` link as the durable container reference. Any normal Essay Castle query or revision endpoint must treat assessment-marked essays as out of scope unless a future release intentionally supports continuing them.
9. Flush, then create first `EssayVersion` with `version_label="first_draft"`, short-writing content, AI feedback JSON, and `llm_call_log_id`.
10. Flush to get `EssayVersion.id`.
11. Compute essay draft deltas using existing `draft_ability_deltas(len(feedback.improvements))`.
12. Apply essay deltas through `apply_ability_delta(session, ability, deltas, TaskType.essay, version.id)`.
13. Create `Assessment` with explicit `sentence_training_id` and `essay_id`.
14. Create assessment `GameEvent` via `settle_task(student, TaskType.assessment, ...)`.
15. Return payload data for the route to commit atomically.

The service must not call `/sentences` or `/essays` HTTP endpoints internally.

## Failure Strategy

Schema-valid LLM fallback can complete assessment. This includes schema validation failures, malformed provider JSON that exhausts retries, or daily-limit fallback handled by `run_validated_llm_task`.

Unhandled provider exceptions that escape the LLM task runner, DB flush/commit errors, and unknown runtime errors must rollback and leave no partial assessment rows. `essay_feedback` ghostwriting `ValueError` maps to 400 and also rolls back, so a sentence artifact cannot remain after a blocked writing submission.

The route should use an explicit `try` boundary around the orchestration and commit. On expected 400/404 errors, rollback before raising. On unexpected errors, rollback and re-raise.

## API Response

The new response is additive:

```json
{
  "assessment": {
    "id": "assessment-id",
    "summary": "完成入门小试炼，生成第一张能力草图。",
    "sentence_training_id": "sentence-training-id",
    "essay_id": "essay-id"
  },
  "ability_sketch": {
    "reading_power": 40,
    "specific_writing_power": 46,
    "revision_power": 40
  },
  "settlement": {
    "xp_delta": 20,
    "level_after": 1,
    "badge_code": null
  }
}
```

The implementation may keep a temporary `game_event` alias for backward compatibility, but new frontend code and tests should use `settlement`.

## Dashboard Behavior

Dashboard already checks whether an `Assessment` row exists. After V0.4 assessment completion:

- `ability_note` becomes "第一张能力草图".
- `child_abilities` comes from `to_child_abilities(ability)`.
- At least one underlying ability differs from default 40, so `choose_today_tasks(ability).main.kind` is no longer `assessment`.
- Demo family dashboards and reports must not change.

## Frontend Flow

Replace the bare form in `apps/web/src/app/children/[studentId]/assessment/page.tsx` with a four-step child-friendly flow:

1. `intro`: "认识你的写作超能力", shows "约 3-5 分钟", primary button "开始小试炼".
2. `sentence magic`: fixed source sentence "公园很美。"; child writes an upgraded sentence. The source sentence is displayed, not edited.
3. `short writing`: fixed prompt "写一写你最近一次开心的经历"; child writes 2-5 sentences and submits the whole assessment once.
4. `ability sketch`: show the returned ability sketch and link back to Dashboard.

The ability sketch uses the selected hybrid visual treatment:

- A small triangular radar chart provides the "first ability sketch" reveal.
- A short explanation calls out the strongest new signal, usually writing specificity.
- Compact labels show all three child-facing abilities.
- `reading_power=40` can display "等待阅读试炼".
- `revision_power=40` should be treated as correct because the assessment does not include a second-draft revision task.

The frontend should include clear loading and retry states. Loading copy should say the AI coach is整理第一张能力草图. Error copy should invite retry without making the child feel at fault.

The radar visualization must be implemented with lightweight inline SVG and CSS only. Do not add a charting dependency for the three-point assessment sketch.

## Testing

Backend tests:

- Migration includes `sentence_training_id`, `essay_id`, indexes, and foreign keys.
- Assessment creates `SentenceTraining`.
- Assessment creates `Essay` and first `EssayVersion`.
- Assessment-created `Essay` is marked with an assessment-only status and cannot be mistaken for an unfinished normal Essay Castle task.
- Assessment creates `Assessment` with explicit artifact references.
- Assessment creates `AbilityHistory` rows with `source_type` sentence/essay only.
- Ability profile changes from all-default 40.
- Response includes `ability_sketch` and `settlement`.
- Post-assessment dashboard no longer recommends `kind="assessment"`.
- Schema-valid fallback can complete assessment.
- Ghostwriting or unhandled failure rolls back all partial rows.
- Overlong sentence/writing inputs return 422.
- Demo family dashboards, recommendations, and reports remain unchanged.

Frontend tests:

- Four steps render in order.
- Sentence source is fixed to "公园很美。".
- Submission sends all three fields once from the short-writing step.
- Loading state disables submit.
- Error state permits retry.
- Ability sketch renders hybrid radar/explanation and three ability labels.
- Ability sketch uses inline SVG/CSS and adds no charting package.

E2E:

- New/default child starts from assessment recommendation, completes assessment, sees ability sketch, returns to Dashboard, and sees a non-assessment recommendation.
- Existing MVP demo flow still passes.

Manual QA notes:

- Record stopwatch timing for the entry trial and verify the flow can complete within 3-5 minutes.
- Verify `reading_power` says waiting for reading trial when still 40.
- Verify `revision_power` staying 40 is not framed as a failure.
- Verify stale DB cleanup instructions before running full local QA.
