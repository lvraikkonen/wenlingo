## 一、当前 MVP 是否形成了真正的学习闭环？

### 评审判定：实现了"骨架闭环"，但尚未跑通"真实数据闭环"

MVP 在代码层面已经实现了学习飞轮的每个节点：

```text
家长登录（apps/web/src/app/page.tsx）
→ 选择孩子档案（4 个预设画像）
→ 极简诊断（assessment 页面 + API）
→ 今日任务推荐（recommendations.py 规则引擎）
→ 句子训练（sentence workshop flow）
→ 作文初稿→AI 点评→二稿→修改对比
→ 战斗结算（gamification.py 产出 GameEvent）
→ 能力画像更新（abilities.py 产出 delta）
→ 家长阶段报告（reports.py 产出 ReportContent）
→ 下一轮推荐
```

**后端测试验证**：61 个测试全部通过，覆盖了从 seed profile 创建到 Essay revision 提交的完整 API 链。

**E2E 验证**：`apps/web/e2e/mvp.spec.ts` 模拟了从家庭入口到阶段报告的完整用户路径。

**但关键缺口使闭环停留在"演示级"而非"内测级"**：

| 闭环节点 | 当前状态 | 缺口 |
|---------|---------|------|
| AI 反馈 | MockLLMProvider 硬编码 | 未接入任何真实 LLM，无法验证反馈质量 |
| 能力更新 | 纯规则驱动 | 未使用 LLM 判断修改质量（spec 要求"规则 + LLM 混合"） |
| 家长报告 | 规则聚合 | 未使用 AI 生成专业报告（spec 要求 LLM 生成） |
| 反代写 | 正则关键词匹配 | 无真实 LLM 场景下的过界输出检测 |
| 阅读训练 | 仅存 session 记录 | 无内置文章内容，无阅读题目生成 |
| **前端 UI** | **裸 HTML，零样式** | **无 Tailwind CSS、无 global.css、无组件样式** |

**结论**：MVP 的工程骨架扎实，但"AI 陪练质量"这个核心硬性门槛尚未被验证，且前端视觉呈现为零——在当前状态下，API 逻辑可以走通，但孩子看到的界面是 1995 年级别的裸 HTML，完全不符合 spec 要求的"明亮、温暖、积极""卡片式布局""游戏元素适度"。

## 二、前三大产品风险

### 风险 1：AI 反馈质量未经内测验证（严重性：高）

**现状**：所有 API 路由硬编码使用 `MockLLMProvider()`（参见 `essays.py:37`、`essays.py:87`）。虽然 `HttpJsonLLMProvider` 已实现，但从未在测试中连接真实 LLM。

**具体隐患**：
- LLM 能否稳定产出符合 `llm_contracts.py` 中 strict schema 的 JSON？schema 校验失败时的降级策略是什么？
- 真实 LLM 的反馈语气是否真正做到"温和、具体、鼓励式"？Prompt 中的"温柔、有经验的小学语文老师"角色设定能否被模型忠实执行？
- 不同 LLM（Claude、GPT、Qwen、DeepSeek）对中文儿童表达的理解差异有多大？

**建议**：在 V0.2 开始前，必须用至少 2 个真实 LLM 对 4 个预设孩子画像完成一轮反馈质量人工评审。

### 风险 2：作文修改闭环依赖孩子的"修改意愿"（严重性：高）

**现状**：初稿→点评→修改任务→二稿 的流程已经实现，但产品没有设计任何机制来应对"孩子收到点评后不愿意修改"的场景。

**数据支撑**：spec 中设定的作文二稿提交率目标是 ≥40%，这意味着超半数场景下孩子不会完成闭环。但没有设计：
- 如果孩子跳过二稿，系统如何跟进？
- 修改任务是否可以根据孩子的拒绝/跳过低频次调整？
- 句子工坊是否可以作为"修改预热"降低修改门槛？

**建议**：增加"跳过修改但获得轻量替代任务"的 fallback 路径，避免孩子因为修改压力而完全离开。

### 风险 3：游戏化系统过于线性，缺乏长期留存机制（严重性：中）

**现状**：游戏化实现（`gamification.py`）是单次战斗结算 + 线性 XP/等级。8 个徽章的设计存在于 spec 中但实现极简——每次都触发 `first_sentence_upgrade` 或 `first_revision` badge，没有进度累积逻辑。

**具体隐患**：
- 孩子完成 10 次句子升级后不会获得任何区别于第 1 次的新反馈
- 没有"连续练习"的激励（spec 中设计了"连续练习者"徽章但未实现）
- 怪物系统虽然定义了 6 种怪物，但 implementation 中只是字符串标签，没有"怪物血量""击退进度"等让孩子感受到持续对抗的机制

**建议**：V0.2 需要实现徽章进度追踪和怪物击退进度，而非每次结算都重置。

### 风险 4：前端 UI 零视觉设计，无法用于真实儿童内测（严重性：高）

**现状**：经代码审查确认，前端完全没有应用任何视觉样式：

- **无 Tailwind CSS**：`tailwind.config.*`、`postcss.config.*`、`globals.css` 均不存在，尽管 spec 明确写了"推荐技术：Next.js + React + Tailwind CSS"。`package.json` 中甚至没有安装 tailwindcss 依赖
- **无 CSS Modules**：所有 `.tsx` 文件零 `className` 使用（除了 ARIA label）
- **5 个组件全部是裸 HTML**：
  - `AbilityBars.tsx`：原生 `<progress>` 元素，在不同浏览器中渲染不一致
  - `PlanetMap.tsx`：纯 `<a>` 链接，无地图视觉
  - `AiCoachPanel.tsx`：`<aside>` + `<strong>` + `<p>`，无教练形象
  - `SettlementPanel.tsx`：纯文本，无结算动画
  - `TaskCards.tsx`：裸 `<article>` 标签，无卡片视觉
- **所有 6 个页面**（home、dashboard、assessment、sentence、essay、reading、report）都是 `<main>` + `<form>` + `<button>` 的浏览器默认样式
- **lucide-react 图标库已安装但从未使用**——0 次 import

**与 spec 的差距**：spec §24.2 明确要求：
> - 儿童友好，但不要过度幼稚
> - 卡片式布局
> - 明亮、温暖、积极
> - 每屏信息不要太多
> - 重要动作按钮明显
> - 游戏元素适度，不做复杂手游界面

当前实现连最基础的"卡片式布局"和"按钮明显"都没有做到。

**为什么高风险**：孩子是视觉驱动的用户群体。一个裸 HTML 界面不仅不会让孩子产生"冒险"的感受，反而会让孩子在 30 秒内关掉页面。**在 UI 未达到基本视觉门槛之前，任何儿童内测都会因"不好看"而失败，无法收集到关于学习有效性的真实数据。**

**建议**：在 P0 任务中加入 UI 基础改造——最低限度安装 Tailwind CSS，实现色彩体系（明亮温暖调）、卡片布局、游戏化视觉元素。

## 三、前三大工程风险

### 风险 1：测试中的 AI 行为与生产环境的 AI 行为完全脱节（严重性：高）

**现状**：
- 所有 61 个后端测试依赖 `MockLLMProvider` 的硬编码返回值
- 测试无法验证：JSON schema 校验、LLM 调用重试、超时处理、输出解析失败降级
- `HttpJsonLLMProvider` 缺少单元测试和集成测试
- 没有针对真实 LLM 输出的 contract validation 测试

**具体场景**：如果真实 LLM 返回的 JSON 中 `strengths` 只有 1 个元素（schema 要求恰好 2 个），当前代码会直接抛出 Pydantic validation error。Mock 测试永远不会触发此路径。

**建议**：添加一层 `test_llm_contracts.py` 测试，用真实的 LLM 输出样本（good case + edge case + failure case）验证 schema 校验和降级逻辑。

### 风险 2：硬编码 MockLLMProvider 阻塞了真实 LLM 集成路径（严重性：高）

**现状**：路由层直接实例化 `MockLLMProvider()`，而非通过依赖注入获取 provider。

```python
# apps/api/app/api/routes/essays.py:37
feedback = await essay_feedback(MockLLMProvider(), request.title, request.draft)
```

这导致：
- 无法通过环境变量或配置切换 mock/real provider
- 无法在测试中使用不同的 mock 返回值
- `HttpJsonLLMProvider` 已经实现但从未被路由使用
- LLM 调用日志（`LLMCallLog`）永远不会被写入（`ai_tasks.py` 中的 `log_llm_result` 函数从未被调用）

**建议**：为 LLM provider 添加 FastAPI dependency injection，通过 `LLM_PROVIDER` 环境变量控制。

### 风险 3：前端设计系统完全缺失，UI 等于零（严重性：高）

**现状**：
- Tailwind CSS 未被安装，postcss 未被配置，globals.css 不存在
- 所有组件和页面是裸 HTML 默认样式——`<button>` 是浏览器原生按钮，`<progress>` 是系统默认进度条
- `lucide-react`（图标库）已在 `dependencies` 中但从未被任何文件 `import`
- 没有色彩体系、间距系统、字体定义、响应式断点

**为什么是工程风险**：这不只是"不好看"——这意味着一旦开始做 UI，所有组件都需要重构。裸 HTML 没有为任何 CSS 框架留下接入点（没有 className、没有 data attributes、没有设计 token），后续视觉层建设必然伴随大面积重写。

**建议**：安装 Tailwind CSS 4（兼容 Next.js 16），建立最小设计 token 集合（4 个主色 + 2 个字体 + 间距 scale），然后在现有组件上逐层添加 className。不要一次性重构所有组件。

### 风险 4：数据库迁移和部署路径未经验证（严重性：中）

**现状**：
- Alembic 配置存在，但未确认是否生成了有效的迁移脚本
- `docker-compose.yml` 定义了 PostgreSQL 服务，但未验证应用能否成功连接并创建表
- 前端 6 个测试文件（含 E2E），因 `@testing-library/jest-dom/vitest` 和 `@playwright/test` 未安装，5 个文件报 import 错误，仅 `api.test.ts` 通过。测试代码本身质量良好，但依赖安装不完整
- 没有 CI/CD 配置

**建议**：在合并到 main 前完成一次完整的 docker-compose up 验证流程。

## 四、在增加新功能之前，哪些功能应该先改进？

### 优先级 P0：前端 UI 基础建设（阻塞儿童内测）

1. **安装并配置 Tailwind CSS** — `pnpm add tailwindcss @tailwindcss/postcss`，创建 `postcss.config.mjs` 和 `globals.css`
2. **建立最小设计 token 集**：4 个主色（暖黄、柔绿、天空蓝、鼓励橙）+ 圆角 scale + 阴影 scale
3. **改造 Dashboard 为首个"有视觉"页面**：卡片布局、彩色能力进度条、圆形角色头像占位、今日任务突出展示
4. **改造战斗结算页**：让孩子能感受到"闯关成功"的快乐

### 优先级 P1：真实 LLM 集成（阻塞所有 AI 质量验证）

1. **将 LLM provider 改为依赖注入**，使 `LLM_PROVIDER=mock|http` 环境变量控制
2. **接入至少一个真实 LLM**（推荐 Claude Sonnet 4.6 或 GPT-4o，因为对中文儿童内容理解较好）
3. **添加 LLM 调用日志**到所有 AI task 路径
4. **实现 JSON schema 校验失败时的重试 + 降级逻辑**
5. **用真实 LLM 输出运行一次人工评审**，评审标准对齐 spec §14.3

### 优先级 P2：能力画像和报告的 AI 化

1. **家长报告改为 AI 生成**，而非 `reports.py` 中的规则模板。当前报告输出对 4 个不同画像的孩子几乎一样，无法体现个性化
2. **能力更新引入 LLM 判断**——目前是纯规则 `+delta`，没有判断孩子是否真的"加入了细节"
3. **实现徽章进度追踪**，而非每次都给同一个 badge

### 优先级 P3：阅读模块补充

1. 内置至少 5 篇配套阅读文章（当前 0 篇）
2. 实现阅读题目生成（当前仅有 session 记录，无题目内容）
3. 实现阅读到写作的迁移技巧生成

### 优先级 P4：产品体验打磨

1. 首诊流程增加"加载状态"和"AI 思考中"动画——孩子在等待 AI 反馈时的体验未在代码中体现
2. 战斗结算页增加动画过渡
3. 错误状态友好化——当前 400/404/409 HTTP 错误直接暴露给前端，没有儿童友好的错误文案

## 五、WenLingo V0.2 应该重点关注什么？

基于以上分析，V0.2 的核心主题应该是：

### 主题：从"演示闭环"到"AI 陪练质量验证"

CLAUDE.md 中已经列出了 V0.2 的方向，但需要调整优先级：

| CLAUDE.md V0.2 方向 | 建议调整 |
|---------------------|---------|
| Writing revision loop | 保持，但先完成 P0 LLM 集成 |
| Structured AI feedback | 保持，这是 V0.2 核心 |
| Draft vs revision comparison | 保持，与 revision loop 联动 |
| Positive growth feedback | 保持，但需要先验证 AI 语气 |
| Parent-visible progress report | 升级为"AI 生成的个性化阶段报告" |

### V0.2 不应做的事情

1. **不要新增训练模块**（词语森林、素材湖泊等）——在 3 个核心模块的质量未验证前，不扩展模块数量
2. **不要做移动 App**——浏览器体验未稳定前不要分叉
3. **不要引入复杂自适应算法**——先用规则 + LLM 混合运行，积累足够数据后再考虑 ML
4. **不要做老师端**——家长端的使用数据尚未积累
5. **不要做语音输入 / OCR**——这些是体验增强，不是核心学习闭环

### V0.2 最小成功定义

> 用至少 2 个真实 LLM，让真实孩子（小宇画像）在 2 周内完成 ≥3 次完整的"写初稿→收 AI 点评→做修改任务→提交二稿→看到修改对比→能力更新→家长看到个性化报告"闭环。AI 反馈质量由产品方人工评审通过。

## 六、为了未来的学习分析，现在必须记录哪些数据？

当前数据模型（`models.py`）已经捕获了核心训练数据，但以下维度的数据缺口会严重制约未来的学习分析能力：

### 6.1 当前已记录（好）

| 数据 | 模型 | 评价 |
|------|------|------|
| 训练次数和类型 | `SentenceTraining`, `Essay`, `ReadingSession` | 有效 |
| 作文版本（初稿/二稿） | `EssayVersion` | 有效，唯一约束防重复提交 |
| AI 反馈内容 | 各模型的 `ai_feedback` JSON 字段 | 有效 |
| 能力画像快照 | `AbilityProfile` + `evidence` JSON | 有效 |
| 游戏事件 | `GameEvent` | 有效 |
| LLM 调用日志 | `LLMCallLog` | 模型存在但从未写入！ |

### 6.2 必须立即添加的数据

#### A. 任务耗时（`duration_seconds`）

**为什么重要**：无法区分"写了 2 分钟"和"写了 20 分钟"的训练，能力成长分析将失去重要维度。

**建议**：在 `SentenceTraining`、`EssayVersion`、`ReadingSession` 中添加 `duration_seconds: int | None` 字段。

#### B. 用户交互事件（`user_interaction_events`）

**为什么重要**：需要知道孩子在哪一步放弃、哪个 UI 造成了困惑。

**建议**：添加轻量事件表：

```
- event_type: "task_started" | "task_abandoned" | "page_viewed" | "button_clicked"
- source_type: "sentence" | "essay" | "reading" | "dashboard"
- source_id: 对应训练记录 ID
- metadata: JSON (可选的额外交互上下文)
```

#### C. LLM prompt 版本（`prompt_version`）

**为什么重要**：当调整 prompt 后，需要能回溯哪些训练记录是用哪个版本的 prompt 生成的。

**建议**：在 `LLMCallLog` 中添加 `prompt_version: str` 字段，并在各训练模型中记录对应的 `llm_call_log_id`。

#### D. 修改任务完成状态（`revision_task_status`）

**为什么重要**：AI 每次给出 1-3 个修改任务，但目前只记录了"提交了二稿"，无法知道孩子具体完成了哪个任务、跳过了哪个。

**建议**：在 `EssayVersion`（revision）中记录 `completed_tasks: list[str]`（完成的任务标题列表）和 `skipped_tasks: list[str]`（跳过/未完成的任务标题列表）。

#### E. 原始 AI 输出（未经 schema 裁剪的原始响应）

**为什么重要**：当 schema 校验裁剪掉了 AI 的一些输出后，被裁剪的内容对于调试 AI 质量至关重要。

**建议**：在 `LLMCallLog` 中添加 `raw_response: str | None` 字段，存储原始 HTTP 响应体。

### 6.3 数据采集原则

- 所有新字段应为可选（`nullable`），不阻塞当前功能
- 优先写入数据，分析可以延后
- 数据写入不应增加用户感知的延迟（异步写入或批处理）
- 敏感内容（作文正文、家长反馈）需标注 PII 级别，为未来合规做准备

## 七、评审总结

### MVP 当前评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 工程骨架完整性 | 8/10 | API 完整，模型合理，61 后端测试通过 |
| AI 集成深度 | 2/10 | 纯 mock，0 次真实 LLM 调用 |
| 前端 UI 质量 | 0/10 | 裸 HTML，零 CSS，无设计系统，无法给孩子看 |
| 学习闭环可演示性 | 7/10 | E2E 流程可走完，但反馈是假的、界面是裸的 |
| 学习闭环可用性 | 1/10 | 未连接真实 AI + UI 零视觉 = 无法给真实孩子使用 |
| 代码质量 | 7/10 | 结构清晰，类型完整，但硬编码 mock + 无样式架构 |
| 测试覆盖 | 6/10 | 后端 61 pass，前端 4 个 import 错误（缺依赖），无 LLM 集成测试 |

### 一句话评审

> WenLingo MVP 的工程骨架扎实、学习闭环结构完整，但两个致命缺口使产品无法进入真实儿童内测：(1) AI 陪练质量完全未验证——所有反馈来自硬编码 mock；(2) 前端 UI 为零——裸 HTML 无任何视觉设计，孩子 30 秒内就会关掉页面。V0.2 必须将"UI 基础建设"和"真实 LLM 接入"作为同等优先级的阻塞项。

### 建议的 V0.2 切入点

优先投入 3 周完成以下 "MVP 质量补全冲刺"：
