# WenLingo V0.6c Topic Breadth + AI Topic Thin Slice Design

Date: 2026-06-29

Status: Patched after gstack/manual review; ready for user review before implementation planning

## 1. Summary

V0.6c is a topic-breadth release for Writing Castle. Its first job is to make
classroom-aligned composition credible across more 3-6 grade assignment types.
Its second job is to unlock the smallest useful AI-generated topic path without
turning this release into a recommendation system or topic-bank project.

The release keeps the V0.6b architecture:

```text
TopicType -> ScaffoldTemplate -> SourceChain -> QA Matrix
```

P0 adds four visible scaffold families:

- `place_scenery`
- `animal_object_observation`
- `practical_writing`
- `story_adaptation`

P0 also adds an AI topic path:

```text
interest + grade_label -> 3 topic ideas -> child selects one -> existing prewriting flow
```

Each AI topic idea must map to a currently supported scaffold. The system must
not generate essay body text or decide the child's specific content.

## 3. Decisions From Brainstorming

- V0.6c is topic-breadth first. AI topic composition is a thin slice.
- `story_adaptation` is P0. `story_summary` remains unsupported and moves to
  V0.7/backlog.
- AI topic generation uses interest + grade context and returns exactly 3 topic
  ideas.
- AI topic generation has no deterministic topic fallback. On failure, the child
  sees a friendly retry or later path.
- Each new scaffold family gets one default template plus key textbook
  variants/aliases.
- `reading_response_recommendation` and `central_idea_reflection` get design
  spike documents only. They are not product-visible in V0.6c.
- Essay archive, multi-round revision, and delete/hide behavior move to V0.6c.1
  and must not expand V0.6c.
- The JSON container `schema_version` must stay `v0.6b.1`; only new
  `scaffold_template_version` values get a `.v0.6c` suffix.
- AI topic provenance uses a new `topic_origin` field. It must not overload the
  existing `selection_source` field.

## 4. Product Goal

The child should feel:

- "This scaffold understands this kind of assignment."
- "I can choose or confirm my own material."
- "AI can suggest a topic idea, but I still decide what to write."

The parent should see:

- The child worked inside an appropriate scaffold family.
- AI did not write copy-ready essay content.
- AI topic ideas are traceable to a supported topic type.

## 5. Non-Goals

V0.6c does not include:

- Token Streaming, Progress SSE, or LLMCallLog streaming fields.
- Full AI topic bank larger than 20 items.
- AI topic fallback from a hidden fixed bank.
- Profile-based intelligent recommendation.
- Recommendation optimization that narrows the child into an interest bubble.
- `story_summary` / 缩写故事 / 作品梗概 scaffold.
- Product-visible `reading_response_recommendation` or `central_idea_reflection`.
- Essay archive, multi-round revision, continue-editing, or delete/hide actions.
- Parent weekly report redesign.
- Database/admin template editor.

## 7. Scaffold Template Design

The backend remains the source of truth for templates. The frontend renders the
resolved scaffold snapshot and must not hardcode family-specific slot logic.

The JSON container shape must not change in V0.6c. The container
`schema_version` stays `v0.6b.1` so existing resume gates and V0.6b.1
source-reference protections keep working. Do not change `SCHEMA_VERSION`.

Only `scaffold_template_version` changes for new templates. Existing four
families keep their `.v0.6b.1` template versions. New families use a V0.6c
template suffix, for example:

```text
place_scenery.default.v0.6c
```

Implementation should decouple the template-version suffix from
`SCHEMA_VERSION`, for example through a per-template version map in
`writing_castle_scaffold.py`. This avoids breaking in-flight V0.6b essays and
keeps `_validate_v06b_material_card_source_refs()` active for V0.6c sessions.

The visible `TopicType` set becomes eight families:

```text
generic_narrative
person_portrait
imaginative_story
expository_introduction
place_scenery
animal_object_observation
practical_writing
story_adaptation
```

The four newly supported families must be removed from `FUTURE_TOPIC_TYPES`.
Unsupported detection must also migrate: `写信`, `书信`, `我想对您说`,
`倡议书`, `故事新编`, and `续写` must no longer return unsupported future types.

### `place_scenery`

Purpose: cover place description, scenery, travel writing, and place
recommendation.

Representative topics:

- 我的乐园
- 游____
- 这儿真美
- ____即景
- 推荐一个好地方

Default slots:

| id | label | content_kind | source note |
|---|---|---|---|
| `place_subject` | 地点是什么 | `subject` | May come from `topic_requirement` when the assignment names the place. |
| `observation_order` | 观察或游览顺序 | `content` | Must be child-confirmed or based on real experience/observation. |
| `key_scene` | 最重要的景物或画面 | `content` | Must not be invented by AI. |
| `sensory_detail` | 颜色/声音/气味/动作等细节 | `content` | Must come from observation, real experience, or child confirmation. |
| `activity_or_experience` | 我在那里做什么或经历什么 | `content` | Requires child-provided or child-confirmed material. |
| `feeling_reason` | 感受或推荐理由 | `content` | Requires child-provided or child-confirmed material. |

Default outline sections:

| id | heading | label | content_kind |
|---|---|---|---|
| `opening_place` | 开头 | 介绍这个地方 | `structural` |
| `order_or_view` | 顺序 | 按观察或游览顺序展开 | `content` |
| `key_scene` | 重点 | 细写最重要的景物或画面 | `content` |
| `activity_feeling` | 体验 | 写活动、感受或推荐理由 | `content` |
| `ending_reason` | 结尾 | 回扣为什么特别 | `content` |

Key variants/aliases:

- `my_paradise`
- `travel_writing`
- `scene_description`
- `place_recommendation`

Source policy:

- allowed: `real_experience`, `observation`, `child_confirmed`
- required for content: `real_experience`, `observation`, `child_confirmed`

`topic_requirement` may identify the assigned place or recommendation target,
but it must not be used as the source for specific scenes, feelings, or lived
details unless the child confirms them.

### `practical_writing`

Purpose: cover format-based practical writing while preserving the child's own
message, position, and feelings.

Representative topics:

- 写日记
- 写信
- 我想对您说
- 学写倡议书

Default slots:

| id | label | content_kind | source note |
|---|---|---|---|
| `format_type` | 文体/格式 | `structural` | May come from `topic_requirement`. |
| `audience_or_date` | 对象或日期信息 | `structural` | May come from `topic_requirement` or child confirmation. |
| `main_message` | 最想表达的事情 | `content` | Must come from child confirmation, real experience, or observation. |
| `reason_or_background` | 为什么要写 | `content` | Must come from child confirmation, real experience, or observation. |
| `specific_details` | 具体事情或建议 | `content` | Must not be filled from format hints alone. |
| `closing_or_call` | 祝福/期待/号召 | `content` | Requires child-confirmed wording or intent. |

Default outline sections:

| id | heading | label | content_kind |
|---|---|---|---|
| `format_opening` | 格式 | 写清称呼/日期/开头格式 | `structural` |
| `main_message` | 正文 | 写最想表达的事情 | `content` |
| `details_or_reasons` | 细节 | 写原因、经历、建议或具体做法 | `content` |
| `closing` | 结尾 | 写祝福、期待或号召 | `content` |
| `signature_or_date` | 落款 | 检查署名和日期等格式 | `structural` |

Key variants/aliases:

- `diary` as a true variant
- `letter` as a true variant
- `proposal` as a true variant
- `heartfelt_letter` (`我想对您说`) may alias `letter`

- allowed: `topic_requirement`, `real_experience`, `observation`,

- required for content: `topic_requirement`, `child_confirmed`

Practical-writing templates may include format hints, but they must not compose
the child's message for them.

| `new_ending` | 新结局 | `content` | Requires imagined setting or child confirmation. |
| `new_meaning` | 新故事想表达的意思 | `content` | Requires child confirmation. |

| id | heading | label | content_kind |
|---|---|---|---|
| `original_setup` | 原故事 | 交代原故事或已有情境 | `structural` |
| `change_start` | 变化 | 写从哪里开始改变 | `content` |
| `new_development` | 新情节 | 展开新的事件或困难 | `content` |
| `new_ending` | 新结局 | 写新的结果 | `content` |
| `ending_meaning` | 新意思 | 点出新故事的意思 | `content` |

Key variants/aliases:

- `story_continuation`
- `story_rewrite`

Source policy:

- allowed: `topic_requirement`, `reading_material`, `imagined_setting`,
  `child_confirmed`
- required for content: `topic_requirement`, `reading_material`,
  `imagined_setting`, `child_confirmed`

`story_summary` remains unsupported in V0.6c. "缩写", "梗概", and similar topics
must continue to surface `unsupported_future_type = "story_summary"`.

AI may ask the child to identify or confirm the original story basis. It must
not fill missing original-story details from common knowledge, and it must not
decide the new event, ending, or meaning before child confirmation.

### Prompt Clauses For New Families

The template registry should not add a static `material_questions` field. V0.6b
derives material questions from `payload.scaffold.material_slots` through the
`material_questions` AI task and deterministic fallback.

V0.6c must update `material_questions` and `material_card_generation` prompt
contracts with topic-type clauses for the new families:

- `place_scenery`: ask for observed or remembered scenes, order, and reasons;
  do not invent scenic details.
- `animal_object_observation`: ask what the child observed, noticed, or
  experienced with the subject.
- `practical_writing`: ask format-aware questions, but require the child's own
  message, reasons, and details.
- `story_adaptation`: ask the child to confirm the original basis and choose new
  events/endings; do not rely on common-knowledge story details as sources.

## 8. AI Topic Generation

### Task Contract

Add a new prompt key:

```text
writing_topic_idea_generation
```

It must be registered through `register_prompt()` with:

- prompt key
- version
- response contract
- system prompt key

It must be routed through ModelRouter as a normal essay task. The recommended
initial routing is:

```python
TaskConfig(
    task_name="writing_topic_idea_generation",
    primary_model="cheap_fast",
    fallback_model="strong_default",
    primary_timeout_seconds=8,
    fallback_timeout_seconds=7,
    max_total_latency_seconds=15,
    daily_limit=5,
    cost_tier="low",
    allowed_prompt_keys=("writing_topic_idea_generation",),
    default_prompt_key="writing_topic_idea_generation",
)
```

There is no `retry_count` field in the current `TaskConfig`; primary plus
fallback is the retry model.

The task input includes:

- `student.grade_label`
- child interest text or selected interest chips
- supported scaffold choices and allowed variants

The output must be exactly 3 topic ideas:

```json
{
  "ideas": [
    {
      "id": "idea-1",
      "title": "",
      "topic_type": "",
      "topic_variant": "",
      "why_it_fits_child_interest": "",
      "practice_focus": "",
      "child_safe_prompt": ""
    }
  ]
}
```

Server-side validation must reject:

- any result that does not contain exactly 3 ideas
- unsupported `topic_type`
- unsupported `topic_variant`
- duplicate idea ids
- empty titles
- titles longer than 30 CJK characters or 60 total characters
- titles or prompts with newlines
- titles or prompts that include copy-ready essay paragraphs
- ideas that decide a specific real event, person, feeling, lesson, or ending
  for the child
- completed-story patterns such as `我那天...最后...`, `我明白了...`, or similar
  title/prompt shapes that read like a finished narrative rather than an
  assignment

The new prompt must append the existing Writing Castle no-ghostwrite rule used
by the other prewriting prompts.

### User Flow

```text
Writing Castle mode shell
-> AI 出题作文
-> child enters/selects interest + backend reads grade_label
-> AI returns 3 ideas
-> child chooses one
-> backend creates a prewriting Essay
-> backend attaches scaffold snapshot from idea topic_type/topic_variant
-> existing topic analysis / material questions / cards / outline / draft flow
```

Generating topic ideas does not create an `Essay`. The `Essay` is created only
after the child selects one idea.

The selected idea should be traceable in ProductEvent payloads and in the
prewriting state as topic requirement metadata. It is a topic prompt, not essay
body content.

### API Shape

Use two endpoints:

```text
POST /api/students/{student_id}/writing-castle/ai-topic-ideas
POST /api/students/{student_id}/writing-castle/ai-topic-essay
```

The first endpoint generates ideas and creates no `Essay`. The second endpoint
accepts a selected idea payload, revalidates it, creates exactly one prewriting
`Essay`, attaches an immutable scaffold snapshot, and records the selected idea
metadata. Interest text is transient in V0.6c; it is not stored as a profile
field. ProductEvent may record whether interest input was present.

### Failure Behavior

If AI topic generation fails, times out, exceeds daily limit, or returns invalid
ideas:

- show child-friendly retry/later copy;
- keep classroom composition and direct draft available;
- do not provide hidden fallback topics;
- log the failed task in LLMCallLog.

## 9. Data And Observability

ProductEvent should record:

- `ai_topic_ideas_requested`
- `ai_topic_ideas_generated`
- `ai_topic_idea_selected`
- existing `scaffold_selected`

Payloads should include:

- `student_id`
- `essay_id` when created
- `interest_input_present`
- `grade_label`
- `idea_count`
- `selected_idea_id`
- `topic_type`
- `topic_variant`
- `scaffold_template_version`
- `topic_origin`

The scaffold's `selection_source` remains limited to `manual`, `ai_suggested`,
or `fallback`. It should continue to mean how the scaffold was selected.

Add a separate topic provenance field:

```text
topic_origin: "teacher_provided" | "ai_topic_idea" | "direct_draft"
```

For AI topic essays, store an optional `selected_topic_idea` block containing
the selected idea id, title, topic type, topic variant, and child-safe prompt.

LLMCallLog already has topic/scaffold metadata. The new AI topic task should use
the same logging path and include prompt key, prompt version, task name, final
status, fallback reason, latency, tokens, and cost where available.

Parent summary must continue to show:

- selected topic type
- selection source
- material sources
- AI body not generated

Parent summary must also show the minimum topic origin for AI topic essays:

```text
题目来源：AI 出题灵感，孩子选择
AI 未生成作文正文
```

Copy polish beyond this minimum is P1. A summary redesign is not part of V0.6c.

## 10. Error Handling

- Existing direct draft must remain available and must not be scaffold-gated.
- Existing V0.6a/V0.6b open sessions must still resume or fail closed exactly as
  they do now.
- Scaffold changes remain blocked after topic analysis, child answers, material
  cards, or outline sections exist.
- Malformed persisted scaffold snapshots must fail closed with 409.
- Unsupported future types must not be silently coerced into supported families.
- `story_summary`, `reading_response_recommendation`,
  `central_idea_reflection`, and `picture_prompt_story` remain visible
  unsupported categories unless a child/parent explicitly selects a supported
  fallback family.
- `detect_unsupported_future_type("写信")`,
  `detect_unsupported_future_type("故事新编")`, and
  `detect_unsupported_future_type("续写故事")` must return `None`.
- `detect_unsupported_future_type("缩写")`,
  `detect_unsupported_future_type("推荐一本书")`, and
  `detect_unsupported_future_type("围绕中心意思写")` must still return their
  future topic types.

## 13. V0.6c.1 Follow-Up: Essay Archive And Multi-Round Revision

Feedback from a colleague and the user's child showed that children and parents
want to see submitted first drafts, AI suggestions, second drafts, comparison
feedback, and later revision history. They also want continue-editing and delete
or hide operations.

This is important to the WenLingo learning loop because visible revision history
is evidence of growth. However, it should be its own release because it changes
history browsing, version semantics, delete policy, and parent-visible progress
data.

V0.6c records this as V0.6c.1 scope:

- essay archive/list entry;
- essay detail showing first draft, feedback, revision, comparison, and
  settlement;
- multi-round continue-revision policy;
- soft delete or hide policy;
- parent/child permissions and data-retention rules.

V0.6c must not implement these features.
