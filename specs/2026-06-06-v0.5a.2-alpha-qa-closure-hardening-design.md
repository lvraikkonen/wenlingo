# WenLingo V0.5a.2 Alpha QA Closure Hardening Design

Date: 2026-06-06
Status: Approved in brainstorming, pending written spec review

## Goal

V0.5a.2 closes the issues found during the V0.5a.1 Railway Dev manual QA run.
This is a small hardening release for the existing Alpha user foundation. It
does not add a new learning product surface or replace the current email
delivery strategy.

The release makes the Dev Alpha flow reliable under the current environment
constraint: Railway Dev does not have confirmed outbound SMTP reachability for
QQ Mail, so Dev QA uses Magic Code dev echo with code `123456`.

V0.5a.2 also adds a tightly guarded Admin Ops action for batch hard deletion of
test accounts. This action is only for Dev/QA data cleanup and must not become a
general-purpose real-family deletion workflow.

## Non-Negotiables

- Preserve real Alpha family, child, learning, invite, feedback, report, and
  event data.
- Do not advance real email delivery in this release.
- Do not add an HTTPS email provider in this release.
- Do not display or log raw Magic Codes, raw invite codes, SMTP secrets, session
  tokens, full phone numbers, child writing text, or AI feedback bodies.
- Keep Magic Code request responses generic so disabled account state is not
  disclosed before verification.
- Do not allow hard deletion of arbitrary accounts. Hard delete is limited to
  test accounts that match the V0.5a.2 allowlist.
- Hard delete requests must fail closed. If a batch contains any non-test
  account, delete nothing.
- Do not introduce user self-service deletion or a retention policy in this
  release.
- Do not productize Reading Canyon.

## Release Scope

Included:

- `/alpha/start` Magic Code verify and legacy bind state-machine fixes.
- Correct disabled-account verify message:
  `账号暂不可用，请联系邀请人。`
- Correct re-enabled-account login redirect to `/parent/children`.
- Per-account pending state for Admin Alpha enable and disable actions.
- Batch hard delete for test accounts from Admin Alpha.
- Phone binding read-only bound state with an explicit edit action.
- Dev Echo runbook updates documenting `MAGIC_CODE_DEV_ECHO=true` and code
  `123456` for Dev QA.
- A new V0.5a.2 manual QA checklist.
- Backend and frontend tests for the hardening behavior.

Excluded:

- Real SMTP delivery follow-up.
- Resend, SendGrid, or any other HTTPS email provider.
- Admin v2 filtering, export, audit dashboard, role model, or admin sessions.
- Deleting real Alpha families or any account outside the test-account allowlist.
- End-user account deletion, retention, or restore workflow.
- Database schema changes unless implementation discovers an existing field
  cannot express the approved behavior.
- Reading page product work.

## Dev Magic Code Policy

Railway Dev currently treats real Magic Code email delivery as a known blocked
environment concern. V0.5a.2 does not try to solve it.

Dev QA must use:

```text
MAGIC_CODE_DEV_ECHO=true
Magic Code: 123456
```

Operational rules:

- Set `MAGIC_CODE_DEV_ECHO=true` on `wenlingo-api`, not `wenlingo-web`.
- Set it in the exact Railway environment serving the Dev web URL.
- Redeploy or restart `wenlingo-api` after changing the variable.
- If request still waits for the SMTP timeout, assume the running API did not
  receive the variable and check service/environment selection before debugging
  frontend code.
- QQ SMTP outbound failure remains a documented known block, not a V0.5a.2
  release blocker.

The `/alpha/start` UI does not need to reveal `123456`. The QA checklist and
runbook may state the code explicitly for operators.

## Alpha Auth State Machine

V0.5a.2 clarifies `/alpha/start` login and legacy binding behavior.

### Disabled Account Verify

Magic Code request remains generic:

- A disabled account may proceed to the verification step.
- The request step must not reveal account status.

Magic Code verify must preserve backend account-state semantics:

- If verify fails because the account is disabled, show
  `账号暂不可用，请联系邀请人。`
- Do not map this case to `绑定失败，请检查验证码后再试。`
- Do not create or preserve a usable parent session for the disabled account.

### Re-Enabled Account Login

After an admin re-enables an account:

- Magic Code verify with Dev Echo code `123456` must create a valid session.
- If the verified session has a linked parent, route directly to
  `/parent/children`.
- The page must not continue into legacy bind handling after a linked-parent
  session is known.
- The UI must not show a binding failure while the session is valid.

### Legacy Bind Continuation

Legacy bind is still supported for a browser with a stored legacy parent id and
an authenticated account without a linked parent.

Rules:

- If the user is already authenticated and unlinked, `绑定并继续` calls
  `POST /api/alpha/legacy-parent-bind`.
- If Magic Code verify succeeds and returns an authenticated but unlinked
  session, the page may continue into legacy bind.
- A transient legacy bind failure may be retried without re-verifying the Magic
  Code.
- If a retry succeeds, route to `/parent/children`.
- If the backend indicates the account is already linked or the current session
  now has a parent, recover by reading session state or routing to
  `/parent/children` instead of showing a stale binding failure.

### Error Mapping

Frontend error mapping should be specific enough for QA and support:

```text
disabled account verify -> 账号暂不可用，请联系邀请人。
invalid or expired code -> 验证码错误或已过期，请重新获取。
invite unavailable -> 邀请码无效或已失效，请检查后再试。
legacy bind true failure -> 绑定失败，请稍后再试。
network or unknown request failure -> 请求失败，请稍后再试。
```

Exact non-disabled copy may continue to use current approved strings where they
already exist, but disabled-account and stale legacy-bind misreporting must be
fixed.

## Admin Account Actions

Admin Alpha remains a Lite token-gated tool using `X-Alpha-Admin-Token`.
V0.5a.2 does not introduce admin accounts, admin sessions, roles, passwords, or
OAuth.

### Enable And Disable Pending State

The Admin account list must show per-account operation feedback:

- Clicking `Disable account` immediately disables that row action.
- The clicked button text becomes `Disabling...`.
- Clicking `Enable account` immediately disables that row action.
- The clicked button text becomes `Enabling...`.
- The same account cannot be submitted twice while pending.
- On success, refresh account data and render the server-backed state.
- On failure, show `Account action failed.` and restore the row action.

Implementation may allow or block concurrent actions on different accounts, but
the UI must not let the same account action double-submit.

### Batch Hard Delete Test Accounts

Add a guarded Admin endpoint:

```text
POST /api/admin/alpha/accounts/delete-test
```

Request body:

```json
{
  "account_ids": ["account-1", "account-2"],
  "confirm": "DELETE TEST ACCOUNTS"
}
```

Rules:

- Require `X-Alpha-Admin-Token`.
- Require `Content-Type: application/json`.
- Require valid Origin/Referer when `AUTH_ALLOWED_ORIGINS` is configured.
- `account_ids` must be non-empty.
- `account_ids` maximum count is 20.
- `confirm` must exactly equal `DELETE TEST ACCOUNTS`.
- All accounts in the batch must exist.
- Every account must match the V0.5a.2 test-account allowlist.
- Protected demo/system/internal accounts must be rejected even when their email
  matches the allowlist.
- If any account fails validation, the entire request fails and deletes nothing.
- The operation must run in a transaction.
- The response may include counts and masked/test-safe identifiers, but must not
  include full email addresses.

### Test Account Allowlist

An account is eligible for hard delete only if its normalized email matches at
least one rule:

```text
domain is example.com
domain is test.local
domain is wenlingo.local
local part contains qa
local part contains test
local part contains dev
```

The local-part match is case-insensitive and applies only to the part before
`@`.

Examples that may be deleted:

```text
parent@example.com
qa-parent@real-domain.invalid
alpha-test@domain.invalid
dev-family@test.local
playwright-family@wenlingo.local
```

Examples that must be rejected:

```text
parent@gmail.com
family@qq.com
invited-family@school.example.org
demo@wenlingo.local
```

Known demo/system/internal accounts must be rejected even if their email matches
the allowlist. If future schema adds account type or internal/system flags, hard
delete must also refuse protected account types unless explicitly designed
later.

### Delete Semantics

This is a real hard delete of Dev/QA account data. It should remove dependent
rows that would otherwise leave broken foreign keys or make Admin overview fail.

For each eligible account, find linked `ParentUser` rows and their children.
Delete rows in dependency-safe order, including:

- `ParentSession` rows for the account.
- `AuthMagicCode` rows for the account email.
- Child-linked learning and generated content rows:
  - `Assessment`
  - `SentenceTraining`
  - `EssayVersion`
  - `Essay`
  - `ReadingSession`
  - `GameEvent`
  - `Report`
  - `AbilityHistory`
  - `AbilityProfile`
  - `LLMCallLog`
- Parent/child feedback and event rows:
  - `FeedbackReaction`
  - `ParentFeedback`
  - `ProductEvent`
- `StudentProfile` rows.
- Consumed `AlphaInviteCode` rows linked to the deleted test parent.
- `ParentUser` rows.
- `ParentAccount` rows.

The implementation must account for cross-references such as:

- `Assessment.sentence_training_id`
- `Assessment.essay_id`
- `EssayVersion.essay_id`
- `EssayVersion.llm_call_log_id`
- `ProductEvent.parent_id`
- `ProductEvent.student_id`
- `ProductEvent.invite_code_id`
- `AlphaInviteCode.consumed_by_parent_id`

The exact delete order may be adjusted during implementation to satisfy SQLite
and PostgreSQL constraints, but tests must prove the operation leaves no broken
Admin Alpha overview or account list state.

### Consumed Invite Handling

When a test account's linked parent consumed an invite, delete that consumed
invite record as part of the test data cleanup. Unconsumed invites and invites
consumed by other parents are not affected.

### Delete Audit

Because `ProductEvent` rows for the target test family are deleted, the delete
operation must leave an audit signal outside those rows. A privacy-safe server
log is sufficient for V0.5a.2.

Allowed audit fields:

```text
action
status
requested_count
deleted_count
target_account_ids
masked_email_values
rejected_reason
```

Disallowed audit fields:

```text
full email
raw invite code
Magic Code
SMTP password
session token
phone number
child writing text
AI feedback body
```

### Admin Delete UI

The Admin UI should expose deletion as a clearly dangerous test cleanup action:

- Allow selecting accounts from the account list.
- Only selected accounts are submitted.
- Show a warning that deletion is permanent and only works for test accounts.
- Require typing `DELETE TEST ACCOUNTS` before enabling the delete button.
- Disable the delete button while the request is pending.
- On success, clear selection, refresh overview and accounts, and show a concise
  success message.
- On rejection, show a clear error and leave data unchanged.

The UI does not need advanced filters in V0.5a.2.

## Phone Binding UX

Phone remains optional in V0.5a.2 and is not used for SMS login.

### Unbound State

If `account.phone_bound=false`:

- Show the `手机号（可选）` input.
- Keep helper copy: `可选填写，V0.5a 不用于短信登录。`
- Show `保存手机号`.
- While saving, disable the button and show `保存中...`.

### Bound State

If `account.phone_bound=true` or a save succeeds:

- Hide the phone input by default.
- Hide `保存手机号` by default.
- Show `已绑定 <masked phone>`.
- Show `修改手机号`.

Clicking `修改手机号`:

- Shows an empty phone input.
- Shows `保存手机号`.
- Shows `取消`.
- Does not display the raw phone number.

Saving a new phone:

- Calls the existing phone binding API.
- Updates the masked phone from the response.
- Returns to the read-only bound state.
- Clears the edit input.

Canceling:

- Returns to the read-only bound state.
- Clears unsaved input and errors.

### Phone Error Handling

- Save failure shows `手机号保存失败，请稍后再试。`
- Save failure keeps the edit form open.
- Save failure does not clear the phone value being edited.
- The UI never shows a raw bound phone number after save.

## Test Plan

Backend tests:

- Magic Code verify for disabled account returns the expected disabled-account
  failure detail and does not create a usable session.
- `POST /api/admin/alpha/accounts/delete-test` requires admin token.
- Delete-test endpoint requires JSON body and Origin/Referer guard when
  configured.
- Delete-test endpoint rejects wrong confirmation text.
- Delete-test endpoint rejects empty list and more than 20 ids.
- Delete-test endpoint rejects any non-test account and deletes none.
- Delete-test endpoint deletes an allowlisted test account and associated
  dependent rows.
- Delete-test endpoint deletes consumed invite rows only for deleted test
  parents.
- Admin overview and account list still load after deletion.

Frontend tests:

- `/alpha/start` maps disabled verify to
  `账号暂不可用，请联系邀请人。`
- `/alpha/start` routes a re-enabled linked-parent session to
  `/parent/children` without stale bind failure.
- Legacy bind transient failure can be retried without another Magic Code
  verify.
- Admin enable/disable buttons show `Enabling...` and `Disabling...` pending
  states.
- Admin delete-test UI requires selection and confirmation.
- Admin delete-test UI refreshes data on success.
- Admin delete-test UI shows rejection errors without clearing real data.
- Phone unbound flow can bind a phone.
- Phone bound initial state hides the input and shows `修改手机号`.
- Phone edit flow can save a replacement phone and return to read-only state.
- Phone save failure keeps the edit form open.

Manual verification:

- Run the V0.5a.2 manual QA checklist in Railway Dev with Dev Echo enabled.
- Treat real email arrival as known blocked/skipped unless Railway SMTP
  reachability changes outside this release.

## Rollout

1. Merge and deploy V0.5a.2 to Railway Dev.
2. Set `MAGIC_CODE_DEV_ECHO=true` on `wenlingo-api`.
3. Redeploy or restart `wenlingo-api`.
4. Run backend and frontend automated tests.
5. Run V0.5a.2 manual QA.
6. Use Admin hard delete only for accounts matching the test-account allowlist.
7. Keep any real-email QA item marked blocked/skipped until an email provider or
   Railway SMTP reachability is addressed in a later release.

## Open Decisions

None. The brainstorming decisions for V0.5a.2 are:

- Real email delivery is not part of this release.
- Dev QA uses Magic Code Dev Echo and code `123456`.
- Phone bound state hides the input until the user chooses `修改手机号`.
- Admin hard delete is included, but only for allowlisted test accounts.
- Hard delete removes consumed invite rows linked to deleted test parents.
