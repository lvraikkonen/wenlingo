## Goal

V0.5c.2 is an Alpha hardening release for authentication runtime boundaries and
session operations.

The release goal is:

```text
Remove MVP demo runtime bypasses and add operator-visible ParentSession controls
before broader external Alpha usage.
```

V0.5c.1 stabilized same-origin auth, auth failure UX, localStorage identity
cleanup Step 3, and external Alpha login behavior. V0.5c.2 should now stop
carrying the MVP demo flow in production/runtime paths and give operators enough
session visibility to support families without adding a new scheduler or a new
learning feature.

## Non-Goals

V0.5c.2 must not include:

- New AI learning task types.
- V0.6 Writing Castle prompt content.
- Streaming or SSE.
- Dynamic model routing, A/B testing, or policy engines.
- New frontend framework, backend framework, scheduler, or worker process.
- Automatic single-account session limits.
- Admin charts, exports, filters, scheduled reports, or advanced analytics.
- A full authenticated rewrite of the old MVP browser E2E flow.
- Product direction changes to onboarding, child creation, Sentence Workshop,
  Writing Castle, or parent progress views.

## Release Boundary

V0.5c.2 ships three scoped changes together because they protect the same Alpha
runtime boundary.

### P0: Remove MVP Demo Runtime Bypasses

Production/runtime must no longer include an unauthenticated MVP demo family
entry point.

Remove or close:

- `/api/auth/demo-login`.
- Web client `demoLogin()` calls.
- Home page behavior that logs into a seeded demo family and links directly to
  child dashboards.
- `FamilyTopbar` fallback that calls demo login after 401, 404, or empty Alpha
  children responses.
- Browser logic that uses demo parent/student ids or `NEXT_PUBLIC_DEMO_*`
  values as runtime identity fallbacks.
- Runtime use of `wenlingo_alpha_parent_id` to decide the current parent.
- Any API path that bypasses `ParentSession` by falling back to demo parent id
  or demo child id.

Preserve product onboarding:

- Create family.
- Create child.
- Introductory child work such as assessment, Sentence Workshop, Writing Castle,
  and parent progress views.

These are not MVP demo flow. They remain product flows and must use
session-aware APIs.

### P0: Add Session Operations

Operators need enough session visibility to support families and investigate
risk without touching raw tokens.

Add:

- Active session detail view for a parent account in Admin Alpha.
- Manual revoke for one active session.
- Manual revoke for all active sessions on one account.
- Idempotent cleanup command for expired and revoked sessions.

V0.5c.2 does not enforce automatic session count limits. Admin may see and
revoke sessions, but a parent is not blocked from logging in because of multiple
active sessions.

### P1: Convert Demo Assets To Dev/Test Or Archive

MVP demo data remains useful for historical reference and selected tests, but it
must not be part of production/runtime navigation.

Keep only as explicitly dev/test scoped:

- Demo seed data, if still needed by unit or integration tests.
- Sample child fixtures.
- Local deterministic AI fallback fixtures.
- Playwright Alpha test account seed guarded by disposable database checks.
- Story/demo content used for UI development.

Archive MVP product knowledge:

- `docs/archive/mvp-demo-flow.md`.
- `docs/archive/mvp-learnings.md`.

## Required Implementation Order

The implementation plan must not start by deleting frontend demo flow. Existing
tests still depend on `/api/auth/demo-login` and seeded demo children, so deleting
the browser path first would make failures hard to diagnose.

Use this order:

1. Add or consolidate authenticated test fixtures for `ParentAccount`,
   `ParentSession`, linked `ParentUser`, and `StudentProfile`.
2. Add session operations service helpers, cleanup command tests, and Admin
   session API tests.
3. Migrate backend and frontend tests away from `demoLogin()` and
   `/api/auth/demo-login` while the old route still exists.
4. Remove `/api/auth/demo-login` and verify the negative route test.
5. Remove web `demoLogin()` and demo fallback UI paths.
6. Archive MVP E2E/history and update deployment, env, and QA docs.

This sequence keeps each failure attributable to one boundary change.

## Architecture

The API remains the owner of authentication, session validation, AI execution,
daily limits, and persistence. The Web app renders session-aware product flows
and calls the API through the same-origin path introduced in V0.5c.1.

```text
Browser
-> Web app /api/*
-> API service
-> ParentSession validation
-> Alpha product data
```

There is no demo runtime side path after V0.5c.2.

```text
Before:
unauthenticated browser -> /api/auth/demo-login -> seeded parent p1 -> child dashboard

After:
unauthenticated browser -> /alpha/start -> Magic Code session -> linked parent -> child dashboard
```

Session cleanup is an operator command, not an application request side effect.

```text
operator or Railway schedule
-> python -m app.ops.cleanup_parent_sessions --dry-run
-> python -m app.ops.cleanup_parent_sessions --execute ...
-> delete expired/revoked rows outside the retention window
```

Admin session controls reuse the existing Admin Alpha token and state-change
protections.

## ParentSession Lifecycle

Keep the existing `ParentSession` model:

```text
id
account_id
token_hash
created_at
expires_at
last_seen_at
revoked_at
```

No new session columns are required in V0.5c.2. The implementation should not
store raw session tokens, raw IP addresses, or full user agent strings. If future
support work needs device labeling or IP metadata, that should be designed as a
separate privacy-reviewed change.

Session validation remains:

1. Read HttpOnly session cookie.
2. Hash token with auth pepper.
3. Look up `ParentSession.token_hash`.
4. Reject missing, revoked, expired, or disabled-account sessions.
5. Touch `last_seen_at` using the existing throttle.
6. Return masked account and linked parent payload.

## Admin Session APIs

Add routes under the existing Admin Alpha account surface:

```text
GET  /api/admin/alpha/accounts/{account_id}/sessions
POST /api/admin/alpha/accounts/{account_id}/sessions/{session_id}/revoke
POST /api/admin/alpha/accounts/{account_id}/sessions/revoke-all
```

### List Sessions

`GET /api/admin/alpha/accounts/{account_id}/sessions` returns active sessions
only by default.

Response shape:

```json
{
  "account": {
    "account_id": "acct_123",
    "email_masked": "p***@example.com",
    "status": "active"
  },
  "sessions": [
    {
      "session_id": "sess_123",
      "created_at": "2026-06-19T10:00:00+00:00",
      "last_seen_at": "2026-06-19T11:00:00+00:00",
      "expires_at": "2026-07-19T10:00:00+00:00",
      "revoked_at": null
    }
  ]
}
```

Do not return `token_hash`, raw cookies, Magic Codes, full email addresses, full
phone numbers, or child writing content.

The active-session definition must match the existing account list count:

```text
revoked_at is null and expires_at > now
```

Move this predicate into a shared helper so account list and session detail stay
consistent.

Optional later, outside V0.5c.2: allow inactive or recently revoked sessions to
be included with an explicit query parameter such as `include_inactive=true`.
Do not add filters or inactive-session UI in this release.

### Revoke One Session

`POST /api/admin/alpha/accounts/{account_id}/sessions/{session_id}/revoke`
sets `revoked_at=now` if the session belongs to the account and is still active.

Behavior:

- Missing account returns 404.
- Missing session or session owned by another account returns 404.
- Already revoked or expired session returns a successful no-op payload with
  `revoked=false`.
- Active session returns `revoked=true`.

### Revoke All Active Sessions

`POST /api/admin/alpha/accounts/{account_id}/sessions/revoke-all` revokes every
active session for the account and returns `revoked_session_count`.

Behavior:

- Missing account returns 404.
- No active sessions returns count 0.
- The operation is idempotent.

State-changing routes must use the existing `require_alpha_admin_state_change`
dependency.

Admin UI must show a confirmation message before revoke-all:

```text
这会让该家长账号的所有设备重新登录。
```

No new permission system is required in V0.5c.2, but the UI should make the
impact clear before the operator submits the action.

## Session Cleanup Command

Add `app.ops.cleanup_parent_sessions`.

The command deletes old session rows that can no longer authenticate anyone:

- Revoked sessions where `revoked_at <= now - revoked_retention_days`.
- Expired sessions where `expires_at <= now - expired_retention_days`.

CLI behavior:

```text
python -m app.ops.cleanup_parent_sessions --dry-run
python -m app.ops.cleanup_parent_sessions --execute --revoked-retention-days 30 --expired-retention-days 30
```

Requirements:

- Default mode is dry-run.
- `--execute` is required to delete rows.
- Retention values must be zero or positive.
- Output includes scanned count, delete count, reason counts, and cutoff times.
- Output must not include token hashes or raw session cookies.
- Running the command twice with the same options is safe.
- Production use should be documented as a Railway schedule or manual ops
  command. V0.5c.2 does not add an in-app scheduler.

Recommended Alpha retention:

```text
revoked-retention-days = 30
expired-retention-days = 30
```

Do not recommend 0-day deletion for Alpha. Operators may need a short recent
history to investigate support issues after a session expires or is revoked.

## MVP Demo Runtime Removal

The MVP demo route and browser flow are removed from active runtime.

### API

Remove `/api/auth/demo-login` from `apps/api/app/api/routes/auth.py`.

Tests that currently call the route must be rewritten to use explicit fixtures:

- Create `ParentAccount`.
- Create `ParentSession`.
- Create linked `ParentUser`.
- Create `StudentProfile`.
- Send the session cookie or call API helpers through authenticated clients.

`seed_demo_data()` must not be called by runtime auth routes.

`seed_demo_data()` must not be imported by production API route modules. Tests
may import it or a future dev seed helper explicitly, but production runtime
paths must not depend on the demo seed module.

### Web

Remove `demoLogin()` from `apps/web/src/lib/api.ts`.

Update the home page so it no longer logs into a seeded family. It should either
link directly to `/alpha/start` or render the existing Alpha entry as the primary
path.

Update `FamilyTopbar`:

- For authenticated Alpha children, show session-aware navigation.
- For 401, surface login recovery or rely on page-level redirect to
  `/alpha/start`.
- For 404 or empty children, show real empty state or link back to
  `/parent/children`.
- Do not call demo login as a fallback.

### localStorage Identity

Runtime pages must not use `wenlingo_alpha_parent_id` as the current parent
identity. If `alphaParent.ts` still has consumers after V0.5c.1, keep only
legacy cleanup or migration helpers. If it has no consumers, remove it.

## Dev/Test Fixtures

Demo-like data may remain only in explicitly non-production contexts.

Preferred locations:

- `apps/api/app/db/seed_dev.py` for development seed data.
- `apps/api/app/db/seed_playwright_alpha.py` for Playwright Alpha seed data.
- `apps/api/tests/*` helpers for API fixtures.
- `apps/web/tests/*` fixtures for component and client tests.
- `docs/archive/` for historical MVP notes.

The existing Playwright Alpha seed keeps its safety model:

- Requires `PLAYWRIGHT_ALPHA_SEED=1`.
- Refuses non-disposable database targets.
- Allows only controlled local SQLite or local test PostgreSQL targets.

V0.5c.2 should not add a production `DEMO_MODE_ENABLED` fallback because the
selected direction is to delete the runtime demo route, not hide it behind a
flag.

## Error Handling

After V0.5c.2, missing auth must not silently turn into demo access.

Rules:

- Old `/api/auth/demo-login` returns 404 because the route is gone.
- Unauthenticated Alpha API access returns 401 as today.
- Web pages that require auth should redirect to `/alpha/start` or show a clear
  login recovery state.
- Empty family state means the account has no children yet; it does not create
  demo children.
- Admin session APIs return 404 for missing accounts and missing sessions.
- Revoke operations are idempotent for already inactive sessions.
- Cleanup command failures should exit non-zero and print a concise reason.

## Testing

### API Tests

Add or update tests for:

- `/api/auth/demo-login` no longer exists.
- Parent session cleanup dry-run scans but does not delete rows.
- Parent session cleanup execute deletes eligible revoked and expired rows.
- Cleanup keeps active sessions and recently revoked/expired sessions inside
  retention.
- Admin account session list returns active sessions without token hashes.
- Admin revoke-one revokes only sessions belonging to that account.
- Admin revoke-all revokes all active sessions for one account.
- Existing disabled-account behavior still revokes active sessions.
- Learning APIs that previously depended on `seed_demo_data()` use explicit
  authenticated fixtures where auth is part of the behavior under test.

### Web Tests

Add or update tests for:

- Home page no longer imports or calls `demoLogin()`.
- Home page points users to Alpha login/start.
- `FamilyTopbar` does not call demo login on 401, 404, or empty children.
- Auth recovery or parent hub links are visible where appropriate.
- `wenlingo_alpha_parent_id` is not written or read as runtime identity.

### E2E And QA

Archive `apps/web/e2e/mvp.spec.ts` so `pnpm e2e` no longer discovers it. Because
the current Playwright config uses `testDir: "./e2e"`, do not keep the archived
file under `apps/web/e2e` with a `.spec.ts` suffix. Either move the historical
notes into `docs/archive/mvp-demo-flow.md` or rename the preserved source to a
non-test artifact such as `docs/archive/mvp-e2e-spec.ts.txt`. Do not rewrite the
entire MVP browser loop into an authenticated Alpha E2E in V0.5c.2.

Keep or add Alpha E2E coverage for:

- Magic Code login.
- Create family.
- Create child.
- Reach core child and parent pages through session-aware navigation.

Create `qa/2026-06-19-v0.5c.2-alpha-auth-runtime-hardening-checklist.md` with
manual checks for:

- Old demo login route is unavailable.
- Fresh browser login works.
- Unauthenticated child/dashboard access does not show demo data.

## Acceptance Criteria

V0.5c.2 is complete when:

- Production/runtime has no `/api/auth/demo-login` route.
- Web runtime has no `demoLogin()` client and no demo fallback navigation.
- Core Alpha pages rely on `ParentSession`, not localStorage identity.
- Unauthenticated direct access to child dashboard or task pages never renders
  seeded demo data.
- Authenticated parents cannot access another family's child dashboard or task
  pages.
- Admin can list active sessions for an account without exposing token hashes.
- Admin can revoke one session or all active sessions for an account.
- Session cleanup command supports dry-run and execute modes and is idempotent.
- Demo seed and sample data are limited to dev/test/archive contexts.
- MVP browser demo flow is archived, not active runtime behavior.
- Relevant unit and integration tests pass.
- Any skipped E2E or manual checks are documented in the v0.5c.2 QA checklist.

## Open Follow-Up After V0.5c.2

These are intentionally deferred:

- Optional soft active-session limit per account.
- Device labels or privacy-reviewed session metadata.
- Including inactive or recently revoked sessions in Admin through an explicit
  query parameter.
- Full authenticated Alpha E2E rewrite of the old MVP learning loop.
- In-app scheduled cleanup worker.
- Advanced Admin session filtering or exports.
