## Fix Now — F1: Stuck `completing_comparison` attempt has no recovery path

**Severity:** P0 availability bug (the only real bug found; the rest are polish).

**Problem:** `completing_comparison` (set atomically by
`_claim_pending_attempt_for_completion`, `essays.py:207`) is treated as active by
`_active_attempt_for_target` (`ACTIVE_REVISION_ATTEMPT_STATUSES`, `essays.py:53`),
but **both** stale sweepers only handle `pending_comparison`:

- global sweeper `mark_stale_pending_attempts_failed` (`essay_archive.py:84`)
- targeted sweeper `_mark_stale_pending_attempt_failed` (`essays.py:169`)

If the process dies between the atomic claim and the final completion commit, the
attempt is stuck in `completing_comparison` forever: never swept, rejected by retry
(`essays.py:691` "not retryable"), and every future submit/retry for that round
returns a permanent 202. It is a permanent soft-lock for that essay's next round.

**Fix — touch both sweepers:**

```python
# essay_archive.py — mark_stale_pending_attempts_failed
attempts = session.exec(
    select(EssayRevisionAttempt).where(
        EssayRevisionAttempt.status.in_(("pending_comparison", "completing_comparison")),
        EssayRevisionAttempt.updated_at < cutoff,
    )
).all()
```

```python
# essays.py — _mark_stale_pending_attempt_failed
def _mark_stale_pending_attempt_failed(session, attempt, *, now) -> bool:
    if attempt.status not in {"pending_comparison", COMPLETING_COMPARISON_STATUS}:
        return False
    if not _attempt_is_stale(attempt, now):
        return False
    attempt.status = "comparison_failed"
    attempt.error_code = "attempt_timeout"
    attempt.updated_at = now
    session.add(attempt)
    session.commit()
    return True
```

**Why this is safe:**
- The `REVISION_ATTEMPT_TIMEOUT_SECONDS = 180` threshold means a healthy in-flight
  completion (LLM already done; just version creation + commit) is never swept.
- On the stuck essay's next submit, the global sweeper (`essays.py:465`) self-heals
  the stuck round before the target-round reservation check; on the next retry, the
  targeted sweeper does the same.
- `submitted_content` was committed at reservation time (`essays.py:510`), so the
  swept attempt retains its content and becomes retryable.
- The existing completion-path guards (`_completion_attempt_conflict_response`,
  `_claim_pending_attempt_for_completion`, partial unique index) already handle the
  theoretical sweeper-vs-completion race.

**Error code:** use `attempt_timeout` for consistency (same 180s staleness rule). A
distinct `completion_timeout` code is acceptable if you want finer telemetry, but it
must remain retryable and preserve content.

**Decision needed (pick one, document it):**
- [x] Align to spec: return 409 + latest continue payload for completed-owner different-key; or

lookup and the reservation `IntegrityError` fallback. Same-key completed replay still
returns the completed result.
