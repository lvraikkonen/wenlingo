# WenLingo V0.4.1 Alpha Enablement Task

Date: 2026-05-25  
Status: Proposed  
Purpose: Prepare WenLingo for 3–5 invited-family Alpha usage and begin collecting real usage data.

## 1. Background

V0.4 Minimal Assessment Entry has been implemented and manually QAed.

V0.4 successfully created the first real learning loop:

```text
new/default child
→ 3–5 minute entry assessment
→ fixed sentence upgrade
→ short writing task
→ real SentenceTraining artifact
→ real Essay / EssayVersion artifact
→ AbilityHistory updates
→ first ability sketch
→ Dashboard recommendation changes from assessment to personalized tasks
```

This is a meaningful step toward the original PRD learning data flywheel:

```text
lightweight assessment
→ ability profile
→ personalized tasks
→ sentence / essay / reading practice
→ AI feedback
→ gamified growth
→ parent insight
→ next recommendation
```

The PRD defines the product as a family-facing learning system where parents create children, children complete practice, and parents understand growth over time.

However, the V0.4 post-implementation review found a critical Alpha readiness gap:

```text
There is no real child creation UI/API.
There is no clear parent-facing vs child-facing usage model.
The current product still behaves more like a demo tool than an inviteable family Alpha product.
```

This is not a V0.4 assessment bug.
It is a product entry / Alpha enablement gap.

## 2. V0.4.1 Goal

V0.4.1 is not a new learning feature release.

The goal is:

> Allow 3–5 invited families to start using WenLingo through a controlled Alpha flow, while the product collects real usage data, child reactions, parent feedback, and learning artifacts.

In other words:

```text
invited parent
→ creates child profile
→ child enters dashboard
→ child completes V0.4 assessment
→ system records learning data
→ parent sees minimal growth summary
→ child/parent provide lightweight feedback
→ developer can observe Alpha usage
```

## 3. Product Positioning

V0.4.1 should be treated as:

```text
Inviteable Family Alpha Entry
```

Not:

```text
public launch
full MVP
complete parent platform
complete auth system
complete reading/writing curriculum
```

The intended audience is:

```text
3–5 invited families
children in elementary school
parent consent required
manual monitoring by developer
no public registration
no payment
no leaderboard
no social sharing
```

## 4. Deployment and Distribution Strategy

### 4.1 Deployment Model

Do not distribute local programs, Docker packages, desktop apps, or scripts to families.

Use a hosted web application.

Recommended model:

```text
Browser
→ Next.js Web App
→ FastAPI Backend
→ PostgreSQL
→ LLM Provider
```

The Alpha should be accessible through a stable web URL, for example:

```text
https://alpha.wenlingo.app
```

or an equivalent temporary Alpha URL.

### 4.2 Why Web Deployment

For WenLingo, cloud/web deployment is required because the product depends on:

- centralized learning data;
- centralized LLM key management;
- consistent product behavior;
- ability profile history;
- parent/child data linkage;
- developer monitoring;
- fast bug fixing;
- real usage data collection.

Local distribution would create problems:

| Distribution Method         | Problem                                            |
| --------------------------- | -------------------------------------------------- |
| Local Docker                | Too hard for non-technical parents, data scattered |
| Desktop app                 | Updates and telemetry are difficult                |
| Running on developer laptop | Unstable and not suitable for families             |
| Public open registration    | Too early and risky for child data                 |

### 4.3 Environments

V0.4.1 should define at least:

```text
local      developer environment
staging    internal verification
alpha      invited-family Alpha
```

Alpha environment must not share a disposable local SQLite database.

For Alpha, use persistent PostgreSQL.

### 4.4 Minimum Alpha Deployment Requirements

V0.4.1 should ensure:

- app is available through HTTPS;
- frontend can reach backend reliably;
- backend uses persistent database;
- environment variables are not exposed;
- LLM provider keys are server-side only;
- database migrations can be applied safely;
- basic error logging exists;
- data backup / export / deletion process exists, even if manual;
- public registration is disabled or gated.

## 5. Invitation Model

### 5.1 Do Not Open Public Registration

V0.4.1 should not implement public self-service registration.

Use invited Alpha only.

### 5.2 Minimum Invitation Options

Acceptable V0.4.1 approaches, from simplest to more complete:

#### Option A: Manual Alpha Link

Developer manually creates an Alpha parent/family entry and sends a private link.

Example:

```text
https://alpha.wenlingo.app/alpha/family/{familyId}
```

This is acceptable for owner-child testing but weaker for colleague-family Alpha.

#### Option B: Invite Code

Preferred V0.4.1 approach.

Add minimal invite code support:

```text
invite_codes
- id
- code
- label
- max_uses
- used_count
- expires_at
- created_at
```

Example invitation URL:

```text
https://alpha.wenlingo.app/invite/ABC123
```

Parent flow:

```text
open invite link
→ accept Alpha notice
→ create parent display name
→ create child profile
→ enter parent home / child dashboard
```

### 5.3 Invite Code Acceptance Criteria

- A valid invite code allows one family to enter Alpha.
- Expired or invalid invite code shows a friendly error.
- Invite code usage is recorded.
- Public unauthenticated child creation is not allowed.
- For V0.4.1, full auth may be deferred if access remains invite-gated and manually monitored.

## 6. Parent / Child Usage Model

The current UI does not clearly distinguish parent usage from child usage.

V0.4.1 must introduce a lightweight parent/child mental model.

### 6.1 Parent-Facing Area

Parent area should support:

```text
view child profiles
create child profile
enter child learning space
view minimal child summary
submit parent feedback
```

Minimum pages:

```text
/parent
/parent/children
/parent/children/new
/parent/children/[studentId]/summary
```

### 6.2 Child-Facing Area

Child area should support:

```text
view dashboard
start assessment
complete sentence/writing tasks
see ability sketch
return to dashboard
submit child reaction
```

Minimum pages:

```text
/children/[studentId]/dashboard
/children/[studentId]/assessment
```

Existing sentence / essay pages may remain as-is if already functional.

### 6.3 Navigation Principle

The parent should see management and summary language.

The child should see learning adventure language.

Example:

Parent copy:

```text
管理孩子档案
查看最近练习
查看能力变化
```

Child copy:

```text
开始今日挑战
看看我的能力草图
继续句子工坊
```

This does not require a complete permission model yet, but the UI should no longer feel like one shared demo navigation for everyone.

## 7. Child Creation

### 7.1 Child Creation API

Add or expose an API to create a child profile.

Minimum input:

```json
{
  "nickname": "小星",
  "grade": 4
}
```

Optional input:

```json
{
  "avatar": "star"
}
```

Do not collect:

- real full name;
- school name;
- address;
- phone number;
- photo;
- birthdate.

### 7.2 Child Creation Behavior

On successful child creation:

- create `StudentProfile`;
- create default `AbilityProfile`;
- child starts from default ability values;
- Dashboard should recommend assessment;
- parent can enter child dashboard.

### 7.3 Child Creation UI

Add a simple child creation page:

```text
孩子怎么称呼？
孩子现在几年级？
[创建孩子档案]
```

After creation:

```text
create child
→ redirect to /children/[studentId]/dashboard
```

or:

```text
create child
→ show child card
→ button: 进入语文冒险
```

## 8. Minimal Parent Summary

The PRD expects parents to understand what the child practiced, where the child improved, and what should happen next.

V0.4.1 does not need a full weekly report.

Instead, implement a minimal parent summary using existing real data.

### 8.1 Parent Summary Should Read

Use available data:

- `Assessment`;
- `SentenceTraining`;
- `Essay`;
- `EssayVersion`;
- `AbilityHistory`;
- `GameEvent`;
- current `AbilityProfile`.

### 8.2 Parent Summary Content

Minimum summary:

```text
孩子最近完成了：
- 入门小试炼 1 次
- 句子训练 N 次
- 小写作 N 次

能力变化：
- 表达力 +X
- 观察力 +Y
- 结构力 +Z

最近亮点：
孩子把一个普通句子写得更具体了。

下一步建议：
继续练习“把句子写具体”。
```

### 8.3 Parent Summary Acceptance Criteria

- Parent can see whether the child completed assessment.
- Parent can see recent training count.
- Parent can see ability changes from real AbilityHistory.
- Parent can see at least one child-friendly or parent-readable highlight.
- Parent can return to child dashboard.

## 10. Feedback Collection

### 10.1 Child Feedback

After assessment or task completion, collect one lightweight child reaction.

Question:

```text
今天这个任务感觉怎么样？
```

Options:

```text
😄 很有意思
🙂 还可以
😐 有点难
😣 不想做
```

Optional free text:

```text
你想对 AI 教练说一句话吗？
```

Table:

```text
child_task_feedback
- id
- student_id
- task_type
- source_id
- reaction
- comment nullable
- created_at
```

### 10.2 Parent Feedback

On parent summary page, collect one parent feedback question.

Question:

```text
这次反馈对你了解孩子有帮助吗？
```

Options:

```text
有帮助
一般
没帮助
```

Optional follow-up:

```text
你最想看到什么？
- 孩子哪里进步了
- 下一步怎么练
- 修改前后对比
- AI 反馈是否准确
- 任务难度是否合适
```

Table:

```text
parent_feedback
- id
- parent_user_id nullable
- student_id
- source_type
- source_id
- usefulness
- desired_next_info_json nullable
- comment nullable
- created_at
```

### 10.3 Feedback Acceptance Criteria

- Child can submit reaction without typing.
- Parent can submit feedback from summary page.
- Feedback is linked to student and source.
- Feedback does not interrupt the learning flow.
- Feedback can be queried for Alpha review.

## 11. Alpha Privacy and Safety Requirements

Because this product is for children, V0.4.1 must follow data minimization.

### 11.1 Required Alpha Notice

Before creating a child profile, show an Alpha notice.

Suggested copy:

```text
这是小文星球 WenLingo 的小范围 Alpha 内测。

系统会保存孩子的昵称、年级、句子改写、短写作内容、AI 反馈、能力变化和使用记录，用于生成学习反馈和改进产品。

请不要填写孩子的真实姓名、学校、住址、电话或其他敏感信息。

继续使用表示家长同意参与本次内测。
```

### 11.2 Data Minimization

Do not collect:

```text
child real full name
school
address
phone
photo
precise birthdate
social profile
```

### 11.3 LLM Disclosure

Alpha notice should explain that child writing may be sent to AI services to generate feedback.

### 11.4 Data Deletion

For V0.4.1, a manual deletion script/process is acceptable.

Minimum requirement:

```text
Given a student_id or family_id, developer can delete or export Alpha data on parent request.
```

## 15. Acceptance Criteria

### 15.1 Family Alpha Entry

- An invited parent-like user can open Alpha entry.
- The user can accept Alpha notice.
- The user can create a child profile.
- The new child gets a default AbilityProfile.
- The child appears in parent children list.
- The parent can enter the child dashboard.

### 15.2 V0.4 Assessment Continuity

- New child dashboard recommends assessment.
- Child can complete V0.4 assessment.
- Assessment creates required artifacts.
- Assessment updates AbilityHistory.
- Assessment returns ability sketch.
- Returning to dashboard no longer recommends assessment.

### 15.3 Parent Insight

- Parent can view minimal summary.
- Summary reads real data, not demo/static data.
- Summary shows assessment completion and ability changes.
- Parent can submit usefulness feedback.

### 15.4 Child Feedback

- Child can submit reaction after assessment/task.
- Reaction is saved.
- Reaction can be queried.

### 15.5 Data Collection

- Core funnel events are recorded.
- Assessment failure events are recorded.
- LLM fallback/error events are recorded.
- Developer can inspect Alpha usage.

### 15.6 Safety

- No child real name required.
- No school/address/phone/photo required.
- Alpha notice is shown before child creation.
- LLM disclosure exists.
- Data deletion/export process is documented.

### 15.7 Regression

- Existing demo family behavior does not break.
- Existing V0.4 assessment tests pass.
- Existing dashboard behavior remains valid.
- Demo children and reports remain stable unless intentionally updated.

## 18. V0.4.1 Release Decision

V0.4.1 can be considered ready for 3–5 family Alpha only when:

```text
A real invited parent can create a child without developer database work.
A real child can naturally reach and complete assessment.
A real parent can see a minimal summary.
Child and parent feedback can be collected.
Developer can inspect usage events.
Data safety notice and deletion/export process exist.
```

## 19. Recommended Next Milestone After V0.4.1

After V0.4.1, do not immediately expand to Reading Canyon unless Alpha data shows writing flow is already strong.

Recommended V0.5:

```text
Writing Practice / Revision Loop
```

Reason:

- V0.4 already creates writing-side data.
- Parent value is strongest when they can see before/after improvement.
- Revision power currently has limited real signal.
- A second-draft loop directly supports the PRD’s writing growth promise.

Possible V0.5 loop:

```text
initial draft
→ AI gives one small revision task
→ child submits second draft
→ AI compares before/after
→ revision/expression/observation ability changes
→ parent sees best improvement case
```

Reading Canyon can follow as V0.6.
