# WenLingo V0.5a.1 Alpha Dev Hardening Design

Date: 2026-06-04
Status: Approved in brainstorming, pending written spec review

## Goal

V0.5a.1 hardens the V0.5a Alpha user foundation before V0.5b work begins. The
release makes the Railway Dev environment operable for real manual QA: admins
can manage low-risk Alpha access operations, Magic Code email can be delivered
through real SMTP, and the report page regression found during manual QA is
fixed.

This is not a product-feature release. It does not expand Reading Canyon, create
a full admin back office, or change the learning loop.

## Non-Negotiables

- Preserve all parent, child, learning, feedback, summary, invite, and product
  event data.
- Do not hard-delete accounts or families from the admin UI.
- Do not let admin create families, children, or accounts directly.
- Do not store raw invite codes or raw Magic Codes.
- Do not show or log Magic Codes, SMTP passwords, child writing text, or AI
  feedback bodies.
- Do not revoke consumed invite codes. Use account disablement to stop an
  already-created family from logging in.
- Keep Reading Canyon out of scope except for documenting that the current page
  remains a placeholder.

## Release Scope

Included:

- Admin invite generation.
- Admin revocation of unused invite codes.
- Admin account listing.
- Admin account disable and re-enable.
- Session revocation when an account is disabled.
- Real Magic Code delivery through a generic SMTP sender.
- QQ Mail SMTP configuration for Railway Dev.
- Report page/API regression fix so the QA report path does not return a server
  error.
- QA checklist and deploy runbook updates.
- Backend and frontend tests for the hardening behavior.

Excluded:

- Admin direct account, family, or child creation.
- Hard deletion of account, family, child, or learning rows.
- User self-service deletion or retention workflow.
- Resend production domain setup.
- Full admin v2 features such as filters, exports, detailed audit dashboards,
  invite bulk operations beyond creation count, or support-case workflows.
- Reading page productization.

## Admin Operations

Admin Alpha continues to use `X-Alpha-Admin-Token`. V0.5a.1 does not introduce
admin sessions, roles, passwords, or OAuth.

### API Surface

Keep existing read endpoints:

```text
GET /api/admin/alpha/overview
GET /api/admin/alpha/families/{parent_id}
```

Add low-risk write/read endpoints:

```text
POST /api/admin/alpha/invites
POST /api/admin/alpha/invites/{invite_id}/revoke

GET  /api/admin/alpha/accounts
POST /api/admin/alpha/accounts/{account_id}/disable
POST /api/admin/alpha/accounts/{account_id}/enable
```

All endpoints require the existing admin token. Parent sessions must not grant
admin access.

### Invite Generation

Request fields:

```text
count
label_prefix
issued_to_note
```

Rules:

- `count` must be at least 1 and should have a small upper bound suitable for
  Alpha operations.
- Each raw invite code is generated server-side.
- The database stores only `code_hash`, label, note, status, and timestamps.
- The response returns raw invite codes exactly once, in the creation response.
- Admin UI must label these codes as one-time display values.
- Generated invites start as `status=issued`.

### Invite Revocation

Rules:

- Only `status=issued` invites with no `consumed_by_parent_id` may be revoked.
- Revocation changes status to `revoked`.
- Consumed invites return 409 and remain unchanged.
- Already revoked invites return 409 and remain unchanged.
- Revoked invites cannot validate or create a new family.

### Account Listing

The account list should show operational state without exposing sensitive data:

```text
account_id
email_masked
status
parent_id
parent_display_name
children_count
last_login_at
active_session_count
created_at
```

Do not expose full email, phone, session tokens, child writing text, or AI
feedback bodies.

### Account Disable And Enable

Account deletion in V0.5a.1 means soft-disable:

```text
active -> disabled -> active
```

Disable rules:

- Set `ParentAccount.status=disabled`.
- Revoke every active, unexpired session for the account by setting
  `ParentSession.revoked_at`.
- Keep parent, child, learning, feedback, summary, invite, and event data.
- A disabled account cannot verify a Magic Code into a new session.
- Existing revoked sessions return unauthenticated behavior.

Enable rules:

- Set `ParentAccount.status=active`.
- Do not automatically create a session.
- The parent signs in again through Magic Code.

### Admin Event Safety

Admin write operations should emit a privacy-safe audit signal. This may be a
server log and/or a `ProductEvent` with a clearly internal event type.

Allowed payload fields:

```text
action
status
target_type
target_id
count
error_category
```

Disallowed payload fields:

```text
full email
raw invite code
Magic Code
SMTP password
child writing text
AI feedback body
phone number
session token
```

## Admin Frontend

The existing Admin Alpha page should stay compact and utilitarian.

Add:

- Invite generation form with `count`, `label_prefix`, and `issued_to_note`.
- One-time generated-code display after successful invite creation.
- Revoke action for issued, unconsumed invites.
- Account list with status and active session count.
- Disable and enable account actions.

Interaction rules:

- Disable and revoke actions require confirmation.
- Disable confirmation text states that learning data is preserved and active
  sessions will be revoked.
- Consumed invite rows do not show a revoke action.
- Errors should be friendly and operational, not raw stack traces or provider
  internals.

## SMTP Email Delivery

V0.5a.1 extends the current sender interface to support real SMTP delivery while
keeping tests deterministic.

Implementations:

```text
CapturedEmailSender
SmtpEmailSender
DisabledProductionEmailSender
```

Rules:

- `MAGIC_CODE_DEV_ECHO=true` uses `CapturedEmailSender` for local and automated
  tests.
- `MAGIC_CODE_DEV_ECHO=false` and `MAGIC_CODE_EMAIL_PROVIDER=smtp` uses
  `SmtpEmailSender`.
- Missing SMTP config returns 503 for Magic Code request and never echoes a
  code.
- SMTP connection/auth/send failures return a friendly generic API error and do
  not leak provider details.
- Magic Codes are still stored only as hashes.
- Logs and events must not contain raw codes, full email addresses, SMTP
  passwords, or provider secrets.
- Use Python standard library `smtplib` and `email.message.EmailMessage` unless
  implementation discovers a strong reason for a dependency.

### SMTP Configuration

Add settings:

```text
SMTP_HOST
SMTP_PORT
SMTP_USERNAME
SMTP_PASSWORD
SMTP_USE_SSL
SMTP_USE_STARTTLS
SMTP_TIMEOUT_SECONDS
```

Keep existing V0.5a email settings:

```text
MAGIC_CODE_EMAIL_PROVIDER
MAGIC_CODE_FROM_EMAIL
MAGIC_CODE_DEV_ECHO
```

Railway Dev QQ Mail configuration:

```text
MAGIC_CODE_DEV_ECHO=false
MAGIC_CODE_EMAIL_PROVIDER=smtp
MAGIC_CODE_FROM_EMAIL=<your@qq.com>
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_USERNAME=<your@qq.com>
SMTP_PASSWORD=<QQ mail authorization code>
SMTP_USE_SSL=true
SMTP_USE_STARTTLS=false
SMTP_TIMEOUT_SECONDS=10
```

QQ Mail requires enabling SMTP service and using an authorization code rather
than the account login password.

### Email Content

Subject:

```text
WenLingo 登录验证码
```

Body should include:

- The 6 digit Magic Code.
- The TTL in minutes.
- A note that the recipient can ignore the email if they did not request it.

## Report Regression

The manual QA run found that the parent report page can show a server error.
V0.5a.1 fixes this regression without expanding the reading/report product.

Rules:

- The report API should not return a 500 for expected missing or insufficient
  student learning data.
- Expected data gaps should return a controlled 400/404 or a stable empty/error
  payload that the frontend handles.
- The frontend report page should show a stable user-facing state instead of a
  framework/server error screen.
- Reading page remains a known placeholder and is not a V0.5a.1 blocker.

## Auth And Security Interactions

- Admin endpoints remain token-gated and do not use parent cookies.
- Admin state-changing endpoints should follow the same JSON-only and
  Origin/Referer protections used for authenticated state-changing routes where
  practical.
- Disabled accounts must be checked during Magic Code verification before a new
  session is issued.
- Account disablement must revoke active sessions in the same transaction as
  the status change.
- Re-enabled accounts regain access only after a new successful Magic Code
  login.

## Testing Plan

Backend tests:

- SMTP provider with missing config returns 503 and does not expose a code.
- SMTP sender sends a Magic Code through a mocked `smtplib` path.
- SMTP sender builds subject/body/from/to correctly.
- Disabled account cannot verify a Magic Code into a session.
- Disabling an account revokes active sessions.
- Enabling an account allows a future Magic Code login.
- Admin account list returns masked email and active session count.
- Admin disable/enable requires admin token.
- Admin invite generation returns raw codes once and stores only hashes.
- Issued invite can be revoked.
- Consumed invite cannot be revoked.
- Revoked invite cannot validate or create a family.
- Admin write events or logs are privacy-safe.
- Report endpoint no longer returns 500 for the QA path.

Frontend tests:

- Admin invite generation displays one-time raw codes.
- Admin revoke action is available only for issued, unconsumed invites.
- Admin handles consumed-invite revoke failure without crashing.
- Admin account list renders status and active session count.
- Admin disable/enable flows update the UI.
- Report page renders a stable result or controlled error state.

Manual QA:

- Configure Railway Dev with QQ SMTP and `MAGIC_CODE_DEV_ECHO=false`.
- Request a Magic Code and confirm it arrives in a real inbox.
- Generate one invite from Admin Alpha.
- Create a new family with the generated invite and emailed Magic Code.
- Complete the existing core learning smoke path.
- Disable the account and confirm the current session loses access.
- Re-enable the account and confirm Magic Code login works again.
- Revoke an unused invite and confirm it cannot be used.
- Confirm a consumed invite cannot be revoked.
- Open the parent report page and confirm no server error page appears.

## Rollout Plan

1. Merge and deploy V0.5a.1 code to Railway Dev.
2. Configure QQ SMTP environment variables.
3. Keep `MAGIC_CODE_DEV_ECHO=false` for real Railway Dev manual QA.
4. Smoke test real email delivery before inviting any external Alpha family.
5. Use Admin Alpha to generate the invite for QA.
6. Run the V0.5a.1 manual QA checklist.
7. Update `qa/2026-06-01-v0.5a-alpha-user-foundation-manual-qa.md` or a new
   V0.5a.1 QA document with the result.

## Rollback Plan

If SMTP email fails:

- Set `MAGIC_CODE_DEV_ECHO=true` only for controlled internal QA, or set
  `AUTH_REQUIRED_FOR_ALPHA=false` to return to legacy Alpha flow.
- Keep account and invite data intact.

If admin write actions misbehave:

- Stop using the new admin write UI.
- Continue using existing ops scripts for invite creation/session revocation.
- Patch forward; do not delete Alpha data.

If report fix causes a regression:

- Roll back the web/API deployment while keeping the database intact.
- Re-run core invite, learning, summary, and admin smoke checks.

## Acceptance Criteria

- Railway Dev can send real Magic Code emails through QQ SMTP with dev echo off.
- Missing SMTP configuration fails closed and does not expose codes.
- Admin can generate one or more invite codes and see the raw codes once.
- Admin can revoke unused invite codes.
- Consumed invite codes cannot be revoked.
- Revoked invite codes cannot create families.
- Admin can list accounts without exposing full email or sensitive child data.
- Admin can disable an account, revoking active sessions.
- Disabled accounts cannot log in through Magic Code.
- Admin can re-enable an account, and the parent can log in again by Magic Code.
- The report page no longer shows a server error for the QA path.
- Reading remains explicitly documented as a placeholder/out-of-scope item.
- Existing invite, child creation, assessment, sentence, essay, feedback,
  summary, and Admin Alpha read flows continue to work.
