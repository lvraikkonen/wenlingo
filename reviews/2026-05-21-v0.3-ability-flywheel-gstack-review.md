## CEO / Product Strategy Review

### What shipped

The ability data flywheel now turns, with one qualified limitation. Every essay draft and essay revision produces source-linked, queryable `AbilityHistory` rows. The `AbilityProfile` updates atomically with training artifacts. Recommendations read the current ability profile directly — demo children with different seed profiles now get differentiated task recommendations without assessment rows.

The critical blocker from V0.2 ("ability growth is fake data") is resolved for the essay path and partially resolved for the sentence path.

### Strategic assessment

**The flywheel foundation is real but incomplete.** The sentence path works with mock LLM output but depends on a fallback when real LLMs return non-canonical ability keys. This is a fundamental tension: the LLM is asked to return `ability_delta` with canonical keys, but the schema allows arbitrary string keys, and real providers don't always follow the contract.

The post-QA fix (`c345cf6`) adds a "valid keys present?" gate before choosing between LLM output and fallback. This is correct defensive engineering but makes the sentence ability growth a two-tier system: mock providers produce real growth from LLM judgment, real providers produce fallback growth. For a product whose PRD thesis is "data-driven personalization," this is a crack in the foundation.

**V0.3 is still a backend/data-model release with no child-facing behavior change.** The child's experience is identical to V0.2. This was by design — the handoff explicitly said "No new UI features." But it means V0.3's value is entirely in data infrastructure. The next release must make this infrastructure visible to someone (child, parent, or system).

### Recommendation

Ship V0.3 as-is. The essay flywheel is solid. The sentence limitation is documented and testable. The risk is not that something is broken — it's that real-LLM sentence growth is coarser than intended. Prioritize Minimal Assessment Entry in V0.4 so the flywheel data actually drives the first user experience.

## Learning Designer Review

### What works

1. **Ability history records actual deltas, not fixed increments.** The `apply_ability_delta` service correctly clamps to 0-100 and records `actual_delta` rather than the raw requested delta. A child at expression=98 who earns +5 gets `new_value=100, delta=2`. This means the history is honest about growth constraints.

2. **Essay deltas are tied to feedback quality, not random.** The deterministic mapping (2 improvements → +5, 3 improvements → +3) rewards cleaner drafts with more growth. This is pedagogically sound: a draft that needs fewer fixes is a stronger draft. The revision delta (+4/+5 based on evidence count ≥2) similarly rewards substantive revision.

3. **Empty/zero/negative deltas create no history.** The service filters `raw_delta <= 0`, preserving the "positive growth only" principle. No child sees their abilities go down.

4. **All-default abilities (40/40/40/40/40/40) recommend "入门小试炼."** This is the correct first experience for a new child — they should complete a diagnostic before the system starts making recommendations. The design preserves this without requiring an `Assessment` database row.

### Concerns

1. **Sentence ability growth from real LLM is not truly personalized.** The post-QA fix treats non-canonical LLM output as equivalent to missing output, falling back to `{"expression": 2, "observation": 2}`. A child who writes an exceptional sentence upgrade gets the same ability growth as one who writes an adequate one. The LLM's judgment ("this was a strong upgrade") is captured in the qualitative feedback but not in the ability delta.

2. **The 6-to-3 ability mapping is still undocumented.** `to_child_abilities()` weights structure at 0.5x in `specific_writing_power`. This is a pedagogical claim that should have a one-line rationale in the code.

3. **No "plateau" or "mastery" ceiling experience.** When abilities approach 100, `apply_ability_delta` clamps silently. A child with expression=98 sees the same feedback loop as one at expression=44. There's no celebration of mastery, no shift to harder challenge types.

### Recommendation

Document the 6-to-3 mapping rationale. For V0.4, consider whether the assessment entry flow should produce a wider spread of initial ability values (20-60 range instead of all 40s) so that post-assessment recommendations feel genuinely personalized.

## Child User Experience Review

### What V0.3 changes (invisibly)

The child sees none of V0.3's work. The dashboard, essay flow, sentence workshop, and report are pixel-identical to V0.2. This was the right call for a data-infrastructure release, but it means the review must focus on whether the invisible changes make the visible experience more truthful.

### Truthfulness assessment

**Before V0.3:** Ability bars on the dashboard reflected seed profile values. After training, they changed by fixed increments (always +4 or +2) regardless of actual performance.

**After V0.3:** Essay ability bars change proportionally to draft quality (fewer improvements needed = stronger growth). Sentence ability bars change by LLM-judged deltas (when the LLM follows the contract) or small fixed fallback deltas. The revision bar changes based on whether the child produced real evidence of revision.

This is a meaningful improvement in truthfulness — the numbers the child sees are now more connected to what they actually did. A child who writes a cleaner draft gets more visible growth. A child who submits minimal revision evidence gets less.

### Unresolved V0.2 UX issues (still present)

1. **No draft-saving.** A child who starts an essay and closes the browser loses their work.
2. **Sentence workshop has no inline guidance.** The focus field is now a typed enum (good), but the child still sees two empty text fields with no example or "what to do" introduction.
3. **Settlement is text-only.** No animation, no visual growth celebration.
4. **Reading Canyon is still "施工中."**

### Recommendation

V0.4 Minimal Assessment Entry should include at least one child-visible moment: the "第一张能力草图" reveal after completing the entry trial. This is the natural place to make ability data visible and delightful.

## Parent User Experience Review

### What V0.3 changes (invisibly)

The parent report now has `AbilityHistory` rows available as a data source, but the report does not yet read them. The report still uses count-based training evidence (sentence training count, revision tasks) and current `AbilityProfile` snapshot.

### Assessment

**The report is now behind the data model.** The `AbilityHistory` table contains exactly the data parents need — "what improved, by how much, from which activity" — but `build_stage_report_content` doesn't query it. The report still tells parents "完成了 3 次句子训练" but can't say "句子表达能力从 44 提升到 48."

This is a V0.3 scope decision that was correct (the handoff said "Do not add report time-windowing or weekly aggregation"), but it leaves the parent value proposition weaker than it could be.

### Unresolved V0.2 parent UX issues

1. Report is per-request, not per-week. Clicking "家长报告" twice creates duplicate rows.
2. Report degrades poorly with no data ("完成了 0 次句子训练").
3. No trend visualization — parents see current state, not growth curve.
4. "给家长看报告" is child-facing language — no separate parent auth.

### Recommendation

V0.4 doesn't need to fix all of these, but the report should at least query `AbilityHistory` to show "最近进步" with ability name + delta. The data exists now. Using it is low-effort and high-impact for parent trust.

### Post-QA fix verification

The sentence fix (`c345cf6`) changes the fallback logic from:
```python
ability_deltas = feedback.ability_delta or SENTENCE_ABILITY_DELTA_FALLBACK
```
to:
```python
ability_deltas = feedback.ability_delta
if not any(
    ability_name in VALID_ABILITY_NAMES and raw_delta > 0
    for ability_name, raw_delta in ability_deltas.items()
):
    ability_deltas = SENTENCE_ABILITY_DELTA_FALLBACK
```

This handles three cases:
1. **Empty `ability_delta`**: `any(...)` returns False → fallback. Same as before.
2. **Non-canonical keys only** (e.g., `{"细节描写": 2}`): no key in `VALID_ABILITY_NAMES` → fallback. Fixed.
3. **Mixed canonical + non-canonical keys** (e.g., `{"expression": 3, "细节描写": 2}`): `expression` is valid and >0 → uses LLM output, filters non-canonical. Reasonable.

The fix also added a test (`test_sentence_training_rejects_non_canonical_ability_delta_keys`) that verifies the fallback path with a provider returning `{"细节描写": 2, "比喻运用": 1}`.

### Release readiness

**V0.3 is ready to ship with one documented limitation:** real-LLM sentence ability deltas currently fall back to fixed values when the LLM returns non-canonical keys. This is a known product behavior, not a bug. The limitation should be documented in release notes.

**V0.3 Ability Flywheel Foundation is a successful data-infrastructure release.** The three critical blockers from the V0.2 gstack review are resolved:

| Blocker | V0.2 Status | V0.3 Status |
|---------|-------------|-------------|
| B1: Ability delta not authenticated | Hardcoded 0.85/0.8 | Deterministic from feedback (essay) or LLM with fallback (sentence) |
| B2: Recommendation ignores ability profiles | Assessment-gated | Always uses AbilityProfile |
| B3: No AbilityHistory table | Missing | Present, indexed, source-linked, atomically committed |

**One limitation remains:** real-LLM sentence ability deltas depend on the provider returning canonical ability names. When the provider returns non-canonical keys, the system falls back to fixed deltas. This is a reasonable V0.3 tradeoff — the infrastructure is correct, the fallback is safe, and the limitation is documented and testable.

**The flywheel foundation is solid enough to build V0.4 on top of it.**

## V0.4 Direction: Minimal Assessment Entry

### Recommended scope

**Goal:** A new child enters 小文星球, completes a 3-5 minute entry trial (one sentence upgrade + one short essay), receives their first ability sketch, and the Dashboard recommends essay/sentence tasks based on this real assessment data.

### Why this now

1. **V0.3 made recommendations ability-driven.** But for a new child with all-default abilities, the system can only recommend "入门小试炼" — a placeholder. V0.4 makes that placeholder real.

2. **V0.3 built the ability persistence infrastructure.** `AbilityHistory` records every change. `apply_ability_delta` is the single write boundary. The assessment flow reuses this infrastructure without new data model concepts.

3. **This closes the PRD's core journey:** 入门诊断 → 能力画像 → 推荐任务. V0.2 validated the training UX. V0.3 built the data plumbing. V0.4 connects them into a complete first-visit experience.

4. **The pre-writing contracts from V0.3 AC8 (`material_questions`, `outline_generation`) are ready.** They were added as dead code in V0.3 to enable exactly this flow.

### What Minimal Assessment Entry includes

| Feature | Description | Reuses |
|---------|-------------|--------|
| Entry trial landing | After child creation, a guided "认识你的写作超能力" intro screen | New UI |
| One sentence upgrade | Same flow as sentence workshop, framed as "试试你的句子魔法" | `POST /api/students/{id}/sentences` |
| One short essay | Write 2-3 sentences about a picture or prompt, get feedback | `POST /api/students/{id}/essays` |
| Ability sketch reveal | Show the 3 ability bars with kid-friendly labels and a "你的写作超能力" card | `GET /api/students/{id}/dashboard` |
| Post-assessment recommendations | Dashboard recommendations driven by the real ability profile | `choose_today_tasks(ability)` |
| Assessment completion flag | `Assessment` row created with sentence/essay references | Existing `Assessment` model |

### What Minimal Assessment Entry does NOT include

- Full multi-dimension diagnostic (comprehension, summarization require reading tasks)
- Pre-writing material cards or outline generation (defer to V0.5)
- Parent-visible assessment report (use existing report with new data)
- Adaptive question selection (one fixed prompt)
- Assessment retake or history

### Non-negotiables for V0.4

1. **The entry trial must complete in 3-5 minutes for a fourth-grade child.** Measure this in manual QA.
2. **The ability sketch must use the same 3 child-facing abilities as the Dashboard** (reading_power, specific_writing_power, revision_power).
3. **Assessment results must create `AbilityHistory` rows** — the assessment is the first data point in the child's growth story.
4. **Post-assessment recommendations must differ from pre-assessment defaults** — if a child's assessment shows strong expression but weak structure, the recommendation must reflect this.
5. **No new LLM task types for V0.4 assessment** — reuse `essay_feedback` and `sentence_upgrade_feedback`.
6. **The existing demo family must still work** — assessment is additive, not required for demo profiles.

### Files likely to change

| File | Change |
|------|--------|
| `apps/api/app/api/routes/assessments.py` | New or extended: create assessment from sentence + essay results |
| `apps/api/app/services/abilities.py` | Add `build_initial_ability_profile(assessment)` helper |
| `apps/api/app/services/recommendations.py` | May need threshold tuning for post-assessment profiles |
| `apps/web/src/app/children/[studentId]/` | New assessment flow pages or components |
| `apps/web/src/components/` | Ability sketch reveal component |
| `apps/api/tests/` | Assessment flow integration tests |
| `apps/web/e2e/` | Assessment entry E2E test |

### Success metrics for V0.4

1. A new child completes the entry trial in under 5 minutes (manual QA stopwatch).
2. The post-assessment dashboard shows at least one ability value different from the default 40.
3. The post-assessment recommendation differs from the all-default "入门小试炼" recommendation.
4. `AbilityHistory` contains rows with `source_type=assessment` linked to the assessment's sentence and essay.
5. Existing demo family dashboards and recommendations are unchanged.

### What comes after (V0.5 candidates)

- Pre-writing flow (material questions + outline generation) using the V0.3 contracts
- Report reads `AbilityHistory` for growth evidence
- Reading Canyon v0 (one passage + comprehension questions)
- Sentence focus selector UI (dropdown instead of hidden constant)
