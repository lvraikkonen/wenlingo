## 1. CEO / 产品战略视角

### 当前位置

WenLingo 现在处于 Alpha 验证的第二阶段。V0.4.1 验证了"AI 反馈闭环是否被孩子接受"，V0.5 验证了"AI 句子训练 thin slice + 用户体系是否可以支撑扩大 Alpha"。

两个核心问题已经回答：
- **学习闭环跑通了吗？** 是的。AI 出题 → 孩子改写 → AI 反馈 → XP 结算 → 家长看到，流程完整。
- **用户体系够用吗？** 是的。Magic Code + Resend 邮件 + server-side session 已经足够支撑 10-20 个家庭。

### 战略判断

**V0.5b 不是一个应该停留的版本，但它是一个可靠的 checkpoint。**

正面信号：
- 每个 Alpha 孩子都能完成句子挑战闭环
- Admin 可以看到 AI 使用量和成本（虽然成本显示需要修正）
- Resend 真实邮件已验证，外部家庭邀请的技术障碍已清除
- Prompt Registry 已经建立，后续 AI 任务有统一管理基础

风险信号：
- 产品稳定度只有 75-80%，loading 体验和 hydration error 让产品感觉"没做完"
- LLM 成本不可观测，无法做规模化决策
- 所有 AI 任务共享一个模型，成本效率无法优化
- 阅读峡谷仍然是死胡同链接，伤害孩子体验

### CEO 建议

1. **V0.5b.1 必须做，且必须尽快（1-2 天）。** 不是因为功能缺失，而是因为产品 polish 不够。真实家庭对"loading 时只有一行文字"和"console 报错"的容忍度很低。
2. **V0.5c 是战略分水岭。** ModelRouter 决定了 WenLingo 能否以合理成本规模化。如果 V0.6 Writing Castle 仍然用单一模型，要么成本失控，要么质量妥协。
3. **在 V0.5c 完成之前，不要开始 V0.6。** 这看起来"慢"，但实际上防止了 V0.6 上线后的成本危机。
4. **阅读峡谷的死胡同链接应该立即隐藏（V0.5b.1），不等 V0.7。** 这是旧路线图的遗留判断，但现在看是一个低成本高回报的改进。

### 与 PRD 愿景的对齐

PRD 定义了 "测评 → 能力画像 → 个性化任务 → 训练 → AI 反馈 → 游戏化 → 家长报告 → 下一轮推荐" 的完整飞轮。

当前状态：飞轮的前半段（测评→训练→反馈→结算）跑通了，但后半段（智能推荐→完整家长报告→数据驱动决策）还没有。

这个差距是预期内的。V0.5 的角色本来就是"打地基"，不是"盖楼"。

## 2. 学习设计师视角

### 核心问题：孩子真的在学吗？

从学习设计角度，V0.5b 的句子挑战有三件事做对了：

**1. AI 出题但不给答案**

```text
source_sentence: "小猫跑了。"
challenge_prompt: "请把句子写具体，加上动作和样子。"
hint: "可以写小猫怎么跑、跑到哪里、看起来怎么样。"
```

这是好的学习设计：给方向，不给答案。孩子在"扩句"这个动作上得到了明确的引导，但没有被告诉应该写什么。

**2. 反馈结构是"先鼓励再建议"**

```text
encouragement → highlight → suggestion → example_upgrade
```

这个顺序符合 PRD §5.2 的"先鼓励，再建议"原则。`suggestion` 每次只给一个（"还可以加一点表情或心情"），符合"每次只提升一个小能力"原则。

**3. 能力增长由后端确定性规则结算，不依赖 LLM 评分**

这是 V0.5b 最重要的学习设计决策之一。`deterministic_challenge_ability_delta()` 确保同一 `target_skill` 的能力增长是可预测的，不受 LLM 随机性影响。这保证了"能力变化"对孩子和家长是可解释的。

### 学习设计缺口

**缺口 1：三种 challenge type 的覆盖面有限**

当前 `expand_sentence`、`action_expression`、`feeling` 三种类型，对应 PRD §14.2 的"加细节"和"加心理"，但缺失：
- **缩句训练**（把啰嗦句子精简）
- **仿写句子**（给定句式，替换内容）
- **比喻/拟人训练**（PRD §14.2 的"加修辞"）

V0.5b 是一个 thin slice，三种类型作为起点是合理的。但如果孩子连续做 10 次都是同样的三种类型，新鲜感会下降。

**缺口 2：没有难度递进**

同一个 `action_expression` challenge，三年级和六年级用的是同一套 fallback 模板。LLM 会通过 `grade_label` 调整生成内容，但 fallback 完全不区分年级。对六年级孩子来说，"小猫跑了"可能太幼稚。

**缺口 3：challenge 选择是轮转而非自适应**

`choose_challenge_target_skill()` 用 `count % 3` 轮转，不依赖孩子薄弱点。这避免了过度设计（Alpha 阶段不需要复杂推荐算法），但长期来看，一个总是做不好 `feeling` 的孩子应该获得更多 `feeling` 挑战。

### 学习设计师建议

1. **V0.5c 或 V0.6 增加 2-3 种新 challenge type**，特别是"缩句"和"仿写"
2. **fallback 模板按年级分段**，至少区分 3-4 年级和 5-6 年级
3. **在 V0.8 数据飞轮之前**，challenge 选择保持轮转（简单可靠），V0.8 后引入基于能力画像的推荐
4. **考虑添加"跳过此题"**，让孩子在遇到不合适的挑战时可以选择换一题，而不是硬着头皮做或放弃

## 3. 孩子用户体验视角

### 以孩子的眼睛看 V0.5b 句子工坊

**进入体验：**

孩子点击"句子工坊"，看到：
- 🧡 橙色图标 + "句子工坊"标题
- "把一句话升级成小画面"副标题
- "正在准备今天的句子挑战"（loading 文字）

**好的部分：**
- 语言友好：没有"任务"、"训练"、"作业"等压迫性词汇
- 视觉温暖：橙色系、圆角卡片
- 等待时有反馈：虽然只是一行文字，但至少不会空白

**挑战展示：**

```text
四年级 · 四年级基础 · 动作描写
小猫跑了。
请把句子写具体，加上动作和样子。
可以写小猫怎么跑、跑到哪里、看起来怎么样。
```

这很清楚：孩子知道这是四年级的题、练的是动作描写、要做什么、从哪里开始想。

**不足的部分：**
- "正在准备今天的句子挑战"等 3-5 秒后，突然出现挑战内容，没有过渡动画
- 提交后等 AI 反馈时，只有按钮 spinner + "AI 教练正在看你的句子"——如果 LLM 慢（8-10 秒），孩子会以为卡住
- 没有进度条、没有趣味性等待动画（比如"AI 教练正在批改你的句子，小猫也在等待..."）
- "自己带句子来练"按钮在表单旁边，可能分散注意力

**反馈展示：**

```text
AI 教练反馈
你写得很有画面感！
你加上了"飞快地冲过去"，动作更清楚了。
还可以加一点表情或心情。
小狗瞪大眼睛，飞快地冲过草地，好像发现了什么宝贝。
```

反馈是好的学习设计，但从孩子 UX 角度：
- `encouragement` 和 `highlight` 视觉上区分不够（一条加粗一条灰色）
- `example_upgrade` 放在最后像个"标准答案"——虽然设计意图是"参考例句"，但孩子可能理解为"这才是正确答案，我写的不够好"
- 没有"你做到了什么"的庆祝感——战斗结算页面目前只有数字，没有打怪动画

### 孩子 UX 建议

1. **V0.5b.1**：loading 改为 3 阶段（"正在出题..." → "AI 教练正在想一个好玩的句子..." → "快好了！"），加上简单动画
2. **V0.5b.1**：`example_upgrade` 加一行说明："这是一个参考，你的写法也很棒！"
3. **V0.6+**：战斗结算加入简单的庆祝动画（哪怕只是一个 🎉 emoji + 橙色脉冲）
4. **V0.7**：完整打怪动画

## 4. 家长用户体验视角

### 以家长的视角看 V0.5b

**登录流程：**

家长打开 `/alpha/start`，选择"已有账号登录"（hotfix 新增），输入邮箱 → 收到 Magic Code 邮件 → 输入验证码 → 登录成功。

这是流畅的。Resend 邮件到达 Hotmail/QQ 的速度在 5-15 秒内，体验接近"正常 App 登录"。

**孩子列表：**

```text
/parent/children
→ 看到孩子"小星V05B"，四年级
→ 点击进入孩子 dashboard
→ 点击"给家长看报告"
```

**家长摘要页：**

当前 parent summary 展示：
- 本周完成 X 次句子挑战
- 主要练习了"动作描写"和"扩句"
- 可以提交"有帮助/一般/没帮助"反馈

这是克制的、不泄露孩子写作内容的。符合 PRD 的隐私要求。

**不足：**
- 没有能力变化趋势（只有练习次数，看不到进步方向）
- 没有 before/after 对比（PRD §18.3 的核心价值）
- 没有"下一步建议"（家长不知道该让孩子多练什么）
- 总结页面的视觉设计偏简陋，不像一个"报告"

### 家长 UX 建议

1. **V0.5c**：parent summary 至少增加"本周练习类型分布"饼图或条形图
2. **V0.8**：完整家长周报（PRD §18 的 5 模块）
3. **当前阶段**：parent summary 保持克制是正确的——过度承诺但交付不足比循序渐进更伤害信任

## 5. 工程经理视角

### 架构健康度

**做得好的：**

1. **数据模型扩展而非破坏** — `SentenceTraining` 增加了 `status`、`challenge_prompt` 等字段，但没有破坏已有 free-input 训练的数据。所有已有行 default="completed" 保证了向后兼容。

2. **Provider 抽象清晰** — `LLMProvider` Protocol 只有 `complete_json(task_name, payload) -> LLMProviderResponse` 一个方法。Mock 和 HTTP 实现完全可互换。添加新 provider（如 Anthropic、Qwen）只需要实现这个接口。

3. **Prompt Registry 与 task runner 解耦** — `get_prompt(key)` → `run_validated_llm_task()` → `provider.complete_json()` 的调用链清晰。添加新 AI 任务只需要：(a) 注册 prompt，(b) 写 task wrapper，(c) 写 route handler。

4. **测试覆盖集中在关键路径** — 9 个后端测试文件覆盖了 prompt、logging、challenge API、guardrails、email。虽然前端测试薄弱，但后端测试质量不错。

**需要警惕的：**

1. **`run_validated_llm_task()` 已经承载太多职责** — 它同时处理：daily limit check、provider call、retry、validation、cost estimation、logging、fallback。这个函数是架构的单点，任何修改都影响所有 LLM 任务。在 V0.5c 加入 ModelRouter 之前，应该先考虑拆分。

2. **admin_alpha.py 路由文件正在膨胀** — 从最初的 overview + invite + family detail，现在已经加了 AI usage、revoked invite 过滤、账号管理。建议 V0.5c 之前拆分为独立路由模块。

3. **前端没有 AI 交互状态机** — `isLoadingChallenge`、`isSubmitting`、`error` 三个独立 state 管理 AI 交互。依赖关系靠 `useEffect` 和 try/catch 隐式控制。随着 AI 交互场景增多（V0.6 会有选题材追问、提纲生成、选材问答等），这个模式会越来越脆弱。

### 工程经理建议

1. **V0.5c**：拆分 `run_validated_llm_task()` — 至少把 daily limit check 和 cost/logging 提取为独立 middleware/decorator
2. **V0.5c**：拆分 `admin_alpha.py` 为 `admin/overview.py`、`admin/invites.py`、`admin/accounts.py`、`admin/ai_usage.py`
3. **V0.5b.1 或 V0.5c**：前端引入 `AIInteractionState` 枚举，在 sentence workshop 先试点，V0.6 推广到所有 AI 交互
4. **持续**：每次发布前运行 `git diff --stat` 确认 scope 没有膨胀

## 综合结论

### 各视角的共识

所有 6 个视角都指向同一个结论：

```text
V0.5b 是一个可靠的功能 checkpoint，但不是一个可以"跳过 V0.5b.1"的版本。
V0.5b.1 的加载体验改善、cost 显示修正、localStorage 清理不是"锦上添花"，
而是决定产品是否能让真实家庭感觉"这是个认真的产品"的关键细节。
```

### 各视角的优先级对齐

| 视角 | 最关心的 | 下一优先级 |
|---|---|---|
| CEO | 成本可控、扩展 ready | V0.5c ModelRouter |
| 学习设计 | challenge 多样性、反馈有效性 | 更多 challenge type |
| 孩子 UX | 等待感、趣味性 | V0.5b.1 loading UX |
| 家长 UX | 看到进步、before/after | V0.8 完整周报 |
| 工程 | 架构不腐化、测试覆盖 | V0.5c 架构整理 |
| QA | 可测试、可回归 | E2E 测试 |

没有矛盾——每个视角的需求都可以在 V0.5b.1 → V0.5c → V0.6 → V0.7 → V0.8 的路线中顺序满足。
