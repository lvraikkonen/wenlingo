## 版本履行总结：我们实际做了什么 vs 旧路线图的预期

旧路线图（2026-06-01）规划 V0.5 是"手机号 + 短信验证码登录"的单一大版本。实际执行中，V0.5 被拆分为三个子版本：

| 版本 | 实际交付 | 与旧路线图的差异 |
|---|---|---|
| V0.5a | ParentAccount、ParentSession、Magic Code 登录、Alpha 邀请管理、Resend/Dev Echo guard | 登录方式是 Magic Code 邮件而非短信验证码——这个决策是正确的（邮件比短信更可靠、更便宜、更适合 Alpha） |
| V0.5a.1/.2 | Dev hardening、QQ Mail SMTP 支持、QA 闭合 | 旧路线图未预期的 hardening 阶段 |
| V0.5b | Prompt Registry、LLMCallLog 元数据、Daily limit、AI 句子挑战 thin slice（3 种类型）、Admin AI usage | 旧路线图未预期的 AI 基础设施版本——句子挑战 thin slice 是 V0.5b 最大的新增价值 |

**关键变化：实际进度比旧路线图多了一个 AI 基础设施 + 句子训练 thin slice，但登录方案从 SMS 变为 Magic Code 邮件。**

这个变化对后续路线图的影响：
- ✅ AI 基础设施已经部分就绪（Prompt Registry、LLMCallLog、daily limits），V0.5c 不需要从零开始
- ✅ 用户体系已经是 product-grade 的 server-side session，不需要重构
- ⚠️ 但 ModelRouter 还没有，所有 AI 任务共享单一模型——这成为 V0.5c 的核心任务
- ⚠️ 句子挑战只有 3 种类型（vs PRD 的 4 种），V0.7 需要补齐

## Phase 4: V0.5c — AI 平台基础（✅ Core 已完成，2026-06-18）

> **V0.5b.1 后复审（2026-06-16）：** 路线图方向正确，但执行需要分层。V0.5c 目标收紧为：**让所有 AI 调用都经过一个可配置、可观测、可降级、可测试的统一执行层，为 V0.6 写作城堡的 4 个新 AI 任务扫清成本、稳定性和代码复杂度风险。**
>
> 关键调整：Cost registry 升 P0；fallback logging/QA 写进验收标准；增加 Alpha 运营观察闭环；V0.6 增加 thin-slice 备选方案；P1 允许滑但不能阻塞发布。

**主题**: 建立多模型能力，让 AI 平台可以按任务选择最合适的模型

**当前状态（2026-06-18）**: V0.5c core 已在 Railway Dev 完成人工 QA，并在
hotfix `eac30c1` 后通过 daily-limit retest。QA 记录见
`qa/2026-06-18-v0.5c-ai-platform-dev-qa.md`。继续扩大外部 Alpha 前，进入
V0.5c.1 polish 清债阶段。

### 为什么这是 V0.6 之前必须做的

当前所有 AI 任务共用一个模型（`LLM_MODEL`）。这导致：
- 句子挑战生成（简单、短输出）和作文反馈（复杂、长输出）用同一个模型
- 要么为简单任务多付钱，要么用便宜模型导致作文反馈质量下降
- 没有 provider fallback，单一 provider 故障 = 所有 AI 功能不可用

V0.6 的 Writing Castle 会引入 4 种新的 AI 任务（审题分析、选材追问、提纲生成、素材卡片分析），每种对模型的 latency/cost/quality 需求不同。没有 ModelRouter 就直接上 V0.6，会累积技术债务。

### 执行分层：V0.5c-core（Must Ship）→ V0.5c-polish（Can Slip）

V0.5c P0 较多，1-2 周偏紧。不是要分两个版本，但执行顺序和 ship 边界必须清楚：
- **V0.5c-core** 是 ship gate —— 全部完成才能说 V0.5c 完成
- **V0.5c-polish** 是 best-effort —— 做了更好，但不阻塞 V0.6

### P0: Must Ship（全部完成才能说 V0.5c 成功）

| # | 交付 | 说明 |
|---|---|---|
| 1 | **ModelRouter config schema + 单元测试先行** | 第一步。定义 YAML/TOML config 格式，写完 config schema 再写路由逻辑。每个 task config 至少包含：primary_model、fallback_model、timeout_seconds、retry_count、cost_tier。unknown task_name fail-closed，不静默使用默认强模型。 |
| 2 | **Task-level model config** | 每个 task_name 可独立配置 model、timeout、retry。Config schema 参考：`sentence_challenge_generation → cheap_fast (10s)`、`sentence_feedback → cheap_fast (12s)`、`essay_feedback → strong_default (30s)` |
| 3 | **Provider fallback + fallback QA** | 主 provider 失败时自动切换到备用 provider。必须手动触发并验证三种失败：A) primary timeout、B) primary 返回 malformed JSON / schema validation fail、C) primary API error / rate limit。每种都在 LLMCallLog 记录：primary_provider、primary_model、fallback_provider、fallback_model、fallback_reason、attempt_count、final_status |
| 4 | **Per-task timeout/retry** | 使用 task config 而非全局常量。所有 task `max_total_attempts=2`（primary 一次 + fallback 一次）。不做 primary 重试 N 次（防止 latency/cost 膨胀）。配置示例：challenge generation 10s、essay feedback 30s |
| 5 | **`run_validated_llm_task()` 拆分为四层** | 参数膨胀 + ModelRouter = 必须拆。但不要拆成太多抽象：`resolve_task_config(task_name)` → `enforce_daily_limit(student_id, task_name)` → `execute_with_retry_and_fallback(task_config, messages, schema)` → `record_llm_call_log(result, task_config, prompt_key, cost)`。不做 plugin system、不做策略引擎、不做 A/B testing、不做自动模型选择 |
| 6 | **Cost registry (升 P0)** | 每个 configured model 都有 input/output price per 1K tokens。pricing 未配置时 Admin 明确显示 `pricing_unconfigured`，不把 unknown cost 当成 `$0`。LLMCallLog 按 resolved_model 记录 estimated_cost |
| 7 | **E2E 测试 + fallback integration test** | Playwright: sentence challenge 完整流程 + Magic Code 登录流程。API integration: given primary fails → fallback provider is used → LLMCallLog records fallback_reason → user receives fallback-generated challenge |
| 8 | **Fallback 用户体验验收** | fallback 成功时：孩子端流程正常完成，不出现错误提示，只是稍慢。fallback 也失败时：显示 child-friendly rest/retry message，而非技术错误。Admin 能区分 primary_success / fallback_success / fallback_failed |
| 9 | **Alpha 运营观察闭环 (新增)** | V0.5c 期间同步邀请 5-10 个新家庭。记录：每个新家庭是否成功登录 → 创建孩子 → 完成至少 1 次句子挑战 → 触发过 AI 失败/fallback/daily limit → 家长看过 summary。通过 Admin + ProductEvent + 人工访谈，不做新功能 |

### 验收标准

#### ModelRouter / Config
- [ ] 所有 AI task 通过 ModelRouter resolve model，不再直接读取全局 `LLM_MODEL`
- [ ] 每个 task config 至少包含：primary_model、fallback_model、timeout_seconds、retry_count、cost_tier
- [ ] unknown task_name fail-closed，不静默使用默认强模型
- [ ] ModelRouter config unit tests 通过

#### `run_ai_task()` 分层
- [ ] 拆为四层：resolve_task_config → enforce_daily_limit → execute_with_retry_and_fallback → record_llm_call_log
- [ ] 所有已有后端测试继续通过

#### Fallback / Reliability
- [ ] 所有 AI task 使用 `max_total_attempts=2`：primary 一次 + fallback 一次。不做复杂 retry（primary 重试 N 次 + fallback 重试 N 次会导致 latency/cost 膨胀）
- [ ] primary timeout 时 fallback 到备用 provider
- [ ] primary API error / rate limit 时 fallback 到备用 provider
- [ ] primary schema validation fail 时 fallback 优先级：（1）直接 fallback provider（不修 JSON、不让另一个 LLM repair）→（2）fallback provider 也 schema fail → 使用 deterministic fallback。LLMCallLog 记录 primary_schema_fail / fallback_schema_fail / deterministic_fallback_used
- [ ] LLMCallLog 记录：resolved_provider、resolved_model、attempt_count、fallback_reason、estimated_cost、primary_provider、primary_model、fallback_provider、fallback_model
- [ ] fallback 成功时用户流程不中断，孩子不感知
- [ ] fallback 也失败时显示 child-friendly retry/rest message
- [ ] Admin 能区分 primary_success / fallback_success / fallback_failed
- [ ] fallback integration test 通过（覆盖三种失败模式：timeout / schema fail / API error）

#### Cost / Observability
- [ ] 每个 configured model 都有 input/output price per 1K tokens
- [ ] pricing 未配置时 Admin 明确显示 `pricing_unconfigured`，不显示误导性 `$0`
- [ ] P0（数据能力）：后端 endpoint 或 raw admin table 可按 task + model 聚合调用次数、成功率、fallback 次数、估算成本。不要求漂亮 UI

- AI 响应速度可能改善（小任务用更快的模型）
- Cost 从 "barely observable" 升级为 "cost controllable"
- fallback 让 AI 功能更可靠——孩子不会因为单一 provider 故障而无法练习

## Phase 5: V0.6 — 写作城堡完整课前构思（预计 3-4 周）

> **V0.5c 复审追加（2026-06-16）：** V0.6 范围偏大——同时做审题、选材、素材卡片、提纲、三种城堡模式、课内导入、难度适配、流程保护，在 3-4 周内可以但风险高于 V0.5c。建议预设 thin-slice fallback plan 防止失控。

**主题**: 从"AI 点评作文"升级为"AI 陪孩子从头构思一篇作文"

### 为什么这是 V0.5c 之后的第一优先级

PRD §15.3-15.5 的课前构思流程是 WenLingo 最强的产品差异化能力。当前作文训练从"空白文本框"开始——这对孩子是最难的时刻。课前构思解决了"不知道写什么"的核心痛点。

V0.6 也是 Writing Castle 三种模式的首次完整呈现。

### Thin-Slice Fallback Plan

如果 V0.6 在第 3 周时进度落后，自动激活 thin slice：

```text
V0.6a（必须）— 课内同步作文一条路径：
  题目输入 → 审题 → 选材问答 → 素材卡片 → 提纲 → 初稿

V0.6b（可以延后）：
  AI 出题作文 + 随笔写 + 难度适配增强
```

**触发条件：** 第 2 周末，审题+选材+素材卡片+提纲 四个 AI 任务中任何一个未完成 integration test，自动切换。

### 交付清单

| # | 功能 | 对应 PRD | 优先级 | 说明 |
|---|---|---|---|---|
| 1 | **审题小助手** | §15.3 | P0 | 孩子输入作文题目 → AI 拆解题意。1 分钟交互，≤3 轮 |
| 2 | **选材问答** | §15.4 | P0 | AI 追问 3-5 个问题 → 孩子回答 → 收集为素材卡片 |
| 3 | **素材卡片** | §8.1 | P0 | 选材问答产出可视化卡片，可排序/删除/添加 |
| 4 | **提纲生成** | §15.5 | P0 | AI 根据素材卡片生成提纲 → 孩子可修改 → 确认后进入写作 |
| 5 | **三种城堡模式** | §15.2 | P0 | ① 课内同步作文 ② AI 出题作文 ③ 随笔写 |
| 6 | **课内作文导入** | §15.2 | P1 | 粘贴老师题目要求 → AI 识别题目类型 |
| 7 | **难度适配 v1** | §12.2 | P1 | 按 grade_label 调整追问深度和提纲详细度 |
| 8 | **已有作文流程保护** | §15.6-15.9 | P0 | 初稿→点评→二稿→对比流程不被破坏 |

### 不做
- OCR 手写识别
- 语音输入
- AI 出题的完整题库（V0.6 只需 10-20 个推荐题目）

### 验收标准
- [ ] 孩子从题目输入到提纲确认全程 ≤5 分钟

- [ ] 不同年级看到不同深度的追问和建议
- [ ] 现有作文 feedback→revision→compare 流程不被破坏

### 数据观察目标
