# WenLingo V0.4.1 Alpha Enablement — Gstack Review

Date: 2026-05-25
Reviewer: Claude Code + gstack
Source: `2026-05-25-v0.4.1-alpha-enablement-proposal.md`, informed by `reviews/2026-05-25-v0.4-post-implementation-gap-review.md`

---

## Executive Summary

The V0.4.1 proposal is **directionally correct and addresses exactly the right problems.** It correctly identifies that V0.4 built a working assessment flow that no real family can reach, and it scopes V0.4.1 as an enablement release rather than a feature release. The proposal's strength is its product thinking: invitation model, parent/child separation, privacy requirements, and data collection are all well-considered.

However, the proposal has one structural risk: **it defines 12 implementation steps, 4+ new database tables, 7+ new pages, 2 feedback systems, an admin page, and deployment infrastructure in a single "non-feature" release.** The scope is large enough that it risks becoming V0.5 rather than V0.4.1. The proposal would benefit from a two-tier prioritization: what is **minimum viable Alpha** vs. what is **nice-to-have for Alpha.**

---

## 1. CEO / Product Strategy Review

### 1.1 The Proposal Gets the Big Picture Right

The proposal correctly frames V0.4.1 as:

> "Allow 3–5 invited families to start using WenLingo through a controlled Alpha flow"

This is the right goal. The V0.4 review identified that WenLingo has a working learning engine with no front door. V0.4.1 is the front door.

The proposal's strategic insight is that **Alpha enablement is not a feature — it's a prerequisite for learning anything from the features already built.** Without real families using the product, the team cannot answer the PRD's validation questions (Section 27.3): "孩子是否愿意主动打开系统?", "游戏化奖励是否有效?", "家长是否觉得周报有价值?".

### 1.2 The Proposal's Implicit Strategic Bet

The proposal implicitly bets on this sequence:

```text
V0.4.1: Alpha enablement (get families in)
→ V0.5: Writing revision loop (strengthen the strongest path)
→ V0.6: Reading Canyon (close the last major PRD feature gap)
```

This is a sound bet. It prioritizes:
1. Getting real users (V0.4.1)
2. Deepening the most mature path (V0.5 writing)
3. Broadening to reading (V0.6)

This is better than the alternative of building Reading Canyon before anyone can use the product.

### 1.3 The Deployment Decision Is Correct

The proposal correctly insists on hosted web deployment over local distribution. The rationale (centralized data, LLM key management, fast bug fixing, usage observation) is solid. The table comparing distribution methods (Section 4.2) makes the case clearly.

One gap: the proposal does not specify **who owns the deployment.** For a 3-5 family Alpha, a single developer-managed VPS or PaaS (Railway, Render, Fly.io) is appropriate. The proposal should state this explicitly so deployment doesn't become a separate planning exercise.

### 1.4 Scope Risk: This Is a Big "Small" Release

The proposal defines 12 implementation steps and introduces:
- Invite code system
- Parent/child navigation distinction
- Child creation API + UI
- Parent children list + summary
- Child reaction/feedback
- Parent feedback
- Product events table
- Admin Alpha page
- Alpha notice + privacy flow
- Data deletion/export process
- Deployment to hosted environment

Measured against the V0.4 scope (assessment flow = backend service + route rewrite + frontend 4-step wizard + E2E), V0.4.1 is significantly larger. The proposal's "Non-Goals" section (Section 13) is excellent at excluding things, but the "what's included" is still substantial.

### 1.5 Recommendation

Consider splitting into **V0.4.1a (minimum viable Alpha)** and **V0.4.1b (Alpha enrichments):**

**V0.4.1a — ship by end of week:**
- Manual invite link (Option A), not invite code system (Option B)
- Child creation API + UI
- Parent children list
- Parent/child navigation distinction
- Alpha notice + privacy flow
- Deployment to hosted environment

**V0.4.1b — ship the following week:**
- Product events table
- Invite codes (Option B)
- Child reaction/feedback
- Parent feedback
- Admin Alpha page
- Data deletion/export docs

This split ensures families can start using the product as soon as possible. The feedback and observation infrastructure can arrive a week later without blocking Alpha start.

## 2. Learning Designer Review

### 2.1 The Child Creation Flow Is Pedagogically Sound

The proposal's child creation form (Section 7.3) is minimal and age-appropriate:
- Nickname only (not real name)
- Grade selection
- No photo, no school, no birthdate

This is correct. The PRD defines the target as grades 3-6, with grade 4 as the core sample. Grade selection enables future difficulty adjustment.

### 2.2 The Assessment Continuity Section Is Correct but Incomplete

Section 15.2 defines V0.4 assessment continuity as acceptance criteria. This is essential — the V0.4 assessment flow must work identically for Alpha-created children. However, the proposal omits one edge case:

**What happens when a parent creates a second child?**

The current system assumes a one-to-one parent-to-child model in some places. `FamilyTopbar` fetches all students via `demoLogin()`. The child switcher shows all children. This should work naturally for multiple children, but the proposal should explicitly call out **multi-child families** as a test scenario.

### 2.3 Child Feedback Design Is Age-Appropriate

Section 10.1's reaction options (很有意思 / 还可以 / 有点难 / 不想做) use language a fourth grader can understand. The emoji + text combination is good for younger children. The optional free text ("你想对 AI 教练说一句话吗？") is low-pressure — a child who doesn't want to type can just pick an emoji.

One concern: the proposal places child feedback "after assessment or task completion." This is the right placement, but the implementation should ensure the feedback prompt **never blocks the ability sketch reveal.** The sketch is the reward. Feedback collection comes after, and should be skippable.

### 2.4 The Parent Summary Reads AbilityHistory — A Critical Gap Closure

Section 8 requires the parent summary to read real `AbilityHistory` data. This was flagged in the V0.3 review and again in the V0.4 review as a key gap. The proposal correctly prioritizes this — parents need to see growth deltas, not just training counts.

## 3. Child User Experience Review

### 3.1 The Navigation Split Is the Most Important UX Change

Section 6.3's principle — "parent sees management language, child sees adventure language" — is exactly right. The current `FamilyTopbar` showing "家长报告" next to "句子工坊" is confusing for a child. The split should be:

**Child navigation:** 我的小文星球 | 作文城堡 | 句子工坊 | 阅读峡谷 (施工中)
**Parent navigation:** 我的孩子 | 成长摘要 | 反馈

### 3.2 The Alpha Entry Flow Needs More Detail on the Child's First Moment

The proposal describes the parent flow well (invite → notice → create child → enter dashboard). But it doesn't specify what the child sees on first arrival. The V0.4 assessment intro page ("认识你的写作超能力") is designed for this moment — the child creation flow should route directly into it.

The flow should be:

```text
Parent creates child → "小星已加入！" confirmation
→ Button: "进入小文星球" (parent clicks this to hand device to child)
→ Child sees Dashboard with "入门小试炼" recommendation
→ Child clicks "开始任务" → V0.4 assessment flow
```

The handoff moment (parent hands device to child) is a critical UX transition that the proposal should call out explicitly.

### 3.3 Missing: What Happens on Child's Second Visit?

The proposal defines the first-visit flow well. But Alpha runs for 2-4 weeks. What does the child see on day 2? The current Dashboard works (it shows today's tasks based on ability profile), but the proposal doesn't verify that returning children have a clear entry path.

Add to manual QA checklist: "Child closes browser, returns next day, Dashboard shows personalized tasks (not assessment)."

## 4. Parent User Experience Review

### 4.1 The Parent Summary Is Correctly Scoped

Section 8's minimal parent summary (assessment completion, training count, ability changes, one highlight, next suggestion) is the right scope. It avoids the full weekly report while giving parents more than the current stage report.

### 4.2 Parent Feedback Design Has a Smart Question

Section 10.2's parent feedback question ("你最想看到什么？") with multiple choice options is strategically valuable. It tells the product team what to prioritize:
- If most parents select "修改前后对比" → strengthen the essay revision path
- If most parents select "任务难度是否合适" → add difficulty calibration
- If most parents select "AI 反馈是否准确" → invest in LLM quality

This is exactly the kind of data that should inform V0.5 scope.

### 4.3 Missing: Multi-Child Parent View

The proposal defines "parent children list" but doesn't specify whether the parent summary aggregates across children or is per-child. For a family with two children, the parent should see:

```text
小星：完成入门小试炼，表达力 +8
小月：完成入门小试炼，观察力 +6
```

Not:

```text
[select a child first to see anything]
```

The proposal should clarify: **parent landing page shows all children at a glance, with per-child summary available on click.**

### 4.4 Missing: Parent Cannot Currently Exist Without demoLogin()

This is the core architectural question for V0.4.1. The current system creates `ParentUser` only through `seed_demo_data()`. The proposal mentions a "minimal `family` or `alpha_family` concept" (Section 14.3) but doesn't commit to a model.

The implementation must decide:
- **Option A:** Create a real `ParentUser` row during invite acceptance. The parent gets a real ID, and children link to it via `parent_id`. This reuses the existing data model.
- **Option B:** Create a lightweight `AlphaFamily` concept that sidesteps `ParentUser` entirely.

Option A is strongly preferred. The `ParentUser` model already exists, and children already have `parent_id` FKs. Creating real parent rows during Alpha means the data model doesn't need migration later when real auth arrives.

## 5. Engineering Manager Review

### 5.1 The Invite Model Decision Has Implementation Consequences

The proposal presents two options (A: manual link, B: invite code) but doesn't commit. This decision should be made before implementation starts because it affects:

- Database schema (invite_codes table vs. no table)
- API routes (invite validation middleware vs. no middleware)
- Frontend pages (invite entry page vs. direct link)
- Security model (no gating vs. code gating)

**Recommendation:** Start with Option A (manual link) for V0.4.1a. It requires zero new backend infrastructure. The "invite" is simply a URL the developer sends to the family. Add Option B (invite codes) in V0.4.1b or V0.5 when there are more than 5 families.

### 5.2 Product Events Table Design Is Good but Under-Specified

Section 9.1's `product_events` table is well-designed (nullable parent/student, event_name, source_type/id, properties_json). However, the proposal doesn't specify:

1. **Where events are written.** Should they go through a service (`record_event(session, ...)`) or be created inline in routes? A service with a simple `async def record_product_event(...)` is preferred for consistency.

2. **Whether events are blocking.** If `product_events` insert fails, should it fail the user request? No — events should be best-effort. A failed event write should log a warning and continue.

3. **Retention/pruning.** For a 3-5 family Alpha, event volume is low. But the proposal should note that events have no TTL yet.

### 5.3 Database Migration Complexity

The proposal introduces up to 4 new tables (`invite_codes`, `product_events`, `child_task_feedback`, `parent_feedback`). If using Option A (manual link), `invite_codes` is deferred. That leaves 3 tables, each with straightforward schemas.

The migration should be a single revision chaining from the V0.4 head (`20260521_assessment_artifacts`).

### 5.4 Regression Risk Assessment

The proposal correctly requires existing demo family behavior to be preserved (Section 15.7). The main regression risks:

| Change | Risk | Mitigation |
|---|---|---|
| Child creation via API | Low — additive endpoint | Test demoLogin still returns 4 children |
| Parent/child navigation split | Medium — FamilyTopbar changes | Keep demo flow using unified topbar, new split for Alpha path |
| Parent summary reading AbilityHistory | Low — read-only query | Test with existing demo data |
| Product events logging | Low — additive, best-effort | Wrap in try/except, log warning on failure |

The highest-risk change is the navigation split. The proposal should specify: **existing `FamilyTopbar` remains unchanged for the demo path; a new `AlphaTopbar` or conditional rendering based on context serves the Alpha path.**

### 5.5 Deployment Is Underspecified

Section 4 lists deployment requirements but doesn't specify:
- Which hosting platform (Railway? Fly.io? VPS?)
- How environment variables are managed
- How database migrations are run in production
- How the app is restarted on deploy
- Whether CI/CD exists or deployment is manual

For a 3-5 family Alpha, manual deployment is acceptable. But the implementation plan should include a `deploy.md` or `ops/alpha-deploy.md` runbook that another developer could follow.

## 6. QA / Release Manager Review

### 6.1 The Manual QA Checklist Is Good but Needs Additions

Section 17's checklist covers the happy path well. Add these edge cases:

```text
- Parent creates child with nickname containing special characters or spaces.
- Parent creates child with empty nickname or invalid grade.
- Parent creates second child — both appear in children list.
- Child starts assessment, closes browser mid-flow, returns — state is lost (expected, but verify UX is not confusing).
- Child completes assessment, parent creates another child — second child's dashboard recommends assessment independently.
- Demo family still works alongside Alpha family (no cross-contamination).
- Parent summary shows "暂无训练数据" state when child is newly created.
- Parent summary updates after child completes additional training (not just assessment).
```

### 6.2 Privacy Checklist

Section 11's privacy requirements are good. Add to QA:

```text
- Database inspection: no real name, school, address, phone, or photo fields contain data.
- LLM request inspection: child writing is sent to LLM but no identifying metadata (real name, location) is included.
- Alpha notice is displayed before any child data is collected.
- Browser dev tools: no personally identifying information in localStorage, sessionStorage, or URL parameters.
```

### 6.3 The "LLM Fallback Used" Event Is Critical for Alpha

Section 9.2 includes `llm_fallback_used` and `llm_error` events. These should be the **first events implemented** because:

1. Alpha uses real LLM providers
2. Fallback behavior is a known limitation (V0.3 review)
3. If fallbacks fire frequently during Alpha, it undermines the "personalized AI feedback" value proposition

The developer should check these events after the first week of Alpha and triage any patterns.

### 6.4 Alpha Success Criteria Are Implicit but Not Stated

The proposal defines what V0.4.1 should enable (Section 2) but doesn't define what a successful Alpha looks like. Add:

```text
Alpha success criteria (after 2-4 weeks):
- At least 3 families create children and complete assessment.
- At least 50% of children return for a second session.
- At least one parent submits feedback.
- LLM fallback rate < 20% of assessment completions.
- At least one child submits a reaction.
- Zero instances of LLM ghostwriting (from manual spot-checks).
- Zero parent requests for data deletion (indicating trust).
```

## 7. Gap Analysis: What the Proposal Misses

### 7.1 No "Device Handoff" Design

The parent creates the child on their device, then... hands the device to the child? Or does the child use a different device? The proposal doesn't address this.

For Alpha, the most likely scenario is a shared family tablet or the parent's phone. The child creation flow should end with a clear handoff moment: "把小文星球交给小星吧！" with a single large button that enters the child dashboard.

### 7.2 No Session/Timeout Consideration

If a child is using the product and walks away, what happens? The proposal doesn't address session management. For V0.4.1 Alpha, this is acceptable — there's no auth to time out. But the Alpha notice should mention that the parent is responsible for supervising device use.

### 7.3 The Proposal Defers "Full Auth" Without Defining What Minimal Auth Means

Section 5.3 says "full auth may be deferred if access remains invite-gated." But what prevents one Alpha family from accessing another family's data? In the current system, any URL like `/children/s1` is accessible to anyone.

For V0.4.1, the minimum security should be:
- Child IDs are UUIDs, not sequential integers (already the case)
- Parent-facing pages check that the requesting context matches the parent
- Direct URL manipulation to another child's dashboard returns data (current behavior) — this is acceptable for 3-5 trusted families but should be documented as a known Alpha limitation

### 7.4 Reading Canyon Remains "施工中" — No Mention in the Proposal

The proposal doesn't address what happens when an Alpha child clicks "阅读峡谷." The current behavior (friendly "施工中" message) is fine, but the proposal should mention it in the non-goals or known limitations section so Alpha parents aren't surprised.

## 8. Summary Verdict

**The V0.4.1 Alpha Enablement proposal is the right plan at the right time.** It directly addresses the critical gap identified in the V0.4 review: the product cannot be used by real families. The proposal shows mature product thinking across privacy, invitation model, feedback collection, and data observation.

**The main risk is scope.** The proposal defines enough work for 2-3 weeks of implementation, but frames it as a single "non-feature" release. A two-tier split (V0.4.1a: minimum viable Alpha entry → V0.4.1b: feedback and observation) would reduce risk and get families into the product faster.

### Priority-Ordered Recommendations

1. **Commit to the identity model before coding.** Use `ParentUser` + real parent rows. Defer invite codes (use manual links). This decision shapes everything else.

2. **Split into V0.4.1a and V0.4.1b.** Ship child creation + parent/child nav split + Alpha notice + deployment first. Add feedback systems and product events second.

3. **Add multi-child and device-handoff scenarios** to the manual QA checklist.

4. **Define Alpha success criteria** explicitly so the team knows when Alpha has produced enough data to plan V0.5.

5. **Write a deployment runbook** as part of V0.4.1a implementation, not as an afterthought.

6. **Keep the demo family path working** by leaving `FamilyTopbar` unchanged and adding Alpha-specific navigation separately.

### Verdict

Approve the proposal with the two-tier split recommended above. The product direction is correct. The scope discipline needs one more pass before implementation begins.
