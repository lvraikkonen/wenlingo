## Findings / 发现的问题

### Blockers Before V0.5b

**None.** V0.5a series has no critical bugs or security holes that would block starting V0.5b development.

However, the following should be addressed **in V0.5b preflight** before adding new LLM-powered features:

#### F1: LLMCallLog missing token/cost/latency fields

- **Evidence**: `LLMCallLog` in `apps/api/app/domain/models.py:293` has `provider`, `model`, `prompt_version`, `input_summary`, `raw_response`, `output_json`, `validation_ok`, `error_message`, `retry_count` — but no `prompt_tokens`, `completion_tokens`, `total_tokens`, `estimated_cost`, or `latency_ms`.
- **Risk**: Adding more LLM calls (AI sentence training) without cost tracking means operating blind on costs. For a small Alpha with 3-5 families this is manageable, but building the habit now prevents future surprises.
- **Recommendation**: Add token/cost/latency fields to `LLMCallLog` in a new migration as the first V0.5b task.
- **Suggested owner**: Codex

#### F2: Prompt management is ad-hoc, no registry

- **Evidence**: System prompt hardcoded in `HttpJsonLLMProvider.complete_json()` (`apps/api/app/services/llm_provider.py:157`). Task contracts in `TASK_RESPONSE_CONTRACTS` dict in same file. `prompt_version` defaults to hardcoded string `"v0.2-quality-spine-2026-05-14"` in every task function. No centralized prompt loading, no version tracking, no change review mechanism.
- **Risk**: Adding AI sentence training would scatter more prompts across code. Without a registry, prompt changes are untraceable, regression debugging is painful, and A/B testing is impossible.
- **Recommendation**: Create a code-level Python module prompt registry (e.g., `apps/api/app/prompts/`) as a V0.5b preflight task. DB-level registry or admin prompt editor can wait until V0.6+.
- **Suggested owner**: Codex (with Claude+gstack review of prompt structure)

#### F3: No startup guard for MAGIC_CODE_DEV_ECHO=true in production

- **Evidence**: Spec V0.5a says "Production startup must fail fast if `MAGIC_CODE_DEV_ECHO=true`." QA document notes "The current app does not fail startup automatically when dev echo is enabled." Code review confirms no startup guard exists.
- **Risk**: Operator error — deploying to production with Dev Echo enabled would expose Magic Code `123456` as a universal login credential.
- **Recommendation**: Add startup check in `app/main.py` or config validation that refuses to start if `MAGIC_CODE_DEV_ECHO=true` and environment is production (detected via `DATABASE_URL` not containing `localhost`, or a new `ENVIRONMENT=production` variable).
- **Suggested owner**: Codex

### Blockers Before External Alpha Families

#### F4: Real Magic Code email delivery not verified

- **Evidence**: Railway Dev QQ SMTP outbound blocked (`OSError: [Error 101] Network is unreachable`). All QA uses Dev Echo code `123456`. Real email arrival never tested end-to-end.
- **Risk**: Cannot invite real external Alpha families without working email delivery. Dev Echo is not acceptable for anyone outside the development team.
- **Recommendation**: Integrate an HTTPS API email provider (Resend, SendGrid, or Mailgun) in V0.5b preflight. These use standard HTTPS outbound, bypassing Railway SMTP restrictions.
- **Suggested owner**: Codex + manual ops for provider account setup

#### F5: Origin/Referer + non-JSON matrix not fully re-run

- **Evidence**: Latest QA document (`qa/2026-06-08-v0.5a-v0.5a.1-v0.5a.2-dev-manual-qa.md`) notes "Full invalid Origin/Referer and non-JSON state-changing request matrix was not re-run." Only basic checks (no-cookie, wrong-token) were verified.
- **Risk**: A state-changing endpoint without proper JSON/Origin guard could be vulnerable to CSRF from malicious origins.
- **Recommendation**: Run the full matrix as part of V0.5b QA, before inviting external families. Code review shows guards are in place (`require_auth_mode_state_change` calls both `require_allowed_origin` and `require_json_state_change`), so risk is low — but verification is prudent.
- **Suggested owner**: Codex manual QA or automated test

#### F6: Cross-family essay revision not verified in latest QA

- **Evidence**: V0.5a QA marked cross-family essay revision as unchecked. V0.5a.1/V0.5a.2 QA did not revisit.
- **Risk**: Theoretical — code review shows `require_essay_for_auth_mode` properly chains `essay_id → Essay.student_id → StudentProfile.parent_id → session parent`, and `require_student_for_parent` returns 404 (not 403) for cross-family access. Risk is low.
- **Recommendation**: Add one cross-family essay revision check to V0.5b QA smoke path.
- **Suggested owner**: Codex QA

### Should Fix During V0.5b

#### F7: Frontend test coverage is minimal

- **Evidence**: Codegraph reports "⚠️ no covering tests found" for `get_session_account`, `touch_parent_session`, `AuthSession`, `requestJson`, and most frontend API functions. Backend tests exist for auth boundaries, admin delete, and LLM logging. Frontend has effectively no Vitest coverage.
- **Risk**: Frontend regressions (like the disabled-account message bug or re-enabled login landing bug) are caught only by manual QA, which is expensive and slow.
- **Recommendation**: Add critical-path Vitest tests for `/alpha/start` state machine, auth session handling, and API client error mapping.
- **Suggested owner**: Codex

#### F8: `raw_response` in LLMCallLog may contain child writing text

- **Evidence**: `log_llm_result` stores `raw_response` from the LLM provider. The LLM response JSON includes feedback fields (encouragement, specific_improvement, etc.) but does NOT include the child's original writing text. The system prompt uses `<student_sentence>` XML tags for the student's input, and the LLM response does not echo these back. However, `raw_response` is a raw string — if the LLM provider ever echoes input, it could leak.
- **Risk**: Low but non-zero. The current prompt instructs the model to output only JSON, and the JSON schema doesn't include student text fields. But the raw response is stored verbatim, creating a theoretical leak path if the model behavior changes.
- **Recommendation**: Document this as a known observation. In V0.5b, add `input_summary` only (already safe), and consider truncating or summarizing `raw_response` if storage/ privacy concerns grow. Do not store full rendered prompts with student text in `LLMCallLog`.
- **Suggested owner**: Claude+gstack to review prompt safety periodically

#### F9: Legacy path endpoints still exist alongside `/me/` endpoints

- **Evidence**: Frontend `api.ts` has both `getAlphaChildren(parentId)` and `getMyAlphaChildren()`. Backend has both `/api/alpha/parents/{parent_id}/children` and `/api/alpha/parents/me/children`. When `AUTH_REQUIRED_FOR_ALPHA=true`, path-based endpoints verify `parent_id == session parent`.
- **Risk**: Legacy endpoints create confusion about which is canonical. Path-based endpoints could be called without session if `AUTH_REQUIRED_FOR_ALPHA=false`.
- **Recommendation**: Gradually migrate frontend to use only `/me/` endpoints. Keep backend path-based endpoints with auth guard for backward compatibility but mark as deprecated in code.
- **Suggested owner**: Codex

### Can Defer

#### F10: Admin Alpha Lite feature scope

- **Evidence**: Admin now includes invite generation, revocation, account list, disable/enable, and hard delete. This is more than the original "Lite" concept, but still manageable without a full Admin v2.
- **Risk**: Admin complexity grows with each release. Currently acceptable for Alpha.
- **Recommendation**: Monitor but defer. Do not add filtering, export, or audit dashboards in V0.5b without a deliberate Admin v2 design review.
- **Suggested owner**: Claude+gstack to gatekeep

#### F11: Legacy family migration not fully end-to-end tested with real migrated data

- **Evidence**: QA verified the migration UI flow appears but did not verify a V0.4.1c family with real assessment/sentence/essay history before and after binding. Given that the migration is additive (no data movement) and the binding only sets `ParentUser.account_id`, risk is low.
- **Risk**: Very low — migration is additive, no data is moved or transformed.
- **Recommendation**: Before inviting the first external Alpha family, verify one legacy family migration with real data.
- **Suggested owner**: Manual ops

## Architecture Review / 架构评审

### Auth Model: ✅ Strong

`ParentAccount 1 — 1 ParentUser — many StudentProfile` 设计正确。

关键设计决策验证：
- `ParentAccount` 和 `ParentUser` 分离：auth identity 和 family profile 解耦，为未来多 guardian、billing、account recovery 留空间
- Session 只存 `token_hash`：即使数据库泄露，攻击者无法伪造 session
- `get_session_account` 同时检查 revoked、expired、account status：三重验证
- `AUTH_REQUIRED_FOR_ALPHA` feature flag：优雅的渐进式 rollout/rollback

### API Authorization Model: ✅ Strong

授权链实现正确：
- `require_student_for_parent` (`auth_deps.py:116`)：`student.parent_id == parent.id`，不匹配返回 404
- `require_essay_for_parent` (`auth_deps.py:127`)：`essay → student → parent`，完整链
- `require_auth_mode_state_change` (`auth_deps.py:61`)：session 验证 + Origin + JSON body，三重守卫
- Admin endpoints 使用 `require_alpha_admin_state_change`：token + JSON + Origin
- `/me/` endpoints 从 session 取 parent_id，不信任路径参数

### Frontend Session Handling: ⚠️ Adequate, improvement possible

`/alpha/start` state machine 经过 hotfix.1 后正确：
- Session check → existing session (skip to children) / legacy bind / new family
- Disabled account → correct error message
- Re-enabled account → correct landing
- Legacy bind retry → works without re-verify

Frontend 仍使用一些 legacy path endpoints（`getAlphaChildren(parentId)` 等），但逐步迁移到 `/me/` endpoints 是好的方向。

### Admin Alpha Design: ✅ Appropriate for Alpha stage

- Token-gated，独立于 parent session
- 只读 overview + family detail（sanitized）
- Write 操作受限：invite gen/revoke, account disable/enable, test-account hard delete
- Hard delete 有完善的 allowlist + confirmation guard
- 没有过度工程化（无 admin sessions, roles, filters, exports）

### Data Preservation and Rollback: ✅ Strong

- Additive migration：只加表/列，不改动现有数据
- `AUTH_REQUIRED_FOR_ALPHA=false` 作为 feature flag
- Rollback 策略清晰：disable auth → legacy flow 仍然工作
- Learning data 不移动、不删除

### LLM Call Logging Architecture: ⚠️ Foundation exists, needs extension

当前 `LLMCallLog` 有基本结构但缺少关键字段：

| 现有字段 | 缺失字段 | 优先级 |
| --- | --- | --- |
| provider, model | — | — |
| task_type, task_name | — | — |
| prompt_version (hardcoded) | prompt_key | High |
| input_summary | — | — |
| raw_response | — | — |
| — | prompt_tokens | High |
| — | completion_tokens | High |
| — | total_tokens | High |
| — | estimated_cost | High |
| — | latency_ms | Medium |
| student_id | parent_id (derivable via student) | Low |

`input_summary` 设计良好：不包含 child writing text，只记录长度和元信息（如 `"句子快练；原句长度：12；升级句长度：25；目标：加动作描写"`）。

### Prompt Management Architecture: ⚠️ Needs establishment

当前状态：
- System prompt 硬编码在 `HttpJsonLLMProvider.complete_json()`
- Task contracts 硬编码在 `TASK_RESPONSE_CONTRACTS` dict
- `prompt_version` 作为参数传递但默认值硬编码
- 无 prompt registry、versioning、change tracking

建议 V0.5b 建立 code-level prompt registry：

```
apps/api/app/prompts/
├── __init__.py
├── registry.py          # PromptRegistry: key → (version, template)
├── system.py            # system_prompt template
├── sentence_feedback.py # sentence_upgrade_feedback prompt
├── essay_feedback.py    # essay_feedback prompt
├── revision_feedback.py # essay_revision_comparison prompt
└── sentence_training.py # NEW: AI sentence training prompts
```

每个 prompt module 返回 versioned template，`LLMCallLog` 记录 `prompt_key` + `prompt_version`。

不需要 V0.5b 做 admin prompt editor 或 DB-level prompt storage。代码级 registry 足够支撑 3-5 个任务的 Alpha 阶段。

## V0.5b Scope Recommendation / V0.5b 范围建议

### Recommendation: `V0.5b = AI Infrastructure Foundation + AI Sentence Training Thin Slice`

### Goal

建立 AI 基础设施（cost tracking、prompt registry），然后基于此基础设施实现 AI 句子训练引擎的 thin vertical slice，让孩子可以进行 AI 自动生成的句子训练题。

### Non-goals

- Writing Castle Pre-writing（推迟到 V0.6）
- 完整句子训练模块（只做 thin slice，3-5 种题型，不追求完整题型库）
- Admin prompt editor UI
- A/B testing framework
- Reading Canyon 扩展
- 公开注册或商业化

### Preflight Phase (V0.5b Week 1)

1. **LLMCallLog 扩展** — 添加 `prompt_key`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `estimated_cost`, `latency_ms` 字段；新增 migration
2. **Prompt Registry** — 创建 `apps/api/app/prompts/` 代码级 registry，迁移现有 prompts
3. **Email Provider Hardening** — 集成 Resend 或 SendGrid HTTPS API；更新 `docs/alpha-deploy.md`；设置 Railway Dev 环境变量
4. **Dev Echo Startup Guard** — 生产环境启动时如果 `MAGIC_CODE_DEV_ECHO=true` 则 fail fast
5. **LLMCallLog 记录 prompt_key** — 每次 LLM 调用记录使用的 prompt key + version

### Main Phase (V0.5b Week 2-3)

6. **AI Sentence Training Engine — Thin Slice**
   - 3-5 种基础题型（扩句、加动作描写、加心理感受、加比喻、写具体/生动）
   - 难度控制（四年级）
   - 孩子提交改写后的句子
   - AI 短反馈（一句肯定 + 一个亮点 + 一个小建议 + 一个升级示例）
   - "再挑战一题"/"下一关"
   - 保存题目、孩子答案、AI 反馈、完成状态
   - XP/成长事件集成
7. **Admin Cost/Usage 基础视图** — 按日期、task_type、model 统计调用次数和成本
8. **ProductEvent Taxonomy Cleanup** — 整理现有 event types，确保新 sentence training events 符合 privacy-safe 规范

### Acceptance Criteria

- LLMCallLog 记录每次调用的 token 数和估算成本
- 所有 prompt 有 stable key 和 version
- 真实 Magic Code email 可通过 HTTPS API 送达（Railway Dev 验证）
- 生产环境无法以 `MAGIC_CODE_DEV_ECHO=true` 启动
- 孩子可以完成 3+ 种题型的句子训练
- AI 反馈展示正确（肯定 + 亮点 + 建议 + 示例）
- Admin 可以看到基础 cost summary（按天/task/model 总计）
- 所有现有流程（invite, assessment, sentence, essay, revision, reaction, summary, admin, demo）不被破坏
- Prompt key + version 记录在 LLMCallLog 中

### Risks

| Risk | Mitigation |
| --- | --- |
| AI sentence training 增加 LLM 调用成本 | 先建 cost tracking，设置 daily limit per student per task（复用现有机制） |
| Prompt registry 过度工程化 | 只用代码级 Python module，不做 DB/UI |
| Email provider 集成延迟 | 可以在 Dev Echo 下并行开发句子训练；email 是独立 track |
| 句子训练 quality 不够好 | Thin slice 策略：先做 3 种题型，QA 后决定是否扩展 |

### Estimated Implementation Complexity: **Medium**

- LLMCallLog 扩展 + migration: Small
- Prompt registry: Small
- Email provider: Small-Medium (integration + config + docs)
- Dev Echo guard: Small
- AI Sentence Training: Medium (new route + new prompt + new UI + XP/game integration)
- Admin cost view: Small
- Total: Medium (2-3 weeks for Codex + Superpowers)
