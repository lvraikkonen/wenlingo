## Bug #1: Alpha Child Dashboard Shows UUID Instead of Name (HIGH)

### Evidence

Deployed Railway app, child dashboard page for a real Alpha child:

- Topbar shows: `当前孩子：54533644-b49d-4fc4-9b72-be532b54584e`
- Page heading correctly shows: `小星的小文星球` (from dashboard API)
- Child switcher nav shows only demo children (小宇, 小晴, etc.)
- Clicking any demo child navigates away from the Alpha child with **no way back**

### Root Cause

`FamilyTopbar.tsx:42`:
```typescript
const currentStudentName = currentStudent?.name ?? currentStudentId;
```

`FamilyTopbar` calls `demoLogin()` (line 18) which only returns the 4 seeded demo children (`s1`, `s2`, `s3`, `s4`). A real Alpha child has a UUID that won't match any demo child, so `currentStudent` is `undefined` and the raw UUID is displayed.

The child switcher nav (line 90-98) renders only demo children. Alpha children are invisible to the topbar.

### Impact

- Every Alpha family child dashboard shows a UUID instead of the child's name in the topbar
- Child switcher is misleading — shows demo children that aren't the user's real children
- Clicking a demo child permanently navigates away from the real Alpha child
- This makes the "parent/child navigation split" requirement **unmet** for Alpha users

### Recommended Fix

`FamilyTopbar` must be aware of Alpha children. Options:

**Option A (minimal):** Check `localStorage` for `wenlingo_alpha_parent_id`. If present, skip the `demoLogin()` call and render a simplified topbar that shows the current child's name (fetched from the dashboard API response, which already returns the correct name) and hides the demo child switcher.

**Option B (preferred):** Pass the child list from the parent page into the topbar, or fetch it from the alpha children API when an alpha parent context exists. Show only the parent's real children in the switcher.

Either fix should be scoped to V0.4.1a (hotfix), not deferred to V0.4.1b.

## Bug #2: AI Feedback Latency Without Clear Loading Indicator (MEDIUM)

### Evidence

Three AI feedback flows have inconsistent loading UX:

| Flow | Spinner | Status text | Visibility |
|------|---------|-------------|------------|
| **Assessment** ("生成能力草图") | None | "AI 教练正在整理第一张能力草图" (small muted text) | Low — easy to miss |
| Sentence ("提交给 AI 教练") | `Loader2` animate-spin | "AI 教练正在看你的句子" (orange bg) | Good |
| Essay ("获得点评") | `Loader2` animate-spin | "AI 教练正在读你的初稿" (plain text) | Medium |
| Essay revision ("提交二稿") | `Loader2` animate-spin | "AI 教练正在比较两次作文" (plain text) | Medium |

The assessment flow — the **first AI interaction** a new Alpha child experiences — has the weakest loading indicator. The button disables but the status text is easily overlooked. With the configured LLM provider taking 3-10 seconds, this creates uncertainty.

### Specific Issues

1. Assessment page (`apps/web/src/app/children/[studentId]/assessment/page.tsx:313-319`): no spinner, text uses `text-[var(--wen-muted)]` which is low-contrast
2. No skeleton or progress indicator during the LLM round trip
3. User reported: "AI的反馈延迟很明显，用户端并不清楚怎么样了"

### Recommended Fix

Add a `Loader2` spinner to the assessment submit button (consistent with sentence and essay pages) and promote the status text to a more prominent visual treatment:

```tsx
// In the assessment writing step, when isSubmitting:
<button disabled>
  <Loader2 className="h-4 w-4 animate-spin" />
  AI 教练正在分析...
</button>
```

Also add a prominent status banner (like the sentence page's orange-bg banner) while waiting.

## Code Quality Observations

### What's Good

1. **Alpha route module** (`apps/api/app/api/routes/alpha.py`) is clean and self-contained. Single-file route with clear helper functions. Backend ownership checks are enforced: `_get_parent_child` verifies `student.parent_id == parent_id` before returning data.

2. **Input validation** is thorough: nickname trimming, length limits, grade range, display name normalization. Both client-side and server-side validation present.

3. **localStorage helpers** (`apps/web/src/lib/alphaParent.ts`) handle edge cases: SSR safety (`typeof window === "undefined"`), storage quota errors, private browsing mode.

4. **Alpha start page** correctly handles the "already have a parent" case with clear UX: "继续使用当前 Alpha 家庭" vs "重新创建 Alpha 家庭".

5. **Device handoff** is a clean state transition — `createdChild` state swaps the form for the handoff confirmation, no route change needed.

6. **Parent summary API** correctly rejects cross-parent access (line 119-123), aggregates real `AbilityHistory` rows, and provides distinct empty/populated states.

7. **Deployment runbook** is thorough: covers first-deploy bootstrap, ongoing migration, recovery from migration failures, CORS configuration, smoke test steps, and rollback guidance.

### What Needs Attention

1. **FamilyTopbar hardcodes demo flow.** `FamilyTopbar.tsx` is the only component coupling child pages to the demo path. Alpha child pages inherit this coupling unintentionally.

2. **No Alpha-aware navigation on child pages.** When a child enters via the Alpha handoff, they land on `/children/{uuid}` which renders `FamilyTopbar`. There's no "back to parent" link. The child is stranded in the child space with only demo navigation.

3. **Assessment loading state is the weakest of three AI flows.** The sentence page has the best pattern (spinner + prominent status banner). The assessment should match it.

4. **`demoLogin()` is called on every child page render** even for Alpha children where it will always fail to find the current child. This is wasted API calls.

5. **No `FamilyTopbar` tests for the Alpha child case.** Tests exist (`family_topbar.test.tsx`) but don't cover the "current student not found in demo response" code path.

## Regression Risk: Demo Flow

The demo entry path at `/` still works: clicking "进入家庭内测" calls `demoLogin()` and shows 4 demo children. Demo child dashboards render correctly with names and proper topbar navigation.

**However**, if a demo child navigates to a page that shares `FamilyTopbar` while the browser also has an `wenlingo_alpha_parent_id` in localStorage, the topbar still uses demo children only. This is technically correct for the demo path but creates a confusing experience if the same browser is used for both Alpha and demo testing.

## V0.4.1b Readiness Assessment

### What V0.4.1b is supposed to include (from spec)

- Invite code table and invite validation
- Product events table
- Child task feedback / reaction collection
- Parent usefulness feedback
- Admin Alpha dashboard
- Formal analytics dashboard
- Full data deletion/export tooling
- Full authentication
- Reading Canyon
- Full weekly report
- Full gamification expansion

### Prerequisites Before V0.4.1b Design Begins

**BLOCKING: Bug #1 must be fixed first.** The navigation split between parent and child is broken for Alpha users. Designing V0.4.1b on top of a broken V0.4.1a means:
- Child reaction collection (a V0.4.1b feature) would be attached to a dashboard that shows the wrong name
- Parent feedback collection would flow from a summary page that the parent can reach, but the child space they enter from has broken navigation
- Observational data from Alpha families would be tainted by confusion over the UUID display

**NOT BLOCKING: Bug #2 is a UX improvement** that can be fixed alongside V0.4.1b design. The loading indicators exist — they just need strengthening.

### Recommendation

Fix Bug #1 as a V0.4.1a hotfix. Then begin V0.4.1b design with:

1. **Highest priority for V0.4.1b:** invite codes + product events table. These are the minimum observability infrastructure needed to learn from the Alpha. Without product events, you're flying blind on whether families complete the assessment, where they drop off, and what they click.

2. **Second priority:** child task reaction + parent usefulness feedback. Simple thumbs-up/thumbs-down on AI feedback, and a "was this summary useful?" on the parent summary page. These close the learning loop with real users.

3. **Defer to V0.4.2+:** admin dashboard, full analytics, Reading Canyon, full weekly report, gamification expansion. These need more design work and shouldn't block the feedback loop.

### V0.4.1b Design Constraints

- Keep the same browser-held Alpha parent context (no auth system yet)
- Add invite codes as a lightweight gate before parent creation (validate code → create parent)
- Product events should be a simple append-only table with `event_type`, `student_id`, `parent_id`, `payload JSON`, `created_at`
- Child reaction: one emoji click per AI feedback (😊 😐 😞)
- Parent feedback: one "有帮助" / "没帮助" per summary view

## Summary Verdict

**V0.4.1a ships the core Alpha entry flow correctly but has one high-severity bug that breaks the child dashboard experience for real Alpha users.** The UUID-in-topbar bug is a direct consequence of `FamilyTopbar` being unaware of the Alpha path — a coupling that the spec explicitly warned against ("Do not do a broad rewrite of FamilyTopbar in V0.4.1a" was followed too literally; the component needed at minimum a conditional skip for Alpha children).

The backend implementation is solid. The Alpha API routes are well-structured with proper ownership checks. The deployment runbook is thorough and the Railway deployment is live and functional. The parent summary correctly aggregates real data and distinguishes empty vs populated states.

**V0.4.1b design can begin after Bug #1 is fixed.** The Alpha Feedback & Observation phase (invite codes, product events, reactions, parent feedback) is the right next step. The infrastructure is ready; what's missing is the observability to learn from the first 3-5 families.

## Handoff to Codex

### Goal
Fix the two Alpha bugs before inviting more families: (1) child dashboard topbar shows UUID instead of name and can't navigate back from demo children, (2) assessment AI loading indicator is too subtle.

### Source Documents
- `specs/2026-05-25-v0.4.1a-minimum-viable-alpha-entry-design.md`
- `reviews/2026-05-27-v0.4.1a-alpha-entry-gstack-review.md` (this document)

### Non-Negotiables
- Alpha child dashboard must show child name in topbar, not UUID
- Demo child switcher must not appear for Alpha children
- Assessment submit button must show a spinner during LLM wait
- Demo flow (`/` → demoLogin → seed children) must still work
- No rewriting `FamilyTopbar` architecture — minimal conditional change

### Acceptance Criteria
- Open `/children/{alpha-child-uuid}` in a browser with `wenlingo_alpha_parent_id` set → topbar shows child name, no demo children in switcher
- Navigate from parent children list into child dashboard → can return to parent pages
- Open `/children/s1` (demo child) without alpha parent context → topbar shows demo children as before
- Click "生成能力草图" in assessment → button shows spinner + prominent status text during LLM wait
- Sentence page and essay page loading states unchanged (they already work)

### Do Not Do
- Don't add authentication
- Don't rewrite FamilyTopbar into a new component
- Don't change the assessment API or backend
- Don't add a new route for child navigation
- Don't modify the demo seed data
