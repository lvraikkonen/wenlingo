## Executive Verdict

**RELEASE RECOMMENDATION: SHIP-WITH-FOLLOW-UPS** (revised after the paired
`/autoplan` dual-voice review — see
`reviews/2026-06-26-v0.6b-topic-scaffold-autoplan-review.md`). The V0.6b Topic
Scaffold System is one of the cleanest, best-scoped implementations in this
codebase. It passes all 8 Scope Guard checks with no scope creep, preserves
every V0.6a compatibility contract, and all three release-gate test suites are
green (backend 192, web 174, E2E 2).

The independent Codex voice in the `/autoplan` pass corroborated the scope guard
AND surfaced two HIGH items this single-pass review missed or overstated, both
of which must be closed (handed to Codex) before V0.6b is called complete:

- **F1 — AI can self-certify a source ref.** The material-card generation path
  validates `source_answer_ids` and slot ids but accepts a model-supplied
  `child_confirmed`/`reading_material` `source_ref` at face value — including
  for expository factual claims — without proving the source exists. Hole in the
  "AI must not invent factual claims" principle (`ai_tasks.py:657-659`,
  `writing_castle_state.py:306-374`). Mitigated by the `NO_GHOSTWRITE` prompt +
  deterministic fallback; fix is server-enforced ref provenance.
- **F4 — Parent summary web UI doesn't render the v0.6b fields.** The backend
  returns them (`alpha.py`), but `summary/page.tsx:183-215` renders only legacy
  process counts. The "parent can understand progress" goal is met at the API,
  not in the UI parents see.

Plus a MEDIUM spec-deviation (F5: scaffold change is over-rejected vs §11's
topic-analysis-only case) to decide on. F2/F3/F6/F7/F8/F9 are LOW/MEDIUM
hardening. Details and adjudication in the autoplan review.

The implementation does exactly what the design asked: it establishes a
backend-owned scaffold architecture (4 P0 families, deterministic unsupported
fallback, snapshot immutability, source-chain validation) without leaking any
template-specific logic into the frontend and without pulling in any V0.6c/V0.7
features. AI topic-type suggestion remains correctly unimplemented (P1).

## Architecture Review

**Single source of truth.** The backend `ScaffoldTemplate` registry
(`writing_castle_scaffold.py`) is the only place template structure is defined.
All backend reads go through one accessor, `resolve_essay_scaffold(essay)`
(`writing_castle_state.py:174-187`), used by every generation endpoint, the
draft editor, resume, and parent summary.

**Snapshot immutability + fail-closed accessor.** The accessor reads the saved
snapshot from `outline.scaffold`, validates `material_card.scaffold_ref` matches
`{topic_type, topic_variant, scaffold_template_version}`, and raises
`scaffold_ref mismatch` on divergence — it never re-resolves from the live
registry. `_validate_scaffold_slot_shape` (141-143) rejects malformed snapshots.
Tests `test_resolve_essay_scaffold_returns_saved_snapshot_not_registry_rebuild`
and `test_resolve_essay_scaffold_fails_closed_on_ref_mismatch` lock both
behaviors. This means a future registry bump or label change cannot silently
mutate an in-progress child essay — exactly the §8 contract.

**409 generation gate.** `_resolved_scaffold_or_legacy` (`writing_castle.py:237-241`)
returns `409 resolved scaffold is required` for any v0.6b session that lacks a
resolved scaffold. It is called at the head of topic-analysis, material-
questions, material-cards, outline, save-material-cards, and save-outline.
`submit_first_draft` deliberately does **not** call it — direct draft must stay
open for unsupported/deferred prewriting (§12), confirmed by the E2E
direct-draft test.

**Scaffold change rejection.** `save_scaffold_selection` raises
`409 scaffold cannot change after prewriting content exists` once any of
topic-analysis-generated / answers / cards / outline-sections exist
(`writing_castle.py:427-436`). No silent migration — the preserve-answers flow is
correctly deferred to V0.6c. Four tests cover the boundary (after answers,
topic-analysis, cards, outline).

**Observability.** `ProductEvent` payloads carry scaffold metadata via
`_scaffold_event_payload` (`writing_castle_state`-adjacent helper at
`writing_castle.py:193-201`) plus `server_completed_at`, and `scaffold_selected`
is registered in the alpha event allowlist with the full set of scaffold/timing
payload keys. `LLMCallLog` gains additive, nullable/defaulted columns
(`topic_type`, `topic_variant`, `scaffold_template_version`,
`source_policy_summary`, `duration_ms`, `request_started_at`,
`response_received_at`) in migration `20260625_v06b_llm_meta`. Frontend timing
fields are accepted-but-optional, so V0.6b does not block on frontend
instrumentation — consistent with §14.

**Migration safety.** `20260625_v06b_llm_meta` is purely additive (`add_column`
with `server_default`, three new indexes), fully reversible in `downgrade()`,
and chains linearly off the true previous head `20260618_v05c1_daily_limit`
(verified — no branchpoint, no merge needed). The revision id was shortened to
fit Alembic's 32-char limit (commit `f97989f`) — good catch.

**AI determinism.** The fallback path (`writing_castle_ai.py`) is scaffold-aware:
`_source_refs_for_answer` (105-128) chooses `imagined_setting` for imaginative,
`child_confirmed` for expository, `observation` for person-portrait,
`real_experience` otherwise. Legacy v0.6a fallbacks (`_legacy_fallback_*`) are
preserved so old sessions keep deterministic behavior. `NO_GHOSTWRITE` is
embedded in every prompt contract.

## Multi-Angle Review

### Product
- **Improves the child's learning?** Yes. The four P0 families map to the
  highest-value 3-6 grade taxonomy slice and give the child a scaffold that
  "understands my kind of作文" instead of forcing every topic into one narrative
  wizard. Variant slots (`learned_skill`, `invention_design`, `experiment_process`)
  make questions materially more relevant.
- **Positive feedback preserved?** Yes. Encouragement copy, the staged "AI 教练
  正在读你的初稿…" wait, and the `child_confirmed` lifecycle all keep the
  coaching, non-judgmental stance. No copy-ready body is ever generated.
- **Parent can understand progress?** Partially — **the API is ready, the UI is
  not (F4).** The backend parent summary now returns selected topic type (child
  + parent label), selection source (manual/ai/fallback), material source
  categories, unsupported-override flag, and `copy_ready_ai_body_generated:
  false`. **But the parent summary web page (`summary/page.tsx`) does not yet
  render any of these** — it shows only legacy process counts. Closing this UI
  gap is a must-do follow-up before V0.6b is complete (see autoplan review F4).

### UX
- **Manual selection is genuinely primary.** The four-family choice screen is
  the P0 entry; AI suggestion is absent, not just demoted. Good.
- **Unsupported fallback is honest and actionable.** On `写信`/`推荐一本书`/
  `围绕中心意思写`, the child sees "这类题目我们还在学习中" plus three real exits:
  pick the closest family, **直接写初稿**, or **重新输入题目**
  (`ClassroomPrewritingWizard.tsx:502-544`). No silent coercion.
- **Staged loading copy** is well-crafted, child-facing, and reinforces "AI is
  helping you think, not writing for you" (e.g. "正在检查有没有替你编内容……").
- **Minor UX note:** when an unsupported topic is detected, the fallback copy
  could name the detected family more concretely (e.g. "这更像书信/读后感"),
  matching the spec's suggested copy in §7. Current copy is safe but generic.
  Non-blocking; nice V0.6b.1 polish.

### Architecture
- Backend owns the registry, versioning, snapshot, and validation; frontend is a
  thin renderer of the snapshot. This is the right boundary and will scale to
  V0.6c/V0.7 without frontend rewrites.
- Prompt keys stay task-level with scaffold in the payload — adding families
  later requires zero new prompts.
- Source-chain model (answer → card `source_refs` → outline `source_card_ids`) is
  sound; the `topic_requirement` factual boundary is a thoughtful safety detail.

### QA
- Coverage maps cleanly to the §15 QA matrix: each P0 family has an API path;
  expository has a factual-source-failure case; unsupported detection covers the
  three release-blocking topics with AI disabled; manual selection works without
  AI; scaffold-change-after-content is rejected in four states; legacy resume and
  direct-draft regressions are covered by both unit and E2E.
- The one matrix item not exercised at the browser level beyond vitest is the
  imaginative/person full E2E — the single E2E uses `person_portrait`. Vitest
  covers the dynamic rendering for both, so this is acceptable for V0.6b.

### Release
- Migration additive + reversible; linear chain; no data backfill needed.
- All release gates green. No feature flags required for P0.
- No new env vars or infra dependencies introduced.

### Documentation
- Spec and plan are accurate to the implementation. The plan's Task 7 example
  referenced a stale `/classroom-essays` path; the implementation correctly uses
  `/classroom` and the frontend `api.ts` matches — doc-only nit, no code impact.
- `qa/2026-06-25-v0.6b-topic-scaffold-system-qa.md` matches the gates that now
  pass. Consider updating its date/run-results footer with the 2026-06-26 run.

## Non-Blocking Observations (recommended follow-ups, none block V0.6b)

1. **Frontend `DEFAULT_SUPPORTED_TOPIC_TYPES` drift.**
   `ClassroomPrewritingWizard.tsx:84-105` hardcodes the four families as a
   defensive fallback when the backend returns no choices, and its
   `display_name_parent` values (`记叙一件事`, `人物描写`, …) differ from the
   backend's (`叙事类：经历 / 活动 / 成长 / 情绪`, …). Today this only renders if
   the backend omits choices, so it is cosmetic — but if backend labels evolve,
   the fallback will silently diverge. **Follow-up:** either drop the fallback
   (creation always returns choices) or derive parent labels from the same
   source.

2. **Deterministic fallback index-mapping.** `fallback_material_cards` maps
   `answer[i] → slot[i]` by position and stamps `child_confirmed` for expository
   factual slots. This is acceptable because the AI path re-validates every card
   against `content_kind=="factual"` and the source policy, but positional
   mapping can mis-attribute a factual answer to a non-factual slot in edge
   cases. **Follow-up (V0.6b.1):** consider slot-keyed answer hints so the
   fallback respects `content_kind` more precisely. Low priority.

3. **Unsupported fallback copy specificity.** See UX note above — surface the
   detected family name in the fallback message per §7.

4. **Plan doc stale path.** Update the Task 7 example in the implementation plan
   to `/classroom` for future readers.

## Handoff Note for Codex

**Two items are required to complete V0.6b** (from the `/autoplan` dual-voice
review, see `reviews/2026-06-26-v0.6b-topic-scaffold-autoplan-review.md`):

- **F1 (HIGH) — server-enforce source-ref provenance.** On the material-card
  generation path, reject model-supplied `child_confirmed` refs (those must be
  created server-side by the child-confirmation lifecycle) and validate
  `reading_material` refs against stored records — otherwise a hallucinated fact
  can look sourced. Add a negative test: model returns a fabricated fact ref →
  rejected. (`ai_tasks.py:657-659`, `writing_castle_state.py:306-374`.)
- **F4 (HIGH) — render v0.6b summary fields in the parent summary page.** The
  backend returns them; `summary/page.tsx` ignores them. Add web tests.

The four items below remain optional V0.6b.1 polish (plus F2/F3/F5/F6/F7/F8/F9
in the autoplan review):
- Item 1 and 3 are small frontend changes; add/adjust vitest cases.
- Item 2 is a `writing_castle_ai.py` fallback refinement; add a state/unit test
  for slot-keyed attribution.
- Do **not** expand to a 5th family, add `topic_type_suggestion`, or introduce
  streaming/difficulty in V0.6b — those remain V0.6c/V0.7 per the roadmap.
