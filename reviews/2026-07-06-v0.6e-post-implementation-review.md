## 1. Executive Summary

**Recommendation: GO WITH FOLLOW-UPS.**

V0.6e is a large, disciplined release. The highest-risk invariants — migration
linearity, exactly-once daily-limit consumption, idempotent submission ledger,
auth boundaries on every new endpoint, no-partial-save, and no provider data
reaching the browser — all hold under direct inspection. The submission ledger
is the single reservation owner; consume/release are idempotent per reservation
token under `SELECT … FOR UPDATE`; the hard daily-limit gate is the
`LLMCallLog` success count (the counter is a soft hold), so even accounting edge
cases cannot over-consume. The focused backend suite was independently re-run:
**130 passed, 2 warnings**.

It is **safe to merge into `main` for Railway Dev browser QA.** No blocker must
be fixed first. The one finding worth attention before this lands (P1) is that
`cleanup_stale_submissions` is implemented but never wired to a lifespan or
scheduler — process-loss mid-stream orphans a submission row and pins that
`client_submission_id` to `202 IN_PROGRESS`. It does not block Dev QA (low
volume, the child can use a new id, the reservation expires lazily, the hard
limit is unaffected) but should be wired before this release ships to real
users. The other findings are P2/P3 reliability and completeness items,
including a disconnect-after-visible-content recovery/UX gap the spec calls for
that the frontend does not yet implement.

## 15. Findings

### [P1] `cleanup_stale_submissions` is implemented but never wired (process-loss recovery gap)

- Evidence: `cleanup_stale_submissions` defined at `apps/api/app/services/essay_feedback_submission.py:316`, but `grep -rn cleanup_stale_submissions apps/api/app` finds NO caller (no lifespan, no scheduler, no periodic task). Contrast: prewriting stale recovery IS wired lazily (`recover_stale_job` on status/events access, writing_castle.py:795/1074/1102).
- Why it matters: If the process exits/deploys/crashes mid-stream, the `EssayFeedbackSubmission` row stays in `streaming_started`/`saving_result` forever, and that specific `client_submission_id` returns `202 IN_PROGRESS` on every retry (`_submission_is_provider_running` → `StreamingAlreadyInProgress`). The reservation itself expires lazily via `_release_stale_reservations` on the next reserve, and the hard daily-limit gate (`LLMCallLog` success count) is unaffected, so this does NOT cause double-consume or a stuck limit. Spec invariant 17 / §7.3 mandate cleanup for process loss. Asymmetric with prewriting jobs.
- File(s): `apps/api/app/services/essay_feedback_submission.py`; wiring point needed (e.g., `app/main.py` lifespan or a periodic task).
- Suggested fix: invoke `cleanup_stale_submissions` on a periodic schedule (lifespan-spawned task every N seconds) and/or lazily on submission access for the requested id (mirroring prewriting's `recover_stale_job` pattern). 
- Tests to run after fix: `tests/test_essay_feedback_submission.py` (add a process-loss/stale-expiry case); focused backend suite.
- Blocks merge? **No** for Railway Dev QA. **Yes** before this release reaches real users.
- Confidence: 9/10

### [P2] Disconnect-after-visible-content: UI shows generic failure instead of recovering the saved result

- Evidence: On a stream error after `sawPreview`, the page re-throws → outer catch shows `setError("这次提交没有成功。先别急，检查一下网络后再试一次。")` (`apps/web/src/app/children/[studentId]/essay/page.tsx:329–331, 365–372`). When the backend had already completed and saved after the disconnect, the saved result is durable but the child is not guided to it.
- Why it matters: Spec §12.1 wants child-friendly "AI coach is still saving" copy and recovery from current essay state / archive. Current behavior can also lead to a duplicate provider call if the child re-clicks submit (which generates a new `client_submission_id`), though the hard daily-limit gate bounds any over-consume. The data is safe; this is a recovery/UX gap.
- File(s): `apps/web/src/app/children/[studentId]/essay/page.tsx`; also `ClassroomPrewritingWizard.tsx` first-draft path.
- Suggested fix: on post-preview stream failure, attempt recovery via the submission ledger / `fetch_url` / archive before showing a hard error; show "still saving" copy.
- Tests to run after fix: `essay_reading_report_flow.test.tsx`; add a disconnect-after-visible recovery case.
- Blocks merge? No.
- Confidence: 7/10

### [P3] `_run_prewriting_job` holds a `session_factory` session open during provider execution

- Evidence: `with session_factory() as session:` wraps `await material_card_generation(..., session=session, …)` and the subsequent commit (writing_castle.py:875–909).
