## Feedback Logic Deep Dive

### Current Frontend Behavior

File: `apps/web/src/components/FeedbackReaction.tsx`

```
User sees: "这次 AI 教练的提示对你有帮助吗？" + 😊 😐 😞

1. Component mounts → selected = null (no fetch of existing state)
2. User clicks 😊 → setSelected("positive") immediately (optimistic)
3. POST /api/students/{studentId}/feedback-reactions fires
4. On success: nothing further happens (selected already set)
5. On failure: setError("这次没有保存成功，稍后可以再点一次。")
   selected STAYS on "positive" (never reverts)
6. User clicks 😐 → setSelected("neutral") immediately
   POST fires again, upserts the same row
7. User refreshes page → selected = null again
   Even though database has reaction = "neutral"
```

Parent summary feedback (`ParentSummaryFeedback.tsx`) has identical behavior pattern.

### Current API Behavior

File: `apps/api/app/api/routes/reactions.py`

```
POST /api/students/{student_id}/feedback-reactions

1. Validate student exists
2. Validate target belongs to student (ownership check)
3. SELECT existing FeedbackReaction WHERE (student_id, target_type, target_id)
4. If exists → UPDATE reaction, updated_at, alpha_session_id
5. If not exists → INSERT new FeedbackReaction
6. ALWAYS: INSERT ProductEvent(event_type="child_feedback_reaction_submitted", ...)
   (wrapped in try/except, non-blocking)
7. session.commit()
8. Return reaction object
```

### Current Database Behavior

- **FeedbackReaction table**: UNIQUE constraint `uq_feedbackreaction_student_target` on `(student_id, target_type, target_id)`. Upsert means exactly ONE row per student per target at all times.
- **ProductEvent table**: NEW row inserted on EVERY POST (every click). No uniqueness constraint. Event name is always `child_feedback_reaction_submitted` regardless of whether this is a first submission or an update.
- **ParentFeedback table**: Same pattern — UNIQUE constraint `uq_parentfeedback_parent_student_target` on `(parent_id, student_id, target_type)`. One row per parent-student pair.

### Current Admin Display

- **Overview**: `reaction_counts` = Counter of all FeedbackReaction rows for the family's children. Shows final state distribution (e.g., `positive: 3, neutral: 1`).
- **Family timeline**: Shows ALL `child_feedback_reaction_submitted` events. Each click is a separate event entry. If a child clicked 😊 then 😐 then 😞, the timeline shows 3 events.

### Is Every Click Recorded?

**Yes and no.** Every click creates a ProductEvent (an event log entry). But the FeedbackReaction table only keeps the LAST state. So:

- ProductEvent table: has the full click history
- FeedbackReaction table: has only the final state per target

### Is Final State Saved?

**Yes.** The upsert ensures the last clicked reaction is persisted in FeedbackReaction.

### Current Implementation Risks

| # | Risk | Severity | Impact |
|---|------|----------|--------|
| R1 | **Silent UX lie on page refresh** | P0 | Child sees no selection after refresh, thinks reaction wasn't saved. Clicks again, creating duplicate events and noise. Parent sees same issue. |
| R2 | **Race condition on rapid clicks** | P0 | Two rapid clicks send two POSTs. If first POST completes after second, database ends up with first reaction but UI shows second. State mismatch. |
| R3 | **No optimistic revert on failure** | P2 | If POST fails, button stays selected. User thinks it saved. Error message may be missed. |
| R4 | **Every click = new ProductEvent** | P1 | Timeline noise. 3 clicks = 3 events. Misleading for admin reading "submitted" — implies 3 separate submissions. |
| R5 | **No loading/disabled state during save** | P2 | User can click rapidly, sending multiple concurrent POSTs. Worsens R2. |
| R6 | **No distinction between create and update** | P1 | ProductEvent always says `child_feedback_reaction_submitted`. Cannot distinguish first choice from change-of-mind. |

### Recommendation: Should we record every click as an event, only store the final state, or support both?

**Answer: Support both, but with clearer semantics.**

For Alpha observability, we want:
1. **Final state** — what the child/parent ultimately chose (already done via upsert)
2. **First submission** — when they first engaged with the feedback (capture this once)
3. **Change events** — optionally, when they change their mind (useful but not critical for 3-5 families)

**Recommended minimal fix (hotfix scope):**

- Keep the FeedbackReaction/ParentFeedback upsert model (final state) — no change
- Change the ProductEvent recording in `reactions.py` to only record on FIRST creation (when upsert creates a new row, not when updating)
- Rename the "change" path to log a different event type (e.g., `child_feedback_reaction_changed`) or simply skip the event on update
- This keeps the timeline clean while preserving the ability to see: (a) when the child first submitted feedback, (b) what they finally chose

**Alternative (more comprehensive, defer to V0.4.2):**

- Add a `version` counter or `revision_history` JSON column to FeedbackReaction
- Keep ProductEvent for first submission only
- Store change history in the FeedbackReaction row itself

**For now (V0.4.1b hotfix):** Change reactions.py to only record `child_feedback_reaction_submitted` on INSERT, not on UPDATE.

## Issues Found

### P0 — Must fix before continuing Alpha  ✅ ALL RESOLVED in V0.4.1c

#### Issue P0-1: Feedback reaction does not load initial state on page refresh ✅ RESOLVED

- **Problem**: `FeedbackReaction` and `ParentSummaryFeedback` components always initialized `selected = null`, never fetched existing reaction from backend. After page refresh, the saved reaction was invisible to the user.
- **Fix in V0.4.1c**: New `feedback_state.py` module provides `feedback_reaction_value()` and `parent_summary_usefulness()` helpers. Backend routes return existing state in API responses. Frontend components accept `initialReaction`/`initialUsefulness` props and initialize `selected` from them. `useEffect` resets when target/parent/student changes.
- **Evidence**: `feedback_state.py:1-34`, `FeedbackReaction.tsx:21,32-33`, `ParentSummaryFeedback.tsx:16,26-27`, all 4 learning pages pass initial values.

#### Issue P0-2: Race condition on rapid feedback clicks ✅ RESOLVED

- **Problem**: Rapid clicks sent concurrent POSTs, causing database/UI state mismatch.
- **Fix in V0.4.1c**: `isSaving` guard at the start of `handleClick` (`if (isSaving) return;`). Buttons get `disabled={isSaving}`. On failure, UI reverts to `lastConfirmedReaction`. `activeTargetKey` ref pattern discards stale responses when target changes mid-request.
- **Evidence**: `FeedbackReaction.tsx:48-79`, `ParentSummaryFeedback.tsx:42-71`.

### P1 — Should fix in V0.4.1b hotfix  ✅ P1-1 RESOLVED, P1-2/P1-3 DEFERRED

#### Issue P1-1: Every feedback click creates a ProductEvent with event_type "submitted" ✅ RESOLVED

- **Problem**: The `child_feedback_reaction_submitted` event was recorded on every POST, whether it was a create or an update. On repeated clicks, the admin timeline showed multiple "submitted" events for the same target, which was misleading.
- **Fix in V0.4.1c**: `is_create` flag set before upsert (`reactions.py:99`, `alpha.py:507`). `record_product_event` is now gated: only called when `is_create` is True. Updates to existing reactions do not create new ProductEvents.
- **Evidence**: `reactions.py:99,115`, `alpha.py:507,523`.

#### Issue P1-2: Admin `_family_events` loads all ProductEvents into memory 🟡 DEFERRED

- **Problem**: `admin_alpha.py:56` does `events = session.exec(select(ProductEvent)).all()` — loads every ProductEvent in the database, then filters in Python.
- **Risk**: With 3-5 families, this is negligible. But it's a bad pattern that will silently degrade as events accumulate.
- **Deferred to V0.4.2**: Push filtering to database query with `OR` conditions.

#### Issue P1-3: `_latest_parent_feedback` aggregates across children without per-child context 🟡 DEFERRED

- **Problem**: `admin_alpha.py:42-46` — returns the single most recent `usefulness` across ALL children of a family.
- **Risk**: With 1 child per family (current Alpha), this is fine. With 2+ children, admin sees only the latest feedback across all children.
- **Deferred to V0.4.2**: Show per-child feedback context.

Wait — looking at the code again, `reaction` is reassigned on line 92-98. After line 98, `reaction` is always the database row (either existing or new). We need to check BEFORE the upsert whether this is a create or update.

Better approach:

```python
# Line 92: check existing before upsert
existing = session.exec(
    select(FeedbackReaction).where(
        FeedbackReaction.student_id == student_id,
        FeedbackReaction.target_type == request.target_type,
        FeedbackReaction.target_id == request.target_id,
    )
).first()

if existing:
    existing.reaction = request.reaction
    existing.parent_id = student.parent_id
    existing.alpha_session_id = request.alpha_session_id
    existing.updated_at = datetime.now(timezone.utc)
    reaction = existing
else:
    reaction = FeedbackReaction(
        parent_id=student.parent_id,
        student_id=student_id,
        target_type=request.target_type,
        target_id=request.target_id,
        reaction=request.reaction,
        alpha_session_id=request.alpha_session_id,
    )
    session.add(reaction)
    # Only record event on first creation
    try:
        record_product_event(
            session,
            "child_feedback_reaction_submitted",
            parent_id=student.parent_id,
            student_id=student_id,
            alpha_session_id=request.alpha_session_id,
            payload={
                "target_type": request.target_type,
                "target_id": request.target_id,
                "reaction": request.reaction,
            },
        )
    except Exception:
        pass
```

  const [isSaving, setIsSaving] = useState(false);  // NEW

    setSelected(reaction);
    setError("");
    setIsSaving(true);  // NEW

        target_id: targetId,
        reaction,
        alpha_session_id: getStoredAlphaSessionId(),
      });
    } catch {
      setError("这次没有保存成功，稍后可以再点一次。");
      setSelected(initialReaction);  // NEW: revert on failure
    } finally {
      setIsSaving(false);  // NEW
    }
  }
  // ... buttons get disabled={isSaving}
