## 执行摘要

V0.6a 是 WenLingo 写作城堡从"AI 点评已有初稿"升级为"AI 帮助孩子课前构思"的关键版本。它实现了从老师作文题目到孩子确认提纲的完整 4 步构思向导，然后接入已有的初稿→点评→二稿→对比→结算闭环。

**V0.6a 的核心产品假设**：如果一个孩子能从空白作文框走到初稿，中间经过审题→选材→整理素材→搭提纲的脚手架，那么孩子的初稿质量会更高、写作恐惧会更低、对写作过程的 ownership 会更强。

**当前状态**：V0.6a 的核心流程在 `wenlingo.com` 上已经可以端到端走通。但 QA 发现了 1 个 P1 bug（提纲确认/编辑保存失败），导致 **No-Go 决策**。AI 调用延迟显著（P3）。最关键的是，基于四年级下册 7 篇课内同步作文的真实数据，当前固定叙事模板 `起因/经过/结果/感受` 只适配 1/7（14%）的课内题目——**此问题已从 P2 升级为 P1**（详见 [`reviews/2026-06-24-v0.6a-p2-reevaluation.md`](./2026-06-24-v0.6a-p2-reevaluation.md)）。

**V0.6a 是一个方向正确、实现基本到位、但需要 1 个 P1 bug fix + 1 个 P1 题型适配设计才能覆盖课内同步作文核心场景的版本。**

## 1. CEO / 产品战略视角

### V0.6a 的战略意义

V0.6a 是写作城堡从"批改工具"升级为"陪练工具"的第一步。在 V0.5 系列建立了用户地基、AI 基础设施、句子训练 thin slice 之后，V0.6 系列的使命是验证作文训练的主线价值。

V0.6a 选择的切入点——课内同步作文的课前构思——是产品策略上最好的选择：

1. **解决真实痛点**：小学生写作文最常见的困难是"不知道写什么"和"不知道怎么开始"。课前构思直接解决这两个问题。
2. **差异化定位**：市面上大多数 AI 写作工具是"帮你写"或"帮你改"，V0.6a 是"帮你准备写"——这个定位更符合家长对 AI 辅助学习的期待。
3. **不代写**：从审题到提纲，AI 只做追问、整理、框架建议，不做内容生成。这坚守了 WenLingo 的核心产品边界。

|---|---|---|

### 产品阶段判断

```text
产品稳定度 (Product stability):      80%（1 个 P1 bug 待修）

```

V0.6a 之后的产品状态：
- 写作城堡现在支持两条完整路径：课内作文构思 + 直接写初稿
- 家长终于能看到孩子"写了什么"之外的信息——孩子有没有审题、回忆了几个素材、有没有搭提纲
- AI 出题作文（V0.6b）入口已预留但正确置灰

### 战略建议

1. **P1 bug 必须修**：提纲确认/编辑的保存失败阻塞了 V0.6a 设计的核心交互（孩子确认或修改提纲）。跳过提纲虽然可以继续写，但提纲确认是 V0.6a 设计中最体现"孩子 ownership"的步骤。不修这个 bug，V0.6a 的核心产品假设没有完全验证。
2. **V0.6b 的范围需要根据 V0.6a 的使用数据调整**：在修完 P1 bug 并让 3-5 个孩子真实使用后，观察以下指标再确定 V0.6b 优先级：
   - 提纲确认率（修完 bug 后）
   - 每步跳过率
   - 素材卡保留数量
   - 初稿提交率
3. **域名 `wenlingo.com` 是正确的长期投资**：自定义域名提升了产品的专业感和可信度。这次 QA 中发现的 CORS/Auth origin 配置问题是正常的域名上线摩擦，已在 QA 过程中修复。
4. **Alpha 扩大节奏**：P1 bug 修完后，建议先让现有 Alpha 家庭中的一个孩子完整走一遍课内作文路径（含提纲确认），确认无问题后再邀请新家庭。不要带着已知 P1 bug 扩大 Alpha。

### CEO 评分

🟡 **方向正确，产品假设合理，但需要 P1 bug fix 后才能判断是否真正达标。**

## 2. 学习设计师视角

### 课前构思的学习设计评估

V0.6a 的 4 步构思向导对应了写作教学中的关键认知过程：

| 步骤 | 对应认知过程 | 学习设计质量 |
|---|---|---|
| 第 1 步：看懂题目 | 审题能力（理解题目要求、确定写作重点） | 🟢 三卡设计好——"题目在问什么""一定要写到什么""可以写精彩的地方"覆盖了审题的三个层次 |
| 第 2 步：想一想素材 | 选材能力（回忆真实经历、筛选可写内容） | 🟢 3 个问题覆盖事件+细节+感受，问题设计合理 |
| 第 3 步：整理素材卡 | 组织能力（分类、筛选、排序素材） | 🟢 事件/细节/心情收获三槽覆盖叙事要素 |
| 第 4 步：搭一个提纲 | 结构能力（建立叙事框架） | 🟡 起因/经过/结果/感受四段适合叙事文，但缺乏灵活性 |

### 做得好的地方

1. **"孩子是作者"原则贯穿始终**：AI 只做追问、整理、框架建议，所有内容来源都标注了 `source_answer_ids` 和 `source_card_ids`。素材卡只用孩子自己的回答，空白回答产生空槽而非编造内容。这是学习设计的底线——脚手架不能替代思考。
2. **跳过不惩罚**：每一步都有"我想直接开始写"的跳过选项。这避免了"卡在某一关"的挫败感。对于已经知道自己要写什么的孩子，跳过脚手架直接写初稿是正确的设计。
3. **语言适合四年级孩子**："看懂题目""想一想素材""搭一个提纲"——指令清晰、不压迫、不学术化。
4. **确认机制**：审题后孩子可以写"我觉得这题最重要的是____"，提纲可以编辑和确认。这些交互让孩子感受到"这是我的作文计划"，而不是"这是 AI 给我做的计划"。

### 需要改进的地方

1. **固定叙事模板（⚠️ P2→P1 升级）**：当前提纲结构 `起因 → 经过 → 结果 → 感受` + 固定素材卡 `事件/细节/心情收获` 只适合叙事类作文。基于四年级下册 7 篇课内同步作文的真实数据，仅 1/7（14%）完全适配。对于《我的奇思妙想》（想象发明）、《我的"自画像"》（写人）、"我的乐园"（地点描写）等课内题目，当前模板不匹配。详见 [`docs/research/grade4-semester2-writing-topic-taxonomy.md`](../docs/research/grade4-semester2-writing-topic-taxonomy.md) 和 [`reviews/2026-06-24-v0.6a-p2-reevaluation.md`](./2026-06-24-v0.6a-p2-reevaluation.md)。建议 V0.6b 引入 `topic_type` + `scaffold_template` 概念，优先覆盖 5/7 课内题型。
2. **没有难度分级**：当前 4 步对所有年级相同。四年级和六年级的审题深度、选材复杂度、提纲粒度应该有区别。例如：
   - 四年级：起因（1-2 句）、经过（按顺序写 2-3 个画面）、结果（1 句）、感受（1 句）
   - 六年级：起因（背景+冲突）、经过（详写关键画面+省略次要）、结果（点题）、感受（升华）
3. **缺少选材追问的反馈**：孩子回答选材问题后，系统没有给任何反馈（如"你回忆了一个真实的画面，很好！"）。加一句鼓励性的反馈可以强化"回忆真实素材"这个学习行为。
4. **素材卡之间的关联不可见**：事件/细节/心情收获三张卡是并列展示的，但孩子可能不理解它们之间的关系（细节支撑事件、心情来自事件）。在卡片之间加一条简单的连线或一句话引导（如"这个细节让你当时的感受是什么？"）可以帮助孩子建立叙事要素之间的联系。

### 隐忧：跳过路径的学习效果

V0.6a 的设计允许跳过每一步。虽然"跳过不惩罚"是正确的 UX 设计，但从学习设计角度看：

- 如果一个孩子连续多次跳过审题和选材，直接写初稿，那课前构思的脚手架就没有产生学习效果。
- **建议**：在家长摘要中不仅显示"是否使用"审题/选材/提纲，还要在孩子连续跳过 3 次后，给 AI 教练一个温和的提示（如"上次你直接开始写得很快！这次要不要试试先花 2 分钟想一想素材？可能会写得更具体哦。"）。这不是惩罚，是引导。

### 学习设计师评分

🟡 **设计方向正确，脚手架合理，但模板适应性不足已从 P2 升级为 P1（7 篇课内题仅 1 篇适配），且缺乏难度分级。**

## 3. 孩子用户体验视角

### 写作城堡模式入口

孩子 dashboard 上的"作文城堡"入口设计简洁：
- `课内同步作文` — 主路径，可操作
- `AI 出题作文 · 稍后开放` — 正确置灰，不产生混淆
- `直接写初稿` — 已有路径保留

这个三选项 shell 清晰不拥挤，孩子应该能快速理解每个选项。

### 4 步向导流程体验

```text
进入体验: 🟢 友好——输入题目 → 点击开始 → 进入步骤 1
步骤展示: 🟢 清晰——每步有 "第 X 步 / 共 4 步：标题"
卡片设计: 🟢 简洁——审题三卡短小可扫描
输入体验: 🟢 轻松——"写一句就可以"降低了写作压力
等待体验: 🔴 显著延迟——AI 生成时等待时间长，只有文字 loading
错误处理: 🟡 有兜底文案——"这一步没有保存成功，可以重试，也可以先继续写"
```

### AI 等待体验是最突出的 UX 问题（P3）— 但解法不一定是 Token Streaming

QA 明确记录了 "AI interaction latency is visibly high during Writing Castle generation and feedback"。孩子在 4 步向导中至少需要等待 4 次 AI 调用（审题分析、选材问题、素材卡生成、提纲生成），之后还要等作文反馈和二稿对比。

**延迟的本质不是"单次太慢"，而是"等待点太多"：**

```text
开始审题 -> 等 AI (1)
开始想素材 -> 等 AI (2)
整理素材卡 -> 等 AI (3)
搭提纲 -> 等 AI (4)
提交初稿 -> 等 AI feedback (5)
提交二稿 -> 等 revision comparison (6)
```

gstack review 说 V0.6a "把延迟从'一个步骤慢'变成'四个步骤都慢'"——这个判断是对的。但解法不一定是 SSE token streaming。

**区分两种 SSE：**

| | Progress SSE（进度流） | Token Streaming（内容流） |
|---|---|---|
| 推送什么 | 任务状态：started → validating → saving → completed | LLM 输出逐字/逐段推送给用户 |
| 适用场景 | Prewriting JSON tasks | Essay feedback / revision comparison |
| 风险 | 低——不展示未验证内容 | 高——半截 JSON 未通过 Pydantic validation、source reference check |
| 用户价值 | 让等待"有进度感" | 让长内容"边生成边看" |

**对 V0.6a 四个 prewriting JSON task 的判断：**

```text
writing_topic_analysis    → 短 JSON，Token Streaming 价值低。Progress SSE 更适合。
material_questions        → 很短 JSON，Token Streaming 价值很低。
material_card_generation  → 中短 JSON，需 source 校验。不应 stream 半成品。
outline_generation        → 中短 JSON，需 source 校验。不应 stream 半成品。
essay_feedback            → 长内容、多个反馈块。最适合首批 Token Streaming。
revision_comparison       → 长内容、结构化反馈。适合第二批 Token Streaming。
```

**关键风险**：Prewriting 的素材卡和提纲涉及"可能进入作文的内容"。如果把 LLM 半截输出直接 stream 给孩子看：
1. 半截内容还没验证 `source_answer_ids` / `source_card_ids`
2. 半截内容可能包含 AI 编造的人物、地点、动作
3. 最终 validation fail 后，要不要撤回孩子已经看到的内容？
4. Fallback 发生时，前面 stream 出去的内容算不算用户可见输出？

**建议的优先级**：

```text
短期（V0.6a.1 / V0.6b.0）:
  1. 先量化延迟：在 LLMCallLog 或 browser network 中记录各 task 的 p50/p90/p95 latency
  2. Staged loading 文案优化（如"AI 教练正在读题目…""AI 教练正在整理重点…""马上好了，正在检查有没有编造内容…"）
  3. 判断最大瓶颈是"题型不适配"还是"等待太慢"

中期（V0.6b.1）:
  4. Progress SSE——服务器推送任务状态，不推送未验证内容

中长期（V0.6c 或 V0.7）:
  5. essay_feedback Token Streaming——最高用户价值
  6. revision_comparison Token Streaming——第二高用户价值

不建议优先：
  ✗ prewriting JSON token streaming——风险高、收益低
```

### 编辑/确认提纲失败的 UX 影响

当孩子在提纲步骤编辑了"结果"部分，点击"确认提纲，开始写"后，UI 停留在第 4 步，显示"这一步没有保存成功，可以重试，也可以先继续写"。虽然错误文案是温和的、有兜底路径的，但：

- 孩子刚刚投入了认知努力编辑提纲，编辑结果没有被保存，这是一个挫败体验
- 孩子可能不理解"为什么我改了但是没保存"
- 跳过路径虽然是可用的，但孩子可能不知道"跳过"和"我的编辑丢失了"之间的区别

**这个 P1 bug 对孩子体验的影响比技术严重性更大——它破坏了一个关键的 ownership 时刻。**

### 孩子 UX 评分

🟡 **流程设计好，语言适合孩子，但 AI 延迟（P3）严重拖累体验，P1 bug 破坏关键交互。**

## 4. 家长用户体验视角

### V0.6a 的家长可见性

V0.6a 在家长端的改动是最小化的——只在 child summary 中增加了 `writing_castle_summary` 字段。这个克制是正确的：V0.6a 的核心是验证课前构思对孩子写作的帮助，不应该在设计验证阶段就投入大量家长端资源。

### 过程摘要字段评估

QA 验证了所有摘要字段都正确渲染：

| 字段 | 对家长的意义 | 评估 |
|---|---|---|
| 作文题目 | 知道孩子在写什么 | ✅ 基本但必要 |
| 是否使用了审题 | 孩子有没有认真读题 | ✅ 体现学习习惯 |
| 是否确认/编辑了题目重点 | 孩子有没有自己的理解 | ✅ 体现独立思考 |
| 回答了几个选材问题 | 孩子回忆了多少真实素材 | ✅ 体现素材积累 |
| 保留了几张素材卡 | 孩子筛选了多少可写内容 | ✅ 体现组织能力 |
| 提纲是否确认/编辑 | 孩子有没有写作计划 | ✅ 体现结构意识 |
| 初稿/二稿/结算完成状态 | 写作闭环完成度 | ✅ 与已有闭环衔接 |

这些字段的信息架构是好的——它们告诉家长的不是"AI 帮你孩子写了什么"，而是"你的孩子在写作前做了哪些准备"。这与 MVP 设计文档中"家长应看到孩子练习了什么、哪里进步了"的原则一致。

### 家长端的缺口

1. **缺少趋势信息**：目前摘要只显示最近一篇 V0.6a 作文的过程数据。家长看不到"孩子这几次的审题越来越认真了"或"孩子最近开始主动编辑提纲了"这样的趋势。这需要多篇作文的数据积累才能做——V0.6a 是合理的第一步。
2. **缺少 actionable 建议**：摘要告诉家长"孩子回答了 1 个选材问题"，但没告诉家长"这意味着什么"或"下一步可以做什么"。例如："孩子这几次选材问题回答较少，可以在日常生活中多和孩子聊聊'今天发生了什么有趣的事'来积累素材。" 这是 V0.8 家长周报的范围。
3. **没有 before/after 对比**：家长看不到"有了课前构思后，孩子的初稿有没有变得更好"。这个对比是验证 V0.6a 产品假设的关键证据。建议至少在后端记录一个简单的指标（如初稿字数、初稿与提纲的匹配度），为后续分析做准备。

### 家长 UX 评分

🟢 **摘要信息架构好，强调过程而非 AI 代写。当前克制是正确策略。需要更多数据积累后才能做趋势和建议。**

### 架构决策评估

**1. JSON 状态存储在 Essay 列（material_card + outline）**

V0.6a 选择复用现有 `Essay` 表的 `material_card` 和 `outline` JSON 列，而非创建新的 prewriting 表。

评估：✅ 正确决策。
- 避免了不必要的数据库迁移
- schema versioning（`v0.6a.1`）为未来演进留了空间
- PATCH ownership 设计（每个端点只写自己拥有的字段）保证了并发安全
- 如果未来 prewriting 数据需要独立查询/索引，再拆表也不迟

**2. 10 个独立端点 vs 1 个状态机端点**

V0.6a 为每个 prewriting 步骤创建了独立端点（`/topic-analysis`、`/material-questions`、`/material-cards`、`/outline` + 对应的 PATCH）。

评估：✅ 设计清晰。
- 每个端点职责单一
- 幂等性可以按步实现（`regenerate: true` 的 409 守卫）
- 前端可以独立控制每个步骤的加载状态
- 缺点是端点数量较多，但这是一次性成本

**3. Source reference validation**

每个 material card 必须引用 `source_answer_ids`，每个 outline section 必须引用 `source_card_ids`。非 placeholder 卡片如果没有 source reference 会 reject。

评估：✅ 这是 V0.6a 最重要的工程决策之一。
- 从代码层面强制"AI 不能编造内容"的产品原则
- Pydantic model_validator 提供了声明式验证
- 后端 `validate_card_sources` 和 `validate_outline_sources` 提供了额外的安全网

**4. Deterministic fallbacks**

每个 AI 任务都有 fallback 工厂函数，在 AI 调用失败时返回固定模板。

评估：✅ 好的防御性设计。
- Fallback 不编造故事内容——符合产品原则
- 即使 AI 完全不可用，孩子仍能走完 4 步向导（只是脚手架会比较通用）

### 技术债务评估

V0.6a 没有引入明显的新技术债务。但以下点值得关注：

1. **`writing_castle.py` 路由文件**：目前包含所有 10 个端点 + 辅助函数，估计 ~400 行。如果 V0.6b 增加 AI 出题作文路径，这个文件会继续膨胀。建议在 V0.6b 或 V0.7 拆分为 `writing_castle.py`（路由）+ `writing_castle_service.py`（业务逻辑）。
2. **前端 `page.tsx` 膨胀**：V0.6a 在已有的 essay page 上叠加了模式 shell + 4 步 wizard。如果 V0.6b 增加新路径，建议考虑路由级拆分（如 `/writing-castle/classroom`、`/writing-castle/direct`）而非继续在一个 page 中堆条件渲染。
3. **AI 延迟累积**：当前 4 步 AI 调用是串行的（每步等待上一步完成），加上后续的作文反馈和二稿对比，孩子最多经历 6 次 AI 等待。这不是"单次太慢"而是"等待点太多"。解决方向不仅是 streaming，还包括：减少可感知等待点、缩短每次等待（faster model/orchestration 优化）、让等待有进度感（staged loading / Progress SSE）。**关键判断：prewriting JSON tasks 优先做 Progress SSE（推送任务状态），essay_feedback/revision_comparison 优先做 Token Streaming（推送内容）。**
4. **SSE streaming 的前置工程工作（P4）**：引入 streaming 不只是前端改动。`LLMCallLog` 需要支持 streaming 模式。最小设计应覆盖：

   ```
   字段级：
   streaming_enabled: bool
   stream_started_at / first_content_at / stream_finished_at
   client_disconnected_at
   final_status (success / fallback_success / partial_failed / client_disconnect)
   visible_output_started: bool
   partial_output_discarded: bool
   usage_available: bool
   input_tokens / output_tokens / estimated_cost
   fallback_reason / attempt_count

   Daily limit 规则（需产品确认）：
   场景 A：provider 成功，用户看到完整结果 → consume limit
   场景 B：provider fail，无用户可见输出 → 不 consume
   场景 C：stream 到一半 client disconnect，provider 已消耗 token → 成本记录；limit 是否 consume 需产品规则
   场景 D：primary stream 失败，fallback 成功 → final_status=fallback_success，记录 primary_partial
   场景 E：Progress SSE 只推状态不推内容 → 只有 final JSON 成功才算用户得到 AI 输出
   ```

   此外，Railway + Next.js same-origin proxy 是否支持无缓冲 SSE 需要在生产环境验证。如果中间层 buffering，SSE 可能退化成一次性返回。

### V0.6a 做得最好的 3 件事

1. **AI 不编造内容的代码级执行**：Source reference validation + 合约约束 + deterministic fallback 构成了三道防线。这是 WenLingo 产品原则在工程层面最完整的执行。
2. **家长过程摘要的信息架构**：不展示 AI 代写、不展示作文全文，而是展示"孩子做了哪些写作前准备"。这是家长信任的基础。
3. **TDD 工程纪律**：18 个 commit 按 Task 1-5 逐任务推进，feat → fix → harden → mark complete 的节奏清晰。P1 bug 虽然逃过了 CI，但整体工程质量是好的。

### V0.6a 最需要改进的 3 件事

1. **P1 bug：提纲确认/编辑保存失败** — 这是阻塞性问题，必须修。它不仅影响功能完整性，更破坏了"孩子 ownership"这个核心产品价值。
2. **AI 延迟（P3）+ Streaming 准备（P4）** — V0.6a 的 4 步 AI 调用让延迟问题从"一个步骤慢"变成了"四个步骤都慢"。V0.6b 把 streaming 从前端需求升级为产品体验需求。
3. **Skip 行为的完整验证** — 设计上每一步都可以跳过，但 QA 只验证了 1/6 的 skip 场景。"跳过"是 V0.6a 最重要的安全网——如果脚手架不适合某个孩子，孩子必须能顺畅地绕过它。

### 对 V0.6b 的影响

V0.6a 的产品假设还没有被完整验证（因为 P1 bug 阻塞了提纲确认路径）。同时，基于四年级下册 7 篇课内同步作文的真实数据，**V0.6b 的优先级需要重大调整**。详细分析见 [`reviews/2026-06-24-v0.6a-p2-reevaluation.md`](./2026-06-24-v0.6a-p2-reevaluation.md) 和 [`docs/research/grade4-semester2-writing-topic-taxonomy.md`](../docs/research/grade4-semester2-writing-topic-taxonomy.md)。

建议的 V0.6b 新范围：

1. **P0：课内同步作文题型适配 v1** — 原 AI 出题作文延后到 V0.6c。引入 `topic_type` + `scaffold_template`，优先覆盖 5/7 课内题型（learned_skill、my_paradise、invention_idea、self_portrait、generic_narrative）。
2. **P0：Template-specific 素材卡** — 从固定 3 槽改为按题型定义卡槽（如《我的奇思妙想》= 样子/功能/用处）。
3. **P0：Content-source-aware 选材问题** — 区分"回忆"和"想象"两种材料来源，不再假设所有作文都来自真实经历。
4. **P0："AI 不替孩子决定内容"原则升级** — 从 "AI 不编造 lived content" 升级为支持 4 种内容来源（真实经历/想象设定/题目要求/孩子确认）。
5. **P1：P1 bug fix（提纲保存）** — 如 V0.6a hotfix 未修，V0.6b 必须修。
6. **P1：Streaming（SSE）** — AI 延迟在 4 步向导中累积效应明显，streaming 从前端需求升级为产品体验需求。
