# Review: V0.6c Topic Breadth + AI Topic Design

Date: 2026-06-29
Reviewer: gstack (product / architecture / QA)
Subject: `specs/2026-06-29-v0.6c-topic-breadth-ai-topic-design.md`
Cross-checked against: `reviews/2026-06-12-v0.5b-to-v1.0-roadmap.md` (rev v4) and the
live V0.6b codebase (not just the spec text).

Role note: Codex is the implementation agent. This review amends the spec so the handoff
is safe; it does not implement.

## Context / why this review

V0.6c adds (a) 4 visible scaffold families — `place_scenery`, `animal_object_observation`,
`practical_writing`, `story_adaptation` — and (b) an AI-generated-topic thin slice
(`writing_topic_idea_generation`). It builds on the V0.6b scaffold system, whose real
implementation I verified in code so the review is grounded.

## Verdict

**Approve with required amendments.** The spec is strong on scope discipline and is
faithful to the V0.6b architecture and the v4 roadmap. But two concrete correctness/safety
gaps would cause real bugs if handed to Codex as-is; both are cheap to fix in the spec
before implementation planning.

## What the spec gets right

- Scope/non-goals are explicit and consistent with roadmap v4 (streaming → V0.6d, essay
  archive/multi-round → V0.6c.1, `story_summary` stays unsupported).
- AI topic must map to a currently-supported scaffold (no orphans); no hidden fallback
  topic bank (avoids the "fake AI" anti-pattern).
- Failure path is sound: retry/later copy, classroom + direct draft stay available.
- Server-side validation rejecting copy-ready paragraphs and "decided" content directly
  extends V0.6b's "AI 不替孩子决定内容" principle (`ai_tasks.py:306-337`).
- Observability plan (3 new ProductEvents + LLMCallLog reuse) is well-scoped.
- Source-policy tokens in the spec match the codebase vocabulary exactly
  (`real_experience / observation / child_confirmed / topic_requirement / reading_material
  / imagined_setting`).
- The 4 new families do achieve 4/7 of the 四下 targets (我的乐园/游→place_scenery,
  故事新编→story_adaptation, 我的动物朋友→animal_object_observation); remaining 3/7
  already covered by existing families.

## Required amendments (P0 — fix before handoff)

### P0-1. `schema_version` must NOT be bumped; only `scaffold_template_version` changes

The spec (§7) says new templates "must still use a V0.6c `scaffold_template_version`."
Correct in intent, but it conflates two different fields and does not state the constraint
that keeps V0.6b safety intact.

In code these are distinct:
- `schema_version` = `"v0.6b.1"` (`writing_castle_scaffold.py:10`) — the **container** schema.
- `scaffold_template_version` = `"{type}.{variant}.v0.6b.1"` (`writing_castle_scaffold.py:283`)
  — a per-template label, currently hardcoded.

`schema_version` is a pervasive safety/resume gate. It is compared at **7+ sites**:
- `ai_tasks.py:344` — source-ref validation runs ONLY when `schema_version == "v0.6b.1"`
  (the F1/F4 follow-up protection).
- `writing_castle_state.py:153,155,167,168,313` — normalize/resume/source-ref-required gates.
- `writing_castle.py:149,269,413,414` and `alpha.py:490,500,501,585,586` — supported-version
  acceptance for material/outline states.

**Risk:** if Codex bumps `SCHEMA_VERSION` → `"v0.6c"` to make the label "consistent", then
(a) every in-flight V0.6b essay falls out of `supported_schema_versions` and breaks resume,
and (b) `_validate_v06b_material_card_source_refs` silently disables for all V0.6c essays —
a regression of the V0.6b F1/F4 hardening.

**Amend the spec to state explicitly:** *"The JSON container schema is unchanged;
`schema_version` stays `v0.6b.1`. The `v0.6c` label lives ONLY in
`scaffold_template_version`. Decouple the suffix at `writing_castle_scaffold.py:283`
(e.g. a per-template version map) — do not touch `SCHEMA_VERSION`."* Also state the 4
existing families keep their `.v0.6b.1` template versions (only new families get `.v0.6c`),
to avoid churning existing template-version tests.

### P0-2. `UNSUPPORTED_RULES` conflicts with the 2 newly-supported families

`writing_castle_scaffold.py:42-48` currently treats these keywords as **unsupported
future types**:
- `("写信","书信","我想对您说","倡议书")` → `practical_writing`
- `("故事新编","续写")` → `story_adaptation`

Once `practical_writing` and `story_adaptation` become **supported** families, these rules
contradict the goal: a child typing "续写故事" or "写信" would still be flagged unsupported
(`detect_unsupported_future_type` → frontend shows the "这类题目我们还在学习中" panel at
`ClassroomPrewritingWizard.tsx:581`). The spec (§7, §10) does not mention removing them.

**Concrete acceptance impact:** 故事新编 is one of the 四下 7 targets the spec claims to
cover — but right now it detects as unsupported `story_adaptation`. The 7/7 criterion is
unreachable without this change.

**Amend the spec §7/§10:** remove the `practical_writing` and `story_adaptation` keyword
rules from `UNSUPPORTED_RULES`; keep `story_summary` (`梗概/缩写`),
`reading_response_recommendation` (`推荐一本书/读后感`), `central_idea_reflection`
(`漫画的启示/围绕中心意思写`) as unsupported. Add an assertion in §11 that
`detect_unsupported_future_type("续写故事")`, `detect("写信")`, `detect("故事新编")`
all return `None`.

## Should-clarify (P1)

### P1-1. New template slots omit `content_kind`
Every existing slot/section carries a `content_kind`
(`content / structural / factual / subject / source` — see `writing_castle_scaffold.py`
and `types.ts:194-205`), and it drives source validation (e.g. `expository_introduction`
has `factual` and `source` slots). Spec §7 lists only `slot_id: label`. Codex must invent
content_kinds for ~24 new slots — and the choices affect source-ref rules. Spec should
either give content_kind per slot, or at minimum give guidance for
`practical_writing` (format slots) and `animal_object_observation` (factual/observation
slots).

### P1-2. `TaskConfig` field names are inaccurate in §8
Spec §8 says routing config has "primary_model, fallback_model, timeout_seconds,
retry_count, cost_tier". The real `TaskConfig` (`ai_routing.py:60`) has
`primary_timeout_seconds` / `fallback_timeout_seconds` / `max_total_latency_seconds`,
**no** `retry_count` (primary+fallback IS the retry), plus `daily_limit`,
`allowed_prompt_keys`, `default_prompt_key`. The handoff must cite the real fields and
must add a `TASK_CONFIGS["writing_topic_idea_generation"]` entry (the spec mentions the
prompt but not the routing entry explicitly).

### P1-3. Mode shell is 2-mode today; AI-topic is net-new UI
`WritingCastleModeShell.tsx:5` is `WritingCastleMode = "classroom" | "direct"`; the
"AI 出题作文 · 稍后开放" button (`:39`) is a disabled label, not a wired mode. "Interest"
exists nowhere in the app (no storage, no chips, no profile field). So V0.6c must: add
`"ai_topic"` to the union, build interest-input UI, the 3-ideas display, and selection.
This is the release's largest net-new frontend surface, not a toggle — the spec should say
so (and confirm interest text is transient: Essay is created only on selection, so interest
is not persisted; the `interest_input_present` boolean in §9 is the right call).

## Nice-to-clarify (P2)

- **P2-1. `daily_limit` for the new task** is unspecified. Recommend a small value
  (3–5/day) — topic ideation is infrequent; `sentence_challenge_generation` uses 10.
- **P2-2. `picture_prompt_story`** is a `FutureTopicType` in code but absent from the
  spec's "remain unsupported" list (§10). Add a line confirming 看图作文 stays future.
- **P2-3. Boundary cases** between new and existing families (我的心爱之物 →
  animal_object vs expository; 推荐一个好地方 → place_scenery) — manual selection
  resolves them; flag for AI-topic prompt design so an idea maps to exactly one family.
- **P2-4. §12 "75% coverage"** denominator is fuzzy — acceptable for a breadth release,
  but pin it (families out of the 57-item taxonomy, with uncovered families explicitly
  listed for V0.7).

## Testing plan — additions (§11)

The 4-file regression gate is correct and all files exist. Add:
- Assert the 4 new families appear in `supported_topic_type_choices()` and are removed
  from `FUTURE_TOPIC_TYPES` / `detect_unsupported_future_type`.
- Assert `SCHEMA_VERSION` unchanged and `_validate_v06b_material_card_source_refs` still
  fires for new-family material cards (ties to P0-1).
- Reject AI ideas whose `topic_type/topic_variant` is unsupported, has duplicate ids,
  empty titles, or copy-ready paragraphs (spec lists these — keep them as explicit cases).
