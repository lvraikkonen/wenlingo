## Executive Summary

The 8-item V0.6b Scope Guard **HOLDS** — Codex independently corroborates this (only 4
P0 families exposed, future types are detector constants not templates, no AI topic
classifier on the happy path, no per-family prompt keys, no Token Streaming/SSE, no AI
topic generation, no difficulty grading, direct draft not scaffold-gated, V0.6a legacy
preserved). Release-gate tests are green (backend 192, web 174, E2E 2).

**But the dual-voice surfaced two real gaps the grounded scope-guard review under-weighted:**

1. **[HIGH] AI can self-certify a source ref.** The material-card AI path validates
   `source_answer_ids` and slot ids, but a model-supplied `child_confirmed` /
   `reading_material` `source_ref` is accepted at face value — including for expository
   factual claims — without proving the source exists or was child-confirmed. This is a
   hole in the core V0.6b principle "AI must not invent factual claims / decide content."
2. **[HIGH] Parent summary UI doesn't show the v0.6b fields.** The backend returns
   `selected_topic_type / selection_source / material_source_categories /
   unsupported_future_type_overridden / copy_ready_ai_body_generated`, but the parent
   summary **web page** renders only legacy process counts. The "parent can understand
   progress" goal is met at the API layer, not in the UI parents actually see.

**Revised release recommendation: SHIP-WITH-FOLLOW-UPS.** The scope guard and tests
support landing the branch, but the two HIGH items above (plus a medium spec-deviation
on scaffold-change timing) should be tracked as **must-do before V0.6b is called
complete** — handed to Codex, not implemented here.

## Phase 1 — CEO / Product Review

**Premise check (not auto-decided — product judgment):** The premise is sound. V0.6b's
job is to make Writing Castle credible across 3-6 grade classroom topics by establishing
an extensible scaffold architecture, not to ship every template. Four P0 families
covering ~53-56% of the taxonomy is the right first slice; manual selection as P0 with AI
suggestion as P1 is the right risk ordering (a child can always start without AI).

- **Right problem?** Yes. The fixed V0.6a narrative wizard forced every topic into one
  shape. A family-based scaffold with a deterministic unsupported detector is the
  10x-better framing versus "add more hardcoded wizards."
- **6-month regret scenario?** The one that would look foolish: shipping the
  `child_confirmed`/`reading_material` self-cert hole (F1) into a real classroom and an
  expository essay surfaces an AI-invented "fact" that looks sourced. Cheap to prevent
  now; expensive to explain to a parent later. This is why F1 is the top follow-up.
- **What already exists (reused, not rebuilt):** Prompt Registry, ModelRouter, Pydantic
  contracts, LLMCallLog, V0.6a source-ref shorthand, Sentence Workshop staged-loading
  pattern. DRY is respected — no parallel prompt system, no parallel state machine.
- **Scope discipline:** Clean. No V0.6c/V0.7 families, no AI topic generation, no
  difficulty adaptation, no recommendation library, no DB editor. P1 items (AI
  suggestion, richer analytics) are correctly absent, not half-built.

**Product verdict: PASS.** The strategic shape is right. F1 is the one product-safety
item to close before broad rollout.

### Adjudicated findings

**F1 — [HIGH] AI can self-certify a source ref. CONFIRM.**
`ai_tasks.py:657-659` `validate_output` calls `_validate_material_card_source_ids` (checks
`source_answer_ids` resolve to real answers) and `_validate_material_card_template_slots`
(slot ids) — neither validates **ref provenance**. `validate_card_sources`
(`writing_castle_state.py:306-374`) only cross-checks refs that carry an `answer_id`
against saved answers; a `child_confirmed`/`reading_material` ref has no `answer_id`, so
it is accepted uncross-checked. A hallucinating model can attach
`{"source_type":"reading_material",...}` to an invented expository fact and it passes
`validate_expository_fact_sources` (which only requires *a* fact-source-type to be
present). This is a direct hole in spec §5 "AI must not invent factual claims." The
deterministic fallback (`_source_refs_for_answer`) and the `NO_GHOSTWRITE` prompt mitigate
it, but the trust boundary should be server-enforced. **Fix (hand to Codex):** reject
model-supplied `child_confirmed` refs on the generation path (those must be created
server-side by the child-confirmation lifecycle); validate `reading_material` refs against
stored reading-material records; or derive all refs server-side from valid answer/card
ids. *(Principle 1 completeness + core safety.)*

**F2 — [LOW-MED] `child_edited` outline notes saved with no source chain. CONFIRM, downgrade.**
`save_outline` passes `allow_child_edited_without_sources=True`
(`writing_castle.py:803`), and `validate_outline_sources` (`writing_castle_state.py:429-433`)
exempts `child_edited` notes with empty `source_card_ids`. This deviates from spec §10's
"every content-bearing outline section needs a source/chain," BUT it is intent-defensible:
a child-editing their own outline note *is* the source (child-authored content is not
AI-invented). The spoofability angle (client sets `child_edited:true`) is low-risk because
it's the child's own authenticated session and the content is the child's words anyway.
**Fix (optional, V0.6b.1):** either document the exemption explicitly, or create a
server-side `child_confirmed` source for child-edited notes so provenance is recorded. *(Principle 5 explicit.)*

**F3 — [MEDIUM] `resolve_essay_scaffold` bypassed by resume + parent summary. CONFIRM.**
Spec §8 says "Generation endpoints, draft editor, resume flow, and parent summary must all
use this accessor." The active-resume endpoint returns raw JSON
(`writing_castle.py:396-411`) and `_writing_castle_summary` reads `outline.scaffold`
directly (`alpha.py:513`) — neither routes through the accessor, so a malformed/mismatched
snapshot would still render/summarize instead of failing closed. Practical risk is low
because `attach_scaffold_snapshot` writes both containers atomically, so divergence
requires DB tampering — but it's a real spec-conformance gap. **Fix (Codex):** call
`resolve_essay_scaffold()` for v0.6b resume + parent summary; fail closed (or treat as
legacy) on mismatch. *(Principle 1 completeness / single-source-of-truth rigor.)*

**F4 — [HIGH] Parent summary web UI doesn't render v0.6b fields. CONFIRM.**
`apps/web/src/app/parent/children/[studentId]/summary/page.tsx:183-215` renders only
legacy fields (`topic`, `topic_analysis_used`, `material_questions_answered`,
`material_cards_retained`, `outline_confirmed`, `first_draft_completed`). It never
references `selected_topic_type / selection_source / material_source_categories /
unsupported_future_type_overridden / copy_ready_ai_body_generated`, which the backend
now returns (`alpha.py`). So the §17 parent-summary acceptance criterion and the "parent
can understand progress" goal are met at the API, not in the UI parents see. **Fix
(Codex):** render the v0.6b fields in the summary page + add web tests. *(Principle 1
completeness — the parent visibility is a stated V0.6b goal.)*

**F5 — [MEDIUM] Scaffold change over-rejected vs spec §11. CONFIRM.**
`save_scaffold_selection` (`writing_castle.py:427-436`) rejects change once
`topic_analysis.status == "generated"` (or answers/cards/sections exist). Spec §11
describes an allowed middle state: "Changing type after topic analysis but before material
answers: warn, preserve topic, clear generated analysis/questions." The implementation is
stricter (rejects immediately after topic analysis). This is **safe** (over-rejection
never loses data silently) but narrower than the spec intends, and §4.2 contract #2 scopes
rejection to "after answers/cards," implying the topic-analysis-only case should be
changeable. **Decision needed (taste):** (a) document that V0.6b P0 only allows scaffold
change *before* topic analysis, or (b) implement the clear-and-regenerate path in V0.6b.1.
*(Principle 5 explicit — pick one and state it; safe over clever.)*

**F6 — [LOW] Malformed snapshots under-validated. CONFIRM (defense-in-depth).**
`resolve_essay_scaffold` validates slot-list shape + ref match, not full
schema_version/topic_type/source_policy. Low risk (snapshots are server-generated).
**Fix (V0.6b.1 hardening):** strict Pydantic snapshot model + family allowlist. *(Principle 1.)*

**F7 — [LOW-MED] Topic-analysis fallback is narrative-only. CONFIRM.**
`fallback_topic_analysis(topic_text)` (`writing_castle_ai.py:46`) takes no scaffold and
always emits real-experience/cause-process-result guidance; `ai_tasks.py:611` doesn't pass
scaffold to it. On AI failure for an expository/person/imaginative topic, the fallback
focus is wrong-flavored. Only triggers when the LLM is unavailable; topic analysis is
somewhat generic. **Fix (V0.6b.1):** make `fallback_topic_analysis(topic_text, scaffold)`
scaffold-aware; test non-narrative fallbacks. *(Principle 1.)*

**F8 — [LOW] Spoofable analytics. CONFIRM (low).** `override_reason` is trusted
(`writing_castle.py:244`) and client `unsupported_future_type` persisted (`:443`).
Authenticated child can only affect own analytics; `suggestion_accepted` is currently
unreachable (no P1 suggestion exists). **Fix (P1 prep):** prefer server-detected
unsupported signals; reject `suggestion_accepted` without a stored suggestion. *(Principle 5.)*

**F9 — [LOW] Alias recursion unguarded. CONFIRM (low).** `_materialize_template`
(`writing_castle_scaffold.py:262`) recurses without a visited set; current aliases are
acyclic. **Fix (hardening):** add visited-set cycle detection + test. *(Principle 1.)*

## Cross-Phase Themes

- **"Backend produces it, but the surface doesn't show it"** — F4 (parent UI) and, to a
  lesser degree, the analytics spoofability (F8). High-confidence signal: build the data
  path to the visible end, not just the API.
- **"Trust the server, not the model/client"** — F1 (model self-cert refs), F2 (client
  child_edited), F8 (client override_reason). The core V0.6b safety principle wants
  server-enforced provenance; the generation path leans on the prompt + downstream checks,
  which is the one place to harden.
