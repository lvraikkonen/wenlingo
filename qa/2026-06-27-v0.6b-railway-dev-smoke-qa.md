# V0.6b Railway Dev Smoke QA

Date: 2026-06-27
Environment: Railway Dev, `wenlingo.com/alpha/start`
Tester: Codex via user-opened Chrome

## Result

Railway Dev smoke result: Go for the V0.6b classroom prewriting happy path after multiple fixes and redeploys.

Follow-up on 2026-06-27:
- Root cause was found locally: model outputs with `source_answer_ids` but empty `source_refs` passed AI task validation, then failed later in the stricter V0.6b material-card state validation.
- Local fix added AI task validation for V0.6b non-placeholder cards to require `source_refs`, so invalid model output falls back to deterministic valid material cards instead of surfacing a generic UI save error.
- The `material_card_generation` prompt contract was bumped to `v0.6b.1-2026-06-27` and now requires non-placeholder cards to include `source_refs`.
- A second failure mode was found in Railway Dev: `material_card_generation` had a `20s` primary plus `20s` fallback timeout budget, exceeding the observed request lifetime of about `28-30s`. The request could be cancelled before the AI runner reached deterministic fallback and before `llmcalllog` was written.
- The material-card generation route budget was reduced to `12s` primary plus `10s` fallback, keeping it within the request lifetime and giving the deterministic fallback path time to return and write observability.
- Final Railway Dev happy-path re-smoke passed with child `QA06b-Happy2` (`535428ea-fa81-41bc-b4c3-b2c626a7e6ca`): scaffold -> topic analysis -> material questions -> material cards -> outline -> first draft feedback -> second draft comparison -> settlement.
- Database check for that child showed `material_card_generation` did create an `llmcalllog`, but final status was still `deterministic_fallback_used`. Both HTTP attempts timed out:
  - primary `deepseek-v4-flash`: `ReadTimeout`, `latency_ms=12311`
  - fallback `deepseek-v4-flash`: `ReadTimeout`, `latency_ms=10308`
- Assessment: the product happy path is unblocked because deterministic fallback returns child-sourced cards within the request window. The live LLM provider latency/timeout remains a performance/reliability issue to monitor separately.

## Findings

### Resolved P0: Material Cards Failed Repeatedly

Topic: 那次经历真难忘
Selected scaffold: 写一件事

Steps:
1. Started classroom essay.
2. Selected 写一件事.
3. Continued from topic analysis to material questions.
4. Answered three material questions.
5. Clicked 整理素材卡.
6. Retried once after the first failure.

Observed:
- Both attempts stayed on 第 2 步 / 共 4 步.
- The UI showed: 这一步没有保存成功，可以重试，也可以先继续写。
- Browser console had no visible warn/error logs.
- The fallback button 我想直接开始写 saved answers and reached the first-draft editor.

Impact:
- During the first Railway Dev smoke, the full prewriting path through material cards and outline was blocked.
- The fallback path worked, and parent summary correctly showed 素材卡：保留 0 张 and 提纲：未确认.

Resolution:
- Backend validation now rejects invalid V0.6b material-card outputs earlier and can fall back to deterministic cards.
- The material-card generation timeout budget now fits inside the observed request lifetime.
- Final re-smoke using `我的“自画像”` reached Step 3 material cards in about `23.7s`, Step 4 outline in about `9.2s`, first-draft feedback in about `9.3s`, and second-draft comparison in about `3.6s`.
- The resulting cards kept child-entered material and left missing card slots blank; no ready-made typical event was invented before the child supplied one.

Remaining observability note:
- `material_card_generation` still used `deterministic_fallback_used` in the final happy-path run because both HTTP attempts timed out. This is acceptable for the smoke pass, but should be tracked as provider latency/reliability work.

### Product Note: Expository Topic Analysis Fact Boundary

Topic: 国宝大熊猫
Selected scaffold: 介绍一种事物

Observed in topic analysis:
- The card listed facts such as black/white coloring, eating bamboo, protected animal status, and an "活化石 / 800万年" fact before the child supplied any source material.

Assessment:
- This is not treated as a V0.6b blocker. Common background facts or facts that plausibly come with the textbook topic can be acceptable as light context.
- The product boundary should remain: AI may offer a small amount of common/background context, but should not produce a large ready-made fact bank. The child should still find, choose, or confirm the material used in the actual material cards, outline, and draft.
