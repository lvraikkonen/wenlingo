### Root-Cause Analysis

Conclusion:

- This is most likely not a primary CORS failure.
- This is most likely a cross-site session-cookie availability failure caused
  by the current two-host Railway deployment shape.

Why it is unlikely to be primary CORS:

- The normal Chrome flow can complete Magic Code login against the same Railway
  web/API hosts.
- In the failing Chrome Incognito flow, the page returned to `/alpha/start`
  after Magic Code submission rather than showing a Magic Code validation error.
- Browser console did not show CORS errors during the reproduced Incognito
  failure.
- If CORS were the primary break, the cross-origin verify/session requests would
  usually fail directly at the fetch boundary.

Why cross-site cookies fit the evidence:

- The Magic Code verification request likely completed, but the authenticated
  session cookie was not available on subsequent protected-page API calls.
- The frontend is served from `wenlingo-web-production.up.railway.app`, while
  the session cookie is set by `wenlingo-api-production.up.railway.app`.
- The frontend uses `credentials: "include"` and expects the browser to store
  and send an API-set HttpOnly cookie on later API requests.
- Chrome Incognito, Safari, and mobile browser privacy modes can block
  cross-site/third-party cookies, causing `/parent/children` to see an
  unauthorized response and redirect to `/alpha/start`.
- Normal desktop Chrome can pass because third-party/cross-site cookies may be
  allowed by the user's browser settings or existing browser state.

Session storage note:

- The current auth design is a server-side session plus browser cookie token.
- The browser receives a random HttpOnly session token.
- The API stores only the hashed token in `ParentSession`.
- This design is acceptable for current Alpha scale. Future polish should add
  session cleanup for expired/revoked rows and optional active-session
  visibility/revocation, but session table growth is not the root cause of this
  login failure.

Current Railway mitigation boundary:

- The current two-host Railway deployment still requires:
  - `CORS_ALLOW_ORIGINS=https://wenlingo-web-production.up.railway.app`
  - `AUTH_ALLOWED_ORIGINS=https://wenlingo-web-production.up.railway.app`
  - `AUTH_SESSION_COOKIE_SECURE=true`
  - `AUTH_SESSION_COOKIE_SAMESITE=none`
  - `NEXT_PUBLIC_API_BASE_URL=https://wenlingo-api-production.up.railway.app`
- These settings can make credentialed cross-origin requests work in browsers
  that allow cross-site cookies.
- These settings do not fully solve Chrome Incognito, Safari, or mobile browser
  third-party-cookie blocking.

Deployment architecture note:

- Deploying web and API on the same physical server is not enough by itself.
- Browser behavior depends on origin/site, not physical hosting location.
- If web and API remain on different browser-visible hosts, the same class of
  login-state issue can remain.

Recommended handling:

- Treat this as a V0.5c.1 auth/deploy polish item before broader external Alpha
  testing.
- Prefer Route A: make browser API traffic same-origin by proxying API calls
  under the web origin, for example `/api/*` on
  `wenlingo-web-production.up.railway.app` forwarding to the API service.
- A same-site custom-domain setup can also help, but the same-origin proxy is
  the strongest browser-compatibility path for Alpha.
- Improve the frontend auth failure UX so a blocked or missing session cookie
  produces a clear login/session message instead of silently returning to the
  default create-family form.
